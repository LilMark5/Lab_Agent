# 20 工程升级上下文（交接文档）

这份文档记录了一次把「智能实验室预约系统」从教程级项目升级到生产级 RAG Agent 的全过程，
供后续会话（人或 Agent）快速接上进度。细节都指向真实文件和提交，不重复实现内容。

## 下一步的目标

按优先级，接下来任选其一：

1. **扩充评测语料**：内置知识库只有 4 篇 Markdown，而检索脚本按 `top_k=5` 召回，
   等于每次都把整个知识库捞回来——三种检索策略（vector / hybrid / hybrid+rerank）
   在 Hit@1 / Hit@3 / MRR / nDCG@3 上**全是满分**，指标已经饱和，
   当前无法区分策略优劣。要造 30~50 篇语料，并加入同义词、专有名词、
   跨文档干扰这类陷阱，检索对比才有意义。
2. 把知识库管理接口限制为管理员（当前只要求登录）。
3. 在 supervisor 模式上把单智能体扩展成多智能体。
4. **评估 Agent 侧能力**：现有评估只覆盖「检索 → 有据作答」这一段，
   工具选择准确率、参数正确率、审批触发率都还没有指标。

### 修复过的坑（容易复发，注意别再踩）

- 多轮历史重复：checkpointer 已存历史时前端不能再回传完整历史，只发本轮新消息；
  system prompt 每次调用模型时注入，不进 state。
- 向量维度写死 384 是错的，已改为运行时读取；换模型会自动重建表。
- pgvector 不能写 `:embedding::vector`，要用 `CAST(:embedding AS vector)`。
- CORS 不能 `allow_origins=["*"]` 配 `allow_credentials=True`，已关掉 credentials。
- Chroma / Milvus 的 `_ensure` 里先设置实例属性再调 `add_chunks`，否则无限递归。
- Milvus Lite 不支持 Windows（pymilvus 的依赖带 `sys_platform != 'win32'`），
  Windows 上要用 Milvus 必须 Docker 起服务。
- **ragas 0.4.3 与 langchain-community 0.4.x 硬冲突**：`ragas/llms/base.py`
  顶层无条件 `from langchain_community.chat_models.vertexai import ChatVertexAI`，
  而该模块从 0.4.0 起被拆走，直接 `ModuleNotFoundError`。
  必须钉 `langchain-community==0.3.31`（它仍带该模块，且要求
  `langchain-core>=0.3.78,<2.0.0`，不用降级任何现有依赖）。
  **千万别为了迁就 ragas 把 langchain-core 降回 0.3.x，那会把整个 LangGraph 打回去。**
- **RAGAS 的 `llm_factory` 默认 `max_tokens=1024`**，推理型模型的思考 token
  会先把预算吃掉，结构化输出被截断后抛 `IncompleteOutputException`。要显式调到 8192。
- **RAGAS 必须用 `AsyncOpenAI`**：`ascore()` 内部走 `agenerate()`，
  传同步 client 会报 `Cannot use agenerate() with a synchronous client`。

## 未决问题（下一会话需要判断）

- **学习文档滞后**：`docs/07-rag-deep-dive.md`、`docs/08-langgraph-from-zero.md`、
  `docs/15-milvus-hybrid-search.md` 仍描述旧实现（整篇嵌入、无 checkpointer），
  与代码不一致，需要重写。
- **知识库接口权限**：`backend/app/api/kb.py` 目前只要求登录，没有限定管理员。
- **评测语料太小**：只有 4 篇内置文档，检索指标全部饱和（三种策略都满分），
  且生成评估的 14 条用例覆盖面有限。检索策略对比在扩语料之前没有说服力。
- **Agent 侧无评估**：现有指标只覆盖「检索 → 有据作答」，
  工具选择、参数正确性、审批触发率都没有度量。
- **评估分数有波动，且比预期严重**：`deepseek-v4-flash` 同时当被测模型和裁判模型，
  **同一段答案重复三次能得到 0.5 / 0.75 / 1.0**（`temperature=0` 无效，
  因为 faithfulness 是「拆句 + 逐句判定」的多步链路）。
  三轮全量跑的 faithfulness 事实类为 1.0000 / 1.0000 / 0.9659，
  而第 3 轮被判扣分的那几条经人工核对**全部是有据的**，属裁判误判。
  唯一稳定的是 context_recall 与 context_precision（由检索结果决定，可复现）。
  下一步应把裁判换成更强的模型（脚本里改 `llm_factory` 的 client 即可），
  汇总均值可用，单条用例分数不可当真。
- **多智能体未开始**：目前是 supervisor 模式的准备工作（状态里预留了 `approval` 字段）。
- **遗留技术债**：同步 SQLAlchemy（未异步）、Docker / K8s 未涉及、无 CI。

## 环境与启动（本机特有）

这台机器的情况和别人不同，交接时必须知道：

- Windows + WSL2 Ubuntu 26.04，PostgreSQL 18 + pgvector 是**原生装在 WSL 里**的，
  **没有用 Docker**。WSL 曾被代理和 Radmin VPN 搞坏网络，靠 `.wslconfig` 的
  `networkingMode=mirrored` 修复。
- 后端虚拟环境是 `backend/.venv-clean`（Python 3.11）。系统默认 Python 是 3.14，
  不要用裸的 `python` / `uvicorn`。
- `.env` 关键项：`DATABASE_URL` 指向本机 PostgreSQL，`VECTOR_BACKEND=pgvector`，
  `CHECKPOINT_DB_PATH` 指向 SQLite 会话库。`.env` 已被 git 忽略。
- `LLM_API_KEY` 曾在对话中明文出现过，**建议吊销并更换**。

启动顺序：

```powershell
# 后端
cd D:\Work\projects\lab_agent_std\backend
.\.venv-clean\Scripts\python.exe -m alembic upgrade head
.\.venv-clean\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

# 前端（另开窗口）
cd D:\Work\projects\lab_agent_std\frontend
npm run dev
```

验证：

```powershell
cd D:\Work\projects\lab_agent_std\backend
.\.venv-clean\Scripts\python.exe -m pytest tests -q              # 21 passed
.\.venv-clean\Scripts\python.exe evaluate_rag.py                 # 三种检索策略
.\.venv-clean\Scripts\python.exe evaluate_generation.py --limit 3 # 生成评估冒烟（全量约 5 分钟）
.\.venv-clean\Scripts\python.exe -m alembic check                # 无差异
```

生成评估的权威分数记在 [docs/21-rag-evaluation.md](21-rag-evaluation.md) 第 5 节，
跑分产物 `backend/eval_reports/` 已被 git 忽略，不做版本管理。
