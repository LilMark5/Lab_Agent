### ✅ B1：知识库接口无管理员权限（已修复）

原问题：`backend/app/api/kb.py` 的上传/列表/删除/检索四个接口只用了
`Depends(get_current_user)`，任何登录用户都能污染/删除 RAG 语料。

**修复**：四个接口的依赖全部从 `get_current_user` 换成 `get_current_admin`。
新增 `tests/test_auth.py`（2 个用例）验证 `get_current_admin` 对 admin 放行、
对 student 抛 `403`。检索能力本身不受影响——Agent 的 `search_lab_docs` 工具
走的是 `kb_service`，不经此 HTTP 接口，该接口是管理后台的单文档检索。

### ✅ B2：前端路由无角色守卫（已修复）

原问题：`frontend/src/router/index.js` 的 `beforeEach` 只判断 token，不判断角色。

**修复**：给 `user` / `audit-reservation` / `kb-manage` 三个管理页加 `meta: { admin: true }`，
`beforeEach` 里新增角色判断——`to.meta.admin && getUser()?.role !== 'admin'`
时重定向回首页。现在前后端双重鉴权闭环。

## 三、重要级（影响健壮性 / 会被追问）

### ✅ C1：事务边界缺失 —— 已修复

原问题：`create_reservation` 里 `db.commit()` 失败没有 `rollback()`，
会留下脏会话；`get_db` 只 `close()` 不 `rollback()`。

**修复**：
- `reservation_service.py` 四处写库（创建/取消/审核/过期扫描）的 `commit`
  全部包 `try/except`，失败时 `rollback()` 再 `raise`。
- `database.py` 的 `get_db` 依赖在 `except` 分支加 `rollback()` 兜底，
  覆盖所有请求会话，防止未来新增 service 漏写。
- 新增 `test_create_reservation_rolls_back_on_commit_failure` 验证
  commit 失败后不落库。

### 🟠 C2：Agent 工具调用无重试 / 无超时 / 无幂等

`agent_service.tool_node` 里工具执行 `except` 后只回填错误文本交给模型，
**没有重试策略、没有超时控制、写库工具没有幂等键**。

企业级 Agent 的三个必问点，这里一个都没覆盖：
1. **工具失败重试**：网络抖动/临时故障时，直接让模型「看到错误」而不是重试。
2. **超时**：`list_open_labs` 若 DB 慢，会卡住整个图执行（无 timeout）。
3. **幂等**：`create_lab_reservation` 若模型重复调用同一参数，会重复落库
   （虽然后面有 HITL 审批，但审批通过后重复调用仍会重复创建）。

### 🟠 C3：MCP 工具加载存在隐患（asyncio.run 嵌套 + 只试一次）

`agent_tools._load_mcp_tools` 里：
- 用 `asyncio.get_running_loop()` 探测是否在 async 上下文，若是则**直接返回 None**（跳过 MCP）。
  这意味着**流式接口（`chat_stream`）实际永远走不到 MCP 工具**——因为整个 agent 都在 async 里跑。
  只有非流式 `chat` 接口能真正加载 MCP 工具。这个行为不一致，且没人知道。
- `_mcp_cache["tried"] = True` 只试一次，MCP 服务重启后需要重启后端才能恢复。

**面试追问点**：「你的 MCP 工具在流式场景下到底生效吗？」——答案是「不生效」，这很尴尬。

### 🟠 C4：上下文窗口无上限保护

`agent_service.agent_node` 直接把 `state["messages"]` 全量塞给 LLM，
多轮对话 + 每次检索都返回大段父上下文，**没有 token 预算管理、没有历史裁剪**。
长对话会超出模型 context window 报错。企业级标配是「滑动窗口 / 摘要压缩 / token 计数」。

## 四、建议级（加分项，面试讲出来是亮点）

### 🟡 D1：无 LLM 调用日志与可观测性

没有任何 token 用量、延迟、工具调用链的记录。Agent 岗面试越来越问「你怎么观测 Agent 的
成本和质量」，接入 LangSmith / Langfuse 或自建 logging 是明确加分项。

### 🟡 D2：输入校验依赖业务层，schema 层过于宽松

`ReservationCreateRequest` 的 `date/start_time/end_time` 都是裸 `str`，
格式（`HH:MM` / `YYYY-MM-DD`）没有在 Pydantic 层约束，全靠 service 里的字符串比较。
企业级应在 schema 层用 `field_validator` 或类型约束。同理 `AuditReservationRequest.status`
是裸 int，靠 service 里 `status not in (1,2)` 兜底。

### 🟡 D3：CORS 全开放 + 静态文件无鉴权

`allow_origins=["*"]`（虽然 `allow_credentials=False` 算合规，但生产应白名单）；
`/uploads` 挂载的静态文件**完全无鉴权**，任何人可猜 URL 访问上传的文件。

### 🟡 D4：SQL 注入面（低危但面试爱问）

`vector_store.PgVectorStore` 里有多处 `f"DROP TABLE {table}"`、`f"CREATE INDEX ... {table}"`
的**字符串拼接**。`table` 来自内部常量 `kb_chunks`，当前不可注入，但 `existing_dim`
判断那段用了参数化（`{"t": table}`）而建表/删表没用，风格不统一，面试容易被追问
「为什么这里拼字符串」。建议统一加白名单校验或明确注释说明 `table` 来源是内部常量。

### 🟡 D5：查询改写已做但默认关闭、无评测对比

上一轮加的 `_rewrite_query` 逻辑正确、有测试、有降级，但 `QUERY_REWRITE_ENABLED=False`
且**没有「改写 vs 不改写」的召回对比实验**。要讲成亮点，需要补一组 A/B 数据。

## 五、做得好的地方（面试要主动讲，这是你的底牌）

1. **预约并发控制是真功夫**：`with_for_update()` + 区间重叠算法
   `A.start < B.end AND A.end > B.start`，这是简历里最硬的一段。
2. **RAG 管线完整且分层清晰**：切块 → 向量+BM25 双路 → RRF → rerank → 父上下文 → 引用，
   每一步都有独立函数，`_expand_context` 处理了动态文档不在缓存里的边界。
3. **评估意识超前**：RAGAS 四指标 + 拒答边界用例 + 裁判分离 + 裁判自检，
   还发现了 `context_precision` 的口径陷阱和裁判噪声——这是 eval-driven 的正向示范。
4. **checkpointer 双后端抽象**：SQLite/PG 切换干净，`from_conn_string` 的 async 语义处理正确。
5. **HITL 是真 interrupt**：不是靠 prompt 骗模型，是 LangGraph 原生 `interrupt` + `Command(resume)`。
6. **SSE 解析健壮**：前端 `getReader` + buffer 半包处理 + `[DONE]` 兼容，比 EventSource 更可控。
7. **安全细节到位**：密码 bcrypt、登录统一提示防账号枚举、JWT 过期、DOMPurify 防 XSS、
   CORS credentials 关闭（注释里解释了为什么）。
