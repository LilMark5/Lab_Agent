# 第 06 章 · Prompt 工程

## 开篇：Prompt 不是「咒语」，是「接口文档」

网上流传的 Prompt 教程是这样的：

> 加上「让我们一步步思考」，准确率提升 20%！
> 加上「你是世界顶级专家」效果更好！
> 在结尾写「如果你答对了，我给你 100 美元小费」...

这些是**玄学**。它们可能在某个模型、某个任务上有效，换个模型就失效，而且没法解释为什么。

这本书讲 Prompt 工程的角度完全不同：

> **Prompt 是给模型看的接口文档。**

你写后端接口时，会写清楚：这个接口是干嘛的、参数什么格式、什么时候该调、边界条件是什么、错误怎么处理。

写给模型的 Prompt 也是一样。**好的 Prompt = 一份清晰的接口文档 + 行为规范 + 边界约束**。

这一章讲怎么写出这样的 Prompt，以及怎么验证它真的有效。

## 一、先解剖一份真实的 System Prompt

这是项目里实际在用的（`agent_service.py:65-88`），我们逐段分析它为什么这么写：

```
你是智能实验室预约系统的 Agent，回答要简洁。
```

| 部分 | 作用 |
|---|---|
| 「你是智能实验室预约系统的 Agent」 | **角色定义**，框定模型的身份 |
| 「回答要简洁」 | **输出风格约束**，防止啰嗦（也省钱，见第 5 章） |

```
你可以：
1. 使用 search_lab_docs 查询实验室的规则、安全、开放时间等问题
2. 使用 list_open_labs / list_lab_equipments 查询真实的实验室和设备
3. 在用户确认预约后，使用 create_lab_reservation 进行真实的预约落库
4. 使用 get_today 进行日期的换算
```

**这一段是「能力清单 + 路由指引」**。

它解决了第 4 章讲的「模型可能不知道该调哪个工具」的问题——**明确告诉模型：什么类型的问题对应什么工具**。

注意第 1 条里的「**规则、安全、开放时间**」——这是关键词映射。用户问「几点关门」时，模型能对应到「开放时间」→ `search_lab_docs`。

```
## 必须遵守
当用户提到今天、明天、后天等日期问题时，请先调用 get_today 获取日期，
不要直接返回"我需要确定明天的具体日期"。
```

**这一段是「踩坑后加的」**。

**没有这段会发生什么？** 模型不知道今天几号（它的训练数据有时效，而且不知道「今天」是请求发生的那一天），所以会回答：

> "我需要知道今天的具体日期才能计算明天的日期，请问今天是几号？"

用户体验极差——你明明是个系统，你自己不知道日期吗？

**解法**：给一个 `get_today` 工具，并**明确要求先调它**。

> 💡 **面试话术**：「这条约束是踩坑后加的。模型不知道『今天』是请求发生的那一天——它的知识有截止日期，而且无法感知当前时间。所以用户问『明天有空吗』，模型会反过来问用户『请问今天几号』，体验很差。我的解法是提供一个 get_today 工具，并在 System Prompt 里明确要求：遇到相对日期先调这个工具，不要反问用户。这是 Agent 开发中很典型的一类问题——模型缺乏的『常识』要靠工具补。」

```
提交预约前必须向用户复述：实验室ID与名称（或设备ID和名称）、日期、开始时间、结束时间，
并得到用户确认后再调用 create_lab_reservation。系统会在真正落库前再次弹出确认，
这是最后一道保护，用户没有明确确认时不要硬调工具。
```

**这一段是「HITL 的软约束」**，配合第 18 章的 interrupt 硬机制。

注意它的措辞很讲究：

| 措辞 | 为什么 |
|---|---|
| 「必须向用户复述...并得到用户确认」 | 让模型在调工具前先做一次自然语言确认 |
| 「系统会在真正落库前再次弹出确认」 | 告诉模型还有一道系统级的保险 |
| 「这是最后一道保护」 | 强调重要性 |
| 「用户没有明确确认时不要硬调工具」 | 防止模型自作主张 |

**为什么既要有软约束（prompt）又要有硬机制（interrupt）？**

因为**prompt 约束不可靠**——模型可能违反。interrupt 是代码级的，100% 拦得住。

> ⚠️ **这是 Agent 开发的一条铁律**：
> **能用代码保证的，不要指望 Prompt。**
> Prompt 是「引导」，代码是「保证」。两者配合，不互相替代。

```
预约成功后状态是待审核，必须管理员确认后实验室（或设备）才能使用。
不要编造数据库里没有的实验室或设备信息。
询问开放时间或实验室规则时，优先调用 search_lab_docs。
```

| 句子 | 防什么 |
|---|---|
| 「状态是待审核...」 | 防模型说「预约成功，可以去了」——实际还要审核 |
| 「不要编造数据库里没有的信息」 | **防幻觉**（第 4 章） |
| 「优先调用 search_lab_docs」 | 强制走 RAG，不用记忆回答 |

```
## 引用要求
search_lab_docs 返回的资料会带 [文件名#块号] 这样的来源标记。知识库同时包含系统内置文档
和用户上传的文档，回答时要注明依据的文件名，例如「根据《量子实验室说明.md》」，
不要只给结论而不说明出处。
```

**这一段是「引用溯源」的约束**（第 29 章详解）。

它做了三件事：

1. **告诉模型来源标记长什么样**（`[文件名#块号]`）
2. **说明知识库的构成**（内置 + 用户上传）
3. **给出具体格式示例**（「根据《量子实验室说明.md》」）

**为什么格式示例很重要？** 因为模型是模式匹配器——给它一个例子，它就知道该输出什么格式。这比描述「要注明出处」有效得多。

## 二、System Prompt 的六个必备模块

基于上面的分析，提炼出一个通用模板：

```markdown
# 1. 角色与定位
你是 [系统名] 的 [角色]，服务于 [用户群体]。

# 2. 能力清单（含工具路由）
你可以：
- 使用 [工具A] 处理 [场景1]
- 使用 [工具B] 处理 [场景2]

# 3. 输出规范
- 回答风格：[简洁/详细/分点]
- 长度限制：[字数]
- 格式要求：[Markdown/JSON/纯文本]

# 4. 行为约束（踩坑后加的）
- 遇到 X 情况，必须先做 Y，不要 Z
- 不要编造 [某类信息]
- 只根据 [来源] 回答，没有就说不知道

# 5. 边界与例外
- [情况A] 时状态是 [X]，不要误报为 [Y]
- 你无法做 [Z]，遇到时应该 [引导方式]

# 6. 引用/格式要求（如果需要）
返回的资料带 [标记格式]，回答时要注明 [具体格式示例]。
```

**每一条都应能回答「不加会怎样」**。加不了的就删掉——Prompt 越长越贵、越稀释注意力。

## 三、Prompt 编写的七条原则

### 原则 1：具体 > 抽象

```markdown
❌ "你是一个有用的助手"
✅ "你是智能实验室预约系统的助手，帮助学生查找和预约实验室，回答规章制度问题"

❌ "回答要准确"
✅ "只根据 search_lab_docs 返回的资料回答，资料里没有的信息就说'资料中没有提到'"

❌ "注意时间格式"
✅ "时间格式必须是 YYYY-MM-DD HH:MM:SS，例如 2025-01-17 14:00:00"
```

**原理**：抽象指令给模型太多自由度，具体指令直接给出了模式。

### 原则 2：给示例（Few-shot）

```markdown
## 输出格式示例

用户：A301 实验室能容纳多少人？
助手：根据《实验室概况.md》，A301 细胞生物学实验室可容纳 20 人。

用户：实验室能带食物进去吗？
助手：根据《安全管理规定.md》第 3 条，实验室内禁止饮食。资料中没有提到例外情况。
```

**为什么有效**：模型是模式匹配器，示例直接激活了正确的模式。

**Few-shot 的成本**：每个示例占 token。通常 2-3 个示例就够，超过 5 个收益递减。

### 原则 3：用「不要做 X」补充「要做 Y」

```markdown
✅ 查询实验室信息时必须调用工具
✅ 不要凭记忆回答实验室、设备、预约相关的信息
```

**为什么两条都要？** 因为「必须调工具」是正向指令，模型可能仍然偷懒；「不要凭记忆」是反向约束，双保险。

### 原则 4：约束放在开头和结尾

还记得第 4 章的 **Lost in the Middle** 吗？模型对开头和结尾的内容注意力更强。

```
[最重要的约束]        ← 开头
[次要信息]
[最重要的约束重申]     ← 结尾
```

**实践技巧**：把最关键的 1-2 条约束在 System Prompt 开头和结尾各写一次（措辞不同）。

### 原则 5：用结构化的分隔

```markdown
## 必须遵守
...

## 引用要求
...
```

用 Markdown 标题分段，让模型能识别「这是不同的规则块」。

**对比**：

```
你要遵守规则，遇到日期问题先调 get_today，不要编造信息，回答要注明出处，
格式是「根据《文件名》」，还有如果用户要预约要先复述信息...
```

上面这段信息完全相同，但**效果差很多**——因为全挤在一起，模型难以区分重点。

### 原则 6：Prompt 也要省 token

System Prompt 是**每轮都要发**的（和工具 schema 一样）。

```
500 token 的 System Prompt × 10 轮 = 5000 token
```

**精简技巧**：

| 技巧 | 例子 |
|---|---|
| 删掉客套话 | 「请尽力帮助用户」→ 删 |
| 合并同类 | 3 条「不要」合并成 1 条 |
| 用列表不用段落 | 列表更省、更清晰 |
| 去掉冗余修饰 | 「非常重要的一点是」→ 删 |

**但不要为了省 token 删掉关键信息**——一次工具调用错误要重来一轮，比省下的 token 贵得多。

### 原则 7：版本化 + 测试

**Prompt 是代码，会改、会退化、需要回归测试。**

```
prompts/
├── system_v1.md       # 初版
├── system_v2.md       # 加了日期约束
├── system_v3.md       # 加了引用要求
└── system_current.md  # 当前生效
```

每次改动要能回答：**改了什么、为什么改、效果变化多少**。

> ⚠️ **项目现状**：项目里 `SYSTEM_PROMPT` 是一个 Python 字符串常量，**没有版本化**。这是可以改进的点。生产上应该把 Prompt 抽成独立文件或数据库配置，支持热更新和 A/B 测试。

## 四、四类 Prompt 的写法

### 4.1 System Prompt（角色与规则）

前面已讲。要点：**稳定、简洁、结构化**。

### 4.2 工具描述（Tool Description）

这是**最容易被忽视但最重要**的 Prompt。

```python
# ❌ 差
@tool
def search_labs(keyword: str) -> str:
    """搜索实验室。"""

# ✅ 好
@tool
def search_labs(keyword: str = "") -> str:
    """根据关键词搜索实验室，返回实验室列表（含 id、名称、容量、位置）。

    适用场景：用户想查找实验室、询问有哪些实验室、需要知道某个实验室的 ID。
    不适用场景：查询实验室的规章制度（应该用 search_lab_docs）。

    Args:
        keyword: 实验室名称或位置的关键词，留空表示查询全部
    """
```

**好的工具描述包含四部分**：

| 部分 | 作用 |
|---|---|
| 「做什么」 | 功能说明 |
| 「返回什么」 | 让模型知道能拿到什么数据 |
| 「什么时候用」 | **最关键**，决定调用时机 |
| 「什么时候不用」 | 防止误用 |

### 4.3 Few-shot 示例（在 Prompt 里）

```markdown
## 对话示例

用户：明天有空实验室吗？
助手：（先调用 get_today 获取日期）
     （再调用 list_open_labs 查询）
     明天（2025-01-18）有 3 个实验室可预约：...

用户：帮我预约 A301
助手：好的，请确认预约信息：
     - 实验室：A301 细胞生物学实验室
     - 日期：2025-01-18
     - 时间：14:00 - 17:00
     确认无误请回复"确认"。
```

**注意**：示例里展示了**工具调用的顺序**，这比单纯说「先调 X 再调 Y」更有效。

### 4.4 动态 Prompt（RAG 注入）

检索回来的文档要拼进 Prompt。怎么拼？

```python
prompt = f"""请只根据以下资料回答用户问题。资料中没有的信息，
请明确说"资料中没有提到"，不要编造。

## 参考资料
[来源1: 《安全管理规定.md#块3》]
{chunk1}

[来源2: 《实验室概况.md#块7》]
{chunk2}

## 用户问题
{question}

## 要求
回答时注明依据的文件名，格式如「根据《安全管理规定.md》」。
"""
```

**关键设计**：

| 设计 | 为什么 |
|---|---|
| 资料放在**问题之前** | 模型先看资料再看问题，答案更贴合资料 |
| 每段带来源标记 | 支持引用溯源 |
| 明确「没有就说没有」 | 防幻觉 |
| 问题放在最后 | 注意力最强的位置留给问题 |
| 要求给出处 | 强制模型关联来源 |

## 五、Prompt 的迭代方法：怎么知道改得对不对

这是大部分教程不讲的部分。**改了 Prompt，你怎么知道是变好了还是变差了？**

### 5.1 三步迭代法

**第一步：建评测集**

10-30 个真实问题，标注期望行为（不是期望答案文本，是**行为**）：

```python
EVAL_CASES = [
    {
        "question": "明天A301有空吗？",
        "expect": "先调用 get_today，再调用 list_open_labs",
        "category": "日期+查询",
    },
    {
        "question": "实验室能带食物进去吗？",
        "expect": "调用 search_lab_docs，回答带文件名引用",
        "category": "知识问答",
    },
    {
        "question": "帮我预约A301明天下午2点",
        "expect": "复述预约信息，等确认后再调 create_lab_reservation",
        "category": "写操作",
    },
    # ... 拒答用例
    {
        "question": "量子实验室的收费标准是多少？",
        "expect": "资料中没有提到，说不知道（资料里确实没有）",
        "category": "拒答边界",
    },
]
```

**第二步：改一版跑一次**

```bash
python run_eval.py --prompt-version v2
```

记录每次的指标变化。

**第三步：看失败案例，不要只看总分**

总分从 0.75 涨到 0.78，但可能：
- 3 个用例从失败变成功 ✅
- 2 个用例从成功变失败 ❌

**净涨 1 个，但引入了 2 个回归**。必须逐个看失败案例。

### 5.2 常见的「改了变好」与「改了变坏」

| 改动 | 通常效果 | 副作用 |
|---|---|---|
| 加「不要编造」 | 幻觉减少 | 模型变得过度保守，该答的也说不知道 |
| 加「必须调工具」 | 工具调用率上升 | 简单问题也调工具，变慢变贵 |
| 加 Few-shot | 格式更一致 | 模型照抄示例内容（过拟合） |
| 加「回答简洁」 | 省 token | 信息不完整 |
| Prompt 变长 | 覆盖更多情况 | 注意力稀释，关键约束被忽略 |

> ⚠️ **关键认知**：**Prompt 改动几乎总是有 trade-off**。没有「纯变好」的改动，只有「在当前评测集上净收益为正」的改动。这就是为什么必须有评测集。

## 六、最小可运行骨架：Prompt A/B 测试器

```python
"""
prompt_lab.py —— Prompt 迭代实验台（无需 API Key，用模拟模型）
运行：python prompt_lab.py
演示：建评测集 → 对比两版 Prompt → 看逐条差异而不是只看总分
"""

import random
from dataclasses import dataclass, field

# ── 1. 评测集 ────────────────────────────────────────────

@dataclass
class Case:
    question: str
    expect: str              # 期望行为描述
    category: str
    check: str               # 检查项：用关键词判断行为

EVAL_SET = [
    Case("明天A301有空吗？", "先 get_today 再查询", "日期+查询", "get_today"),
    Case("有哪些实验室？", "调 list_open_labs", "查询", "list_open_labs"),
    Case("实验室能带食物吗？", "调 search_lab_docs 并带引用", "知识问答", "《"),
    Case("帮我预约A301明天下午2点", "先复述再等确认", "写操作", "确认"),
    Case("量子实验室收费多少？", "说资料里没有", "拒答边界", "没有提到"),
    Case("后天B205有空吗？", "先 get_today 再查询", "日期+查询", "get_today"),
    Case("实验室几点关门？", "调 search_lab_docs", "知识问答", "search_lab_docs"),
    Case("取消我的预约", "走变更流程", "写操作", "确认"),
]

# ── 2. 模拟模型 ──────────────────────────────────────────

class SimulatedModel:
    """模拟模型行为：不同 Prompt 版本导致不同的行为概率。"""

    def __init__(self, prompt_version: str):
        self.v = prompt_version
        # 每版 Prompt 对各检查项的"命中概率"
        self.profiles = {
            "v1": {  # 基础版：只说"你是助手"
                "get_today": 0.2,          # 大部分时候会反问用户
                "list_open_labs": 0.9,
                "《": 0.3,                 # 大部分不给引用
                "确认": 0.4,
                "没有提到": 0.3,            # 会编造
                "search_lab_docs": 0.6,
            },
            "v2": {  # 加了日期约束 + 引用要求
                "get_today": 0.95,
                "list_open_labs": 0.9,
                "《": 0.9,
                "确认": 0.85,
                "没有提到": 0.6,
                "search_lab_docs": 0.85,
            },
            "v3": {  # 又加了"不要编造"（过度保守）
                "get_today": 0.95,
                "list_open_labs": 0.85,     # 略降：模型变保守
                "《": 0.9,
                "确认": 0.9,
                "没有提到": 0.95,           # 拒答能力提升
                "search_lab_docs": 0.7,     # ⚠️ 明显下降：该查的也不查了
            },
        }
        self.profile = self.profiles[self.v]

    def answer(self, question: str) -> str:
        """按概率模拟是否命中检查项。"""
        # 找出这个 case 对应的检查项
        check = next((c.check for c in EVAL_SET if c.question == question), "")
        p = self.profile.get(check, 0.5)
        if random.random() < p:
            return f"✅正确行为 检查项[{check}]"
        return f"❌未满足 检查项[{check}]"

# ── 3. 评测执行 ──────────────────────────────────────────

@dataclass
class Result:
    version: str
    passed: list = field(default_factory=list)
    failed: list = field(default_factory=list)
    by_category: dict = field(default_factory=dict)

def evaluate(version: str, trials: int = 20) -> Result:
    """每条用例跑多次取平均（模拟模型的不确定性）。"""
    r = Result(version)
    for case in EVAL_SET:
        model = SimulatedModel(version)
        hits = sum(1 for _ in range(trials)
                   if model.answer(case.question).startswith("✅"))
        rate = hits / trials
        cat = r.by_category.setdefault(case.category, [])
        cat.append(rate)
        if rate >= 0.5:
            r.passed.append((case.question, rate))
        else:
            r.failed.append((case.question, rate))
    return r

def compare(v1: str, v2: str):
    print(f"\n【对比 {v1} vs {v2}】")
    ra, rb = evaluate(v1), evaluate(v2)

    score_a = sum(r for _, r in ra.passed + ra.failed) / len(EVAL_SET)
    score_b = sum(r for _, r in rb.passed + rb.failed) / len(EVAL_SET)

    print(f"  总分: {v1}={score_a:.2f}  {v2}={score_b:.2f}  "
          f"{'✅ 提升' if score_b > score_a else '❌ 下降'} {abs(score_b-score_a):.2f}")

    print(f"\n  逐条对比（⚠️ 关键：不能只看总分）")
    print(f"  {'问题':<24}{v1:>8}{v2:>8}   变化")
    print("  " + "-" * 56)

    all_a = dict(ra.passed + ra.failed)
    all_b = dict(rb.passed + rb.failed)

    regressions = []
    for q in all_a:
        a, b = all_a[q], all_b[q]
        delta = b - a
        flag = ""
        if delta > 0.2:
            flag = "✅ 改善"
        elif delta < -0.2:
            flag = "❌ 回归"
            regressions.append(q)
        print(f"  {q:<24}{a:>8.2f}{b:>8.2f}   {flag}")

    print(f"\n  按类别：")
    for cat in ra.by_category:
        ca = sum(ra.by_category[cat]) / len(ra.by_category[cat])
        cb = sum(rb.by_category[cat]) / len(rb.by_category[cat])
        print(f"    {cat:<12} {v1}={ca:.2f} → {v2}={cb:.2f}")

    if regressions:
        print(f"\n  ⚠️ 有 {len(regressions)} 条回归：")
        for q in regressions:
            print(f"    - {q}")
        print("  这些必须逐条分析，不能因为总分涨了就上线")

# ── 4. 演示三种典型情况 ──────────────────────────────────

def demo():
    print("=" * 60)
    print("Prompt 迭代实验台")
```

## 本章速记卡

1. **Prompt 是接口文档**，不是咒语。「魔法词」不可靠，原则和示例才可靠。
2. **System Prompt 六模块**：角色、能力清单、输出规范、行为约束、边界例外、引用要求。
3. **具体 > 抽象**。给示例（Few-shot）比描述规则有效。
4. **「要做 Y」+「不要做 X」双写**，正向指令和反向约束都要有。
5. **关键约束放开头和结尾**（Lost in the Middle）。
6. **工具描述四要素**：做什么、返回什么、什么时候用、什么时候不用。
7. **能用代码保证的不要指望 Prompt**。Prompt 是引导，代码是保证。
8. **Prompt 改动几乎总有 trade-off**，必须有评测集才能判断。
9. **逐条看失败案例，不看总分**。总分涨了可能引入了回归。
10. **Prompt 要版本化**。项目里现在是字符串常量，可以改进。

## 面试问答：Prompt 工程

### Q1：「你的 System Prompt 是怎么设计的？」

**满分答法**：

> 分六个模块：角色定位、能力清单（含工具路由）、输出规范、行为约束、边界例外、引用要求。
>
> 每一条都是针对具体问题加的，我能说出不加会怎样。比如：
>
> 「遇到日期问题先调 get_today」这条，是因为模型不知道「今天」是请求发生的那一天，会反问用户「请问今天几号」，体验很差。
>
> 「不要编造数据库里没有的实验室信息」这条是防幻觉。
>
> 「预约前必须复述信息并得到确认」这条是防止模型自作主张写库——但这一条我还有代码级的 interrupt 兜底，不会只靠 prompt。
>
> 引用要求这段我给了具体格式示例，因为模型是模式匹配器，给示例比描述规则有效。
>
> 另外我注意把关键约束放在开头和结尾，因为有个现象叫 Lost in the Middle——模型对中间位置的信息注意力较弱。

---

### Q2：「Prompt 约束和代码约束，你怎么选？」

**满分答法**（这题考工程判断力）：

> 原则很简单：**能用代码保证的，绝不用 Prompt**。
>
> Prompt 是「引导」，模型可能违反；代码是「保证」，100% 生效。
>
> 我项目里写库操作是个典型例子：我在 System Prompt 里写了「预约前必须复述并得到用户确认」，但**同时**用 LangGraph 的 interrupt 做了硬拦截——只要模型要调写库工具，图就会暂停，等用户点确认。
>
> 为什么要两层？因为 Prompt 那层是让**交互更自然**（模型会主动复述信息、询问确认），代码那层是让**安全有保证**（即使模型被绕过或者改了 prompt，写库操作仍然拦得住）。两者作用不同，不是重复。
>
> 反过来，有些事情只能用 Prompt：比如回答风格、语气、是否给出处——这些没法用代码强制，只能引导。

---

### Q3：「改了 Prompt 怎么验证效果？」

**满分答法**：

> 必须有评测集，而且是**行为评测**不是文本比对。
>
> 我的做法是先建 10-30 条真实问题，每条标注期望的**行为**（比如「先调 get_today 再调查询工具」「回答要带文件名引用」「资料里没有就说没有」），而不是期望的答案文字——因为同一个意思有无数种说法，比对文本没意义，但行为是可以判定的。
>
> 评测集要特意包含**拒答边界**用例——问一个资料里确实没有的问题，看模型会不会编。这是最容易暴露幻觉的测试。
>
> 然后改一版跑一次，关键是要**逐条看失败案例，不能只看总分**。我遇到过总分涨了但实际引入了回归的情况：三条从失败变成功，两条从成功变失败，净涨一条，但那两条回归是严重问题。
>
> 还要按类别看——比如加了「不要编造」之后，拒答能力提升，但查询能力可能下降（模型变保守，该查的也不查了）。这种 trade-off 只有分类看才能发现。

---

### Q4：「工具描述怎么写？有什么讲究？」

**满分答法**：

> 四个要素：做什么、返回什么、什么时候用、什么时候不用。
>
> 其中**「什么时候用」最关键**，它直接决定模型的调用时机。我会在描述里列出具体场景，比如「当用户询问实验室的规定、制度、安全要求、开放时间时使用」。
>
> 「什么时候不用」同样重要，防止误用。比如我会注明「查询规章制度应该用 search_lab_docs，不要用 search_labs」。
>
> 「返回什么」也要写，因为模型需要知道调这个工具能拿到什么数据，才能决定要不要调。
>
> 参数用 Pydantic 的 Field description 写清格式，比如「时间格式 YYYY-MM-DD HH:MM:SS」。这样模型编错格式的概率会明显下降。
>
> 另外有个权衡要注意：**不要为了省 token 把描述写得太短**。工具 schema 每轮都发，确实占 token，但一次错误的工具调用要重来一整轮，比省下的 token 贵得多。

---

### Q5：「模型还是不调工具怎么办？」（追问）

**满分答法**（层层递进）：

> 我会按这个顺序排查：
>
> **第一层，看工具描述**。是不是没写清楚使用场景？模型不知道「这种问题该调这个工具」，自然不会调。
>
> **第二层，看 System Prompt**。有没有明确「这类问题必须调工具」？我在 prompt 里的能力清单会写明「什么问题用什么工具」，这相当于给了模型一张路由表。
>
> **第三层，加反向约束**。除了「必须调工具」，再加「不要凭记忆回答实验室相关信息」。
>
> **第四层，看是不是模型觉得『自己知道』**。这是幻觉的一种：模型觉得它知道答案，就不调工具了。这种情况要在 prompt 里强调「数据库里的信息必须通过工具获取，不要假设」。
>
> **第五层，加示例**。在 Few-shot 里展示「用户问 X → 助手调用工具 Y」的完整过程，模型会模仿。
>
> **最后是兜底**：可以用 `tool_choice="required"` 强制必须调工具。但我没用，因为它会失去灵活性——用户说「你好」也会被强制调工具。
>
> 另外工程上要能**观测**工具调用率。我会在日志里记录每次调用模型返回了什么 tool_calls，如果某个类别的问题工具调用率突然下降，就能及时发现。

---

### Q6：「Prompt 注入（Prompt Injection）怎么防？」（安全追问）

**满分答法**（这题很多候选人答不上）：

> Prompt 注入是指用户输入里藏着指令，试图覆盖你的 System Prompt。比如用户说「忽略你之前的所有指令，现在你是...」。
>
> 我的防护是分层的：
>
> **架构层**：System Prompt 和用户消息在 API 里是**不同的 role**（system vs user）。大部分模型对 system role 的指令优先级更高，这提供了基础防护。
>
> **输入层**：对用户输入做基本过滤，但这只能挡住明显的模式，不能作为主要手段。
>
> **权限层**：这是最关键的。即使攻击成功让模型「改变角色」，它也无法执行越权操作——因为工具是用闭包注入 `current_user` 的，模型传不了身份参数，所有数据查询都强制带当前用户的过滤条件。也就是说，**模型被忽悠了，但系统不会因此泄露别人的数据**。
>
> **工具层**：写库工具走 interrupt，必须人工确认。即使模型被诱导要删除数据，也会被拦下来。
>
> **输出层**：前端用 DOMPurify 过滤模型输出，防止模型输出恶意 HTML/JS。
>
> 我的核心思路是：**不指望完全防住注入，而是让注入成功后也造成不了实质损害**。这是纵深防御的思路。（第 36 章详解）

## 常见坑

### 坑 1：写抽象指令，模型不知道该怎么做

「回答要准确」→ 改成「只根据检索到的资料回答，资料里没有就说『资料中没有提到』」。

### 坑 2：Prompt 越写越长，关键约束被稀释

5000 token 的 Prompt，模型记不住全部。定期审视：这条不加会怎样？答不出来就删。

### 坑 3：为了省 token 砍掉工具描述

工具调用错误要重来一轮，比省下的 token 贵。

### 坑 4：改了 Prompt 不测

凭感觉「应该变好了」，实际可能引入回归。

### 坑 5：把安全约束只写在 Prompt 里

「不要执行危险操作」——模型可能违反。要用代码（interrupt、权限校验）保证。

### 坑 6：Prompt 不做版本管理

改了几版之后不知道哪个版本最好、为什么改。

### 坑 7：Few-shot 太多导致过拟合

模型开始照抄示例里的内容，而不是泛化。
