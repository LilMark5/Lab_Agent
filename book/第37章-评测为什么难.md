# 第 37 章 · 评测为什么难：三个致命陷阱

> **这一章要回答的核心问题**：为什么"我跑了个评测，准确率 92%"这句话基本不可信？评测集怎么建才不自我欺骗？裁判模型和被测模型为什么要分开？

---

## 37.1 引子：一个"92% 准确率"的假象

假设你兴冲冲地跑了个评测，得到：

```
准确率：92%
faithfulness：0.95
answer_relevancy：0.91
```

**这三个数字可能全是假的。** 本章会告诉你为什么，以及本项目踩过的三个坑。

**先说结论**：**评测最大的风险不是"分数低"，而是"分数高但你不知道为什么高"** —— 一个被污染的评测会给你虚假的信心，让你在生产环境翻车。

---

## 37.2 陷阱一：检索指标饱和（天花板效应）

### 37.2.1 现象

本项目跑检索评测时，发现三种策略的分数**几乎一样**：

```
策略            Hit@3    MRR     nDCG@3
vector          0.93     0.88    0.86
hybrid          0.93     0.89    0.87
hybrid+rerank   0.93     0.89    0.87
```

**看起来"混合检索和 rerank 都没用"** —— 但这是错的。

### 37.2.2 原因：评测集太简单

三个可能的原因（本项目都存在）：

**① 语料太小**

知识库只有几份文档、几十个块。在这种规模下，**任何策略都能轻松找到答案**——甚至"返回全部块"都能 100% 命中。

**② 问题太直接**

评测集的问题基本是原文改写：

```
文档："人工智能实验室周末 09:00 开放，17:00 关闭"
问题："人工智能实验室周末几点开放？"     ← 字面高度重合
```

BM25 都能完美匹配，向量检索更不在话下。**没有区分度。**

**③ 指标只看"在不在 Top-K"**

`Hit@3` 只问"正确答案在不在前 3 名"，不区分"第 1 名"和"第 3 名"（虽然 MRR/nDCG 部分区分）。

### 37.2.3 怎么破

| 方法 | 做法 |
|---|---|
| **增加语料规模** | 加入干扰文档，让知识库达到几百上千块 |
| **增加难例** | 设计语义远但意图近的问题（"周末能去做实验吗" vs "周末开放时间"） |
| **加干扰项** | 故意放入相似但错误的文档（"机器人实验室周末也开放"——错的） |
| **看区分度** | 如果所有策略分数一样，**说明评测集无效**，不是策略无效 |

> **面试金句**："我跑检索评测时发现三种策略分数几乎一样（Hit@3 都是 0.93），第一反应是'混合检索没用'，但深入分析后发现**是评测集饱和了**——语料太小、问题太直接，任何策略都能轻松命中。
>
> 这个坑的价值在于：**当所有方案分数一样时，先怀疑评测集，而不是怀疑方案。** 判断评测集是否有效的一个方法是看**区分度**——如果所有策略都拿满分，那这个评测集给不了你任何信息。"

### 37.2.4 一个实用的自检方法

**加一个"随机基线"和"最差基线"**：

```
随机排序        → Hit@3 应该是 0.1~0.3（如果也是 0.93，说明评测集有问题）
纯 BM25         → 应该明显低于混合（如果一样，说明问题太字面）
```

**如果连随机排序都能拿高分，你的评测集就是废的。**

## 37.3 陷阱二：裁判模型的噪声

### 37.3.1 现象

用 LLM 做裁判（LLM-as-Judge）评估生成质量时，发现：

- 同一份答案，**两次跑分数不一样**（0.82 vs 0.91）
- 某些明显正确的答案被判低分
- 分数分布集中在某个区间（比如都在 0.7-0.9）

### 37.3.2 四个噪声源

**噪声源 1：裁判模型本身不稳定**

即使是 `temperature=0`，LLM 的输出也可能有细微差异（尤其是推理模型）。

**噪声源 2：裁判太弱**

如果用和被测模型**同一个**模型做裁判，它倾向于认可自己的输出（**自我偏好偏差**）。

> **本项目踩过的坑**：早先用 DeepSeek 生成答案，也用 DeepSeek 评判 → 分数虚高。
> **解法（第 38 章的"裁判分离"）**：配置独立的 `JUDGE_MODEL`，用不同的模型（或更强的模型）做裁判。

**噪声源 3：`max_tokens` 太小导致输出被截断**

**这是本项目真实踩过的坑**：

```python
llm = ChatOpenAI(..., max_tokens=1024)
```

DeepSeek-R1 这类**推理模型**会先输出大量 thinking token，**1024 的预算被思考过程吃光**，最终的结构化输出被截断 → RAGAS 解析失败或得到错误分数。

**解法**：提高 `max_tokens`（本项目加了 `RAGAS_MAX_TOKENS` 配置项）。

> ⚠️ **坑（真实）**：**用推理模型做裁判时，`max_tokens` 必须足够大**。思考 token 和输出 token 共用一个预算。这是很多人第一次接 RAGAS 就失败的原因。

**噪声源 4：评分标准模糊**

"这个答案好不好？" —— 1 到 5 分，不同裁判理解不同。

**解法**：给出**明确的评分锚点**（rubric）：

```
5分：完全正确，且引用了出处
4分：正确，但没引用出处
3分：基本正确，有小错
2分：部分正确，有重要遗漏
1分：错误或答非所问
```

### 37.3.3 怎么破

| 方法 | 做法 |
|---|---|
| **裁判与被测分离** | 用不同模型（本项目 `JUDGE_MODEL`） |
| **多次采样取平均** | 跑 3 次取均值，降低随机性 |
| **固定 temperature=0** | 减少抖动 |
| **足够大的 max_tokens** | 特别是推理模型 |
| **明确评分标准** | 写 rubric，别让裁判自由发挥 |
| **人工抽查** | 随机抽 20 条，看裁判和人的判断是否一致 |

> **面试可以说**："LLM-as-Judge 的噪声来自四处：裁判模型本身不稳定、裁判太弱（尤其用同一模型时有自我偏好）、`max_tokens` 太小导致输出被截断（我们用推理模型时真实踩过这个坑）、评分标准模糊。
>
> 我们的对策是：**裁判和被测模型分离**（配置独立的 `JUDGE_MODEL`）、固定 `temperature=0`、把 `max_tokens` 单独配置成 `RAGAS_MAX_TOKENS`、以及**人工抽查验证**（随机抽 20 条看裁判和人的判断是否一致）。最后一条最重要——**裁判本身也需要被评测**。"

## 37.4 陷阱三：指标口径不一致

### 37.4.1 现象

本项目 `context_precision` 这个指标，算出来的分数和直觉不符，一度以为代码写错了。

**RAGAS 的 `context_precision` 定义**：

> 在检索到的 contexts 里，**相关的是否排在前面**（考虑排序的精度）。

它的计算逻辑大致是：

```python
# 逐条判断每个 context 是否相关（用 LLM 判断）
relevances = [True, False, True, False, False]   # 第1、3条相关

# 然后计算"考虑排序的精度"
precision@k = (前 k 条里相关的数量) / k，再加权平均
```

**关键**：它**依赖 LLM 判断每一条 context 是否相关**，而这个判断本身有噪声（陷阱二）。

### 37.4.2 口径不一致的表现

| 你以为 | 实际 |
|---|---|
| "context_precision 是检索精度" | 它是**用 LLM 判断**的检索精度，不是基于标注的 |
| "高分 = 检索好" | 高分可能是"LLM 判宽松了" |
| "和我的 Hit@K 应该相关" | 两者口径完全不同（一个是标注命中，一个是 LLM 判断） |

**本项目的处理**：在文档里明确说明这个指标的口径，不拿它和 Hit@K 直接对比。

### 37.4.3 怎么破

**原则：不同口径的指标不要横向比较，要在自己的维度上纵向对比。**

```
✅ 正确：改了 chunk_size 后，Hit@3 从 0.85 → 0.91（同一指标，纵向对比）
❌ 错误："我们的 Hit@3 是 0.91，比 context_precision 0.75 高，所以检索没问题"
```

**另一个原则**：**每个指标都要写清楚它衡量什么、怎么算的、有什么局限。** 本项目的 `eval_dataset.py` 文件头注释就做了这件事（说明 `expected_source` 只服务检索指标，拒答用例不计入）。

## 37.5 评测集怎么建才不自我欺骗

### 37.5.1 本项目的做法

`eval_dataset.py`（14 条用例）的结构：

```python
CASES: list[dict] = [
    {
        "question": "人工智能实验室周末几点开放？",
        "ground_truth": "人工智能实验室周末 09:00 开放，17:00 关闭。",
        "expected_source": "开放时间",        # 检索指标用
        "category": "factual",                 # factual / refusal
    },
    {
        "question": "实验室里可以养宠物吗？",
        "ground_truth": "知识库中没有相关信息，应当说明资料里没有。",
        "expected_source": None,               # ★ 拒答用例，不计入检索指标
        "category": "refusal",
    },
]
```

**四个字段，每个都有明确用途**：

| 字段 | 用途 |
|---|---|
| `question` | 输入 |
| `ground_truth` | RAGAS 需要 reference 的指标（context_recall 等） |
| `expected_source` | 检索指标（Hit@K/MRR/nDCG）；`None` = 拒答用例 |
| `category` | 分组统计（`factual` vs `refusal`） |

**★ 关键设计：拒答用例**

```
"实验室里可以养宠物吗？"  → 期望：坦承资料里没有，而不是编造
```

这类用例**没有** `expected_source`（因为知识库确实没有），所以**不计入检索指标**（否则会拉低分数，但那不是检索的错）。

**但它在生成侧极其重要** —— 它检验模型会不会编造。这是 RAG 系统最危险的行为。

### 37.5.2 文件头的注释很有价值

```python
"""
为什么单独抽成一个文件：检索评估（evaluate_rag.py）和生成评估
（evaluate_generation.py）必须问同一批问题，两个分数才能互相印证；
各写一份必然随时间发散，最后没人知道哪个分数对应哪套题。
"""
```

**这是一个真实的工程洞察**：**评测集要集中管理，两个评估脚本共用**。否则两边各改各的，分数就不可比了。

### 37.5.3 建评测集的五条原则

| 原则 | 说明 |
|---|---|
| **① 覆盖不同难度** | 简单（字面匹配）+ 中等（语义改写）+ 困难（推理、多跳） |
| **② 包含负例** | 拒答场景（知识库没有答案时应当拒答） |
| **③ 标注来源** | 每条标注"应该命中哪份文档"，才能算检索指标 |
| **④ 独立于实现** | **不要从现有系统的输出里挑"好答案"当 ground truth**（这会自我证实） |
| **⑤ 持续增长** | 生产环境发现 bad case → 补充进评测集 |

**第 ④ 条最重要也最容易犯**：如果你从系统的输出里挑答案当标准答案，那你测的是"系统能否复现自己"，不是"系统是否正确"。

> **面试金句**："建评测集最容易犯的错是**从系统输出里挑答案当 ground truth**——那样测的是'系统能否复现自己'。正确做法是人工根据原始资料独立标注，且要覆盖不同难度、包含拒答负例、标注期望命中来源。另外，**生产环境的 bad case 要持续补充进评测集**，这样评测集才会越来越贴近真实分布。"

## 37.6 评测的正确心态

### 37.6.1 评测不是"证明系统好"，是"找到系统哪里差"

**错误心态**：跑个评测拿到高分，写进简历/汇报。
**正确心态**：**评测是发现问题的工具，不是装点门面的数字。**

一个"分数低但你知道为什么低"的评测，比"分数高但你不知道为什么高"有价值得多。

### 37.6.2 A/B 实验才是评测的真正用法

单次绝对分数意义有限。**有价值的是对比**：

```
改了 chunk_size：500 → 300
  Hit@3:  0.85 → 0.91   ✅ 变好
  nDCG@3: 0.80 → 0.87   ✅ 变好
  → 采用

开启 rerank：
  nDCG@3: 0.87 → 0.89   ✅ 小幅提升
  → 采用（但要知道提升幅度）

开启查询改写：
  Hit@3:  0.91 → 0.91   ⚠️ 无变化
  → 需要分析：是不是评测集里没有口语化问题？
```

**本项目的现状**：检索侧做了三策略对比（`vector` / `hybrid` / `hybrid+rerank`），但**查询改写的 A/B 没做**（第 28 章提过）。

### 37.6.3 评测要自动化

`run_eval.py` 提供一键评测入口。价值：

- 每次改动后能快速回归
- 参数调整有据可依
- 可以放进 CI（虽然 LLM 评测慢且有成本，通常不放）

## 37.7 最小骨架：评测集有效性自检

```python
"""
minimal_eval_check.py —— 评测集有效性自检
运行：python minimal_eval_check.py  （纯 Python）
目的：验证你的评测集是不是"废的"（所有策略都满分）
"""
import random


# ── 一个玩具检索系统 ──────────────────────────────────────
CORPUS = [
    {"id": "c0", "doc": "人工智能实验室周末 09:00 开放，17:00 关闭", "source": "开放时间"},
    {"id": "c1", "doc": "机器人实验室周一至周五 08:30-18:00 开放", "source": "开放时间"},
    {"id": "c2", "doc": "进入实验室必须穿戴实验服和防护眼镜", "source": "安全规范"},
    {"id": "c3", "doc": "离心机使用前需检查转子是否平衡", "source": "设备说明"},
]

# ── 评测集（问题 → 应命中的 source）───────────────────────
EASY_CASES = [          # 字面高度重合 → 太简单
    ("人工智能实验室周末几点开放？", "开放时间"),
    ("进入实验室要穿什么？", "安全规范"),
]

HARD_CASES = [          # 语义改写 / 需要推理 → 有区分度
    ("周末能去做实验吗？", "开放时间"),          # 意图相同，用词完全不同
    ("离心机有什么安全注意事项？", "设备说明"),   # 跨文档推理
]


def tokenize(text):
    chars = [c for c in text.lower() if c.isalnum()]
    return set(chars) | {a + b for a, b in zip(chars, chars[1:])}


def retrieve(query, top_k=3, strategy="bm25"):
    q = tokenize(query)
    scored = []
    for c in CORPUS:
        d = tokenize(c["doc"])
        score = len(q & d) / len(q | d) if (q | d) else 0
        scored.append({**c, "score": score})
    scored.sort(key=lambda x: x["score"], reverse=True)
    return scored[:top_k]


def random_baseline(query, top_k=3):
    """★ 随机基线：如果它也拿高分，评测集就是废的。"""
    cs = CORPUS[:]
    random.shuffle(cs)
    return cs[:top_k]


def hit_at_k(expected, hits, k=3):
    return 1.0 if any(h["source"] == expected for h in hits[:k]) else 0.0


def evaluate(cases, label):
    print(f"\n{'='*62}\n【{label}】{len(cases)} 条用例")

    strategies = {
        "bm25": lambda q: retrieve(q, strategy="bm25"),
        "random(基线)": lambda q: random_baseline(q),
    }
    for name, fn in strategies.items():
        scores = [hit_at_k(exp, fn(q)) for q, exp in cases]
        avg = sum(scores) / len(scores) if scores else 0
        print(f"  {name:14} Hit@3 = {avg:.2f}")
    return avg


if __name__ == "__main__":
    print("评测集有效性自检")
    print("判据：如果 random 基线和真实策略分数接近 → 评测集无效")

    evaluate(EASY_CASES, "简单用例（字面重合）")
    evaluate(HARD_CASES, "困难用例（语义改写）")

    print(f"\n{'='*62}")
    print("【结论】")
    print("  语料只有 4 条，Top-3 覆盖了 75% → 随机都能命中")
    print("  ★ 这说明：**语料规模必须远大于 Top-K**，评测才有意义")
    print("     经验值：语料块数 > 100×Top_K（比如 Top-5 就要 500+ 块）")
```

**预期输出**：

```
【简单用例（字面重合）】2 条用例
  bm25           Hit@3 = 1.00
  random(基线)   Hit@3 = 1.00     ← ★ 随机也满分！

【困难用例（语义改写）】2 条用例
  bm25           Hit@3 = 0.50
  random(基线)   Hit@3 = 1.00     ← 仍然很高
```

**这个演示揭示的核心问题**：**语料只有 4 条，Top-3 就覆盖 75%，随机策略都能拿满分。**

**经验值**：**语料块数应该远大于 Top-K**（比如 Top-5 至少要几百个块），否则指标饱和。

## 37.8 面试问答

### Q1：你怎么做 RAG 评测？遇到过什么坑？

**答**：分两侧。检索侧评 Hit@1/3、MRR、nDCG@3；生成侧用 RAGAS 四指标（faithfulness、answer_relevancy、context_precision、context_recall）。评测集 14 条，检索和生成共用同一批问题（单独抽成 `eval_dataset.py`，避免两边发散）。

**遇到过三个坑**：

**一是检索指标饱和**——三种策略分数几乎一样（Hit@3 都是 0.93）。深入分析发现是评测集太简单：语料太小、问题太直接。教训是**当所有方案分数一样时，先怀疑评测集**。

**二是裁判模型噪声**——用同一个模型生成和评判会有自我偏好，分数虚高；而且用推理模型做裁判时 `max_tokens` 太小会导致输出被思考 token 吃光。对策是裁判分离（独立 `JUDGE_MODEL`）、固定 temperature=0、单独配置 `RAGAS_MAX_TOKENS`。

**三是指标口径不一致**——`context_precision` 是 LLM 判断的检索精度，和基于标注的 Hit@K 口径完全不同，不能横向比较。原则是**同指标纵向对比，不同口径不横向比**。

### Q2：什么是"评测集饱和"？怎么发现？

**答**：所有策略都拿满分（或分数几乎一样），说明评测集区分度不够，给不了你任何信息。

**发现方法**：加一个**随机基线**。如果随机排序也能拿高分，评测集就是废的。

原因是语料太小（Top-K 覆盖了大部分语料）或问题太直接（字面高度重合，任何策略都能命中）。

**经验值**：语料块数应该远大于 Top-K。另外要加难例（语义改写、跨文档推理）和干扰项（相似但错误的文档）。

### Q3：LLM-as-Judge 的噪声怎么处理？

**答**：四个噪声源和对应对策：

**裁判不稳定** → 固定 `temperature=0`，多次采样取平均。

**裁判太弱 / 自我偏好** → **裁判和被测模型分离**（我们配置了独立的 `JUDGE_MODEL`）。这是最重要的一条。

**输出被截断** → 单独配置 `max_tokens`。我们用推理模型时真实踩过：思考 token 和输出 token 共用一个预算，1024 被思考吃光了，结构化输出被截断导致 RAGAS 解析失败。

**评分标准模糊** → 写明确的 rubric（5分=完全正确且引用出处，4分=正确但没引用…）。

**最后也是最重要的**：**裁判本身也需要被评测** —— 随机抽 20 条，人工看裁判和人的判断是否一致。

### Q4：评测集怎么建？

**答**：五条原则。

一是**覆盖不同难度**（简单/中等/困难）。
二是**包含负例**（拒答场景——知识库没有答案时应当坦承，这是 RAG 最危险的行为）。
三是**标注来源**（每条标注"应命中哪份文档"，才能算检索指标）。
四是**独立于实现**——**最容易犯的错是从系统输出里挑答案当 ground truth**，那样测的是"系统能否复现自己"。正确做法是人工根据原始资料独立标注。
五是**持续增长**——生产环境的 bad case 要补充进来，让评测集贴近真实分布。

我们 14 条用例里专门有拒答类（"实验室里可以养宠物吗？"），它们的 `expected_source` 是 `None`，**不计入检索指标**（否则会拉低分数，但那不是检索的错），但在生成侧检验模型会不会编造。

### Q5：评测的正确心态是什么？

**答**：**评测是发现问题的工具，不是装点门面的数字。**

一个"分数低但你知道为什么低"的评测，比"分数高但你不知道为什么高"有价值得多。

而且单次绝对分数意义有限，**有价值的是 A/B 对比**：改了某个参数后，同一指标的变化。这才是评测的真正用法。

我们做了检索侧的三策略对比（vector / hybrid / hybrid+rerank），但**查询改写的 A/B 还没做**——这是明确的待办，因为改写的价值体现在口语化问题上，需要按查询类型分组统计才能看出来。

### Q6：为什么检索和生成要共用评测集？

**答**：因为两个分数要互相印证。

如果检索侧 Hit@3 是 0.9 但生成侧 faithfulness 只有 0.5，说明**检索到了但模型没用好**——问题在生成而不是检索。反之如果检索差但生成好，可能是模型在用参数知识（危险，说明它在编）。

**如果两个评估各写一份评测集，必然随时间发散**，最后没人知道哪个分数对应哪套题。所以我们把用例单独抽成 `eval_dataset.py`，两边共用。这是 `eval_dataset.py` 文件头注释里明确写的理由。

## 37.9 速记卡

> **评测的三大陷阱：指标饱和 / 裁判噪声 / 口径不一致。**

**陷阱一：饱和** —— 所有策略分数一样 → **先怀疑评测集**
- 判据：**随机基线也拿高分**
- 原因：语料太小（块数应 >> Top-K）、问题太字面
- 破：加难例、加干扰项、扩大语料

**陷阱二：裁判噪声** —— 四源：不稳定 / **自我偏好** / **max_tokens 截断** / 标准模糊
- 破：**裁判分离**（JUDGE_MODEL）/ temperature=0 / 单独配 max_tokens / 写 rubric / **人工抽查**

**陷阱三：口径** —— `context_precision` 是 LLM 判断的，和 Hit@K 不同口径
- 破：**同指标纵向比，不同口径不横向比**

**评测集五原则**：难度分层 / **含拒答负例** / 标注来源 / **独立于实现（别从输出挑答案）** / 持续增长

**★ 共用评测集**：检索和生成问同一批问题，分数才能互相印证

**★ 正确心态**：评测是**发现问题的工具**；有价值的是 **A/B 对比**不是绝对分数

**代码位置**：`backend/eval_dataset.py`、`evaluate_rag.py`、`evaluate_generation.py`、`run_eval.py`

## 37.10 延伸思考

1. **如果生产环境的 bad case 和评测集分布差异很大，怎么办？**
   提示：这是**分布漂移**问题。解法：① 定期从生产日志采样（尤其是用户点了"不满意"的）补充进评测集；② 保留一个"生产分布"的小评测集和一个"标准"评测集，分开统计；③ 监控生产指标（比如拒答率、平均轮次）作为辅助信号。

2. **评测本身也有成本（LLM 调用），怎么平衡？**
   提示：① 检索指标不需要 LLM（基于标注，几乎免费），可以经常跑；② 生成指标需要 LLM，成本高，可以只在重要改动时跑，或者抽样跑（比如 14 条里跑 5 条）；③ 用便宜模型做裁判（但要和被测模型不同——这是一对矛盾，需要权衡）。

3. **"用户满意度"能不能作为评测指标？**
   提示：能，而且是最真实的指标。但噪声大（用户可能因为 UI 不好而点不满意）、反馈稀疏（大部分用户不点）。实务做法是**多信号组合**：点赞/点踩 + 会话轮次 + 是否重复提问 + 是否转人工。**这些"隐式信号"往往比显式评分更有用。**
