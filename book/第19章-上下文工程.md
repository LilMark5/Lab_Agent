# 第 19 章 · 上下文工程：长对话怎么不撑爆上下文窗口

> **这一章要回答的核心问题**：多轮对话 + 每次检索都返回一大段原文，context window 是怎么被撑爆的？token 怎么估算才靠谱？裁剪时为什么必须保护 `tool_calls` 与 `ToolMessage` 的配对？滑动窗口和摘要两种策略怎么选？

---

## 19.1 引子：一个必然会发生的事故

假设你的 Agent 上线了，用户很爱用，一个会话聊了 30 轮。第 31 轮时，用户问了个简单问题："明天几点开门？"

然后请求失败了。日志里：

```
BadRequestError: This model's maximum context length is 65536 tokens.
However, you requested 78231 tokens.
```

**这不是模型的错，是你没做上下文管理。**

我们来算算 30 轮对话是怎么到 78K 的：

| 来源 | 每轮增量 | 30 轮累计 |
|---|---|---|
| 用户消息 | ~50 token | 1,500 |
| AI 回复 | ~200 token | 6,000 |
| 工具调用参数 | ~100 token | 3,000 |
| **检索返回的原文** | **~2,000 token** | **60,000** ← 大头 |
| System Prompt | 每次都带 | 500 |
| **合计** | | **~71,000** |

**发现问题了吗？** 大头不是对话，是**工具返回的内容**。每一轮检索都会把几千 token 的文档原文塞进 `ToolMessage`，然后**永久留在 messages 里**，因为 Reducer 是追加。

更糟的是第 14 章讲过的**平方级增长**：第 N 轮调用模型时，要带上前 N-1 轮的**全部内容**。所以 30 轮下来，累计消耗的 token 不是 71K，而是：

```
第 1 轮: 2.4K
第 2 轮: 4.8K
...
第 30 轮: 71K
─────────────
累计 ≈ 1.1M token
```

按 DeepSeek 的定价，这一个会话就烧掉几块钱。**1000 个这样的会话 = 几千元。**

这就是为什么上下文工程（Context Engineering）是 Agent 开发里**最值钱**的技能之一——它直接决定了你的系统能不能用、要花多少钱。

## 19.2 上下文里到底装了什么

先看清楚一次 LLM 调用时，实际送进去的是什么。本项目 `agent_service.py:264-270`：

```python
async def agent_node(state: AgentState) -> dict:
    history = _trim_messages(state["messages"], settings.MAX_CONTEXT_TOKENS)
    response = await llm.ainvoke([SystemMessage(content=SYSTEM_PROMPT), *history])
    return {"messages": [response]}
```

送进去的是：

```
[SystemMessage(SYSTEM_PROMPT)] + history
```

而 `history` 是 `state["messages"]`（裁剪后），包含：

| 消息类型 | 来源 | 典型大小 |
|---|---|---|
| `HumanMessage` | 用户输入 | 小 |
| `AIMessage`（纯文本） | 模型回复 | 中 |
| `AIMessage`（带 tool_calls） | 模型的工具调用决策 | 小（但参数是元数据开销） |
| `ToolMessage` | 工具返回值 | **可以非常大** |

**四类"上下文吞噬者"**：

1. **检索返回的文档原文**（本项目最大头）
2. **工具返回的完整 JSON**（比如 `list_open_labs` 返回 10 个实验室的详细信息）
3. **错误重试的痕迹**（失败调用 + 错误 + 重试 + 又失败……）
4. **用户的粘贴**（用户可能一次粘几千字的需求文档）

## 19.3 Token 估算：不引入依赖的务实方案

### 19.3.1 为什么不用 tiktoken？

最"正确"的做法是用 tiktoken（OpenAI 官方的分词器）精确计算。但本项目没用，理由是：

| 问题 | 说明 |
|---|---|
| **模型不匹配** | tiktoken 的分词表是 OpenAI 的。我们用的是 DeepSeek，分词规则不同，算出来的数不准 |
| **依赖重** | tiktoken 要下载 BPE 词表文件（几 MB），首次加载慢，容器化部署麻烦 |
| **中文不准** | 中文在 BPE 下通常 1 字 = 1-2 token，和英文的 4 字符/token 差异巨大 |
| **要按模型选编码** | 不同模型对应不同 encoding（`cl100k_base`、`o200k_base`…），维护成本高 |

### 19.3.2 本项目方案：字符数 / 4

`agent_service.py:176-190`：

```python
def _estimate_tokens(message: AnyMessage) -> int:
    """轻量 token 估算：字符数 / 4 向上取整。

    不引入 tiktoken（依赖重、且对中文分词不准），用「字符/4」做保守近似：
    英文 1 token ≈ 4 字符，中文 1 token ≈ 1~1.5 字符，因此对中文这是
    偏高的估计（更早触发裁剪），宁多剪不越界。工具调用参数也会计入，
    避免大段检索结果被漏算。
    """
    content = getattr(message, "content", "") or ""
    text = content if isinstance(content, str) else str(content)
    extra = 0
    tool_calls = getattr(message, "tool_calls", None)
    if tool_calls:
        extra += len(json.dumps(tool_calls, ensure_ascii=False, default=str))
    return (len(text) + extra + 3) // 4
```

**三个设计点，每个都有讲究**：

**① 为什么要"+3 再整除"？**

```python
return (len(text) + extra + 3) // 4
```

这是**向上取整的整数技巧**。`(n + 3) // 4` 等价于 `ceil(n / 4)`。

比如 `n=5`：真实是 1.25 token，但我们算成 `(5+3)//4 = 2`。**宁可高估**（保守），因为高估会**更早触发裁剪**，而低估会**撑爆上下文**。

**② 为什么用 `ensure_ascii=False`？**

```python
len(json.dumps(tool_calls, ensure_ascii=False, default=str))
```

`ensure_ascii=True`（默认）会把中文转成 `\u4e2d\u6587`，一个中文字符变成 **6 个字符**，导致估算严重偏高（6 倍！）。设 `False` 保持原字符。

这是一个很容易漏的细节，也是"中文场景下 JSON 序列化要格外小心"的典型例子。

**③ 为什么 `default=str`？**

`tool_calls` 里可能有非 JSON 原生类型（比如 Pydantic 对象、枚举），`json.dumps` 默认会抛 `TypeError`。`default=str` 让它们退化成字符串表示，保证不崩。

### 19.3.3 这个估算有多准？

| 场景 | 真实 token | 我们的估算 | 偏差 |
|---|---|---|---|
| 1000 字英文 | ~250 | 250 | ✅ 准 |
| 1000 字中文 | ~700-1000 | 250 | ❌ **低估 3-4 倍** |

**等等，注释里说"对中文是偏高的估计"，但算出来是低估？**

仔细看：英文 1000 字符 ≈ 250 token（4 字符/token）；中文 1000 字符 ≈ 700-1000 token（1-1.5 字符/token）。我们用「字符/4」，中文 1000 字符算出 250 —— **严重低估**。

> ⚠️ **这是一个真实的偏差，需要诚实面对**。注释里写的"对中文是偏高的估计"这个措辞值得商榷。准确的说法是：
> **对英文准确，对中文偏低。** 但因为中文模型（DeepSeek 等）的 context window 通常较大（64K-128K），且我们的默认预算 `MAX_CONTEXT_TOKENS=4000` 相对保守，实际使用中不容易撑爆。
>
> **如果你要改进**：可以按 CJK 字符加权。一个务实的修正是：
> ```python
> cjk = sum(1 for ch in text if '\u4e00' <= ch <= '\u9fff')
> return (len(text) + cjk * 2 + extra + 3) // 4   # 中文字符按 2 倍权重
> ```
> 这样中文 1000 字 → (1000 + 2000)/4 = 750 token，接近真实值。
> **这是一个很好的简历优化点**——证明你不只是用了现成方案，还针对中文场景做了调优。

### 19.3.4 更精确的方案（了解即可）

如果要求精确，三条路：

1. **用模型厂商的 tokenizer**：DeepSeek 提供了 tokenizer，但引入依赖
2. **用 API 返回的 usage**：调用后读 `response.usage.prompt_tokens`，用真实值做反馈校准（**推荐**，零成本）
3. **混合方案**：估算做前置裁剪，真实 usage 做监控告警

**方案 2 最实用**：

```python
response = await llm.ainvoke(...)
usage = response.response_metadata.get("token_usage", {})
logger.info("prompt_tokens=%s completion_tokens=%s", usage.get("prompt_tokens"), usage.get("completion_tokens"))
```

把真实消耗打点，接到监控上。超出阈值告警。

## 19.4 裁剪策略：滑动窗口 vs 摘要

### 19.4.1 项目实现（`agent_service.py:193-246`）

```python
def _trim_messages(messages: list[AnyMessage], budget_tokens: int) -> list[AnyMessage]:
    """把消息裁剪进 token 预算，保证 model 不因超长而报错。"""
    if not messages or budget_tokens <= 0:
        return list(messages)

    total = sum(_estimate_tokens(m) for m in messages)
    if total <= budget_tokens:
        return list(messages)

    # 找出「AI 带 tool_calls」的位置，其后的 ToolMessage 与它绑定，裁剪时成组处理。
    protected = set()
    for i, m in enumerate(messages):
        if isinstance(m, AIMessage) and getattr(m, "tool_calls", None):
            j = i + 1
            while j < len(messages) and isinstance(messages[j], ToolMessage):
                protected.add(j)
                j += 1
    # 最新的那条（可能是 ToolMessage）也始终保留，它是本轮要回应的依据。
    if messages:
        protected.add(len(messages) - 1)

    keep = list(messages)
    strategy = settings.TRIM_STRATEGY
    dropped = 0
    i = 0
    while i < len(keep) and sum(_estimate_tokens(m) for m in keep) > budget_tokens:
        if i in protected:
            i += 1
            continue
        del keep[i]
        dropped += 1
        # 删除后索引整体前移，受保护索引需同步左移。
        protected = {p - 1 if p > i else p for p in protected}

    if strategy == "summary" and dropped > 0:
        summary = HumanMessage(
            content=f"[系统提示] 更早的 {dropped} 条对话因上下文长度已省略，"
            "请仅基于下方仍然保留的内容回答。"
        )
        keep = [summary, *keep]

    return keep
```

### 19.4.2 三步拆解

**第一步：快速判断（不超预算原样返回）**

```python
total = sum(_estimate_tokens(m) for m in messages)
if total <= budget_tokens:
    return list(messages)
```

99% 的调用走这条路径，几乎零成本。

**第二步：标记受保护的消息**

```python
protected = set()
for i, m in enumerate(messages):
    if isinstance(m, AIMessage) and getattr(m, "tool_calls", None):
        j = i + 1
        while j < len(messages) and isinstance(messages[j], ToolMessage):
            protected.add(j)
            j += 1
if messages:
    protected.add(len(messages) - 1)
```

**这是整个函数最容易出错、也最关键的部分。** 详见 19.5。

**第三步：从最老开始删，直到进预算**

```python
while i < len(keep) and sum(_estimate_tokens(m) for m in keep) > budget_tokens:
    if i in protected:
        i += 1
        continue
    del keep[i]
    dropped += 1
    protected = {p - 1 if p > i else p for p in protected}
```

三个细节：

- **`protected` 索引要同步左移**：删除元素后，后面所有元素的索引都减 1。这行 `protected = {p - 1 if p > i else p for p in protected}` 就是干这个的。**忘了这行会产生极难排查的 bug**——保护错位，可能删掉不该删的。
- **`i` 不递增**：因为删除后，下一个元素移到了当前位置 `i`，所以继续检查 `i` 而不是 `i+1`。
- **循环条件里有 `i < len(keep)`**：防止全被保护时死循环。

### 19.4.3 两种策略对比

| 策略 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **sliding_window**（默认） | 直接丢弃最老的消息 | 简单、确定、无额外成本 | 丢失早期上下文（用户可能引用前几轮内容） |
| **summary** | 丢弃后插入一条摘要占位 | 保留"前面还有内容"的语义线索 | 摘要是"有 N 条被省略"，不是真正的语义摘要 |

`agent_service.py:239-244`：

```python
if strategy == "summary" and dropped > 0:
    summary = HumanMessage(
        content=f"[系统提示] 更早的 {dropped} 条对话因上下文长度已省略，"
        "请仅基于下方仍然保留的内容回答。"
    )
    keep = [summary, *keep]
```

**诚实说明**：这个 `summary` 策略其实是"**占位符策略**"，不是真正的 LLM 摘要。它只告诉模型"前面被省略了 N 条"，并没有把早期对话**压缩成语义摘要**。

真正的 LLM 摘要长这样：

```python
async def summarize_history(messages: list[AnyMessage]) -> str:
    """用 LLM 把早期对话压缩成一段摘要（额外的 LLM 调用，有成本）。"""
    text = "\n".join(f"{type(m).__name__}: {m.content}" for m in messages)
    resp = await cheap_llm.ainvoke(
        f"把下面这段对话压缩成 100 字以内的摘要，保留关键事实（人名、时间、地点、决策）：\n{text}"
    )
    return resp.content
```

**为什么本项目没做真摘要？** 三个理由：

1. **成本**：每次裁剪都要额外调一次 LLM
2. **延迟**：用户要多等一次模型调用
3. **收益不确定**：我们的场景（实验室预约）对话轮次浅，滑窗够用

> **面试标准答法**："裁剪我实现了两种策略：默认 sliding_window 直接丢最老的；另一种是 summary，会插入一条占位消息告诉模型'前面省略了 N 条'。诚实地讲，后者是占位符而不是真正的 LLM 语义摘要——真摘要需要额外一次模型调用，会带来成本和延迟，我们评估后认为当前场景轮次浅、滑窗够用。如果要支持超长对话（比如几十轮的深度咨询），会引入真摘要，并考虑用便宜的小模型来做压缩。"

## 19.5 最关键的坑：tool_calls 与 ToolMessage 的配对

这是本章**最重要**的一节，也是最能体现工程深度的地方。

### 19.5.1 问题是什么

第 16 章讲过：`AIMessage.tool_calls` 和 `ToolMessage` 必须按 `tool_call_id` 严格配对。OpenAI 协议要求：

```
AIMessage(tool_calls=[{id: "c1", ...}])   ← 必须
ToolMessage(tool_call_id="c1")             ← 紧跟其后
```

**如果裁剪时只删了 ToolMessage，留下了 AIMessage 的 tool_calls**，下次调用模型时，协议不完整，API 直接报 400：

```
BadRequestError: An assistant message with 'tool_calls' must be followed by
tool messages responding to each tool_call_id.
```

这是一个**隐蔽且致命**的 bug：它不会在裁剪时立刻报错，而是在**下一次 LLM 调用**时才炸，而且错误信息指向的是消息序列，很难联想到是裁剪导致的。

### 19.5.2 项目的解法

```python
protected = set()
for i, m in enumerate(messages):
    if isinstance(m, AIMessage) and getattr(m, "tool_calls", None):
        j = i + 1
        while j < len(messages) and isinstance(messages[j], ToolMessage):
            protected.add(j)
            j += 1
```

逻辑：**找到所有"带 tool_calls 的 AIMessage"，把它后面紧跟着的 ToolMessage 全部加入保护集合。**

举例：

```
[0] HumanMessage: "预约显微镜"           ← 可删
[1] AIMessage(tool_calls=[c1])          ← 可删（但删了 c1 就没意义了）
[2] ToolMessage(id=c1, "检索结果...")    ← 🔒 保护
[3] AIMessage(tool_calls=[c2])          ← 可删
[4] ToolMessage(id=c2, "预约成功")       ← 🔒 保护
[5] HumanMessage: "谢谢"                ← 🔒 保护（最新一条）
```

**一个值得推敲的点**：代码只保护了 `ToolMessage`，**没有保护带 tool_calls 的 `AIMessage` 本身**。

这意味着可能出现这种情况：

```
删除 [1]（AIMessage with tool_calls），保留 [2]（ToolMessage id=c1）
→ 结果：一条孤立的 ToolMessage，引用了一个不存在的 tool_call_id
```

这个情况会不会报错？**实测结果是：大部分 OpenAI 兼容接口对"孤立 ToolMessage"比对"缺失 ToolMessage"宽容**——通常不会报 400，但模型可能困惑（看到一个没有对应调用的回复）。

**更严谨的做法是成对保护**：

```python
for i, m in enumerate(messages):
    if isinstance(m, AIMessage) and getattr(m, "tool_calls", None):
        protected.add(i)          # ★ 连 AIMessage 本身一起保护
        j = i + 1
        while j < len(messages) and isinstance(messages[j], ToolMessage):
            protected.add(j)
            j += 1
```

> ⚠️ **这是一个可以改进的真实点**。当前实现对"缺失 ToolMessage"防住了（这是会报 400 的硬错误），对"孤立 ToolMessage"没有防住（软问题）。面试时主动指出这一点，说明你理解得很深。
>
> 不过要注意：如果同时保护 AIMessage 和 ToolMessage，可用的裁剪空间会变小（一整组要么全留要么全删）。这是"安全性"和"裁剪效率"的取舍。

### 19.5.3 为什么要保护"最新一条"

```python
if messages:
    protected.add(len(messages) - 1)
```

因为**最新一条是本轮要回应的依据**。如果它被删了，模型就不知道用户刚说了什么。

尤其在 `tools → agent` 的循环里，最新一条是刚返回的 `ToolMessage`（工具结果）。删掉它，模型就看不到工具结果了，等于白调一次工具。

### 19.5.4 一个完整的裁剪示例

假设预算 1000 token，消息序列（每行括号是估算 token）：

```
[0] HumanMessage: "你好"                              (10)
[1] AIMessage: "有什么可以帮你？"                       (30)
[2] HumanMessage: "显微镜实验室有什么设备？"             (40)
[3] AIMessage(tool_calls=[c1])                        (60)
[4] ToolMessage(id=c1): "扫描电镜、离心机、..."          (400)  🔒
[5] AIMessage: "有扫描电镜、离心机..."                   (80)
[6] HumanMessage: "离心机明天下午有空吗？"               (50)
[7] AIMessage(tool_calls=[c2])                        (60)
[8] ToolMessage(id=c2): "14:00-16:00 已被占用..."      (500)  🔒
```

总计 = 1230 token > 1000，需要裁剪。

保护集合 = `{4, 8, 8}` = `{4, 8}`（最新一条是 [8]，已在保护里）

裁剪过程（从 i=0 开始）：

```
i=0: 不在保护 → 删 [0]，dropped=1，总 1220  索引左移：保护 {3, 7}
i=0: 不在保护 → 删（原[1]），dropped=2，总 1190  保护 {2, 6}
i=0: 不在保护 → 删（原[2]），dropped=3，总 1150  保护 {1, 5}
i=0: 不在保护 → 删（原[3] AIMessage tool_calls），dropped=4，总 1090  保护 {0, 4}
i=0: 在保护 → i=1
i=1: 不在保护 → 删（原[5]），dropped=5，总 1010  保护 {0, 3}
i=1: 不在保护 → 删（原[6]），dropped=6，总 960   保护 {0, 2}
i=1: 总 960 <= 1000 → 退出循环
```

最终保留：

```
[0] ToolMessage(id=c1): "扫描电镜、离心机、..."     (400)
[1] ToolMessage(id=c2): "14:00-16:00 已被占用..."  (500)
```

（外加 summary 模式下前面会插入一条占位消息）

**注意结果**：保留了两条 ToolMessage，但它们的父 AIMessage 被删了。这正是 19.5.2 讨论的情况——**不会报 400，但语义上有点怪**。这就是为什么"成对保护"是个值得做的改进。

### 19.5.5 循环复杂度：一个性能隐患

```python
while i < len(keep) and sum(_estimate_tokens(m) for m in keep) > budget_tokens:
```

**每次循环都重新计算总和** → O(n) 的计算放在 O(n) 的循环里 = **O(n²)**。

对于 100 条消息、裁掉 50 条的场景，就是 50 × 100 = 5000 次 `_estimate_tokens` 调用，每次都要 `json.dumps` tool_calls……这个开销不小（虽然比 LLM 调用小得多）。

**优化方案**：增量维护 total。

```python
total = sum(_estimate_tokens(m) for m in messages)
keep = list(messages)
i = 0
while i < len(keep) and total > budget_tokens:
    if i in protected:
        i += 1
        continue
    total -= _estimate_tokens(keep[i])      # ★ 只减去被删的那条
    del keep[i]
    ...
```

这样是 O(n)。

> 📝 **又一个简历优化点**：把 O(n²) 的裁剪改成 O(n) 的增量维护。这是一个具体、可验证、有技术含量的改进。

## 19.6 配置项与调优

### 19.6.1 配置

```bash
# .env
# 送入模型的对话历史 token 预算（默认 4000）
MAX_CONTEXT_TOKENS=4000
# 裁剪策略：sliding_window（默认）| summary
TRIM_STRATEGY=sliding_window
```

### 19.6.2 `MAX_CONTEXT_TOKENS=4000` 是怎么定的？

这是一个**权衡**：

| 太大 | 太小 |
|---|---|
| 逼近 context window，有报错风险 | 丢失上下文，模型"健忘" |
| token 成本高 | 成本低 |
| 延迟高（prefill 时间长） | 延迟低 |

考虑因素：

1. **模型 context window**：DeepSeek 是 64K，4000 只占 6%，非常安全
2. **典型对话长度**：本项目场景多数 3-5 轮，正常情况 1000-2000 token，**根本不会触发裁剪**
3. **单次检索返回**：检索 top-5 块，每块约 500 token = 2500 token，加上对话刚好接近 4000

**所以 4000 的含义是**："正常情况下不裁剪；只有检索返回特别多或对话特别长时才触发"。

这是一个**保守但合理**的默认值。如果你的场景需要更长的记忆，可以调大；如果成本敏感，可以调小。

### 19.6.3 裁剪只影响"送入模型"，不影响"存储"

这一点必须清楚：

```python
history = _trim_messages(state["messages"], settings.MAX_CONTEXT_TOKENS)
response = await llm.ainvoke([SystemMessage(content=SYSTEM_PROMPT), *history])
```

`_trim_messages` 的返回值**只用于这一次 LLM 调用**，`state["messages"]` **没有任何变化**。

**好处**：checkpointer 里存的还是完整历史，不会丢失信息；下次如果预算变了（或消息变短了），还能看到全部。

**坏处**：第 17 章讲过的**存储膨胀问题没有解决**——state 里的消息一直在涨。

要同时解决存储膨胀，需要在**写入 state 时**就限制。这是一个"视图裁剪 vs 存储裁剪"的区别：

| 类型 | 时机 | 影响 |
|---|---|---|
| **视图裁剪**（本项目） | 送入模型前 | 只省 token，不省存储 |
| **存储裁剪** | 写入 state 前 | 省 token + 省存储，但永久丢失信息 |

## 19.7 最小骨架：亲手验证裁剪

```python
"""
minimal_context.py —— token 估算与上下文裁剪最小实现
运行：python minimal_context.py  （纯 Python，无需任何依赖）
"""
import json
from dataclasses import dataclass, field


# ── 简化的消息类型（模拟 LangChain 的 Message） ──────────────
@dataclass
class Msg:
    role: str                       # human / ai / tool / system
    content: str = ""
    tool_calls: list | None = None
    tool_call_id: str | None = None


# ── token 估算 ──────────────────────────────────────────────
def estimate_tokens(m: Msg) -> int:
    """字符/4 向上取整；中文按 2 倍权重修正（可选开关）。"""
    text = m.content or ""
    extra = 0
    if m.tool_calls:
        extra += len(json.dumps(m.tool_calls, ensure_ascii=False, default=str))
    # CJK 修正：中文 1 字 ≈ 1~1.5 token，比 4 字符/token 密得多
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    return (len(text) + cjk * 2 + extra + 3) // 4


# ── 裁剪 ────────────────────────────────────────────────────
def trim(messages: list[Msg], budget: int, strategy: str = "sliding_window",
         protect_ai: bool = False) -> list[Msg]:
    """把消息裁剪进 token 预算。

    protect_ai=True 时连「带 tool_calls 的 AI 消息」一起保护（成对保护）。
    """
    if not messages or budget <= 0:
        return list(messages)

    total = sum(estimate_tokens(m) for m in messages)
    if total <= budget:
        return list(messages)

    # 标记受保护项
    protected = set()
    for i, m in enumerate(messages):
        if m.role == "ai" and m.tool_calls:
            if protect_ai:
                protected.add(i)          # ★ 成对保护
            j = i + 1
            while j < len(messages) and messages[j].role == "tool":
                protected.add(j)
                j += 1
    protected.add(len(messages) - 1)      # 最新一条永保

    keep = list(messages)
    dropped = 0
    i = 0
    while i < len(keep) and total > budget:
        if i in protected:
            i += 1
            continue
        total -= estimate_tokens(keep[i])  # ★ 增量维护，O(n)
        del keep[i]
        dropped += 1
        protected = {p - 1 if p > i else p for p in protected}

    if strategy == "summary" and dropped > 0:
        keep.insert(0, Msg(role="human",
                           content=f"[系统提示] 更早的 {dropped} 条对话因上下文长度已省略。"))
    return keep


# ── 演示 ────────────────────────────────────────────────────
def show(title, msgs):
    print(f"\n{title}")
    tot = sum(estimate_tokens(m) for m in msgs)
    print(f"  {len(msgs)} 条 / {tot} token")
    for m in msgs:
        c = (m.content or "")[:40].replace("\n", " ")
        tag = f" [tool_calls×{len(m.tool_calls)}]" if m.tool_calls else ""
        tid = f" (id={m.tool_call_id})" if m.tool_call_id else ""
        print(f"    {m.role:6}{tag}{tid}: {c}...")


if __name__ == "__main__":
    # 构造一段有工具调用的对话
    msgs = [
        Msg("human", "你好"),
        Msg("ai", "有什么可以帮你？"),
        Msg("human", "显微镜实验室有什么设备？"),
        Msg("ai", "", tool_calls=[{"id": "c1", "name": "list_lab_equipments"}]),
        Msg("tool", "扫描电镜一台、高速离心机两台、超净工作台…" + "长" * 800, tool_call_id="c1"),
        Msg("ai", "有扫描电镜、离心机和超净工作台。"),
        Msg("human", "离心机明天下午有空吗？"),
        Msg("ai", "", tool_calls=[{"id": "c2", "name": "create_lab_reservation"}]),
        Msg("tool", "14:00-16:00 已被占用，建议改约 16:00-18:00。" + "长" * 600, tool_call_id="c2"),
    ]

    show("【原始】", msgs)

    r1 = trim(msgs, budget=800, strategy="sliding_window")
    show("【裁剪后 · sliding_window】", r1)
    print("  → ToolMessage 是否都在：", all(
        m.role != "tool" or m.tool_call_id in {"c1", "c2"} for m in r1))

    r2 = trim(msgs, budget=800, strategy="summary")
    show("【裁剪后 · summary】", r2)

    r3 = trim(msgs, budget=800, strategy="sliding_window", protect_ai=True)
    show("【裁剪后 · 成对保护 protect_ai=True】", r3)

    # 验证：不裁剪的情况
    r4 = trim(msgs[:3], budget=800)
    print(f"\n【未超预算】{len(r4)} 条（应为 3，原样返回）")
```

**跑起来你会看到**（关键差异）：

- `sliding_window`：前面几轮被丢掉，保留两条大 ToolMessage
- `summary`：同样，但最前面多了一条 `[系统提示] 更早的 N 条对话因上下文长度已省略。`
- `protect_ai=True`：两条 AIMessage（带 tool_calls）也被保留，消息**成对**，语义完整

**动手验证建议**：把 `budget` 改成 100，看会发生什么。你会发现即使预算极小，受保护的消息也不会被删——这就是保护机制在起作用。

## 19.8 上下文工程的完整工具箱

裁剪只是手段之一。完整的上下文管理有**六个策略**，了解全貌能让你在设计时有的放矢：

| 策略 | 做法 | 适用场景 | 本项目 |
|---|---|---|---|
| **① 裁剪（Trim）** | 丢弃最老的消息 | 通用 | ✅ 已做 |
| **② 摘要（Summarize）** | LLM 压缩历史 | 超长对话 | ⚠️ 仅占位符 |
| **③ 卸载（Offload）** | 大工具结果存外部，只在上下文里放引用 ID | 工具返回巨大 | ❌ 未做 |
| **④ 隔离（Isolate）** | 子 Agent 在独立上下文里干活，只回传结论 | 多 Agent | ❌ 未做 |
| **⑤ 缓存（Cache）** | 复用 prefill（prompt caching） | 重复的前缀 | ❌ 未做 |
| **⑥ 压缩（Compress）** | 检索结果去重、截断 | 检索返回大 | ⚠️ 部分（工具里截断） |

**策略 ③ 特别值得说**，它是解决"检索返回巨大"的正解：

```python
# 不在 ToolMessage 里塞全文，而是存到临时存储，只回一个引用
def search_lab_docs(query: str) -> str:
    results = kb.search(query)
    ref_id = save_to_temp(results)      # 存到 Redis / 文件
    return f"已检索到 {len(results)} 个相关片段，引用 ID: {ref_id}。摘要：{summarize(results)}"
```

**代价**：模型看不到全文，如果需要引用原文就得再取一次（多一轮工具调用）。

**策略 ⑤（prompt caching）** 是省钱利器：System Prompt + 早期历史在多次调用中不变，很多厂商（DeepSeek、Anthropic、OpenAI）会自动缓存这部分，第二次调用起价格大幅降低。这也是"不要动态修改 System Prompt"的理由之一——**改动会打破缓存**。

本项目把 System Prompt 放在节点里注入（而不是塞进 state），客观上保证了它的稳定性，利于缓存命中。✅

## 19.10 面试问答

### Q1：长对话会撑爆上下文吗？你怎么解决的？

**答**：会，而且这是必然会发生的。我算过一笔账：一轮检索返回几千 token 的原文，它作为 ToolMessage **永久留在 messages 里**（Reducer 是追加），30 轮下来轻松超过 70K，再叠加 ReAct 的平方级增长，累计消耗能到百万 token 级。

我们的解法是在 `agent_node` 送入模型前做 token 预算裁剪：先估算全部消息的 token，超预算就从最老的开始丢，直到进预算。

有两个关键的边界处理：一是保护"AI 带 tool_calls + 其后 ToolMessage"的配对，因为拆散它们会导致 OpenAI 协议报 400；二是最新一条消息永远保留，它是本轮要回应的依据。

### Q2：token 怎么估算的？为什么不用 tiktoken？

**答**：用「字符数 / 4 向上取整」的轻量近似。不用 tiktoken 有三个理由：一是它的分词表是 OpenAI 的，我们用的 DeepSeek 规则不同，算出来不准；二是它要下载 BPE 词表、依赖重、容器化麻烦；三是不同模型对应不同 encoding，维护成本高。

不过要诚实说明这个估算的偏差：对英文准确（4 字符/token），**对中文偏低**（中文 1 字约 1-1.5 token，远密于 4 字符/token）。我们评估后认为默认预算 4000 相对保守，实际够用。**如果要改进，可以按 CJK 字符加权**，比如中文字符按 2-3 倍权重计算。

另外工具调用的 `tool_calls` 参数也会计入（`json.dumps` 后算字符），避免大段检索结果被漏算。序列化时用 `ensure_ascii=False`，否则中文会变成 `\uXXXX` 导致估算虚高 6 倍。

### Q3：裁剪时为什么必须保护 tool_calls 和 ToolMessage 的配对？

**答**：因为 OpenAI 消息协议要求：**每个 `tool_call` 必须有一条同 `tool_call_id` 的 `tool_message` 回应**。如果裁剪时删掉了 ToolMessage 但留下 AIMessage 的 tool_calls，消息序列就不合法，下次调用模型时 API 直接返回 400：

```
An assistant message with 'tool_calls' must be followed by tool messages
responding to each tool_call_id.
```

这个 bug 很隐蔽——它不在裁剪时报错，而是在**下一次 LLM 调用**时才炸，而且错误信息指向消息序列，很难联想到是裁剪导致的。

我们的做法是：扫描消息列表，找到所有带 tool_calls 的 AIMessage，把它后面紧跟着的 ToolMessage 全部加入保护集合，裁剪时跳过。同时删除元素后要同步左移保护索引（因为后面的元素索引都减了 1），这行很容易漏。

补充一点：当前实现只保护了 ToolMessage，没保护带 tool_calls 的 AIMessage 本身，理论上可能出现"孤立 ToolMessage"。这不会报 400（协议对孤立的 tool message 更宽容），但语义上有点怪。**成对保护**是明确的改进方向。

### Q4：滑动窗口和摘要两种策略怎么选？

**答**：默认用 sliding_window，直接丢最老的，简单确定、零额外成本。另一种是 summary，会在裁剪后插入一条占位消息告诉模型"前面省略了 N 条"。

**要诚实说明**：这个 summary 是占位符，不是真正的 LLM 语义摘要。真摘要需要额外一次模型调用（成本和延迟），我们评估后认为当前场景对话轮次浅（多数 3-5 轮，正常根本不触发裁剪），滑窗够用。

如果要支持几十轮的深度咨询，会引入真摘要，而且会考虑用便宜的小模型来做压缩，而不是用主模型。

### Q5：裁剪会丢失信息吗？怎么权衡？

**答**：会。滑动窗口的本质就是"用丢失早期上下文换不撑爆窗口"。

权衡上我们做了三件事：一是预算设成 4000（模型窗口的 6%），**正常情况下根本不触发裁剪**；二是只做"视图裁剪"——裁剪结果只用于这一次 LLM 调用，**state 里存的还是完整历史**，checkpointer 里也没丢，下次预算变了还能看到；三是最新消息永远保留。

不过这也带来一个副作用：state 里的消息一直在涨，checkpointer 的存储会膨胀。这是"视图裁剪 vs 存储裁剪"的区别，存储裁剪能省空间但会永久丢信息。我们目前选了前者。

### Q6：除了裁剪，上下文管理还有哪些手段？

**答**：六个策略。

一是**裁剪**（我们做了）；二是**摘要压缩**，用 LLM 把早期对话压成语义摘要；三是**卸载**，把大的工具结果存到外部（Redis/文件），上下文里只放引用 ID 和一小段摘要——这是解决"检索返回巨大"的正解；四是**隔离**，让子 Agent 在独立上下文里干活只回传结论，多 Agent 场景常用；五是**缓存**，利用厂商的 prompt caching，System Prompt 和早期历史不变时价格大幅降低；六是**压缩**，对检索结果做去重和截断。

有个细节和缓存相关：我们把 System Prompt 在节点里注入而不是塞进 state，客观上保证了它的稳定性，利于缓存命中——如果每次动态修改 System Prompt，会打破缓存。

## 19.11 速记卡

> **上下文工程 = 在有限的 context window 里，用最低成本装最有用的信息。**

**为什么会爆**：工具返回永久留在 messages（Reducer 追加）+ ReAct 平方级增长

**估算公式**：`(len(text) + cjk*2 + tool_calls_json + 3) // 4`
- 向上取整技巧：`(n+3)//4`
- `ensure_ascii=False`（否则中文变 `\uXXXX` 虚高 6 倍）
- 英文准，**中文偏低**（可 CJK 加权修正）

**裁剪三步**：快速判断 → 标记保护 → 从最老删到进预算

**★ 配对保护**：`AIMessage(tool_calls)` 后的 `ToolMessage` 不可删
- 删了 → 下次 LLM 调用报 400（不是裁剪时报错，很难排查）
- 删除后**保护索引要左移**：`{p-1 if p > i else p for p in protected}`

**两策略**：`sliding_window`（默认，丢最老）/ `summary`（占位符，非真摘要）

**视图裁剪 vs 存储裁剪**：本项目是视图裁剪，省 token 不省存储

**六策略全图**：裁剪 / 摘要 / 卸载 / 隔离 / 缓存 / 压缩

## 19.12 延伸思考

1. **把裁剪从 O(n²) 改成 O(n) 要怎么改？会影响保护索引的维护吗？**
   提示：增量维护 `total -= estimate_tokens(keep[i])`。保护索引的左移逻辑不变，因为它只和"删除位置"有关，和 total 无关。

2. **如果实现真正的 LLM 摘要，摘要应该什么时候触发？存在哪里？**
   提示：不要在每次调用时触发（太贵）。可以在"丢弃的消息数超过 N 条"时触发一次，把摘要**存进 state**（新字段 `summary`），而不是每次重算。这样是 O(1) 摊销成本。

3. **检索返回 5 个块，每块 800 token。如果只把 top-2 放进上下文，会影响答案质量吗？**
   提示：这正是 RAG 的核心权衡——召回数量和上下文预算的矛盾。可以做：重排后只取高分块（第 27 章）、块本身做截断、或者只放"命中句 + 上下文句"而不是整块。这引出一个评测问题：**裁剪到底损失了多少准确率？** 这正是可以用 RAGAS 量化的问题（第 38 章）。
