# 第 23 章 · 切块策略：文本怎么切才不丢语义

> **这一章要回答的核心问题**：为什么不整篇文档做向量？切多大合适？overlap 到底解决什么问题？递归切分的"递归"体现在哪？为什么块太小会丢失上下文，块太大又检索不准？

---

## 23.1 引子：切块是 RAG 里最容易做错的一步

先做个实验。假设你有一份《实验室安全手册》，5000 字。

### 方案 A：整篇作为一个块

```
[块1] 《实验室安全手册》全文 5000 字
```

**问题**：
- 向量化时，5000 字的语义被压成一个 512 维向量——**信息严重损失**
- 用户问"离心机怎么用"，整篇的向量相似度不高（因为大部分内容不相关）
- 检索到之后，5000 字全部进 prompt，成本爆炸

**本质问题**：**向量是"整体语义"的压缩，文档越长，压缩损失越大，匹配越不精准。**

### 方案 B：每句话一个块

```
[块1] 实验室开放时间为 8:00 至 22:00。
[块2] 节假日另行通知。
[块3] 进入实验室必须穿戴实验服。
```

**问题**：
- 块1 和块2 被切开了，用户问"节假日开放时间"，检索到块2（"节假日另行通知"），但**不知道指的是什么**
- 检索时召回很多碎片，每个都不完整
- 语义孤立：模型看到"节假日另行通知"完全无法理解

**本质问题**：**块太小 = 上下文丢失。** 单独一句话往往没有完整语义。

### 方案 C：合理大小 + overlap（正确解法）

```
[块1] ...实验室开放时间为 8:00 至 22:00，节假日另行通知。... （500 字）
[块2] ...（末尾 50 字重复）... 进入实验室必须穿戴实验服... （500 字）
```

**这就是本章要讲的**。

## 23.2 切块的三个核心参数

| 参数 | 含义 | 本项目默认 |
|---|---|---|
| **chunk_size** | 每块的目标大小（字符数） | `CHUNK_SIZE=500` |
| **chunk_overlap** | 相邻块的重叠大小 | `CHUNK_OVERLAP=50` |
| **分隔符优先级** | 优先在哪里切 | `["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]` |

### 23.2.1 chunk_size 怎么定？

这是一个**权衡**，没有标准答案，但有三个约束：

**约束 1：embedding 模型的输入上限**

大部分 embedding 模型（如 bge-small-zh）的最大输入是 512 token。超过会被截断。

中文 1 token ≈ 1-1.5 字，所以 512 token ≈ 500-700 字。**500 字符是个安全值。**

**约束 2：语义完整性**

一个块要能表达一个完整的意思。500 字大约能容纳：
- 一个完整的规定条目
- 一个 Q&A 对
- 一个小节的开头

**约束 3：检索精度**

块越大，语义越"杂"，向量匹配越不准；块越小，上下文越残。

**经验值**：
| 场景 | 建议 chunk_size |
|---|---|
| FAQ / 短问答 | 200-300 |
| 规章制度 / 说明文档 | 400-600 |
| 技术文档 / 论文 | 600-1000 |
| 对话记录 | 按轮次切，不按字数 |

本项目选 **500**，对应"规章制度/说明文档"这个场景，合理。

### 23.2.2 chunk_overlap 解决什么问题？

**overlap 的存在是为了解决"语义被切断"的问题。**

看这个例子（无 overlap）：

```
原文：...实验室开放时间为 8:00 至 22:00。节假日另行通知。进入实验室必须穿戴实验服...
                                        ↑ 在这里切
块1：...实验室开放时间为 8:00 至 22:00。节假日另行通知。
块2：进入实验室必须穿戴实验服...
```

用户问"节假日怎么安排"，检索到块1，块1 里"节假日另行通知"是完整的。✅

但如果切点在这里：

```
原文：...实验室开放时间为 8:00 至 22:00。节假日另行通知。进入实验室必须穿戴实验服...
                    ↑ 在这里切
块1：...实验室开放时间为 8:00 至 22:00。节
块2：假日另行通知。进入实验室必须穿戴实验服...
```

用户问"节假日怎么安排"——两个块都不完整！"节"和"假日另行通知"被拆开了。

**有了 overlap**：

```
块1：...实验室开放时间为 8:00 至 22:00。节假日另行通知。
块2：...（重叠 50 字）...节假日另行通知。进入实验室必须穿戴实验服...
```

无论切点在哪，关键词"节假日"至少在一个块里是完整的（大概率在两个块里都出现）。

**overlap 的代价**：
- 存储膨胀：overlap=50、size=500 → 约 10% 冗余
- 检索时可能召回重复内容（需要去重）

**经验值**：`overlap = size * 10% ~ 20%`。本项目 50/500 = 10%，偏保守但合理。

### 23.2.3 为什么是"字符数"而不是"token 数"？

```python
if len(part) < chunk_size:     # len() 是字符数
```

项目注释里说了原因（`kb_chunking.py:8`）：

> 用 `len()` 计长度，按字符切，对中文更直接，不引入 langchain-text-splitters 依赖。

**为什么不按 token？**
- 按 token 需要引入 tokenizer（依赖重，且中文不准，见第 19 章）
- 中文场景下**字符数比 token 数更直观、更稳定**
- 1 个汉字 = 1 字符，1 个英文字母 = 1 字符，切分逻辑简单

**代价**：中英文混排时，"500 字符"对应的 token 数差异很大。但对本项目的场景（中文文档为主）足够。

## 23.3 递归切分：为什么"递归"

### 23.3.1 核心思想

**优先在"粗"的分隔符处切，切不动的长片段再用"细"的分隔符递归地切。**

分隔符优先级（`kb_chunking.py:15`）：

```python
SEPARATORS = ["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]
```

从粗到细：
1. `\n\n` —— 段落（最理想）
2. `\n` —— 换行
3. `。！？；` —— 句子
4. `，` —— 分句
5. `" "` —— 空格（英文单词）
6. `""` —— **单字符**（最后一招，硬切）

**为什么这个顺序？** 因为：

- 在段落处切 → 语义最完整
- 在句子处切 → 语义较完整
- 在逗号处切 → 勉强
- 在字符处切 → **破坏语义，但至少保证不超限**

**这是一个"逐级降级"的策略**：能用粗的就用粗的，实在不行才用细的。

### 23.3.2 算法逐步拆解

`kb_chunking.py:51-88`：

```python
def _split_recursive(text, separators, chunk_size, chunk_overlap) -> list[str]:
    """递归切分：先找第一个能命中的分隔符，再处理切不动的长片段。"""
    final: list[str] = []
    separator = separators[-1]          # 默认用最后一个（""，即单字符）
    new_separators: list[str] = []

    # ① 找到第一个在文本里出现的分隔符
    for index, candidate in enumerate(separators):
        if candidate == "":
            separator = candidate
            break
        if candidate in text:
            separator = candidate
            new_separators = separators[index + 1:]     # ★ 更细的分隔符留给递归
            break

    # ② 按这个分隔符切
    splits = _split_with_regex(text, separator)

    good_splits: list[str] = []
    for part in splits:
        if len(part) < chunk_size:
            good_splits.append(part)                     # ③ 够短，攒着
        else:
            # ④ 太长：先把攒着的合并输出，再递归处理这个长片段
            if good_splits:
                final.extend(_merge_splits(good_splits, separator, chunk_size, chunk_overlap))
                good_splits = []
            if not new_separators:
                # ⑤ 没有更细的分隔符了 → 硬切（保底，不丢内容）
                final.append(part)
            else:
                final.extend(_split_recursive(part, new_separators, chunk_size, chunk_overlap))

    # ⑥ 收尾
    if good_splits:
        final.extend(_merge_splits(good_splits, separator, chunk_size, chunk_overlap))
    return [chunk for chunk in final if chunk.strip()]
```

**"递归"体现在第 ⑤ 步**：`_split_recursive(part, new_separators, ...)` —— 用**更细的分隔符**处理切不动的长片段。

### 23.3.3 一个完整的例子

输入（chunk_size=30，为了演示设得很小）：

```
实验室开放时间为 8:00 至 22:00。节假日另行通知。\n\n进入实验室必须穿戴实验服和防护眼镜，禁止穿拖鞋。
```

**第一层递归**（separators = 全部）：

1. 找分隔符：`\n\n` 在文本里 → `separator = "\n\n"`，`new_separators = ["\n", "。", ...]`
2. 按 `\n\n` 切：
   - `"实验室开放时间为 8:00 至 22:00。节假日另行通知。"` —— **长度 25 < 30** → good_splits
   - `"进入实验室必须穿戴实验服和防护眼镜，禁止穿拖鞋。"` —— **长度 27 < 30** → good_splits
3. 两个都够短，合并输出

**结果**：
```
["实验室开放时间为 8:00 至 22:00。节假日另行通知。",
 "进入实验室必须穿戴实验服和防护眼镜，禁止穿拖鞋。"]
```
✅ 完美——在两个段落处切，语义完整。

**换个例子**（一段超长无段落）：

```
为加强实验室安全管理，保障人身安全，特制定本手册。本手册适用于全校各类实验室。所有进入实验室的人员必须遵守本手册规定。
```

假设 chunk_size=30。

1. 找分隔符：`\n\n` 不在 → `\n` 不在 → `。` 在 → `separator = "。"`，`new_separators = ["！", "？", "；", "，", " ", ""]`
2. 按 `。` 切：
   - `"为加强实验室安全管理，保障人身安全，特制定本手册"` —— **22 字 < 30** → good
   - `"本手册适用于全校各类实验室"` —— 13 字 → good
   - `"所有进入实验室的人员必须遵守本手册规定"` —— 18 字 → good
3. 三个都够短 → 合并

**如果 chunk_size=15**：

- `"为加强实验室安全管理，保障人身安全，特制定本手册"` —— **22 字 > 15** → 太长！
  - 先把攒着的（空）输出
  - 递归：`_split_recursive(这句话, ["！","？","；","，"," ",""])`
    - `。` 不在了（被切掉了），找 `；` 不在，`，` **在** → `separator = "，"`
    - 按 `，` 切：`"为加强实验室安全管理"`（10）、`"保障人身安全"`（6）、`"特制定本手册"`（6）
    - 都 < 15 → 合并（带 overlap）

**这就是"递归"**：段落切不动就用句子，句子切不动就用分句，分句切不动就用空格，最后按字符硬切。

### 23.3.4 `_merge_splits`：合并 + overlap

`kb_chunking.py:26-48`：

```python
def _merge_splits(splits, separator, chunk_size, chunk_overlap) -> list[str]:
    """把切出来的小片段合并成不超过 chunk_size、且带 overlap 的块。"""
    separator_len = len(separator)
    docs: list[str] = []
    current: list[str] = []
    total = 0

    for part in splits:
        part_len = len(part)
        # 当前块已经装不下这一片时，先落盘，再按 overlap 从头部裁剪。
        if current and total + part_len + (separator_len if current else 0) > chunk_size:
            docs.append(separator.join(current))          # ① 输出当前块
            while current and total > chunk_overlap:      # ② 从头部裁剪到只剩 overlap
                removed = len(current[0]) + (separator_len if len(current) > 1 else 0)
                total -= removed
                current.pop(0)

        current.append(part)
        total += part_len + (separator_len if len(current) > 1 else 0)

    if current:
        docs.append(separator.join(current))              # ③ 收尾
    return docs
```

**核心逻辑**：**贪心装填 + 溢出时保留尾巴作为下一块的开头。**

例子（chunk_size=20, overlap=5，片段是 ["AAAA", "BBBB", "CCCC", "DDDD", "EEEE"]，分隔符是空）：

```
current=[], total=0
→ part="AAAA": 装下。current=["AAAA"], total=4
→ part="BBBB": 4+4=8 < 20，装下。current=["AAAA","BBBB"], total=8
→ part="CCCC": 8+4=12 < 20，装下。total=12
→ part="DDDD": 12+4=16 < 20，装下。total=16
→ part="EEEE": 16+4=20，**不 > 20**，装下。total=20
→ 结束：docs=["AAAABBBBCCCCDDDDEEEE"]   （刚好 20）
```

再试 chunk_size=15：

```
→ "AAAA": total=4
→ "BBBB": total=8
→ "CCCC": total=12
→ "DDDD": 12+4=16 > 15 → 溢出！
   输出 "AAAABBBBCCCC"
   裁剪：while total > 5: 弹出 "AAAA"(total=8), 弹出 "BBBB"(total=4) → 停（4 <= 5）
   current=[], total=0
   然后装 "DDDD": current=["DDDD"], total=4   ← 注意：CCCC 被裁掉了！
→ "EEEE": total=8
→ 输出 "DDDDEEEE"
```

**结果**：`["AAAABBBBCCCC", "DDDDEEEE"]` —— **CCCC 没有出现在第二块里**。

> ⚠️ **这是一个真实的行为特征**：overlap 的实现是"从头部裁到只剩 overlap 的量"，但裁剪是以**整个片段**为单位的。所以重叠是"**尽量接近** overlap，但不能保证精确等于"，而且**可能小于预期**。
>
> 这不是 bug，是贪心算法的自然结果。面试时如果问到"overlap 精确吗"，可以这样答：**我们的实现是片段粒度的贪心裁剪，实际重叠量会略小于设定值，这是可接受的实现取舍——overlap 的目的是"降低切断风险"，不需要精确到字符。**

### 23.3.5 `separator_len` 的细心之处

```python
total += part_len + (separator_len if len(current) > 1 else 0)
```

注意：只有 **`len(current) > 1`** 时才加分隔符长度。因为第 1 个片段前面不需要分隔符（`join` 只在元素之间加）。

这个细节看起来微不足道，但它保证了对切块大小的**精确控制**。少了它，每块会多算一个分隔符的长度，实际块会偏小。

## 23.4 三种切块策略对比

除了"递归字符切分"，还有两种常见策略。了解它们能让你在面试时有完整的知识地图。

### 策略 1：固定大小切分（Fixed-size）

```python
def split_fixed(text, size, overlap):
    return [text[i:i+size] for i in range(0, len(text), size - overlap)]
```

| 优点 | 缺点 |
|---|---|
| 极简、快 | **会在句子中间硬切**，语义破碎 |
| 块大小完全均匀 | 破坏了文档的自然结构 |

**适用**：快速原型、对语义完整性要求不高的场景。

### 策略 2：递归字符切分（Recursive）⭐

本项目用的。

| 优点 | 缺点 |
|---|---|
| 尊重文档结构（段落 > 句子） | 实现复杂（递归 + 合并） |
| 语义完整性好 | 块大小不均匀 |
| 零依赖可自己实现 | |

**适用**：**绝大多数场景的默认选择。**

### 策略 3：语义切分（Semantic）

```python
# 按语义相似度切：相邻句子相似度高就合并，相似度骤降就切
embeddings = model.encode(sentences)
for i in range(len(sentences) - 1):
    sim = cosine(embeddings[i], embeddings[i+1])
    if sim < threshold:
        cut_here()
```

| 优点 | 缺点 |
|---|---|
| 语义边界最准 | **慢**（每个句子都要 embedding） |
| 块大小自适应 | 需要额外的 embedding 调用（成本） |
| | threshold 难调 |

**适用**：高质量要求的场景，且能接受索引构建慢。

### 策略 4：结构化切分（Markdown/HTML 感知）

```python
from langchain.text_splitter import MarkdownHeaderTextSplitter

# 按 Markdown 标题层级切，每个块带上它的标题路径
splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[
    ("#", "h1"), ("##", "h2"), ("###", "h3"),
])
```

**这个策略对本项目其实很合适**——知识库是 Markdown 文件！

每个块带上标题路径，比如：

```
[块] 标题路径：实验室安全手册 > 第三章 设备使用 > 离心机
     内容：离心机使用前需检查转子是否平衡...
```

**好处**：检索时标题路径提供了额外的语义信息，模型也能知道这块内容属于哪个章节。

> 📝 **这是一个明确的改进方向**（简历优化点）：当前实现是按分隔符递归切，**没有利用 Markdown 的标题结构**。改成 MarkdownHeaderTextSplitter 后，检索质量和答案的上下文都会更好。

## 23.5 最小骨架：动手跑通递归切分

```python
"""
minimal_chunking.py —— 递归切分器（本项目 kb_chunking.py 的等价实现）
运行：python minimal_chunking.py  （纯 Python，无需依赖）
"""
import re

SEPARATORS = ["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]


def split_with_regex(text: str, separator: str) -> list[str]:
    """按分隔符切分，分隔符本身丢弃。"""
    if separator == "":
        return list(text)                       # 最后一招：按字符切
    parts = re.split(re.escape(separator), text)
    return [p for p in parts if p]


def merge_splits(splits, separator, chunk_size, chunk_overlap) -> list[str]:
    """贪心合并 + overlap：装不下就输出，然后从头部裁剪到只剩 overlap。"""
    sep_len = len(separator)
    docs, current, total = [], [], 0

    for part in splits:
        part_len = len(part)
        if current and total + part_len + (sep_len if current else 0) > chunk_size:
            docs.append(separator.join(current))
            # 从头部裁剪，直到剩余长度 <= overlap
            while current and total > chunk_overlap:
                removed = len(current[0]) + (sep_len if len(current) > 1 else 0)
                total -= removed
                current.pop(0)
        current.append(part)
        total += part_len + (sep_len if len(current) > 1 else 0)

    if current:
        docs.append(separator.join(current))
    return docs


def split_recursive(text, separators, chunk_size, chunk_overlap) -> list[str]:
    """递归切分：找第一个命中的分隔符；切不动的长片段用更细的分隔符递归。"""
    final = []
    separator = separators[-1]
    new_separators = []

    for index, candidate in enumerate(separators):
        if candidate == "":
            separator = candidate
            break
        if candidate in text:
            separator = candidate
            new_separators = separators[index + 1:]
            break

    splits = split_with_regex(text, separator)
    good = []
    for part in splits:
        if len(part) < chunk_size:
            good.append(part)
        else:
            if good:
                final.extend(merge_splits(good, separator, chunk_size, chunk_overlap))
                good = []
            if not new_separators:
                final.append(part)              # 无更细分隔符 → 硬切保底
            else:
                final.extend(split_recursive(part, new_separators, chunk_size, chunk_overlap))

    if good:
        final.extend(merge_splits(good, separator, chunk_size, chunk_overlap))
    return [c for c in final if c.strip()]


def split_text(text, chunk_size=500, chunk_overlap=50) -> list[str]:
    if chunk_overlap >= chunk_size:
        chunk_overlap = max(0, chunk_size // 4)     # ★ 防御：overlap 不能 >= size
    text = (text or "").strip()
    if not text:
        return []
    if len(text) <= chunk_size:
        return [text]
    return split_recursive(text, SEPARATORS, chunk_size, chunk_overlap)
```

## 23.7 切块质量的评估

怎么知道切得好不好？三个指标：

### 指标 1：块大小分布

```python
import statistics
sizes = [len(c["doc"]) for c in chunks]
print(f"平均 {statistics.mean(sizes):.0f}, 最小 {min(sizes)}, 最大 {max(sizes)}")
```

**异常信号**：
- 最大块远超 `chunk_size` → 有硬切发生，检查是不是文档没有分隔符
- 大量块远小于 `chunk_size` → 文档被过度切碎（可能是换行太多）

### 指标 2：语义完整度（人工抽样）

随机抽 10 个块，问自己：**这个块单独拿出来，人能看懂吗？**

如果答案是"看不懂，缺上下文"，说明块太小或者切点不对。

### 指标 3：端到端召回率

用评测集（第 38 章）测。**这是终极指标**。

如果某个问题总是检索不到，去看它的答案在哪个块里——很可能切块时被切断了。

## 23.8 面试问答

### Q1：为什么要切块？整篇文档做向量不行吗？

**答**：不行，两个原因。

一是**向量的语义压缩损失**。一个 512 维向量要表达整篇 5000 字文档的语义，信息损失严重；而且大部分内容和不相关，导致相似度分数低，检索不准。

二是**成本和精度**。整篇进 prompt 成本爆炸，而且会触发"迷失在中间"问题——长上下文里模型对中间部分注意力弱。

切块让每个向量聚焦一个小主题的语义，匹配更精准，进 prompt 的内容也更聚焦。

### Q2：chunk_size 怎么定？

**答**：三个约束。

一是**embedding 模型的输入上限**。bge-small-zh 是 512 token，中文 1 token 约 1-1.5 字，所以 500 字符是安全值。

二是**语义完整性**。一个块要能表达完整意思——一个规定条目、一个 Q&A 对。

三是**检索精度**。块越大语义越杂、匹配越不准；块越小上下文越残。

我们选 500，对应规章制度/说明文档这个场景。FAQ 类可以小一些（200-300），技术文档可以大一些（600-1000）。

### Q3：overlap 解决什么问题？设多大？

**答**：解决"语义被切断"的问题。

如果切点刚好落在一个关键词或一句话中间，那么两块都不完整，检索效果会很差。有了 overlap，相邻块有重叠，关键信息至少在一个块里是完整的。

经验值是 `size` 的 10%-20%，我们设 50/500 = 10%。

代价是存储冗余（约 10%）和可能召回重复内容。

补充一个实现细节：我们的 overlap 是**片段粒度**的贪心裁剪（从头部弹出整个片段直到剩余量 <= overlap），所以实际重叠量会略小于设定值。这是可接受的取舍——overlap 的目的是"降低切断风险"，不需要精确到字符。

### Q4：什么是递归切分？为什么"递归"？

**答**：核心思想是**优先在粗的分隔符处切，切不动的长片段用更细的分隔符继续切**。

分隔符优先级是：段落(`\n\n`) > 换行 > 句号 > 分号 > 逗号 > 空格 > 单字符。

"递归"体现在：按段落切完之后，如果某个片段还是超过 chunk_size，就**用下一级分隔符（句子）对它递归调用同样的逻辑**；句子还切不动就用逗号，最后按字符硬切。

这是一个"逐级降级"策略——能用粗的就用粗的（语义完整），实在不行才用细的（保底不超限）。

### Q5：递归切分和固定大小切分、语义切分怎么选？

**答**：

**固定大小**（每 N 字符一刀）最简单最快，但会在句子中间硬切，语义破碎。适合快速原型。

**递归切分**尊重文档结构，语义完整性好，块大小不均匀。这是**绝大多数场景的默认选择**，我们用的就是它。

**语义切分**按相邻句子的 embedding 相似度决定切点——相似度骤降就切。语义边界最准，但每个句子都要 embedding（慢、有成本），threshold 也难调。适合高质量要求且能接受索引慢的场景。

还有一种是**结构化切分**（Markdown 感知），按标题层级切并带上标题路径。我们的知识库是 Markdown，其实很适合这个——**这是明确的改进方向**，能让检索和答案的上下文都更好。

### Q6：块的元数据为什么要带 chunk_index？

**答**：两个用途。

一是**父上下文扩展**（第 29 章）。检索命中一个块后，我们按 `source` + `chunk_index` 找到同源文档里前后相邻的块，拼成更大的上下文再给模型——这样既能精准检索（小块），又能完整理解（大上下文）。

二是**引用溯源**。`[文件名#块号]` 这样的标记让模型能说出答案出处。

还有 `document_id` 字段，它支撑了检索范围过滤：静态知识库是 `"static"`，上传文档是真实 ID。用户在前端勾选"是否包含我上传的文档"，就是通过这个字段实现的。

### Q7：`overlap >= chunk_size` 会怎样？你们怎么防？

**答**：如果不防，`merge_splits` 里的 `while current and total > chunk_overlap` 可能把内容全裁掉，产生空块甚至死循环。

我们的防御（`split_text` 里）：

```python
if overlap >= size:
    overlap = max(0, size // 4)
```

自动降级到 `size // 4`，保证 overlap 一定小于 size。这是配置防御性处理的典型例子——**不能假设调用方一定传合理的参数**。

## 23.9 速记卡

> **切块 = 在"检索精度"（块小）和"语义完整"（块大）之间找平衡。**

**三参数**：`chunk_size=500` / `chunk_overlap=50` / `SEPARATORS`

**为什么切**：向量语义压缩损失 + 成本 + 迷失在中间

**size 三约束**：embedding 上限（512 token） / 语义完整 / 检索精度

**overlap 作用**：防止语义被切断；代价是 ~10% 存储冗余

**递归思想**：**逐级降级** —— 段落 → 句子 → 分句 → 空格 → 字符（硬切保底）

**两函数**：
```python
_split_recursive()   # 递归：找分隔符 → 切 → 长片段用更细分隔符再切
_merge_splits()      # 贪心装填 + 溢出时从头部裁到只剩 overlap
```

**★ 防御**：`overlap >= size` → 自动降为 `size // 4`

**元数据三字段**：`source`（溯源）/ `chunk_index`（父上下文）/ `document_id`（范围过滤）

**四种策略**：固定大小 / **递归（默认）** / 语义 / 结构化（Markdown）

## 23.10 延伸思考

1. **如果 chunk_size 从 500 改成 200，检索效果会变好还是变差？**
   提示：不一定。块小 → 匹配更精准，但上下文更残。要**用评测集量化**（第 38 章）——这正是"为什么要有评测"的理由之一：**没有评测，参数调优就是瞎猜**。可以设计 A/B 实验：固定其他条件，只变 chunk_size，看 Hit@K 和答案质量。

2. **父上下文扩展（第 29 章）和"直接切大块"有什么区别？**
   提示：前者是"**小块检索 + 大块生成**"——检索用精准的小块，生成时扩展成完整上下文。这是**两全其美**的方案：检索精度不受损，生成上下文不残缺。这是本项目设计得很好的一个点。

3. **overlap 导致的重复内容，会让 rerank 或生成出问题吗？**
   提示：会稍微影响——rerank 时两个高度相似的块都排前面，浪费了 Top-K 名额。可以做去重（按 `id` 或按内容相似度）。本项目没做，因为 `FINAL_CONTEXT_K=5` 且父上下文扩展会合并相邻块，重复影响有限。
