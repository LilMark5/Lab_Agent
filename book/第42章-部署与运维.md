# 第 42 章 · 部署与运维：从"我电脑上能跑"到"别人也能用"

> 到这一章为止，我们一直在"我的电脑上"讨论系统。
> 这一章把它搬出去。
>
> 部署这一章的特殊之处在于：**它的坑 90% 不在代码里，在配置和编排里**。
> 项目里有一个真实的例子：`docker-compose.yml` 起了一个 PostgreSQL 后端，
> 但**没有任何一步跑数据库迁移**——第一次启动必崩。这个 bug 在单机开发时
> 永远不会出现，因为开发用的是 SQLite + `create_all`。
>
> 我们会把这类"只在部署时暴露"的问题一个个揪出来。

---

## 42.1 为什么需要它：六个"只在部署时爆炸"的差异

开发环境和生产环境有六个结构性差异，每一个都会带来一类独特的故障。

### 差异一：数据是持久的

开发时你可以随便删库重来。生产上：

- 数据库有真实用户数据
- 向量库有真实文档
- **checkpoint 表有用户的会话历史**（第 17 章）

**后果**：你不能再用 `Base.metadata.create_all()` 了——它只在表不存在时创建，**不会修改已有表**。改了模型字段就必须写迁移。

### 差异二：配置来自环境，不是 .env 文件

开发时读 `.env`。生产上配置来自环境变量 / K8s ConfigMap / 密钥管理服务。

**后果**：**容易漏配**。某个变量没设，代码里可能静默降级（比如 `REDIS_URL` 为空 → 不缓存），也可能直接崩（`LLM_API_KEY` 为空）。

**而且这两类失败的表现完全不同**——前者是"能用但慢"，后者是"起不来"。"能用但慢"这类最危险，因为没人会发现。

### 差异三：有多个实例

开发时一个 uvicorn 进程。生产上为了高可用会跑多个副本。

**后果**：**所有"进程内状态"全部失效**。

```
开发（单实例）              生产（3 副本）
─────────────────          ──────────────────────────────
SQLite checkpointer  ✅     ❌ 3 个实例各有各的文件，会话乱窜
Chroma（嵌入式）      ✅     ❌ 3 个实例各有各的数据，检索结果不一致
内存限流计数器        ✅     ❌ 每实例限 10 次 = 实际限 30 次
内存指标              ✅     ❌ 每个实例只看到 1/3 的流量
```

**这一条是 Agent 系统部署的头号杀手**，因为它不会报错——它会**静默地给出错误结果**。

### 差异四：外部依赖会挂

LLM API 会超时、限流、维护。向量库会 OOM。Redis 会连不上。

**后果**：必须有**降级**和**重试**。项目里做了不少（第 25/27/28 章的降级日志），但部署层还要有**健康检查**和**自动重启**。

### 差异五：有反向代理和网关

开发时浏览器直接连 8000 端口。生产上中间有 nginx / 负载均衡 / CDN。

**后果**：**SSE 会被缓冲**（第 31 章）——nginx 默认开启 `proxy_buffering`，会把流式响应攒起来一次性发。用户看到的是"卡了 8 秒然后全部出现"，流式完全失效。

而且 nginx 默认的 `proxy_read_timeout` 是 **60 秒**——**超过 60 秒的 SSE 连接会被直接切断**。

### 差异六：镜像里有什么，由构建上下文决定

`Dockerfile` 里一句 `COPY . .`，会把整个目录塞进镜像——**包括 `.env`（里面有 API 密钥）和 `data/`（里面有本地数据库文件）**。

**后果**：密钥进了镜像层（推到镜像仓库就是泄露），本地数据文件覆盖了容器里的数据卷。

## 42.2 它到底是什么：部署清单八项

把上面六个差异对应成可执行的检查项：

```
┌─────────────────────────────────────────────────────────────┐
│  1. 配置外置：所有可变项走环境变量，镜像里不带 .env          │
│  2. 密钥管理：密钥不进镜像、不进 git、可轮换                │
│  3. 数据持久化：DB / 向量库 / checkpointer / 上传文件 都要卷 │
│  4. 数据库迁移：用 Alembic，不用 create_all                │
│  5. 健康检查：liveness / readiness 分离（第 40 章）          │
│  6. 无状态化：进程内状态外移到 Redis / PG                    │
│  7. 代理配置：SSE 必须关缓冲、调大超时                       │
│  8. 优雅关闭：断连接前先排空在途请求                         │
└─────────────────────────────────────────────────────────────┘
```

下面逐项展开，并结合项目现状说清楚**做对了什么、漏了什么**。

### 42.2.1 配置外置

项目的配置层是 `pydantic-settings`（`config.py:129-133`）：

```python
model_config = SettingsConfigDict(
    env_file=BASE_DIR / ".env",
    env_file_encoding="utf-8",
    extra="ignore",
)
```

**这个设计本身是对的**：环境变量优先、`.env` 兜底、`extra="ignore"` 防止无关环境变量导致启动失败（K8s 会注入一堆 `KUBERNETES_*` 变量，没有 `extra="ignore"` 会直接崩）。

**但部署时的坑在镜像构建**，见 42.5 坑 1。

### 42.2.2 密钥管理

项目里有两个密钥：

| 密钥 | 默认值 | 风险 |
|---|---|---|
| `JWT_SECRET_KEY` | `dev-only-secret-key-change-me-in-production` | **默认值泄露 = 任何人可伪造 token** |
| `LLM_API_KEY` | `None` | 泄露 = 账单被盗刷 |

`config.py:55` 的默认值带着 `dev-only` 和 `change-me-in-production` 两个警示词——**这个命名习惯很好**，但只是"提醒"，不是"强制"。

**生产上应该有启动校验**：

```python
if not settings.DEBUG and settings.JWT_SECRET_KEY.startswith("dev-only"):
    raise RuntimeError("生产环境必须设置 JWT_SECRET_KEY")
```

**把"容易忘的事"变成"启动即失败"，是运维工程的核心思路。** 靠文档提醒是没用的，靠代码强制才有用。

### 42.2.3 数据持久化

项目有**四处**需要持久化的状态，缺一个都会出问题：

| 状态 | 默认位置 | 生产要求 |
|---|---|---|
| 业务数据 | SQLite `lab_agent.db` / PG | 必须卷 |
| 向量库 | Chroma `./data/chroma` / Milvus Lite / pgvector | 必须卷（或外部服务） |
| **会话 checkpoint** | SQLite `data/checkpoints.db` / PG | **必须卷或外置**（第 17 章） |
| 上传文件 | `backend/uploads/` | 必须卷 |

`docker-compose.yml:48` 挂载了 `./backend/data:/app/data`——覆盖了向量库和 checkpointer，但**上传目录没挂**。容器重建后用户上传的文档全没了（数据库里还有记录，指向不存在的文件）。

### 42.2.4 数据库迁移：Alembic

项目有两个迁移（`backend/alembic/versions/`）：

```
0001_initial_schema.py      初始 5 张表
0002_add_kb_documents.py    加知识库文档表
```

启动逻辑（`main.py:32-34`）：

```python
# 1. 表结构：Postgres 走 Alembic（alembic upgrade head），SQLite 零配置仍用 create_all。
if not settings.DATABASE_URL:
    Base.metadata.create_all(bind=engine)
seed_if_empty()
```

**注意这个分支**：

- **SQLite（开发）**：`create_all` 自动建表，零配置
- **PostgreSQL（生产）**：注释说"走 Alembic"，但**代码里没有任何一行调用 Alembic**

而这个项目的 `docker-compose.yml:32` 恰恰配了 `DATABASE_URL` 指向 PostgreSQL。

**结果：容器启动时不会建表，第一个数据库请求就会报 "relation does not exist"。**

这是一个**只在部署路径上出现的 bug**，单机开发永远碰不到。修复见 42.5 坑 2。

### 42.2.5 无状态化：多实例下的三个陷阱

这是 Agent 项目部署最容易翻车的地方。

**陷阱一：SQLite checkpointer**

第 17 章讲过，项目支持 SQLite 和 PostgreSQL 两种 checkpointer（`agent_service.py:128-134`）：

```python
logger.info("checkpointer 已就绪：PostgreSQL")
...
logger.info("checkpointer 已就绪：SQLite（%s）", path)
```

**多实例下 SQLite 方案必崩**：3 个副本各有各的 `checkpoints.db` 文件，用户的请求被负载均衡随机分发，**每次可能落到没有他会话历史的实例上**。

表现是："AI 突然不记得我刚才说的话了"——而且**时好时坏**（取决于落到哪个副本）。

**这是最难排查的一类故障**：不是必现、不是报错、只是"偶尔失忆"。

**陷阱二：Chroma 嵌入式向量库**

`VECTOR_BACKEND` 默认是 `auto`（`config.py:84`），会选 Chroma。Chroma 在项目里是**嵌入式**（进程内），数据写在本地文件。

多实例下：文档在实例 A 上入库，实例 B 查不到。**表现是"我上传的文档有时候能搜到有时候搜不到"**。

**陷阱三：内存限流**

`dependencies/rate_limit.py` 用 Redis 做限流，但**Redis 不可用时降级到内存**。多实例下每个实例各限各的——你配了"每分钟 10 次"，实际是 30 次。

**第 36 章讲过这是"三级降级"的设计**，但部署多实例时必须知道：**降级后的限流形同虚设**。

### 42.2.6 代理配置：SSE 的两个必须项

项目的 `frontend/nginx.conf` **做对了一半**：

```nginx
location /api/ {
    proxy_pass http://backend:8000/api/;
    proxy_http_version 1.1;            # ✅ SSE 需要 HTTP/1.1
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    # SSE 流式输出不要缓冲。
    proxy_buffering off;               # ✅ 关键
    proxy_cache off;                   # ✅ 关键
    proxy_set_header Connection '';    # ✅ 让 nginx 不改写 Connection 头
}
```

**这四个配置是对的**，缺任何一个流式都会失效。

**但漏了一个**：

```nginx
proxy_read_timeout 3600s;              # ❌ 缺失！默认 60s
```

**后果**：Agent 一次回答如果需要 90 秒（多轮工具调用 + 慢 LLM），**第 60 秒时 nginx 会直接断开连接**，前端看到流突然中断。

**这是 SSE 部署最经典的坑**，因为它只在"慢请求"上出现——快请求一切正常，你测十次可能都测不出来。

### 42.2.7 优雅关闭

`main.py:29-50` 的 `lifespan` 做了关闭清理：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    ...
    task = asyncio.create_task(reservation_service.run_expire_scan())
    yield
    task.cancel()
    await agent_service.close_checkpointer()
```

**做对的两点**：

1. **后台任务被 cancel**——否则容器关闭时会有僵尸协程
2. **checkpointer 连接被关闭**——否则 PG 连接池泄漏

**这是 Agent 项目特有的清理项**：checkpointer 持有数据库连接池（第 17 章的全局单例），不关的话每次重启泄漏一批连接，几次之后 PG 的 `max_connections` 就被打满。

## 42.3 最小可运行骨架：启动自检

部署类问题的最好解法是**在启动前检查出来**，而不是等用户报错。下面这个 `preflight.py` 是一个零依赖（只用标准库 + 可选 psycopg2）的启动自检脚本，可以放在容器 `CMD` 之前跑。

```python
"""部署前自检：把"启动后才炸"的问题提前到"启动前就报"。

八项检查：
  1. 必填环境变量是否齐全
  2. 密钥是否还是开发默认值
  3. 数据库是否可连
  4. 迁移是否落后（对比 alembic head 与库内版本）
  5. 向量库是否可用 + 是否有数据
  6. LLM API 是否可连（可选，超时就跳过）
  7. 上传目录是否可写
  8. 各依赖版本号留档

用法（容器 entrypoint）：
    python preflight.py && uvicorn app.main:app --host 0.0.0.0 --port 8000

退出码：0 通过；1 阻断性失败（不许启动）；2 警告（可启动但要关注）
"""
from __future__ import annotations

import os
import sys
from dataclasses import dataclass, field

PASS = "  \033[32m✓\033[0m"
FAIL = "  \033[31m✗\033[0m"
WARN = "  \033[33m!\033[0m"


@dataclass
class Report:
    blocking: list[str] = field(default_factory=list)
    warnings: list[str] = field(default_factory=list)

    def fail(self, msg: str) -> None:
        self.blocking.append(msg)
        print(f"{FAIL} {msg}")

    def warn(self, msg: str) -> None:
        self.warnings.append(msg)
        print(f"{WARN} {msg}")

    def ok(self, msg: str) -> None:
        print(f"{PASS} {msg}")


def check_env(report: Report) -> None:
    print("\n[1] 环境变量")
    # 「必填」和「可选」分开：可选缺失只告警（因为代码有降级路径）
    required = ["LLM_API_KEY"]
    optional = ["DATABASE_URL", "REDIS_URL", "CHECKPOINT_DATABASE_URL"]

    for key in required:
        if os.getenv(key):
            report.ok(f"{key} 已设置")
        else:
            report.fail(f"{key} 未设置 —— Agent 无法工作")

    for key in optional:
        if os.getenv(key):
            report.ok(f"{key} 已设置")
        else:
            report.warn(f"{key} 未设置 —— 将走降级路径")


def check_secrets(report: Report) -> None:
    print("\n[2] 密钥")
    jwt = os.getenv("JWT_SECRET_KEY", "")
    env = os.getenv("APP_ENV", "dev")

    # ★ 把"容易忘的事"变成"启动即失败"
    if env == "prod":
        if not jwt:
            report.fail("生产环境未设置 JWT_SECRET_KEY")
        elif jwt.startswith("dev-only") or jwt == "change-me-in-production":
            report.fail("生产环境仍在使用默认 JWT_SECRET_KEY —— 任何人可伪造 token")
        elif len(jwt) < 32:
            report.warn(f"JWT_SECRET_KEY 长度 {len(jwt)}，建议 ≥32 字符")
        else:
            report.ok("JWT_SECRET_KEY 已自定义")
    else:
        report.warn(f"APP_ENV={env}（非生产），跳过密钥强度检查")

    llm_key = os.getenv("LLM_API_KEY", "")
    if llm_key and len(llm_key) < 20:
        report.warn("LLM_API_KEY 长度异常，可能是占位符")


def check_database(report: Report) -> None:
    print("\n[3] 数据库")
    url = os.getenv("DATABASE_URL")
    if not url:
        report.warn("DATABASE_URL 未设置 → 使用 SQLite（不建议生产使用）")
        return

    try:
        from sqlalchemy import create_engine, text
    except ImportError:
        report.warn("未安装 sqlalchemy，跳过数据库检查")
        return

    try:
        engine = create_engine(url, pool_pre_ping=True)
        with engine.connect() as conn:
            version = conn.execute(text("SELECT version()")).scalar()
        report.ok(f"数据库可连：{str(version)[:40]}")
    except Exception as exc:
        report.fail(f"数据库连不上：{type(exc).__name__}: {exc}")
        return

    # ★ 生产必查：多实例下 SQLite checkpointer 会静默丢会话
    if not os.getenv("CHECKPOINT_DATABASE_URL"):
        if "postgresql" in url:
            report.warn(
                "业务库是 PG 但 CHECKPOINT_DATABASE_URL 未设置 → "
                "checkpointer 走 SQLite，多实例下会话会乱窜"
            )
        else:
            report.warn("checkpointer 走 SQLite，多实例部署会丢会话")


def check_migrations(report: Report) -> None:
    print("\n[4] 数据库迁移")
    url = os.getenv("DATABASE_URL")
    if not url:
        report.ok("SQLite 模式，启动时 create_all，无需迁移")
        return

    # ★ 关键检查：库内版本 vs 代码里的 head
    # 这是 docker-compose 场景下最容易漏的一步
    try:
        from alembic.config import Config
        from alembic.runtime.migration import MigrationContext
        from alembic.script import ScriptDirectory
        from sqlalchemy import create_engine
    except ImportError:
        report.warn("未安装 alembic，跳过迁移检查")
        return

    try:
        cfg = Config("alembic.ini")
        script = ScriptDirectory.from_config(cfg)
        head = script.get_current_head()

        engine = create_engine(url)
        with engine.connect() as conn:
            ctx = MigrationContext.configure(conn)
            current = ctx.get_current_heads()

        if not current:
            report.fail(
                f"数据库没有任何迁移记录（head={head}）→ "
                "请执行 alembic upgrade head"
            )
        elif head not in current:
            report.fail(
                f"迁移落后：库内={current} 代码={head} → 请执行 alembic upgrade head"
            )
        else:
            report.ok(f"迁移已是最新（{head}）")
    except Exception as exc:
        report.warn(f"迁移检查失败（可能是库为空）：{type(exc).__name__}: {exc}")


def check_vector_store(report: Report) -> None:
    print("\n[5] 向量库")
    backend = os.getenv("VECTOR_BACKEND", "auto")
    report.ok(f"VECTOR_BACKEND={backend}")

    if backend in ("auto", "chroma"):
        report.warn(
            "Chroma/Milvus-Lite 是进程内嵌式 → 多实例部署时各副本数据不同步"
            "（生产建议 pgvector）"
        )
    if backend == "milvus" and sys.platform == "win32":
        report.fail("Milvus Lite 不支持 Windows")


def check_uploads(report: Report) -> None:
    print("\n[6] 上传目录")
    path = os.getenv("UPLOAD_DIR", "./uploads")
    try:
        os.makedirs(path, exist_ok=True)
        probe = os.path.join(path, ".preflight")
        with open(probe, "w") as f:
            f.write("ok")
        os.remove(probe)
        report.ok(f"{path} 可写")
    except Exception as exc:
        report.fail(f"{path} 不可写：{exc}")

    # ★ 上传目录没挂卷 = 容器重建后文件全丢，但 DB 里还有记录
    if not os.path.exists(os.path.join(path, "..", "data")):
        report.warn("未检测到 data/ 目录 —— 确认向量库与 checkpointer 已挂卷")


def check_llm(report: Report, timeout: float = 5.0) -> None:
    print("\n[7] LLM API")
    key = os.getenv("LLM_API_KEY")
    base = os.getenv("LLM_BASE_URL", "https://api.openai.com/v1")
    if not key:
        report.fail("LLM_API_KEY 未设置")
        return

    # 只做一次轻量调用（列模型），失败不阻断——LLM 挂了服务也应该能起来
    try:
        import urllib.request
        req = urllib.request.Request(
            f"{base.rstrip('/')}/models",
            headers={"Authorization": f"Bearer {key}"},
        )
        with urllib.request.urlopen(req, timeout=timeout) as resp:
            report.ok(f"LLM API 可连（HTTP {resp.status}）")
    except Exception as exc:
        report.warn(f"LLM API 不可连（不阻断启动）：{type(exc).__name__}: {exc}")


def main() -> int:
    print("=" * 72)
    print("部署前自检 preflight")
    print("=" * 72)

    report = Report()
    check_env(report)
    check_secrets(report)
    check_database(report)
    check_migrations(report)
    check_vector_store(report)
    check_uploads(report)
    check_llm(report)

    print()
    print("=" * 72)
    if report.blocking:
        print(f"阻断性问题 {len(report.blocking)} 项 —— 不允许启动")
        for msg in report.blocking:
            print(f"  ✗ {msg}")
        return 1
    print("自检通过")
    if report.warnings:
        print(f"（{len(report.warnings)} 项警告，见上方）")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

```
  ! CHECKPOINT_DATABASE_URL 未设置 —— 将走降级路径

[2] 密钥
  ! APP_ENV=dev（非生产），跳过密钥强度检查

[3] 数据库
  ! DATABASE_URL 未设置 → 使用 SQLite（不建议生产使用）

[4] 数据库迁移
  ✓ SQLite 模式，启动时 create_all，无需迁移

[5] 向量库
  ✓ VECTOR_BACKEND=auto
  ! Chroma/Milvus-Lite 是进程内嵌式 → 多实例部署时各副本数据不同步

[6] 上传目录
  ✓ ./uploads 可写

[7] LLM API
  ✗ LLM_API_KEY 未设置

========================================================================
阻断性问题 1 项 —— 不允许启动
  ✗ LLM_API_KEY 未设置
```

**这个脚本的价值**：把"部署文档里写了但没人看"的东西，变成"不通过就不许启动"。

**注意第 7 项的设计**：LLM 连不上**只告警不阻断**——因为 LLM 挂了服务也应该能起来（其他接口还能用），这是**分级阻断**的思想：**只有"起来也等于废了"的问题才阻断。**

## 42.4 项目代码定位

### 42.4.1 Dockerfile：做对了什么

`backend/Dockerfile`：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1
# 先装依赖层，利用 Docker 缓存；源码变化不会重复装依赖。
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**三个做对的地方**：

1. **`slim` 基础镜像**：python:3.12 完整版 1GB+，slim 版约 150MB。Agent 项目依赖重（torch 系），选 slim 很有必要。
2. **依赖层与源码层分离**：先 `COPY requirements.txt` 再 `pip install`，**改代码不会重新装依赖**。这是 Docker 构建缓存的标准用法，能把二次构建从 5 分钟降到 10 秒。
3. **`PYTHONUNBUFFERED=1`**：让 print / logging 直接输出到 stdout，**不加这个 Docker 日志会延迟甚至丢失**（Python 默认块缓冲）。这一条和第 40 章的日志直接相关。

前端 `frontend/Dockerfile` 用了**多阶段构建**：

```dockerfile
FROM node:20-alpine AS build
...
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

**多阶段构建的价值**：最终镜像里**没有 node_modules、没有源码**，只有构建产物。镜像从 ~500MB 降到 ~25MB。

### 42.4.2 docker-compose.yml：做对了什么

```yaml
postgres:
    image: pgvector/pgvector:pg16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10

backend:
    depends_on:
      postgres:
        condition: service_healthy      # ★ 关键
```

**`condition: service_healthy` 是这一章最值得学的一行。**

普通的 `depends_on: [postgres]` 只保证"容器启动了"，**不保证数据库能接受连接**。PG 容器启动后还要初始化数据目录，这段时间内连接会被拒绝——后端会在启动时连 DB 失败然后退出。

加了 `condition: service_healthy`，Docker 会等 healthcheck 通过（最多 10 × 5s = 50s）才启动 backend。**这一行消除了"偶尔启动失败"这一类玄学故障。**

### 42.4.3 docker-compose.yml：漏了什么

**① 没有跑数据库迁移**（最严重）

`backend` 服务的 `CMD` 就是 uvicorn，中间没有任何 `alembic upgrade head`。而 `DATABASE_URL` 指向 PostgreSQL，`main.py` 里 PG 分支又不做 `create_all`。

**第一次启动必崩。** 修复见 42.5 坑 2。

**② MCP 服务没定义但开关是开的**

`docker-compose.yml` 里只有 postgres / redis / backend / frontend 四个服务，但 `.env.example` 里：

```bash
MCP_ENABLED=true
MCP_URL=http://127.0.0.1:8100/mcp
```

**容器里 MCP Server 根本没起。** 结果是每次请求都尝试连 `127.0.0.1:8100`（那是容器自己），失败后降级到本地工具（第 30 章的降级逻辑）。

**这个降级是"正确"的——但它的代价是每次启动/首次加载工具时的一次连接失败和日志噪音。** 而且开发者会困惑"为什么 MCP 工具没生效"。

**③ 密钥硬编码**

```yaml
POSTGRES_PASSWORD: 123456
JWT_SECRET_KEY: change-me-in-production
```

这两个都写在了 compose 文件里（会进 git）。**开发用没问题，但必须明确标注"仅限本地"**，或者改用 `${JWT_SECRET_KEY:?必须设置}` 这种语法——**变量未设置时直接报错**，比写个默认值安全。

**④ 上传目录没挂卷**

只挂了 `./backend/data:/app/data`，`uploads/` 没挂。容器重建后文件丢失。

**⑤ 没有 `.dockerignore`**

`COPY . .` 会把 `.env`、`lab_agent.db`、`data/`、`__pycache__`、`tests/`、`book/`（如果放在 backend 下）全打进镜像。**密钥泄露 + 镜像臃肿**。

### 42.4.4 MCP Server 独立进程

第 30 章讲过，MCP Server 是一个**独立进程**（`mcp_server.py`，103 行），监听 8100 端口。

**部署含义**：它不是 backend 的子进程，必须**单独启动**：

```bash
python -m app.mcp_server        # 起 MCP Server（8100）
uvicorn app.main:app            # 起主服务（8000）
```

**这意味着 compose 里要么加一个 `mcp` 服务，要么把 `MCP_ENABLED` 设为 false。** 当前配置是两个都没做——这是本章发现的第二个真实部署缺陷。

### 42.4.5 lifespan 与优雅关闭

`main.py:29-50` 完整看一遍：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 1. 表结构
    if not settings.DATABASE_URL:
        Base.metadata.create_all(bind=engine)
    seed_if_empty()

    # 2. 预热向量库，把模型加载成本放在启动阶段。
    try:
        await asyncio.wait_for(asyncio.to_thread(kb_service.warmup), timeout=30)
    except asyncio.TimeoutError:
        logger.warning("向量库预热超时，服务先启动，首个 RAG 请求会稍慢")
    except Exception:
        logger.exception("向量库预热失败，服务继续启动")

    # 3. 启动后台扫描：每 60 秒把过期待审核预约自动取消。
    task = asyncio.create_task(reservation_service.run_expire_scan())
    yield
    task.cancel()
    await agent_service.close_checkpointer()
```

**这个 lifespan 写得不错**，三个启动步骤都有降级：

- 建表：SQLite 自动，PG 走迁移（**虽然没接上**）
- 预热：**带超时 + 异常捕获，失败不阻断**
- 后台任务：**关闭时 cancel**

**关闭时 `await agent_service.close_checkpointer()` 这一行是 Agent 项目特有的**，普通 Web 服务没有这个需求。它对应第 17 章的全局单例 checkpointer——持有 PG 连接池，必须显式关闭。

## 42.5 踩过的坑

### ⚠️ 坑 1：没有 .dockerignore，密钥和本地数据进了镜像

**现象**：`docker build` 出来的镜像里能找到 `.env` 文件，里面有 `LLM_API_KEY`。

**原因**：`COPY . .` 复制了整个构建上下文。

**后果**：镜像推到仓库 = 密钥泄露；镜像里的 `lab_agent.db` 会覆盖挂载卷的数据。

**修复**：加 `.dockerignore`：

```
.env
.env.*
!.env.example
*.db
data/
uploads/
__pycache__/
*.pyc
.pytest_cache/
tests/
.git/
book/
```

**这条应该写进所有 Python 项目的肌肉记忆：`COPY . .` 之前必须有 `.dockerignore`。**

### ⚠️ 坑 2：docker-compose 起了 PG 但没跑迁移

**现象**：`docker-compose up` 后，第一次访问报 `relation "users" does not exist`。

**原因**：

- `docker-compose.yml:32` 设了 `DATABASE_URL` 指向 PostgreSQL
- `main.py:33` 的逻辑是 `if not settings.DATABASE_URL: create_all()`——**有 DATABASE_URL 时不建表**
- 注释说"Postgres 走 Alembic"，但 compose 里没有任何一步执行 `alembic upgrade head`

**这是本章发现的最严重部署缺陷**：这条路径**从来没被跑通过**（开发一直用 SQLite）。

**修复**（三选一）：

```yaml
# 方案 A：单独的迁移服务（推荐，迁移失败不影响应用启动）
  migrator:
    build: ./backend
    command: alembic upgrade head
    environment:
      DATABASE_URL: postgresql+psycopg2://postgres:123456@postgres:5432/lab_agent
    depends_on:
      postgres:
        condition: service_healthy
  backend:
    depends_on:
      migrator:
        condition: service_completed_successfully    # ★ 迁移成功才起应用

# 方案 B：entrypoint 脚本里跑
#   docker-entrypoint.sh:
#     alembic upgrade head && exec uvicorn app.main:app ...

# 方案 C：应用启动时跑（不推荐，多副本会并发迁移冲突）
```

**推荐方案 A**：迁移是**一次性任务**，不是应用的一部分。用 `service_completed_successfully` 保证顺序，迁移失败时应用根本不会启动（而不是启动后一半功能不能用）。

### ⚠️ 坑 3：多实例下 SQLite checkpointer 静默丢会话

**现象**：多副本部署后，用户反馈"AI 偶尔不记得刚才说过的话"。**不是必现，不报错**。

**原因**：`CHECKPOINT_DATABASE_URL` 未配置 → 回退 SQLite → 每个副本一份文件 → 请求随机分发到不同副本。

**这是最难排查的一类故障**：日志全绿、指标正常、只有用户能感觉到。

**修复**：多实例必须设 `CHECKPOINT_DATABASE_URL` 指向 PG（第 17 章讲过这是生产推荐）。

**通用教训**：**"能降级"不等于"降级后还正确"。** 设计降级时要问一句："降级状态下多实例还正确吗？"

### ⚠️ 坑 4：nginx 的 proxy_read_timeout 会切断长 SSE

**现象**：短回答正常，长回答（多轮工具调用）进行到 60 秒左右突然断流。

**原因**：nginx 默认 `proxy_read_timeout 60s`——两次读之间的空闲超过 60 秒就断。SSE 在模型思考期间是没有数据流的。

**修复**：

```nginx
location /api/ {
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;      # ★ 必须加
    proxy_send_timeout 3600s;
    chunked_transfer_encoding off;  # 某些场景需要
}
```

**这个坑的经典之处**：你测十次短问题都正常，上线后用户问了个复杂问题才发现。**SSE 的问题总在"最慢的那 5% 请求"上暴露。**

### ⚠️ 坑 5：MCP Server 是独立进程，忘了起

见 42.4.4。compose 里没定义 `mcp` 服务，但 `MCP_ENABLED=true`。

**这类坑的本质**：**配置开关和实际编排不一致**。开关说"开"，编排没提供依赖。

**通用检查法**：把所有"依赖外部服务"的开关列出来，逐个确认编排里有对应的服务。

### ⚠️ 坑 6：健康检查写了但没接探针

`docker-compose.yml` 里 postgres 和 redis 有 healthcheck，但 **backend 没有**。

后果：Docker/K8s 不知道 backend 是否就绪，容器启动就开始导流，而此时 embedding 模型还没加载完（预热要几秒到几十秒）——**前几个请求会超时**。

**修复**：第 40 章讲的 `/healthz` + `/readyz` 两个接口，然后：

```yaml
backend:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/readyz"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 60s        # ★ 模型加载慢，给足启动宽限期
```

`start_period` 是容易被忽略的一项——**没有它，慢启动的服务会在就绪前被判定失败然后反复重启。**

### ⚠️ 坑 7：Python 缓冲导致容器日志丢失

不加 `PYTHONUNBUFFERED=1` 时，Python 的 stdout 是块缓冲（4KB）。容器被 kill 时缓冲区里的日志**直接丢失**——而你可能正需要那些日志排查崩溃原因。

项目 Dockerfile 里有这一行（`Dockerfile:6`），做对了。

## 42.6 面试问答

### Q1：开发和生产环境部署有哪些关键差异？

**答**：六个。

**数据持久**——不能删库重来，必须写迁移；**配置来源**——从 .env 变成环境变量/密钥服务，容易漏配；**多实例**——进程内状态全部失效（SQLite checkpointer、嵌入式向量库、内存限流都会出问题）；**外部依赖会挂**——LLM API 有超时和限流；**有反向代理**——nginx 默认缓冲会破坏 SSE；**镜像内容**——`COPY . .` 会把密钥和本地数据打进去。

其中**多实例**这条最危险，因为它不报错，只是静默给出错误结果。

### Q2：多实例部署时，Agent 系统有哪些特有的坑？

**答**：三个。

**一是 checkpointer**——如果用 SQLite，每个副本一份文件，用户的请求被随机分发，可能落到没有他会话历史的实例上，表现为"AI 偶尔失忆"，不报错、不是必现。

**二是嵌入式向量库**——Chroma/Milvus-Lite 是进程内嵌的，文档在实例 A 入库，实例 B 搜不到。

**三是内存限流**——Redis 不可用降级到内存后，3 个副本各限各的，配的 10 次/分钟实际是 30 次。

**共同点是：这些都"能降级"，但降级后多实例下不正确。** 所以设计降级时必须问一句"多实例还正确吗"。

### Q3：为什么不能在生产用 `create_all`？

**答**：因为它**只在表不存在时创建，不会修改已有表**。改了模型字段（加列、改类型）它完全无感，导致代码和库结构不一致，直到某个查询报 "column does not exist" 才暴露。

正确做法是用 Alembic 写版本化迁移，启动时检查迁移是否落后。

我们项目有个相关的真实问题：`docker-compose.yml` 起了 PostgreSQL，但 `main.py` 里 PG 分支不做 `create_all`，而 compose 里又没有任何一步跑 `alembic upgrade head`——**第一次启动必崩**。这条路径因为本地一直用 SQLite，从没被跑通过。

### Q4：`depends_on` 加 `condition: service_healthy` 有什么用？

**答**：普通 `depends_on` 只保证"容器进程启动了"，不保证服务能接受连接。

比如 PostgreSQL 容器启动后还要初始化数据目录，这段时间内连接会被拒绝。如果后端这时启动就会连不上 DB 然后退出——表现为"偶尔启动失败"，重启一次又好了，非常难排查。

`condition: service_healthy` 让 Docker 等 healthcheck 通过（我们配了 `pg_isready`，最多等 50 秒）才启动依赖方。这一行能消除一整类玄学故障。

### Q5：SSE 在反向代理后面要注意什么？

**答**：四个配置，缺一个流式就失效或中断：

```nginx
proxy_http_version 1.1;      # SSE 需要 HTTP/1.1
proxy_buffering off;         # 否则响应被攒起来一次性发
proxy_cache off;
proxy_read_timeout 3600s;    # ★ 最容易被漏，默认 60s 会切断长流
```

最后一条最阴险：短请求一切正常，只有"慢请求"才暴露。而 Agent 多轮工具调用很容易超过 60 秒。

另外后端要设 `X-Accel-Buffering: no` 响应头（第 31 章），因为有些代理只看这个头。

### Q6：健康检查怎么做才对？liveness 和 readiness 的区别？

**答**：两个接口，失败处理动作不同。

**liveness**（`/healthz`）只查"进程活着吗"，**不查任何外部依赖**。失败 → 重启容器。用于检测死锁这类"进程在但废了"的情况。

**readiness**（`/readyz`）查所有关键依赖（DB、向量库）。失败 → 从负载均衡摘除，但**不重启**——因为进程是好的，重启没用。

**合成一个的后果**：DB 变慢时 readiness 失败，如果按 liveness 处理就会不停重启健康的进程，把偶发抖动放大成全面故障。

另外要配 `start_period`，给慢启动的服务（要加载 embedding 模型）足够的宽限期，否则它会在就绪前被判失败然后反复重启。

### Q7：Dockerfile 里为什么要先 COPY requirements.txt 再 COPY 源码？

**答**：利用构建缓存。Docker 是按层缓存的，如果先 `COPY . .` 再 `pip install`，**改一行代码就会让依赖层失效**，每次构建都重装依赖（Agent 项目的依赖很重，torch 系要几分钟）。

分开之后，只要 `requirements.txt` 没变，依赖层就命中缓存，二次构建从 5 分钟降到 10 秒。

另外要配 `.dockerignore`，否则 `COPY . .` 会把 `.env`（含密钥）、本地数据库文件、`__pycache__` 全打进镜像——既是安全问题也让镜像变大。

### Q8：容器的优雅关闭要注意什么？Agent 项目有什么特殊的？

**答**：普通 Web 服务要 cancel 后台任务、关闭连接池。

Agent 项目**多一个 checkpointer**：它是全局单例（第 17 章），持有 PostgreSQL 连接池。不显式关闭的话，每次容器重启泄漏一批连接，几次之后 PG 的 `max_connections` 就被打满，表现为"数据库突然连不上"。

我们项目在 `lifespan` 的 yield 之后做了 `await agent_service.close_checkpointer()`，这是对的。

另外要设 `PYTHONUNBUFFERED=1`，否则容器被 kill 时缓冲区里的日志直接丢失——而你可能正需要那些日志排查崩溃。

### Q9：密钥管理在部署层要做什么？

**答**：三件事。

**一是不进镜像**——靠 `.dockerignore` 排除 `.env`；**二是不进 git**——`.env` 必须 gitignore，只提交 `.env.example`；**三是启动校验**——把"用了默认密钥"变成"启动即失败"：

```python
if env == "prod" and settings.JWT_SECRET_KEY.startswith("dev-only"):
    raise RuntimeError("生产环境必须设置 JWT_SECRET_KEY")
```

**靠文档提醒没用，靠代码强制才有用。** 我们项目现在的默认值叫 `dev-only-secret-key-change-me-in-production`，命名上有警示但没有强制校验，这是可以补的一项。

### Q10：如果让你给这个项目加 CI/CD，第一步做什么？

**答**：第一步不是流水线，是**启动自检脚本**（本章的 `preflight.py`）。

因为它能立刻抓出"只在部署路径出现"的问题——比如迁移落后、密钥是默认值、checkpointer 走 SQLite 但业务库是 PG。**这些问题在 CI 里跑 `pytest` 完全抓不到**，因为测试用的是 SQLite 内存库。

有了自检之后，CI 的顺序是：

```
lint → 单元测试 → preflight（对测试环境）→ 构建镜像
     → 部署到预发 → preflight（对预发）→ 冒烟测试 → 生产
```

**评测（第 37-39 章）放哪一步？** 放"部署到预发之后"，因为评测要调真实 LLM，成本高、有随机性，不适合每个 PR 都跑，但适合发布前跑一次看有没有退化。

## 42.7 速记卡

**六个环境差异**：数据持久 / 配置外置 / **多实例** / 依赖会挂 / 有代理 / 镜像内容

**★ 多实例三陷阱**（都不报错，只是静默错）
```
SQLite checkpointer  → AI 偶尔失忆
嵌入式向量库         → 文档有时搜得到有时搜不到
内存限流             → 配 10 次/分实际 30 次
```

**部署清单八项**
```
1. 配置外置（镜像不带 .env）
2. 密钥管理（不进镜像/git，启动校验）
3. 数据持久化（DB/向量库/checkpointer/uploads 四处卷）
4. 数据库迁移（alembic，不用 create_all）
5. 健康检查（liveness/readiness 分离 + start_period）
6. 无状态化（进程内状态外移）
7. 代理配置（SSE 关缓冲 + 调大超时）
8. 优雅关闭（cancel 任务 + close checkpointer）
```

**Dockerfile 三个对的地方**
- `slim` 基础镜像（150MB vs 1GB）
- 依赖层/源码层分离（改代码不重装依赖）
- `PYTHONUNBUFFERED=1`（否则 kill 时日志丢失）

**compose 一个对的地方**
- `depends_on: condition: service_healthy`（消除玄学启动失败）

**★ SSE 四配置**：`proxy_http_version 1.1` / `proxy_buffering off` / `proxy_cache off` / **`proxy_read_timeout 3600s`**（最易漏）

**项目已发现缺陷（本章）**
- ⚠️ **compose 起 PG 但没跑 `alembic upgrade head`** ← 最严重，第一次启动必崩
- ⚠️ 无 `.dockerignore` → `.env` 进镜像
- ⚠️ MCP 服务未定义但 `MCP_ENABLED=true`
- ⚠️ `uploads/` 未挂卷
- ⚠️ backend 无 healthcheck
- ⚠️ 密钥硬编码在 compose（`123456` / `change-me-in-production`）
- ✅ nginx SSE 四配置做对了三个（缺 `proxy_read_timeout`）
- ✅ lifespan 优雅关闭 + 预热带超时降级

## 42.8 延伸思考

1. **迁移和应用启动的时序怎么保证？多副本同时部署时会冲突吗？**
   提示：**会冲突**。如果两个副本同时启动、都执行 `alembic upgrade head`，可能并发修改同一张表（虽然 Alembic 有 advisory lock，但不同数据库行为不同）。所以**迁移必须是独立的一次性任务**，不能放在应用启动里。K8s 里用 **Job / initContainer** 跑迁移，Deployment 等它完成（对应 compose 的 `service_completed_successfully`）。**"迁移是部署的一部分，不是应用的一部分"** 这个区分很重要。

2. **怎么做到"零停机更新"？Agent 项目的难点在哪？**
   提示：普通服务靠滚动更新 + 就绪探针。Agent 项目多两个难点：① **SSE 长连接**——滚动更新时旧副本上的流式连接会被切断，用户看到回答中断。需要**优雅关闭：先停止接受新连接，等已有流写完再退出**（FastAPI 里要自己管理在途 SSE 的计数）。② **checkpointer 版本兼容**——新代码改了 State 结构，旧 checkpoint 反序列化可能失败。第 17 章讲过 checkpoint 有版本链，真正的零停机需要**向前兼容的状态结构**。

3. **embedding 模型怎么更新？换模型意味着什么？**
   提示：**换 embedding 模型 = 全库重新向量化**。因为不同模型的向量空间不兼容，旧向量和新 query 向量比较毫无意义。具体影响：① 知识库所有文档要重新 encode（成本 = 文档量 × 模型推理时间）；② 期间服务要么停要么双写双读（新旧两套集合）；③ 向量维度变化会牵动建表/索引（项目里 `get_embedding_dim` 动态探测维度就是为此，见 `vector_store.py:45-50`）。**所以选 embedding 模型要慎重，它是 RAG 系统里迁移成本最高的一个决策。**

4. **如何验证部署是否真的成功？（不是"起来了"而是"能用"）**
   提示：三层验证。① **存活**：`/healthz` 返回 200；② **就绪**：`/readyz` 所有依赖 ok；③ **可用**：跑一次真实的端到端冒烟——用一条评测集里的问题（第 37 章那 14 条里挑一条）打一次 `/api/ai/chat`，检查有没有返回非空答案。**只有第三层能证明"部署成功"**，前两层只能证明"进程活着"。这个冒烟测试应该自动跑，而不是人工点一下。
