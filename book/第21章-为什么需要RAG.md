# 第 21 章 · 为什么需要 RAG：从"模型知道"到"模型能查"

> **这一章要回答的核心问题**：大模型已经读过了整个互联网，为什么还要给它外挂一个知识库？RAG 到底解决了什么？它和"把资料塞进 prompt"、"微调"有什么区别？

---

## 21.1 引子：三个让纯 LLM 崩溃的瞬间

### 瞬间一：它不知道你的实验室

用户问："量子实验室的激光安全规程是什么？"

模型的训练语料里有"激光安全"的通用知识，但**不可能有你们学校量子实验室的具体规程**。它只能：

- 编一段听起来很专业的内容（**幻觉**，最危险）
- 说"我不知道"（体验差，但诚实）

**根因**：模型的知识在训练结束那一刻就**冻结**了。它不知道你公司上周发布的制度，不知道你数据库里的数据，不知道你上传的 PDF。

### 瞬间二：它的知识过期了

用户问："DeepSeek 最新版本是哪个？"

如果你的模型是 2025 年初训练的，它不知道 2026 年的事。要让它知道，你得重新训练——**几百万美元 + 几个月**。

**根因**：知识更新成本和模型参数强绑定。

### 瞬间三：它不告诉你答案从哪来

即便它答对了，你也无法验证。它不会说"这句话出自《量子实验室安全手册》第 12 页"。

在实验室安全、医疗、法律、金融这类**高风险领域**，不可溯源 = 不可用。

**根因**：模型是"参数化知识"——知识溶解在权重里，无法定位到具体来源。

---

## 21.2 RAG 是什么：一句话和三个词

**RAG（Retrieval-Augmented Generation，检索增强生成）**：

> **在生成答案之前，先从外部知识库里检索出相关资料，把这些资料作为上下文一起喂给模型，让它"看着资料回答"。**

三个关键词：

| 词 | 含义 | 对应本项目 |
|---|---|---|
| **Retrieval（检索）** | 从知识库里找出和问题相关的片段 | `kb_service.retrieve()` |
| **Augmented（增强）** | 把检索结果拼进 prompt | `kb_service.search()` 返回带引用的文本 |
| **Generation（生成）** | 模型基于资料生成答案 | `agent_node` 的 LLM 调用 |

**整个流程一句话**：

```
用户提问 → 检索相关资料 → 资料 + 问题 → 模型 → 答案（带引用）
```

本项目的实际链路（`agent_tools.py:79-86` → `kb_service.search()`）：

```
用户："实验室开放时间是几点？"
  ↓ Agent 决定调 search_lab_docs
  ↓ kb_service.search(query="实验室开放时间")
  ↓ 查询改写 → 向量召回 + BM25 召回 → RRF 融合 → rerank → 父上下文扩展
  ↓ 返回："[实验室管理规定.md#3]\n实验室开放时间为 8:00-22:00…"
  ↓ 这段文本作为 ToolMessage 回给模型
  ↓ 模型："根据《实验室管理规定.md》，开放时间是 8:00 到 22:00。"
```

**注意最后一步**：模型说出了**文件名**。这就是"可溯源"。

## 21.3 RAG 解决了什么：四个核心价值

### 价值 1：私有数据可用

模型不知道你的数据，但你的数据库里有。RAG 把"模型的语言能力"和"你的数据"接在一起。

本项目的知识库有两层：

- **静态知识库**：`KB_DIR` 下的 Markdown 文件（实验室管理规定、设备说明等）
- **动态上传**：用户在"知识库管理"页上传的 PDF/Word/Markdown

都通过同一个检索接口访问（`kb_service.search`），区别只是 `document_id` 过滤。

### 价值 2：知识可即时更新

上传新文档 → 切块 → 向量化 → 入库 → **立刻可检索**。

对比微调：

| 维度 | RAG | 微调 |
|---|---|---|
| 更新成本 | 秒级（重新索引） | 小时~天级（重新训练） |
| 更新范围 | 单文档 | 整个模型 |
| 成本 | 近乎为零 | 数千~数百万 |
| 可逆 | ✅ 删文档即可 | ❌ 权重已改，难以撤销 |

**本项目的更新机制**（`kb_service.py:87-91`）：

```python
def invalidate_cache() -> None:
    """文档新增/删除后清空语料缓存，并让 Redis 缓存键失效。"""
    global _chunks_cache, _corpus_version
    _chunks_cache = None
    _corpus_version += 1
```

注意 `_corpus_version += 1` —— **缓存键里带版本号**：

```python
cache_key = f"rag:v{_corpus_version}:{scope}:" + hashlib.md5(query.encode()).hexdigest()
```

版本号一变，**所有旧缓存自动失效**（因为键变了，永远查不到）。这是一个非常优雅的缓存失效方案——**不需要遍历删除，靠键命名空间天然隔离**。

> **面试可以讲这个**："我们的缓存失效用的是版本号方案——cache key 里带 corpus_version，文档变更时版本号 +1，旧键自然永远读不到，不需要遍历清理。这是避免缓存雪崩和脏数据的低成本方案。"

### 价值 3：答案可溯源

这是 RAG 相对纯 LLM 的**杀手级优势**。

本项目的 System Prompt 里明确要求（`agent_service.py`）：

```
## 引用要求
search_lab_docs 返回的资料会带 [文件名#块号] 这样的来源标记。知识库同时包含系统内置文档
和用户上传的文档，回答时要注明依据的文件名，例如「根据《量子实验室说明.md》」，
不要只给结论而不说明出处。
```

**"不要只给结论而不说明出处"** —— 这句话直接写进 prompt，是硬要求。

### 价值 4：降低幻觉

模型有了参考资料，就不容易瞎编。但要注意——**RAG 降低幻觉，不消除幻觉**。模型仍可能：

- 忽略检索到的资料，用自己的知识回答（**尤其当资料和问题"看起来"不相关时**）
- 把多份资料的信息混淆
- 资料里没有答案时，仍然编一个

所以 System Prompt 里还有一句（第 29 章详述）：

```
不要编造数据库里没有的实验室或设备信息。
```

## 21.4 RAG vs 三种替代方案

面试常问："为什么不直接把资料塞进 prompt？为什么不微调？"

### 对比 1：长上下文（直接塞全部资料）

"现在模型有 128K 甚至 1M 上下文了，我把整个知识库塞进去不就行了？"

| 维度 | 长上下文 | RAG |
|---|---|---|
| 成本 | 每次请求都要付费处理全部 token | 只处理检索出的几 K |
| 延迟 | prefill 时间长（几十秒） | 快 |
| 注意力稀释 | **"迷失在中间"（Lost in the Middle）** —— 长上下文里模型对中间部分注意力弱 | 只有最相关的几段 |
| 容量上限 | 有上限 | 无上限（知识库可以无限大） |
| 溯源 | 差 | ✅ 天然带来源 |

**"迷失在中间"**是一个重要的实证发现（斯坦福 2023）：当相关信息位于长上下文的**中间**位置时，模型的召回率显著下降；位于开头或结尾时表现好。

RAG 的效果等价于"每次只给你最相关的那几段，且放在最显眼的位置"。

> **面试金句**："长上下文和 RAG 不是替代关系，是互补。长上下文是'容量'，RAG 是'精准度 + 成本控制'。即便模型有 1M 上下文，把一个 100 万字的知识库每次都塞进去，成本和延迟都不可接受，而且会触发'迷失在中间'问题。"

### 对比 2：微调（Fine-tuning）

| 维度 | 微调 | RAG |
|---|---|---|
| 知识更新 | 慢、贵 | 快、便宜 |
| 适合教什么 | **形式**（格式、风格、任务范式） | **事实**（具体内容） |
| 幻觉 | 无改善（甚至更自信地编） | 显著改善 |
| 溯源 | ❌ 不可能 | ✅ 天然 |
| 数据量需求 | 需要大量样本 | 一篇文档就够 |

**核心区分**：

> **微调教模型"怎么做"（how），RAG 给模型"用什么"（what）。**

举例：
- 想让模型用固定的 JSON 格式输出 → **微调**
- 想让模型知道你们实验室的规程 → **RAG**
- 想让模型学会"先查后答"的行为模式 → **微调**（但也可以靠 prompt）

### 对比 3：Agent + 工具（不检索，直接查数据库）

本项目其实**两者都有**：

| 方式 | 工具 | 数据形态 | 适用 |
|---|---|---|---|
| **RAG** | `search_lab_docs` | 非结构化文本（文档） | "规程是什么" |
| **直接查询** | `list_open_labs`、`list_lab_equipments` | 结构化数据（数据库表） | "有哪些实验室" |

**这是一个重要的架构判断**：

> **结构化数据不要用 RAG，直接用 SQL 查；非结构化文本才用 RAG。**

很多初学者的错误是把数据库表也向量化，然后用 RAG 查"有哪些实验室"——结果既慢又不准（向量检索无法保证完整性，SQL 的 `SELECT *` 才是精确的全集）。

本项目的分工很清晰：

```python
# 结构化 → 直接查库
@langchain_tool
def list_open_labs(keywords: str = "") -> str:
    page = lab_service.get_lab_page_list(db, page=1, page_size=10, keywords=keywords, status=1)

# 非结构化 → RAG
def _search_lab_docs(query: str) -> str:
    return kb_service.search(query, document_id=scope_document_id)
```

> **面试加分词**："结构化数据走 SQL，非结构化文本走 RAG——这是我在这个项目里坚持的一个原则。向量检索是'模糊的、Top-K 的'，无法保证返回全集；而'有哪些实验室'这类问题需要的是精确完整的结果，用 SQL 才对。"

## 21.5 RAG 的完整架构：不只是"检索 + 拼 prompt"

很多人以为 RAG 就是"向量搜索 + 塞进 prompt"。真实的 RAG 系统有**离线**和**在线**两条链路，每条都有多个环节。

### 21.5.1 离线链路（索引构建）

```
文档 → 解析 → 切块 → 向量化 → 存入向量库 + 关键词索引
```

本项目对应：

| 环节 | 代码 |
|---|---|
| 解析（PDF/Word/MD） | `kb_parser.py`（第 22 章） |
| 切块 | `kb_chunking.split_text()`（第 23 章） |
| 向量化 | `vector_store` 内部的 embedding 模型（第 24 章） |
| 存储 | `vector_store`（第 25 章） |

### 21.5.2 在线链路（检索生成）

```
问题 → 查询改写 → 多路召回 → 融合 → 重排 → 上下文扩展 → 拼 prompt → 生成
```

本项目对应（`kb_service.retrieve()`）：

| 环节 | 函数 | 章节 |
|---|---|---|
| 查询改写 | `_rewrite_query()` | 第 28 章 |
| 向量召回 | `_vector_search()` | 第 24-25 章 |
| BM25 召回 | `_bm25_search()` | 第 26 章 |
| RRF 融合 | `_rrf_fusion()` | 第 26 章 |
| Rerank 重排 | `_rerank()` | 第 27 章 |
| 父上下文扩展 | `_expand_context()` | 第 29 章 |
| 拼装带引用 | `search()` | 第 29 章 |
| 缓存 | `_cache_get/_cache_set` | 本章 21.3 |

**认知要点**：RAG 不是"一个技术"，是**一条流水线**。每个环节都能独立优化，也都能独立出问题。面试时能画出这条链路并说出每个环节的作用，就已经超过大多数候选人了。

## 21.6 最小骨架：30 行实现最朴素的 RAG

在看本项目的完整实现前，先跑一个**零依赖**的最简版本，建立直觉。

```python
"""
minimal_rag.py —— 最朴素的 RAG：分词 + 词频打分 + 拼 prompt
运行：python minimal_rag.py  （纯 Python，无需任何依赖）
不需要向量模型，用"关键词重叠度"模拟检索，目的是理解 RAG 的结构。
"""

# ── 1. 知识库（真实项目里是解析后的文档块） ──────────────────
DOCS = [
    {"id": "规定#0", "text": "实验室开放时间为每日 8:00 至 22:00，节假日另行通知。"},
    {"id": "规定#1", "text": "进入实验室必须穿戴实验服和防护眼镜，禁止穿拖鞋。"},
    {"id": "规定#2", "text": "激光设备使用前需预约，操作时必须佩戴专用护目镜。"},
    {"id": "规定#3", "text": "离心机使用前需检查转子是否平衡，严禁超速运行。"},
    {"id": "规定#4", "text": "实验结束后必须关闭电源、清理台面，并填写使用记录。"},
]


# ── 2. 分词（中文用二元组，见第 26 章） ──────────────────────
def tokenize(text: str) -> set[str]:
    chars = [c for c in text.lower() if c.isalnum()]
    unigrams = set(chars)
    bigrams = {a + b for a, b in zip(chars, chars[1:])}
    return unigrams | bigrams


# ── 3. 检索：打分排序取 Top-K ────────────────────────────────
def retrieve(query: str, top_k: int = 2) -> list[dict]:
    q = tokenize(query)
    scored = []
    for doc in DOCS:
        d = tokenize(doc["text"])
        score = len(q & d) / len(q | d) if (q | d) else 0   # Jaccard 相似度
        scored.append({**doc, "score": score})
    scored.sort(key=lambda x: x["score"], reverse=True)
    return [s for s in scored if s["score"] > 0][:top_k]


# ── 4. 拼 prompt：★ 这是 RAG 的灵魂 ────────────────────────
def build_prompt(query: str, hits: list[dict]) -> str:
    context = "\n".join(f"[{h['id']}] {h['text']}" for h in hits)
    if not context:
        # 没有检索到 → 明确告诉模型，而不是让它自己编
        context = "（知识库中没有相关资料）"
    return f"""请只根据下面的资料回答用户的问题。
如果资料中没有答案，就明确说"知识库中没有相关信息"，不要编造。
回答时要注明依据的资料编号。

资料：
{context}

问题：{query}
"""


# ── 5. 生成（这里用规则模拟，真实项目里是 LLM 调用） ──────────
def fake_llm(prompt: str) -> str:
    if "（知识库中没有相关资料）" in prompt:
        return "知识库中没有相关信息。"
    # 真实项目里这里是一次 LLM API 调用
    return "（模拟生成）根据资料，答案如下：……"


def rag(query: str) -> str:
    hits = retrieve(query)
    print(f"  检索到 {len(hits)} 条：")
    for h in hits:
        print(f"    [{h['id']}] score={h['score']:.3f}  {h['text'][:30]}...")
    prompt = build_prompt(query, hits)
    return fake_llm(prompt)


if __name__ == "__main__":
    for q in ["实验室几点关门？", "离心机怎么用？", "食堂在哪？"]:
        print(f"\n{'='*50}\n问：{q}")
        print("答：", rag(q))
```

**跑起来的关键观察**：

1. **检索是"模糊匹配"**：问"几点关门"能匹配到"开放时间"（因为有共同的字/二元组），但分不高
2. **没检索到时会明确说明**：第三个问题"食堂在哪"检索不到，模型说"知识库中没有相关信息"——**这正是我们要的拒答行为**
3. **prompt 里写死了"不要编造"**：这是 RAG 降低幻觉的关键

**这个朴素版的三个致命缺陷**（引出后面各章）：

| 缺陷 | 后果 | 解法章节 |
|---|---|---|
| 只能匹配字面相同的词 | "关门" 匹配不到 "开放时间" | 第 24 章 Embedding |
| 长文档没法整体检索 | 一个 100 页 PDF 怎么算相似度？ | 第 23 章 切块 |
| 只返回命中的那句，上下文不完整 | "……严禁超速运行" 前面是什么？ | 第 29 章 父上下文 |

## 21.7 RAG 的五个失败模式（面试必问"RAG 有什么问题"）

只会讲 RAG 的好处，说明你没真正做过。这一节是**面试官区分候选人水平的分水岭**。

### 失败模式 1：检索错了（召回失败）

**表现**：相关资料在库里，但没被检索出来。

**原因**：
- 查询和文档用词差异大（"关门" vs "开放时间"）→ **词汇鸿沟**
- 切块把关键信息切断了
- Top-K 太小

**本项目对策**：混合检索（向量 + BM25，第 26 章）+ 查询改写（第 28 章）

### 失败模式 2：检索到了但排序靠后（排序失败）

**表现**：相关资料被检索出来，但排在 Top-K 之外，没进 prompt。

**原因**：向量相似度和真实相关性不完全对齐。

**本项目对策**：Rerank 重排（第 27 章）

### 失败模式 3：上下文不完整（切块失败）

**表现**：检索到的块只包含答案的一半，另一半在相邻块里。

**原因**：切块大小不合适 / 没有 overlap / 没有父上下文扩展。

**本项目对策**：overlap（第 23 章）+ 父上下文扩展（第 29 章）

### 失败模式 4：模型忽略了检索到的资料（生成失败）

**表现**：资料明明在 prompt 里，模型还是按自己的知识回答，甚至编造。

**原因**：
- 资料太长，被"迷失在中间"
- prompt 没有强制要求"只根据资料回答"
- 模型觉得自己更懂

**本项目对策**：System Prompt 硬约束 + 资料带来源标记

### 失败模式 5：资料里没有答案时模型编造（拒答失败）

**表现**：用户问了个知识库外的问题，模型依然自信满满地编。

**这是最危险的一类**，尤其在实验室安全场景。

**本项目对策**：
- 工具返回 `"没有检索到相关的资料"`（`agent_tools.py:82-84`）
- System Prompt 里"不要编造数据库里没有的实验室或设备信息"
- 评测集里专门有"资料没有时不许编造"的拒答用例（第 38 章）

## 21.9 面试问答

### Q1：什么是 RAG？解决什么问题？

**答**：RAG 是检索增强生成：在生成答案前先从外部知识库检索相关资料，把资料作为上下文一起送给模型。

它解决四个问题：一是**私有数据**——模型不知道我们实验室的规程；二是**知识时效**——文档上传后立刻可检索，而微调要重新训练；三是**可溯源**——答案能标注出处；四是**降低幻觉**——模型有依据就不容易瞎编。

但要说明：**RAG 降低幻觉，不消除幻觉**。模型仍可能忽略资料、混淆多份资料、或者在资料没有答案时编造。所以我们在 prompt 里写死了"不要编造数据库里没有的信息"，评测集里也有专门的拒答用例。

### Q2：为什么不直接把资料塞进长上下文？

**答**：四个理由。

一是**成本**：每次请求都要为全部 token 付费。100 万字的知识库，每次全塞进去，成本不可接受。

二是**延迟**：prefill 时间长，用户等几十秒。

三是**"迷失在中间"**：斯坦福的研究发现，长上下文里模型对**中间部分**的注意力显著弱于开头和结尾。RAG 相当于每次只把最相关的几段放在最显眼的位置。

四是**容量上限**：长上下文再大也有上限，RAG 的知識库容量是无限的。

当然两者是互补的——长上下文是容量，RAG 是精准度 + 成本控制。

### Q3：RAG 和微调怎么选？

**答**：核心区分是**微调教"怎么做"，RAG 给"用什么"**。

微调适合教模型形式：输出格式、语气风格、任务范式。RAG 适合给模型事实：具体的规程、产品信息、最新数据。

我们选 RAG 是因为：知识更新要快（上传文档立刻生效）、需要溯源（答案要能标出处）、数据量小（几份文档就够，微调需要大量样本）、成本敏感。

如果要让模型稳定输出某种 JSON 格式，那才考虑微调。

### Q4：结构化数据要不要用 RAG？

**答**：不要。这是我在这项目里坚持的原则。

结构化数据（实验室列表、设备清单、预约记录）应该直接查 SQL。"有哪些实验室"需要的是精确完整的结果，而向量检索是模糊的 Top-K，**无法保证返回全集**。

我们的分工：非结构化文档走 RAG（`search_lab_docs`），结构化数据直接查库（`list_open_labs`、`list_lab_equipments`）。

### Q5：RAG 有哪些失败模式？

**答**：五个。

一是**检索错了**——资料在库里但没检索出来，原因是词汇鸿沟，我们用混合检索 + 查询改写解决。

二是**排序靠后**——检索到了但排在 Top-K 外，用 rerank 重排解决。

三是**上下文不完整**——命中的块只包含答案一半，用 overlap + 父上下文扩展解决。

四是**模型忽略资料**——资料在 prompt 里但模型还是按自己知识答，靠 prompt 硬约束和资料结构化。

五是**资料没答案时编造**——最危险的一类。我们的对策是工具明确返回"没有检索到相关的资料"，prompt 里写死"不要编造"，评测集里有专门的拒答用例。

### Q6：你们的 RAG 链路有哪些环节？

**答**：两条链路。

**离线**：文档解析（PDF/Word/MD）→ 递归切块（带 overlap）→ 向量化 → 存向量库。

**在线**：查询改写 → 向量召回 + BM25 召回（双路）→ RRF 融合 → CrossEncoder 重排 → 父上下文扩展 → 拼装带引用的文本 → 缓存。

每个环节都能独立优化，也都能独立出问题。后面几章会逐个展开。

## 21.10 速记卡

> **RAG = 检索 + 拼 prompt + 生成。让模型"看着资料回答"。**

**解决四件事**：私有数据 / 知识时效 / 可溯源 / 降幻觉

**不消除幻觉**：仍可能忽略资料、混淆来源、无答案时编造

**vs 长上下文**：成本、延迟、迷失在中间、容量上限
**vs 微调**：**微调教 how，RAG 给 what**
**vs 直接查库**：结构化数据走 SQL，**不要向量化**（Top-K 无法保证全集）

**离线链路**：解析 → 切块 → 向量化 → 存储
**在线链路**：改写 → 双路召回 → 融合 → 重排 → 父上下文 → 拼 prompt → 生成

**五失败模式**：检索错 / 排序后 / 上下文残 / 模型忽略 / 无答案编造

**缓存失效妙招**：cache key 带 `corpus_version`，版本号 +1 → 旧键自然失效

## 21.11 延伸思考

1. **如果知识库里有两份互相矛盾的文档（旧规程说 21:00 关门，新规程说 22:00），模型会怎么处理？**
   提示：两份都可能被检索到，模型会随机选一个或者混淆。解法：文档加**时间元数据**，检索时优先新文档；或者让模型在矛盾时明确指出"存在两个版本"。这是一个真实且常见的生产问题。

2. **"知识库里没有答案"和"检索没找到答案"是两回事，怎么区分？**
   提示：前者是知识库确实没有（应拒答），后者是检索失败（应该改进召回）。区分方法是**评测集**：用已知有答案的问题测召回率。如果召回率高但仍拒答，说明是拒答逻辑的问题。

3. **RAG 的检索环节会不会成为性能瓶颈？**
   提示：会。向量检索 + BM25（全量扫）+ rerank（模型推理）都在关键路径上。本项目用 Redis 缓存缓解（相同问题直接返回）。但如果问题各不相同，缓存命中率低。第 41 章会讲性能优化。
