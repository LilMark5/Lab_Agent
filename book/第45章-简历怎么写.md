# 第 45 章 · 简历怎么写：技术栈怎么表述才不虚标

> 这一章不讲"排版技巧"，讲的是**怎么让简历上的每一句话都扛得住追问**。
>
> 核心观点先放出来：**简历不是"展示你有多强"，是"为面试设定你将被追问的范围"。**
> 你写的每一个技术点，都是邀请面试官来问。写你不熟的东西 = 给自己挖坑。
> 所以这一章的方法论是**反向的**：不是"怎么多写"，是"怎么只写你扛得住的，并且把它写透"。

---

## 45.1 为什么需要这一章

### 45.1.1 简历的三个读者，三种标准

同一份简历会被三个人用三种标准读：

```
HR（30 秒）   → 看关键词：有没有 Python？有没有 Agent？学历？实习经历？
技术一面（5 分钟）→ 看技术栈的广度和匹配度：他用过 LangGraph 吗？
技术二面（30 分钟）→ 逐条追问：你说你做了 X，那 X 的 Y 是怎么处理的？
```

**绝大多数简历的失败发生在第三关**——不是为了通过前两关而夸大，就是为了"看起来厉害"而堆砌。

> **一个残酷的事实**：面试官判断你是不是真做过，平均只需要 **两层追问**。
>
> ```
> Q: 你用了 RAGAS 做评估？
> A: 是的，用了四个指标。
> Q: context_precision 在拒答类用例上算吗？
> A: ...（如果没真的跑过，这里就断了）
> ```

### 45.1.2 三种"简历死法"

**死法一：技术栈清单式**

```
熟悉：Python、Java、Go、C++、React、Vue、Spring、Docker、K8s、
      MySQL、Redis、MongoDB、Kafka、LangChain、LangGraph、RAG...
```

**问题**：这一行里任何一项都可能被追问，而你能扛住的也许只有三项。**清单越长，你的"命中率"越低。**

**死法二：功能罗列式**

```
- 实现了用户登录
- 实现了预约功能
- 实现了 AI 对话
```

**问题**：这是需求文档，不是简历。**面试官看不到你的技术判断**——任何人都能写"实现了登录"。

**死法三：过度包装式**

```
- 主导设计了高可用、高并发的分布式 AI Agent 架构，支撑千万级 QPS
```

**问题**：一个单机毕业设计项目写"千万级 QPS"，面试官一问"你压测过吗"就崩。而且**这会让你前面所有真实的内容都被怀疑**。

## 45.2 它到底是什么：三档标注法

这是这一章的核心方法论。**把你简历上的每个技术点分到三档，并按档位用不同的表述。**

### 45.2.1 三档的定义

```
┌─────────────────────────────────────────────────────────────┐
│  A 档 · 实跑验证                                              │
│  定义：你亲手部署/跑通，见过它的输出，踩过它的坑              │
│  表述：直接用动词，"实现 X，用 Y 解决 Z"                      │
│  能扛：三层追问（原理 / 实现 / 故障）                         │
│                                                              │
│  B 档 · 代码接入但未实跑 / 只做过 Demo                        │
│  定义：代码写了、接口调通了，但没在真实环境跑过完整场景        │
│  表述："实现了 X 的接口适配（未实跑验证）"                    │
│  能扛：两层追问（原理 / 实现），第三层（故障）要坦白          │
│                                                              │
│  C 档 · 了解                                                  │
│  定义：读过文档、知道它解决什么问题，没写过代码              │
│  表述：单独列一行"了解：X、Y、Z"，**不写进项目经历**          │
│  能扛：一层追问（它是什么、解决什么问题）                     │
└─────────────────────────────────────────────────────────────┘
```

### 45.2.2 为什么必须分档

**因为"不知道自己不知道"是最危险的状态。**

如果你分不清"我跑过 Chroma"和"我了解 Milvus"的区别，面试时被问到 Milvus 的具体行为，你会本能地用 Chroma 的经验去猜——**而这两者的行为差异正是面试官想考的**。

分档之后，你的回答会变成：

> "Milvus 我只做到了接口层适配，没有起真实服务验证。它的 HNSW 参数调优和 Milvus Lite 在 Windows 上的限制我是在文档里看到的，没有实测。如果要上生产我会先做 X 验证。"

**这个回答比硬撑可信十倍，而且它本身展示了你的工程严谨性。**

### 45.2.3 本项目的三档清单（可以直接抄）

这是这个项目真实的分档结果，**也是全书反复强调的"诚实说明"的来源**：

**A 档（实跑验证）**

```
FastAPI 分层架构 + 依赖注入 + 统一异常
SQLAlchemy 2.0 + 事务 + SELECT FOR UPDATE + 并发测试
JWT + bcrypt + RBAC + 前端路由守卫
LangGraph：StateGraph / Reducer / 条件路由 / checkpointer / interrupt
Function Calling + ReAct + 工具工程（超时/重试/to_thread）
上下文裁剪（sliding_window + 配对保护）
RAG 全链路：切块 / embedding / 混合检索 / RRF / rerank / 父上下文 / 引用
向量库：Chroma ✅、pgvector ✅
SSE 流式（前后端）
评测：Hit@K / MRR / nDCG@3 + RAGAS 四指标 + 裁判分离
pytest（37 个测试）
```

**B 档（代码接入未实跑）**

```
Milvus（接口实现了，未起服务；Milvus Lite 不支持 Windows）
Redis（代码完整，.env 未配置，走降级）
MCP（服务端和客户端都实现了，compose 里没起，容器里走降级）
Docker（Dockerfile 和 compose 写了，部分问题未验证：迁移未接）
```

**C 档（了解）**

```
多 Agent 编排（Supervisor / Swarm，做过设计对比未落地）
LangSmith / Langfuse（知道是什么，没接，考虑数据出境）
K8s、Prometheus、OpenTelemetry
TypeScript（前端是 JS）
```

**这份清单本身就是面试素材**——被问"你有什么没做过的"，直接按 B/C 档答，并给出补上的方案。

## 45.3 项目经历怎么写：STAR + 量化 + 技术判断

### 45.3.1 一条项目经历的四要素

```
[动词] + [做了什么] + [用什么技术] + [解决什么问题/避免什么后果] + [可验证的数字]
```

对比一下：

**❌ 改前**

```
- 使用 LangGraph 实现了 AI Agent，支持工具调用和人工审批
```

**✅ 改后**

```
- 基于 LangGraph 构建 ReAct Agent：模型自主决定调用知识检索、实验室查询、
  预约落库等工具；用 checkpointer 将会话状态持久化（服务重启后可继续多轮对话），
  写库类操作通过 interrupt 中断等待用户确认、确认后用 Command(resume) 恢复执行；
  为审批闭环、多轮历史不重复等关键行为补了确定性集成测试。
```

**差异在哪？**

| 维度 | 改前 | 改后 |
|---|---|---|
| 动词 | 使用（弱） | 构建、持久化、中断、恢复、补测试（强） |
| 技术点 | LangGraph（1 个） | LangGraph / checkpointer / interrupt / Command / 集成测试（5 个） |
| 问题 | 无 | 重启失忆、写库需确认、测试不确定 |
| 可验证 | 无 | "确定性集成测试"是可被追问的具体物 |

### 45.3.2 动词表（按强度排序）

```
弱：使用、参与、了解、学习、接触
中：实现、开发、完成、搭建、接入
强：设计、解决、优化、定位、重构、验证、压测、灰度
```

**原则**：**一条经历里至少有一个"强动词"**，而且要对应到一个你真的做过的判断。

```
❌ "解决了 Agent 的上下文问题"          ← 太泛
✅ "定位并修复了上下文裁剪拆散 tool_calls 与 ToolMessage 配对的问题"
                                        ← 具体到能验证
```

### 45.3.3 量化：能写什么数字

这个项目里有这些**真实可查的数字**：

| 数字 | 来源 |
|---|---|
| 31 个 REST 接口 | 9 组路由 |
| 37 个单元/集成测试 | `backend/tests/` |
| 后端 52 个 Python 文件 / 4216 行 | `find backend/app -name "*.py" \| xargs wc -l` |
| 前端 2776 行 | `frontend/src` |
| 14 条评测用例（12 factual + 2 refusal） | `eval_dataset.py` |
| 5 张数据表 | `models/` |
| `recursion_limit=10`、`MAX_CONTEXT_TOKENS=4000` | `config.py` |
| `FINAL_CONTEXT_K=3`、`CHUNK_SIZE=200/40` | `config.py` |

**量化原则**：**宁可少而准，不要多而假。**

```
✅ "37 个单元/集成测试，覆盖并发预约、审批闭环、切块重叠等"
❌ "测试覆盖率 95%"（如果没跑过 coverage）
❌ "性能提升 300%"（如果没有压测数据）
```

### 45.3.4 一条被低估的写法：写"你避免了什么"

大部分人只写"我做了什么"，很少写"我避免了什么坏事发生"。**而后者恰恰是工程能力的证明。**

```
❌ "用 SELECT FOR UPDATE 做并发控制"
✅ "预约并发场景用 SELECT FOR UPDATE 防止重复预订，配套并发集成测试"

❌ "加了工具超时"
✅ "工具调用加超时 + 有限重试，最终失败回填结构化错误给模型自纠，
    避免单次卡死拖垮整张图"

❌ "prompt 里要求不要编造"
✅ "自建 14 条标注用例（含「资料没有时不许编造」的拒答边界），
    用于检测'为优化其他指标而放宽拒答约束'导致的退化"
```

**第三条的"避免"是隐性的、只有做过的人才会想到的**——这就是区分度。

## 45.4 专业技能怎么写

### 45.4.1 分类 + 分档的标准格式

```markdown
- **后端开发**：Python、FastAPI（分层架构 / 依赖注入 / lifespan 生命周期 /
  异步流式接口）、Pydantic v2 校验、SQLAlchemy 2.x、Alembic 迁移、
  JWT + bcrypt 鉴权、统一响应与四级异常处理
- **数据库**：PostgreSQL、SQLite、Redis（限流 / 检索结果缓存，可选依赖、
  未配置时优雅降级）；事务边界与失败回滚、并发控制（SELECT FOR UPDATE +
  时间区间重叠判定）、pgvector 向量检索与 HNSW 索引
- **RAG**：...；ChromaDB / pgvector 实跑，Milvus 了解
```

**三个写法要点**：

**① 括号里放"深度证据"**

```
❌ "熟悉 Redis"
✅ "Redis（限流 / 检索结果缓存，可选依赖、未配置时优雅降级）"
```

括号里的东西是**你把追问锚定在你熟悉的点上**。面试官看到"优雅降级"会问降级逻辑，而不是问 Redis 的持久化配置。

**② 主动标注未实跑的**

```
✅ "ChromaDB / pgvector 实跑，Milvus 了解"
```

**这半句是整份简历里最值钱的六个字。** 它做了三件事：表明你有 honest 的自我评估、把追问引导到实跑的部分、避免被问穿。

**③ 把"了解"单独列，不混进项目经历**

```
❌ 项目经历里："实现了基于 Milvus 的向量检索"
✅ 专业技能里："Milvus（了解）" + 项目经历里："向量库抽象为
   ChromaDB / pgvector / Milvus 三后端统一接口"
```

**注意第二句的表述**：写的是"抽象为三后端统一接口"——这是**真做过的**（抽象层确实写了），而不是"实现了 Milvus 检索"（没实跑）。

**这个措辞差异就是虚标和诚实的分界线。**

### 45.4.2 五个虚标雷区

| 雷区 | 例子 | 一问就穿的点 |
|---|---|---|
| **把"了解"写成"熟悉"** | "熟悉 Kubernetes" | "你用过哪些资源对象？" |
| **把"跑过 Demo"写成"生产经验"** | "有高并发经验" | "峰值 QPS 多少？怎么测的？" |
| **把"用过库"写成"懂原理"** | "深入理解 Transformer" | "注意力的 QKV 怎么来的？" |
| **把"团队项目"写成"独立开发"** | "独立设计了 XX 架构" | "这个决策是谁做的？为什么？" |
| **把"打算做"写成"做了"** | "接入了 LangSmith 做链路追踪" | "trace 长什么样？" |

**特别提醒最后一条**：很多人把"我在计划里写了要做 X"当成"做了 X"。**简历上只写你能在面试当场打开代码验证的东西。**

## 45.5 完整改写案例

下面是这个项目几条经历的**改前 / 改后**对照，都来自真实表述。

### 案例一：并发控制

**❌ 改前**

```
- 实现了预约功能，处理了并发情况
```

**✅ 改后**

```
- 从零实现 FastAPI + Vue3 的业务闭环（登录注册、实验室/设备管理、预约提交与
  管理员审核）：API / Service / Model / Schema 分层，JWT 鉴权、统一响应与全局
  异常，共 31 个接口；用 Alembic 管理数据库迁移，预约并发场景用 SELECT FOR
  UPDATE 防止重复预订，配套并发集成测试。
```

**改了什么**：加了分层（架构能力）、接口数（量化）、Alembic（工程习惯）、`FOR UPDATE` + 并发测试（深度）。

### 案例二：Agent 稳定性

**❌ 改前**

```
- 用 LangGraph 做了 AI 对话，支持多轮
```

**✅ 改后**

```
- 补齐 Agent 线上稳定性三处工程细节：checkpointer 双后端抽象（SQLite 零配置 /
  PostgreSQL 多实例、会话与业务库同源）；按 token 预算裁剪对话历史（滑动窗口与
  摘要两种策略，并保护 tool_calls 与 ToolMessage 配对不被拆散）；工具调用加超时
  + 有限重试，最终失败回填结构化错误给模型自纠，避免单次卡死拖垮整张图。
```

**改了什么**：三条都指向"为什么这么做"——多实例、配对完整性（这是真踩过的坑）、错误回填（ReAct 的核心机制）。

**"保护 tool_calls 与 ToolMessage 配对不被拆散"这一句**，是只有真的被 API 400 报错折磨过的人才会写的。面试官看到这一句大概率会追问，而你已经准备好了。

### 案例三：评测

**❌ 改前**

```
- 用 RAGAS 评估了 RAG 效果
```

**✅ 改后**

```
- 建立离线评估体系：检索侧评 Hit@1/3、MRR、nDCG@3，生成侧接入 RAGAS 四指标
  （faithfulness / answer_relevancy / context_precision / context_recall），
  自建 14 条标注用例（含「资料没有时不许编造」的拒答边界）；裁判模型与被测模型
  分离配置，避免模型自评引入系统性噪声；通过对照实验定位出检索指标饱和、
  判官模型噪声、context_precision 排序口径三个评测陷阱，形成评估文档。
```

**最有价值的是最后半句**——它写的不是"我用了什么"，是"我发现了什么"。**发现问题的能力 > 使用工具的能力**，这是实习生和工程师的分界线。

### 案例四：自我评价

**❌ 改前**

```
- 热爱技术，学习能力强，有团队精神，抗压能力好
```

**✅ 改后**

```
- 对 AI Agent 方向有明确职业目标，能独立完成从需求、开发、测试到评估的完整闭环。
- 注重工程习惯：代码分层清晰、关键逻辑有注释、密钥不提交仓库、用 Git 管理版本。
- 学习以"能讲清原理 + 能跑通验证"为标准，不满足于会调 API。
```

**原则**：**自我评价要么写可验证的行为，要么不写。** "热爱技术"无法验证；"密钥不提交仓库"能当场打开 `.gitignore` 验证。

## 45.6 面试前 30 分钟：简历自检清单

投简历前，逐条过一遍。

### 检查项 1：每个技术点能不能扛两层追问

随机挑 5 个技术点，自己问自己两层：

```
LangGraph → ① Reducer 是什么？② 节点返回全量会怎样？
pgvector  → ① HNSW 和 IVFFlat 区别？② 空表建索引会怎样？
SSE       → ① 为什么不用 WebSocket？② nginx 后面要配什么？
RAGAS     → ① 哪些指标需要标准答案？② 拒答类为什么不算 answer_relevancy？
interrupt → ① 它做了什么？② 恢复时节点会怎样？
```

**有两层答不上来的，从简历里降级表述或删掉。**

### 检查项 2：所有数字能不能当场验证

```
"31 个接口" → 能：grep 一下路由
"37 个测试" → 能：pytest --collect-only
"14 条用例" → 能：打开 eval_dataset.py
"QPS 1000"  → 不能！删掉
```

### 检查项 3：有没有"看起来很厉害但你没做过"的句子

自查关键词：**高可用、高并发、分布式、千万级、性能优化、架构设计、自研**。

对着每一个问："**我有数据吗？**" 没有就改成具体的事实描述。

### 检查项 4：GitHub 链接能不能自证

如果简历写了 GitHub，面试官**真的会点开**。检查：

```
✅ README 有项目介绍、架构图、启动步骤
✅ 有 commit 历史（不是一次 push）
✅ 没有 .env、没有密钥
✅ 有测试目录
```

**一个能跑起来、README 清楚的仓库，比简历上的任何一句话都有说服力。**

### 检查项 5：有没有为"最可能被问的三件事"准备好故事

```
1. 最难调的 bug        → 并发预约冲突（有测试、有修法、有边界条件）
2. 最有价值的设计      → 裁判模型分离 / 拒答哨兵用例（有数字、有推理）
3. 你自己的缺陷        → Milvus 未实跑 / 部署缺迁移（诚实 + 修复方案）
```

**第三件最重要**——能说出自己缺陷的人极少，而它是面试官判断"这个人有没有真的做过"的最快方式。

## 45.7 面试问答：关于简历本身的追问

### Q1：你简历上写了 Milvus，用过吗？

**答**：**接口层实现了，但没有起真实服务验证过。** 项目里向量库抽象了三个后端（Chroma / pgvector / Milvus），Milvus 那部分的代码是按 Milvus Lite 的 API 写的，本地实际跑的是 Chroma 和 pgvector。

Milvus 的 HNSW 参数调优、Milvus Lite 在 Windows 上的限制（不支持），我是从文档里看到的，没有实测。如果要上生产，我会先起 Docker 版 Milvus 验证召回效果，并且要注意多实例下 Milvus Lite 的文件冲突问题。

**★为什么这么答**：把"没做过"限定到具体范围（哪一层做了、哪一层没做），并给出下一步——**这比"用过"或"没用过"都可信。**

### Q2：简历写"独立开发"，这个项目真的只有你一个人吗？

**答**：代码是我一个人写的，从数据库设计到前端页面。但在技术选型上我参考了大量的开源项目和官方文档，比如 LangGraph 的状态机设计参考了官方的 ReAct 模板，RAG 的评估方法参考了 RAGAS 的文档和几篇工程博客。

**如果问"有没有 AI 辅助"**：如实说——部分代码的初稿我用了 AI 辅助，但**每个模块我都跑通并理解了**，尤其是踩坑的部分（并发、interrupt 重放、裁剪配对）都是自己调试出来的。

**★加分点**：不回避 AI 辅助。**面试官在意的是你能不能解释代码，不是谁敲的键盘。**

### Q3：你写了"37 个测试"，覆盖率多少？测了什么？

**答**：**没有跑过覆盖率统计，这是我没有做的一项。** 测试集中在几个核心路径：并发预约冲突、切块的边界和重叠、文档解析、Agent 的审批闭环（用假 LLM 保证确定性）、鉴权。

**没覆盖的**：API 层的参数校验、工具层的各种异常分支、前端。

**★为什么这么答**：主动说明没覆盖的部分，比报一个虚高的覆盖率可信。

### Q4：你怎么证明简历上写的是真的？

**答**：可以当场看代码。比如：

- "并发控制" → 打开 `reservation_service.py` 看 `FOR UPDATE` 和重叠判断
- "interrupt 审批" → 打开 `test_agent_service.py:67-127` 跑那个测试
- "裁判分离" → 打开 `config.py:68-70` 和 `evaluate_generation.py:294-309`
- "拒答哨兵" → 打开 `eval_dataset.py` 最后两条用例

**★这是最有杀伤力的一句话**：把简历上的每个技术点都锚定到具体文件和行号。**编造的人做不到这一点。**

### Q5：你是实习生/应届生，凭什么做这么复杂的项目？

**答**：我没有凭空做，是**分层的**——先做一个没有 AI 的完整业务系统（约 7 天），再把 Agent 一层层加上去（14 天），最后是 RAG 和评测。每一层都建立在上一层已经跑通的基础上。

而且这个项目**有很多不成熟的地方**：可观测性基本没有（只有标准库 logging）、部署有多处问题（迁移没接上、缺 .dockerignore）、测试覆盖不全。**我清楚它的边界在哪。**

**★加分点**：主动降低预期反而更可信。**过度自信是应届生最常见的减分项。**

### Q6：简历上要不要写"了解"的东西？

**答**：**要写，但要单独成行、明确标注。**

写"了解：Kubernetes、Langfuse、多 Agent 编排"的价值是：① 表明你的技术视野不止于项目用到的；② 把面试官的追问引导到"它是什么、解决什么问题"这一层（你能答）；③ 如果岗位正好需要，说明你有学习基础。

**千万不要把"了解"混进项目经历**——那等于邀请面试官用"做过"的标准追问你。

### Q7：简历要几页？格式怎么选？

**答**：**一页，PDF，不用花哨模板。**

应届生/实习生一页足够。格式用最简单的（Markdown 转 PDF 或 Word 默认模板），**不要花时间做设计**——HR 和技术面试官都不看版式，花哨的模板反而显得重心放错了。

**唯一要注意的技术细节**：文件名用 `姓名-求职意向-简历.pdf`，不要用"简历最终版2.pdf"。

### Q8：教育背景和课程要写吗？成绩不好呢？

**答**：写学校、专业、时间。**主修课程挑和岗位相关的写**（数据结构、数据库原理、计算机网络、操作系统）。

成绩好就写 GPA/排名，不好就不写——**没有人会因为简历上没写 GPA 而拒你，但写了低分会被追问。**

如果学校不是优势，就把重心放在项目经历上，教育背景放最简。

## 45.8 速记卡

**三档标注法**

| 档 | 定义 | 表述 | 能扛几层追问 |
|---|---|---|---|
| **A 实跑** | 亲手跑通、踩过坑 | 直接用动词 | 3 层 |
| **B 接入未实跑** | 代码写了没验证 | "实现了 X 的接口适配（未实跑）" | 2 层 |
| **C 了解** | 只读过文档 | 单独列"了解：X"，**不进项目经历** | 1 层 |

**★ 简历的作用是"设定你将被追问的范围"，不是"展示你有多强"**

**项目经历四要素**：强动词 + 做了什么 + 用什么技术 + **避免了什么后果** + 可验证数字

**动词强度**：使用/参与 < 实现/开发/接入 < **设计/定位/优化/验证**

**★ 写"你避免了什么"比写"你做了什么"更有区分度**

**真实可量化数字**：31 接口 / 37 测试 / 14 条评测用例 / 5 张表 /
后端 4216 行 / `recursion_limit=10` / `FINAL_CONTEXT_K=3`

**五个虚标雷区**：了解→熟悉 / Demo→生产 / 用库→懂原理 / 团队→独立 / 打算做→做了

**★ 最值钱的六个字**："pgvector 实跑，Milvus 了解"

**投前五检**
```
1. 随机 5 个技术点，各扛两层追问
2. 所有数字能当场验证（QPS 这类没有数据的删掉）
3. 自查"高可用/高并发/分布式/千万级/自研"→ 有数据吗？
4. GitHub 能自证（README / commit 历史 / 无密钥）
5. 三个故事准备好：最难 bug / 最有价值设计 / 自己的缺陷
```

**★ 把每个技术点锚定到 文件:行号** —— 编造的人做不到

**格式**：一页 PDF，简单模板，文件名 `姓名-意向-简历.pdf`

## 45.9 延伸思考

1. **如果项目比较小，怎么让它看起来有价值？**
   提示：**不要包装规模，包装深度**。一个"登录注册 + CRUD"的项目，如果里面有三处别人没有的东西——并发控制、幂等设计、审计日志——它就能讲 20 分钟。面试官问项目时，听的是**你在哪些地方做了判断**，不是功能有多少。**深度的可验证性远高于广度的不可验证性。**

2. **要不要写和岗位无关的经历（比如学生会、兼职）？**
   提示：**只在两种情况写**：① 能提炼出可迁移能力（组织大型活动 = 项目管理 + 跨部门协调）；② 岗位明确要求（比如要抗压、要沟通）。否则**宁可留白给技术内容**。一页简历里，一行无关经历的机会成本是一行技术点。

3. **简历投出去没回音，问题通常在哪？**
   提示：三种可能，排查顺序：① **关键词不匹配**——ATS 系统和 HR 按关键词筛，你的简历里没有 JD 里的词（JD 写"LangChain"，你只写"大模型应用"）；② **定位不清**——既投后端又投算法又投前端，看起来哪个都不专；③ **项目描述无法快速看懂**——第一句话没说清"这是个什么系统"。**第 ① 条最容易被忽略**：同一份经历，针对不同 JD 要调整技术词的分布（不是改内容，是改词）。

4. **面试时发现了简历上的错误怎么办？**
   提示：**主动指出，不要等被发现**。开场可以说"我简历上有一处表述不太准确——XX 那部分实际是接口适配，没有实跑验证，我在这里更正一下"。这看起来是减分，实际是**大幅加分**——因为它证明了你的自我评估是可靠的，而**面试官最怕的不是你不会，是你不知道自己不会**。
