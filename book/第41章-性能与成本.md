# 第 41 章 · 性能与成本：延迟从哪来，钱花在哪

> Agent 系统上线后最先暴露的通常不是"答案不对"，而是两个更朴素的问题：
> **"怎么这么慢？"** 和 **"怎么这么贵？"**
>
> 这一章把这两个问题拆成能算的数字。你会看到：一个 5 轮的 ReAct 循环，
> token 消耗不是 5 倍而是 **15 倍**——因为每一轮都要把前面所有内容重新发一遍。
> 这是 Agent 成本模型里最重要、也最容易算错的一个数。

---

## 41.1 为什么需要它：Agent 的钱烧法和你想的不一样

### 41.1.1 一个反直觉的事实

很多人以为 Agent 的成本是这么算的：

```
成本 = 单次调用成本 × 调用次数
```

**这是错的。** 正确的是：

```
第 1 轮：prompt = system + 用户问题                          = 1 份
第 2 轮：prompt = system + 用户问题 + AI回复1 + 工具结果1      = 2 份
第 3 轮：prompt = system + 用户问题 + ...   + AI回复2 + 工具2  = 3 份
第 4 轮：                                                    = 4 份
第 5 轮：                                                    = 5 份
────────────────────────────────────────────────────
总 prompt = 1 + 2 + 3 + 4 + 5 = 15 份
```

**5 轮对话烧掉 15 份 prompt，不是 5 份。** 因为每一轮 LLM 调用都要把完整历史重新发一遍——模型是无状态的，它不记得上一轮说过什么。

一般化：

```
N 轮 ReAct 的总 prompt token ≈ N(N+1)/2 × 单轮基础量
```

**这是 O(N²)，不是 O(N)。** 轮次翻一倍，成本翻四倍。

### 41.1.2 这意味着什么

看一个具体的数。假设：

- 单轮基础 prompt：1200 token（system 800 + 问题 100 + 检索上下文 300）
- 每轮工具结果：400 token
- 每轮 AI 回复：150 token
- 走 5 轮

```
轮次  本轮 prompt   累计
 1     1200        1200
 2     1750        2950      (+550)
 3     2300        5250      (+800)
 4     2850        8100      (+1100)
 5     3400       11500      (+1400)
```

**5 轮下来 11500 token，而"单次问答"只要 1200。差了 9.6 倍。**

按 gpt-4o-mini 的价格（$0.15/1M input）：11500 token ≈ $0.0017。看起来很小？

**乘上量**：每天 1 万次对话 = $17/天 = **$510/月**。而这还只是一个中等流量的内部系统。

如果换成更强的模型（gpt-4o 是 $2.5/1M）：**$8500/月**。

**这就是为什么"减少一轮工具调用"的优化价值，往往大于"换个便宜模型"。**

### 41.1.3 延迟也是同一个形状

延迟的构成：

```
总延迟 = Σ(每轮 LLM 推理时间) + Σ(工具执行时间) + 检索时间 + 网络往返
```

LLM 推理时间大致和 **completion token 数**成正比（自回归逐 token 生成），而**首 token 延迟（TTFB）**和 prompt 长度成正比（要先把整个 prompt 过一遍前向）。

所以 prompt 越长：

- **TTFB 越长**（用户感觉"卡了一下才开始出字"）
- **每 token 生成越慢**（KV cache 变大）
- **成本越高**

**三个问题同向恶化。** 这就是为什么"上下文裁剪"（第 19 章）不只是防崩溃，它同时是性能优化和成本优化。

### 41.1.4 用户感知的延迟 ≠ 实际延迟

这是流式（第 31 章）的价值所在：

```
无流式：用户等 8 秒 → 一次看到全部答案      感知：8 秒，很慢
有流式：用户等 1.2 秒看到第一个字 → 边出边看  感知：快，虽然总时间还是 8 秒
```

**用户感知的延迟是"首字延迟"（TTFB），不是总耗时。** 优化感知延迟最有效的手段是流式，而不是真的把系统变快。

所以性能优化要分两个目标：

| 目标 | 指标 | 手段 |
|---|---|---|
| **感知延迟** | TTFB | 流式输出、减少首轮前的串行步骤 |
| **真实延迟** | 总耗时 | 并行、缓存、减少轮次 |
| **成本** | token 总量 | 裁剪、缓存、模型分层 |

**三个目标的优化手段不一样，别混着谈。**

## 41.2 它到底是什么：三层优化杠杆

Agent 的性能与成本优化，本质上有三个杠杆，优先级从高到低：

```
┌────────────────────────────────────────────────────────────┐
│  杠杆 1：减少轮次（O(N²) → 影响最大）                        │
│  让模型一次就选对工具、填对参数，少走冤枉路。                │
│  手段：工具描述清晰、prompt 给足信息、工具粒度合理            │
├────────────────────────────────────────────────────────────┤
│  杠杆 2：减少每轮 token（线性，但每轮都生效）                 │
│  手段：上下文裁剪、控制 FINAL_CONTEXT_K、精简 system prompt   │
│        工具结果截断、历史摘要                                │
├────────────────────────────────────────────────────────────┤
│  杠杆 3：不重复干活（缓存 / 并行）                           │
│  手段：embedding 缓存、检索缓存、LLM 缓存、独立工具并行       │
└────────────────────────────────────────────────────────────┘
```

**为什么按这个顺序？** 因为影响量级不同：

- 杠杆 1 减一轮 = 省掉一整个 O(N) 的尾巴（第 5 轮是 5 份，省掉就是省 5 份）
- 杠杆 2 减 30% token = 线性省 30%
- 杠杆 3 命中缓存 = 该次调用省 100%，但**有命中率上限**

**很多人的错误是只做杠杆 3**（加缓存），因为它最容易做。但缓存命中率通常只有 20-40%，而减少一轮是稳稳的。

### 41.2.1 杠杆 1：减少轮次的三个具体手段

**① 工具描述要"可决策"**

对比两个描述：

```python
# 差：模型不知道什么时候该用
@tool
def query_labs(date: str) -> str:
    """查询实验室。"""

# 好：说清楚用途、参数格式、返回什么
@tool
def query_labs(date: str) -> str:
    """查询指定日期可用的实验室列表（只读）。

    参数 date 使用 YYYY-MM-DD 格式，例如 2025-06-10。
    返回 JSON 数组，每项含 id / name / capacity / open_hours。
    当用户问"有哪些实验室""某天有没有空实验室"时使用本工具。
    """
```

第 20 章讲过：**docstring 就是提示词**。描述不清楚 → 模型填错参数 → 工具报错 → 再试一次 → **多一轮**。

**② 一次给全，不要挤牙膏**

用户的"明天下午帮我约个有投影仪的实验室"，理想路径是 1 轮工具调用。但如果工具设计成 `query_labs(date)` 和 `query_equipment(lab_id)` 两个，模型就得：

```
轮1: query_labs("2025-06-10")  → 得到 5 个实验室
轮2: query_equipment(lab_1)    → 没投影仪
轮3: query_equipment(lab_2)    → 有
```

**3 轮。** 如果有一个 `query_available_labs(date, require_equipment="投影仪")`，**1 轮搞定**。

**这就是"工具粒度"的成本含义**：工具拆得太细，轮次爆炸。

**③ 能并行的别串行**

两个无依赖的工具调用应该同时发出（LLM 可以在一次响应里返回多个 `tool_calls`）。这依赖 prompt 里说明"无依赖的工具可以一次调用多个"。

### 41.2.2 杠杆 2：减少每轮 token

项目里已有的四个手段：

| 手段 | 配置 | 位置 |
|---|---|---|
| 上下文预算 | `MAX_CONTEXT_TOKENS = 4000` | `config.py:122` |
| 裁剪策略 | `TRIM_STRATEGY = "sliding_window"` | `config.py:127` |
| 最终上下文块数 | `FINAL_CONTEXT_K = 3` | `config.py:80` |
| 父上下文窗口 | `CONTEXT_WINDOW = 1` | `config.py:81` |

`FINAL_CONTEXT_K = 3` 尤其关键——它直接决定了每轮注入多少 token。从 3 调到 10，每轮多 7 块 × 约 200 token = 1400 token，**5 轮就是 7000 额外 token**。

**还有两个容易被忽略的点**：

**① system prompt 的隐性成本**

system prompt 是**每一轮都要重发**的。800 token 的 system prompt × 5 轮 = 4000 token，占了总成本的 35%。

**精简 system prompt 是所有优化里 ROI 最高的**——改一次，每次请求都省。

**② 工具结果的截断**

工具返回 50 条实验室记录，全部塞进上下文就是几千 token。项目里有 `_tool_output_preview`（`agent_service.py`）做截断，但**只用于展示**。

**生产上应该对写入上下文的工具结果也做截断**：返回前 N 条 + "共 50 条，已省略 45 条"。模型通常只需要知道有多少、前几个是什么。

### 41.2.3 杠杆 3：缓存与并行

**三层缓存**（按性价比排序）：

| 层 | 缓存什么 | 命中率 | 省什么 |
|---|---|---|---|
| **embedding** | 文本 → 向量 | 高（文档块重复） | CPU（本地模型）或 API 费（云端模型） |
| **检索结果** | query → 上下文串 | 中（相似问题） | 检索耗时 + 重排耗时 |
| **LLM 响应** | 完整 prompt → 响应 | 低（prompt 几乎不重复） | API 费 + 延迟 |

项目**只做了第二层**（`kb_service.py:265-296`），且 Redis 未配置时降级为不缓存。

**为什么 LLM 缓存命中率最低？** 因为 prompt 里包含完整对话历史，**只要历史有一个字不同，key 就不同**。所以 LLM 缓存只对"完全相同的重试"或"系统级固定 prompt"有意义。

但有个例外：**`temperature=0` 的确定性场景**。项目里 Agent 调用设了 `temperature=0`（`agent_service.py:260`），这让相同输入产出相同输出——**为缓存创造了条件**，虽然实际命中率依然取决于历史是否一致。

**并行**：LangGraph 里如果模型一次返回多个 `tool_calls`，`tool_node` 应该并发执行它们。串行执行 3 个各 200ms 的工具 = 600ms，并发 = 200ms。

## 41.3 最小可运行骨架

下面的 `minimal_cost.py` 把上面的模型变成可计算的数字。**零依赖，直接跑。**

```python
"""Agent 成本与延迟模型：把"慢"和"贵"变成能算的数。

三件事：
  1. 算 N 轮 ReAct 的 token 总量（揭示 O(N²)）
  2. 算不同优化手段的收益（哪个杠杆最划算）
  3. 演示三层缓存的效果与命中率天花板

跑法：python minimal_cost.py
"""
from __future__ import annotations

import hashlib
import time
from dataclasses import dataclass, field


# ------------------------------------------------------------ token 估算


def estimate_tokens(text: str) -> int:
    """轻量估算：中文 1 字 ≈ 1 token，故按字符/4 会严重低估。

    项目里用 (len+3)//4（agent_service.py:176-190），那是英文经验值，
    对中文偏乐观。这里提供一个更贴近中文的版本做对照。
    """
    chinese = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    rest = len(text) - chinese
    return int(chinese * 1.0 + rest / 4)      # 中文 1 字≈1 token


# ------------------------------------------------------- 成本模型


@dataclass
class Price:
    """每百万 token 单价（美元）。"""
    input_per_m: float
    output_per_m: float


PRICES = {
    "gpt-4o-mini": Price(0.15, 0.60),
    "gpt-4o": Price(2.50, 10.00),
    "deepseek-chat": Price(0.27, 1.10),
}


@dataclass
class Session:
    """一次 ReAct 会话的成本账本。"""
    system_tokens: int = 800
    question_tokens: int = 100
    context_tokens: int = 300      # 每轮注入的检索上下文
    tool_result_tokens: int = 400
    ai_reply_tokens: int = 150

    rounds: int = 5
    model: str = "gpt-4o-mini"

    # 优化开关
    trim_enabled: bool = False     # 上下文裁剪：每轮 prompt 上限
    trim_budget: int = 4000
    cache_enabled: bool = False
    cache_hit_rate: float = 0.30

    log: list[dict] = field(default_factory=list)

    def run(self) -> dict:
        """模拟 N 轮，返回 token 与成本明细。"""
        price = PRICES[self.model]
        total_in = 0
        total_out = 0
        history = 0          # 累积的"历史"部分（AI 回复 + 工具结果）

        for r in range(1, self.rounds + 1):
            prompt = (
                self.system_tokens
                + self.question_tokens
                + self.context_tokens
                + history
            )
            if self.trim_enabled and prompt > self.trim_budget:
                prompt = self.trim_budget

            completion = self.ai_reply_tokens
            total_in += prompt
            total_out += completion

            self.log.append(
                {
                    "round": r,
                    "prompt": prompt,
                    "completion": completion,
                    "cum_in": total_in,
                }
            )
            # 下一轮的历史 = 本轮 AI 回复 + 工具结果
            history += self.ai_reply_tokens + self.tool_result_tokens

        cost_in = total_in / 1_000_000 * price.input_per_m
        cost_out = total_out / 1_000_000 * price.output_per_m
        return {
            "total_in": total_in,
            "total_out": total_out,
            "cost": cost_in + cost_out,
            "cost_per_1k_requests": (cost_in + cost_out) * 1000,
        }

    def with_cache(self) -> dict:
        """开启 LLM 缓存后：命中率内的调用不花钱。"""
        base = self.run()
        saved = base["cost"] * self.cache_hit_rate
        return {**base, "cost": base["cost"] - saved, "saved": saved}


# ------------------------------------------------------- 三层缓存演示


class CacheLayer:
    """一个带统计的缓存层，用来展示命中率天花板。"""

    def __init__(self, name: str):
        self.name = name
        self.store: dict[str, str] = {}
        self.hits = 0
        self.misses = 0

    def _key(self, text: str) -> str:
        return hashlib.md5(text.encode()).hexdigest()

    def get_or_compute(self, text: str, compute) -> str:
        key = self._key(text)
        if key in self.store:
            self.hits += 1
            return self.store[key]
        self.misses += 1
        value = compute(text)
        self.store[key] = value
        return value

    @property
    def hit_rate(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total else 0.0


def demo_cache_layers() -> None:
    print()
    print("=" * 72)
    print("演示：三层缓存的命中率天花板")
    print("=" * 72)

    # 场景：100 次请求，其中文档块只有 20 个不同的（embedding 高命中）
    #       问题有 60 个不同的（检索中等命中）
    #       完整 prompt 有 95 个不同的（LLM 低命中）
    blocks = [f"实验室开放时间说明第 {i % 20} 段" for i in range(100)]
    questions = [f"实验室 {i % 60} 的开放时间？" for i in range(100)]
    prompts = [f"system+history{i}+q{i % 60}" for i in range(100)]   # 历史让它几乎全不同

    embed_cache = CacheLayer("embedding")
    retrieval_cache = CacheLayer("检索结果")
    llm_cache = CacheLayer("LLM 响应")

    for b in blocks:
        embed_cache.get_or_compute(b, lambda x: x.upper())
    for q in questions:
        retrieval_cache.get_or_compute(q, lambda x: x.upper())
    for p in prompts:
        llm_cache.get_or_compute(p, lambda x: x.upper())

    for layer in (embed_cache, retrieval_cache, llm_cache):
        print(f"  {layer.name:<12} 命中率 {layer.hit_rate:>6.1%}   "
              f"(hit={layer.hits}, miss={layer.misses})")
    print()
    print("  → 结论：LLM 缓存命中率天然最低，因为 prompt 含完整历史，")
    print("    历史差一个字 key 就不同。**别指望 LLM 缓存解决成本问题。**")


# ------------------------------------------------------- 延迟演示


def demo_latency() -> None:
    print()
    print("=" * 72)
    print("演示：并行 vs 串行（3 个无依赖工具）")
    print("=" * 72)

    def fake_tool(ms: int) -> str:
        time.sleep(ms / 1000)
        return "ok"

    tools = [200, 180, 250]

    start = time.perf_counter()
    for ms in tools:
        fake_tool(ms)
    serial = (time.perf_counter() - start) * 1000

    # 并发版：真实项目用 asyncio.gather，这里用线程模拟
    import concurrent.futures as cf
    start = time.perf_counter()
    with cf.ThreadPoolExecutor(max_workers=3) as ex:
        list(ex.map(fake_tool, tools))
    parallel = (time.perf_counter() - start) * 1000

    print(f"  串行：{serial:.0f}ms")
    print(f"  并发：{parallel:.0f}ms")
    print(f"  → 省 {serial - parallel:.0f}ms（{(1 - parallel / serial):.0%}）")
    print("  → 每轮 3 个工具 × 5 轮 = 这个差距会乘 5")


if __name__ == "__main__":
    print("=" * 72)
    print("Agent 成本模型：N 轮 ReAct 的 O(N²) 真相")
    print("=" * 72)

    for rounds in (1, 3, 5, 8):
        s = Session(rounds=rounds)
        r = s.run()
        base = Session(rounds=1).run()["total_in"]
        print(
            f"  {rounds} 轮：prompt 累计 {r['total_in']:>6} token   "
            f"是单轮的 {r['total_in'] / base:>5.1f} 倍   "
            f"单次 ${r['cost']:.5f}"
        )
    print()
    print("  ★ 注意：8 轮不是 8 倍，是 22 倍。这就是 O(N²)。")

    print()
    print("=" * 72)
    print("优化杠杆对比：哪个最划算？")
    print("=" * 72)
    baseline = Session(rounds=5).run()
    print(f"  基线（5 轮，无优化）        ${baseline['cost']:.5f}  "
          f"prompt={baseline['total_in']} token")

    fewer = Session(rounds=4).run()
    print(f"  杠杆1：减一轮（5→4）        ${fewer['cost']:.5f}  "
          f"省 {(1 - fewer['cost'] / baseline['cost']):.0%}")

    trimmed = Session(rounds=5, trim_enabled=True, trim_budget=4000).run()
    print(f"  杠杆2：开裁剪（上限4000）    ${trimmed['cost']:.5f}  "
          f"省 {(1 - trimmed['cost'] / baseline['cost']):.0%}")

    cached = Session(rounds=5, cache_enabled=True, cache_hit_rate=0.30).with_cache()
    print(f"  杠杆3：LLM 缓存（命中30%）   ${cached['cost']:.5f}  "
          f"省 {(1 - cached['cost'] / baseline['cost']):.0%}")

    print()
    print("  → 减一轮的收益 ≈ 开缓存的 2 倍，且**不依赖命中率**")

    print()
    print("=" * 72)
    print("模型选择：同样的流量，不同模型的月度账单")
    print("=" * 72)
    for model in PRICES:
        s = Session(rounds=5, model=model)
        r = s.run()
        print(f"  {model:<15} 单次 ${r['cost']:.5f}   "
              f"1万次/天 → ${r['cost_per_1k_requests'] * 10 * 30:>9.2f}/月")

    demo_cache_layers()
    demo_latency()
```

**这说明什么？** 说明**裁剪是一道保险，不是优化手段**。它在长对话时才生效，而"长对话"恰恰是少数场景。想靠裁剪降低成本，前提是你的对话真的会撑爆预算。

**真正的日常成本优化在杠杆 1（减轮次）和杠杆 3（缓存）。**

## 41.4 项目代码定位

### 41.4.1 已做的六个优化

**① 本地 embedding，零 API 成本**（`vector_store.py:31-42`）

```python
def _embed_texts(texts: list[str]) -> list[list[float]]:
    """用本地 sentence-transformers 模型把文本转成向量。"""
    global _sentence_model
    try:
        from sentence_transformers import SentenceTransformer
    except Exception as exc:
        raise RuntimeError("未安装 sentence-transformers，无法进行向量化") from exc

    # 模型加载很重，必须复用同一个实例，不能每次检索都重新加载。
    if _sentence_model is None:
        _sentence_model = SentenceTransformer(EMBEDDING_MODEL)
    return _sentence_model.encode(texts, normalize_embeddings=True).tolist()
```

两个关键点：

- **本地模型**：`BAAI/bge-small-zh-v1.5`，512 维。**embedding 调用每次请求至少 1 次（query）+ 每次入库 N 次**，如果用 API embedding，这部分成本会远超 LLM 成本。本地模型把边际成本降到 0（只吃 CPU）。
- **单例复用**：`_sentence_model` 是模块级全局。模型加载要几秒，**如果每次检索重新加载，接口延迟会+3s**。

**② 启动时预热**（`vector_store.py:493-501` + `main.py:38-44`）

`main.py:38-44` 里还加了 30 秒超时：

try:

**为什么预热重要？** 首次调用时要做三件重活：加载 sentence-transformers 模型（几秒）、连 Chroma（建 client）、跑一次真实检索（触发索引加载）。**不预热，第一个用户的请求会卡 10 秒以上。**

**注意 cache_key 里有两个东西**：

- **`_corpus_version`**：知识库版本号。**上传/删除文档时 `invalidate_cache()` 会递增这个版本号**（`kb_service.py:87-91`）

**版本号进 key 是缓存设计的经典手法**——它把"失效一批 key"变成了"改一个计数器"，避免遍历删除。这叫 **cache key versioning**。

**④ 上下文预算与裁剪**（`config.py:117-127` + `agent_service.py:176-246`）

> ⚠️ **一个已知的精度问题**：`(len+3)//4` 是英文的经验值（1 token ≈ 4 字符）。**中文 1 个字大约 1 token**，所以这个估算对中文会**低估 3-4 倍**。

> 后果：`MAX_CONTEXT_TOKENS=4000` 实际可能允许 12000+ 真实 token 进入上下文。这是一处**已知的、尚未修正的偏差**，面试时可以主动指出。

**⑤ 工具超时与重试**（`config.py:115-118` + `agent_service.py:155-173`）

```python
TOOL_TIMEOUT_SECONDS: float = 30.0
TOOL_MAX_RETRIES: int = 1
```

**超时是性能保护**：一个慢查询工具如果不设超时，会拖住整个图的执行，用户等到 HTTP 网关超时（通常 60s）才失败。**30 秒超时 + 1 次重试**把最坏情况控制在 60 秒内，且错误会以 Observation 形式回填给模型（第 20 章），让它换个思路。

**⑥ 图执行深度上限**（`agent_service.py:333`）

```python
return {"configurable": {"thread_id": thread_id}, "recursion_limit": 10}
```

**这是成本的最后一道闸门。** `recursion_limit=10` 意味着最多 10 个 superstep（第 15 章讲过，一个完整 ReAct 循环约 4 个 superstep），即**最多约 2-3 轮工具调用**。

**如果没有这个限制**，模型陷入"调工具→报错→再调"的死循环，一次请求可能烧掉几十万 token。第 36 章讲过这是**成本攻击**的一种（用户故意诱导死循环）。

**关于 Redis 未配置**：代码是完整的降级设计——

```python
def _cache_get(key: str) -> str | None:
    client = _redis_client()
    if client is None:
        return None
    try:
        return client.get(key)
    except Exception:

```

`_redis_client()` 在 `REDIS_URL` 为空时返回 `None`，且**所有 Redis 异常都被吞掉返回 `None`**。这是正确的降级：**缓存挂了不应该让检索挂掉**。

但副作用是：**你在日志里看不到"缓存没配"这件事**。这个可以补一条启动时的 info 日志。

### 41.4.3 一次请求的实际延迟构成（估算）

```
POST /api/ai/chat/stream
├── JWT 校验                      ~1ms       (本地验签，无 DB)
├── 限流检查                      ~1ms       (Redis 未配则跳过)
├── Checkpointer 加载历史          ~5-20ms    (SQLite/PG 读 checkpoint)
├── ── 进入 Agent ──
│   ├── 第 1 轮 LLM               800-2500ms  ← 主要成本
│   │   ├── 查询改写（若开启）      300-600ms   ← 额外一次 LLM 调用！
│   │   └── 检索（embedding+BM25+rerank）  50-300ms
│   ├── 工具执行                   10-200ms    (DB 查询)
│   ├── 第 2 轮 LLM               900-2800ms  ← prompt 变长了
│   └── ...
├── SSE 流式写回                  贯穿全程
└── 总耗时                        2-8 秒
```

**注意"查询改写"那一行的感叹号**：`QUERY_REWRITE_ENABLED` 开启后，每次检索前要**额外做一次 LLM 调用**（第 28 章）。它把延迟增加 300-600ms、成本增加一次调用。

**这就是为什么它默认关闭**（`config.py:96`）：

```python

```

**这是一个明确的成本/质量权衡**，而且注释里写清楚了"未配置 key 或改写失败时自动回退原始问题"。

## 41.5 踩过的坑

### ⚠️ 坑 1：以为成本是 O(N)，实际是 O(N²)

见 41.1.1。**每一轮都要重发完整历史**，这是 Agent 成本模型的核心。

**后果**：你按"单次调用 0.0003 美元"做预算，实际账单是 10 倍。

**缓解**：`recursion_limit=10` 是硬闸门；`MAX_CONTEXT_TOKENS` 是软闸门。

### ⚠️ 坑 2：`(len+3)//4` 对中文严重低估

**现象**：`MAX_CONTEXT_TOKENS=4000` 但实际送入的 token 远超 4000。

**原因**：`(len+3)//4` 是英文经验值（1 token ≈ 4 字符）。中文 1 个字约 1 token，**低估 3-4 倍**。

项目注释（`config.py:119-121`）说"对中文更友好"——**这个表述不准确**，它的真实优点是"不引入 tiktoken 依赖"，不是"更准"。

**修复方案**：用 `tiktoken` 的 `cl100k_base` 对中文也不准（中文约 1.5-2 token/字，取决于是否被拆分）。务实的做法是**按字符数设预算**：`MAX_CONTEXT_CHARS = 8000`（约合中文 8000 token），或者接入真实的 tokenizer。

**面试时主动指出这一点会加分**——说明你不是照抄配置，而是验证过它的实际效果。

### ⚠️ 坑 3：缓存 key 忘了带版本号

```python
cache_key = f"rag:v{_corpus_version}:{scope}:" + md5(query)
```

如果 key 里没有 `_corpus_version`，**用户上传新文档后，旧答案还会从缓存里出来**——用户会看到"我明明上传了文档，怎么 AI 还是说找不到"。

项目做对了（有版本号 + `invalidate_cache()`），但这个坑很常见。

**通用模式**：任何"依赖外部数据"的缓存，key 里必须有数据版本号，或者接受"数据更新后最长 TTL 时间内不一致"。

### ⚠️ 坑 4：预热没有超时，服务启动被拖死

`warmup()` 里要下载/加载 embedding 模型。网络差时这一步可能几分钟。

项目加了 30 秒超时（`main.py:40`）：

```python
await asyncio.wait_for(asyncio.to_thread(kb_service.warmup), timeout=30)
```

**为什么要超时？** 因为预热失败的代价（首个请求慢）远小于服务起不来的代价（整个系统不可用）。**"降级启动"优于"启动失败"。**

### ⚠️ 坑 5：同步阻塞函数放进 async 链路，整个事件循环卡死

```python
await asyncio.to_thread(kb_service.warmup)     # ✅
await kb_service.warmup                        # ❌ 不存在这种写法
kb_service.warmup()                            # ❌ 阻塞事件循环
```

embedding 编码、PDF 解析、BM25 计算都是 CPU 密集的同步操作。不加 `to_thread`，**一个请求在处理时会阻塞所有其他请求**（第 03 章的核心）。

项目在 `warmup`、`_embed_texts` 调用处都用了 `to_thread`（第 20 章详细讲过）。

### ⚠️ 坑 6：把"感知延迟"当"真实延迟"优化

**现象**：加了流式之后用户说"快多了"，但总耗时没变。

**这其实是正常的**——流式优化的是 TTFB（感知），不是总耗时。但如果你的目标是降低**成本**，流式一点用没有。

**三个目标别混**：
```
降 TTFB → 流式、减少首轮前的串行步骤
降总耗时 → 并行、缓存、减轮次
降成本 → 裁剪、缓存、模型分层、精简 system prompt
```

### ⚠️ 坑 7：`FINAL_CONTEXT_K` 调大的隐性成本

从 3 调到 10，看起来只是"多给点资料更准"。实际：

```
每轮多 7 块 × ~200 token = 1400 token
5 轮 = 7000 额外 token
1 万次/天 × 30 天 = 21 亿额外 token/月
```

**而且第 39 章讲过：`context_precision` 不会惩罚这个**（分母是相关块总数）。所以**这个参数调大，评测指标可能还涨了，只有账单会告诉你真相**。

**这是"指标涨了、成本爆了、评测没发现"的典型场景。**

## 41.6 面试问答

### Q1：Agent 的成本为什么是 O(N²) 而不是 O(N)？

**答**：因为 LLM 是无状态的，每一轮调用都要把完整历史（system prompt + 所有轮次的 AI 回复和工具结果）重新发送一遍。

所以第 n 轮的 prompt 是 n 份基础量，N 轮总共是 `N(N+1)/2` 份。我们算过：5 轮是单轮的 9.6 倍，8 轮是 22 倍。

这个认知决定了优化优先级——**减少一轮工具调用，比换便宜模型更有效**，因为它是从 O(N²) 的尾巴上砍掉一整块。

### Q2：优化 Agent 成本有哪些杠杆？优先级怎么排？

**答**：三个杠杆，按影响量级排序：

**杠杆 1：减少轮次**（O(N²)，影响最大）。手段是工具描述写清楚让模型一次选对、工具粒度别太细免得多轮、prompt 里说明无依赖工具可一次调用多个。

**杠杆 2：减少每轮 token**（线性）。手段是上下文裁剪、控制 `FINAL_CONTEXT_K`、精简 system prompt（它每轮都重发，ROI 最高）、截断工具结果。

**杠杆 3：缓存与并行**。embedding 缓存命中率最高（文档块重复），检索结果中等，LLM 响应最低（prompt 含完整历史，差一个字 key 就不同）。

**常见错误是只做杠杆 3**——因为它最容易做，但缓存有命中率天花板，而减少轮次是稳赚的。

### Q3：为什么 system prompt 精简的 ROI 最高？

**答**：因为 system prompt **每一轮都要重发**。800 token 的 system prompt 走 5 轮就是 4000 token，可能占总成本的 35%。

而其他优化（裁剪、缓存）都是有条件的：裁剪只在超预算时生效，缓存只在命中时生效。**system prompt 精简是"改一次，每次请求都省"，无条件生效。**

### Q4：三层缓存的命中率分别大概多少？为什么 LLM 缓存最低？

**答**：embedding 最高（70-90%，因为文档块重复、入库后就固定），检索结果中等（30-50%，相似问题会重复），LLM 响应最低（5-15%）。

LLM 缓存低的原因是 **prompt 包含完整对话历史，历史差一个字 key 就不同**。所以只有"完全相同的重试"才能命中。

**结论：别指望 LLM 缓存解决成本问题。** 它适合缓存系统级固定 prompt（比如固定的分类任务），不适合多轮对话。

### Q5：你们项目的 token 估算准吗？

**答**：**不准，这是已知问题。** 我们用 `(len+3)//4`（`agent_service.py:176-190`），这是英文的经验值（1 token ≈ 4 字符）。中文 1 个字大约 1 token，所以对中文会**低估 3-4 倍**。

后果是 `MAX_CONTEXT_TOKENS=4000` 实际可能放行 12000+ 真实 token。

注释里写的"对中文更友好"其实不准确，它真正的优点是避免了引入 tiktoken 依赖。要修的话务实方案是按字符数设预算，或者接真实 tokenizer。

### Q6：为什么查询改写默认关闭？

**答**：因为它是**一次额外的 LLM 调用**，每次检索前都要跑，增加 300-600ms 延迟和一次完整的调用成本。

我们把它做成可选开关（`QUERY_REWRITE_ENABLED`，默认 False），并且失败时静默回退原始问题（`kb_service.py:63` 有 warning 日志）。

这是一个明确的成本/质量权衡：**改写能提升召回（第 28 章），但代价是一次 LLM 调用**。在成本敏感场景下关掉，在质量敏感场景下打开。

### Q7：流式输出能降低成本吗？

**答**：**不能。** 流式优化的是**感知延迟**（TTFB），总耗时和 token 消耗完全不变。

如果用户抱怨"慢"，先搞清楚他抱怨的是哪种慢：
- "要等好久才出字" → TTFB 问题 → 流式能解决
- "全部出来要好久" → 总耗时问题 → 流式解决不了，要并行/缓存/减轮次

**三个目标（TTFB / 总耗时 / 成本）的优化手段不一样，别混着谈。**

### Q8：`recursion_limit` 除了防死循环还有什么作用？

**答**：它是**成本闸门**。

模型可能陷入"调工具 → 报错 → 换个参数再调"的循环，如果不限制，一次请求能烧掉几十万 token。而第 36 章讲过，这还可能被用户**故意诱导**（成本攻击）。

我们设 `recursion_limit=10`（`agent_service.py:333`），按"一个完整 ReAct 循环约 4 个 superstep"算，相当于最多 2-3 轮工具调用。超出后 LangGraph 抛 `GraphRecursionError`。

**这是所有 Agent 系统必配的防护，没有之一。**

### Q9：缓存 key 为什么要带知识库版本号？

**答**：因为缓存的内容依赖知识库。如果 key 只有 query 的哈希，用户上传新文档后会继续拿到旧缓存，表现为"我明明上传了文档，AI 还是说找不到"。

我们的做法（`kb_service.py:271-274`）是把 `_corpus_version` 放进 key，文档变更时调用 `invalidate_cache()` 递增版本号。

**这是 cache key versioning 的经典手法**：把"失效一批 key"变成"改一个计数器"，不需要遍历删除，也不依赖 TTL。

### Q10：如果预算有限，你会优先做哪个优化？

**答**：先做**可观测性**（第 40 章），因为没有数据你不知道该优化什么。

有了数据之后，按 ROI：
1. **精简 system prompt**（改一次，无条件生效）
2. **工具描述优化**（减少多轮重试，O(N²) 收益）
3. **开 Redis 检索缓存**（我们代码写好了，只差配 `REDIS_URL`，成本几乎为零）
4. **考虑模型分层**（简单问题用小模型）

**第 3 条在我们项目里是"免费的"**——代码完整实现了降级，只要填个环境变量就生效。这在面试时是个很好的例子：**先写好降级代码，配置留空，随时可以打开。**

## 41.7 速记卡

**成本模型**

```
N 轮 ReAct 的 prompt ≈ N(N+1)/2 × 单轮基础量     ★ O(N²) 不是 O(N)
  5 轮 = 9.6 倍，8 轮 = 22 倍
原因：LLM 无状态，每轮重发完整历史
```

**三个杠杆（按 ROI）**

| 杠杆 | 影响 | 手段 |
|---|---|---|
| 1. 减轮次 | O(N²) | 工具描述、工具粒度、并行调用 |
| 2. 减 token | 线性 | **精简 system prompt**（每轮重发，ROI 最高）、裁剪、控 K |
| 3. 缓存/并行 | 有上限 | embedding 80% > 检索 40% > LLM 5% |

**★ 常见错误：只做缓存。缓存有命中率天花板，减轮次是稳赚的。**

**三层缓存命中率**：embedding 70-90% / 检索 30-50% / **LLM 5-15%**
**★ LLM 缓存低的原因**：prompt 含完整历史，差一个字 key 就不同

**两个延迟概念**
```
TTFB（首字延迟）→ 用户感知的"慢" → 流式可解
总耗时          → 真的慢          → 流式不可解
```

**项目已做**
- 本地 embedding（0 边际成本）+ 单例复用（`vector_store.py:31-42`）
- 启动预热 + 30s 超时降级（`main.py:38-44`）
- 检索缓存，**key 带 `_corpus_version`**（`kb_service.py:271`）
- `MAX_CONTEXT_TOKENS=4000` / `FINAL_CONTEXT_K=3`
- `recursion_limit=10`（**成本闸门**，`agent_service.py:333`）
- `TOOL_TIMEOUT_SECONDS=30` / `TOOL_MAX_RETRIES=1`
- 查询改写默认关（**额外一次 LLM 调用**）

## 41.8 延伸思考

1. **"模型分层路由"具体怎么设计？风险是什么？**
   提示：用一个小模型（或规则）判断问题难度，简单问题走小模型、复杂问题走大模型。风险有三个：① **路由本身有成本**（多一次调用）；② **路由错了代价不对称**——把复杂问题路由给小模型会得到自信的错答案，比多花钱更糟；③ **用户体验不一致**（同样的问法两次得到质量不同的答案）。**缓解**：路由只在"高置信度简单"时才降级，不确定就走大模型；并且把路由决策记进日志，定期审计准确率。

2. **怎么在不损失质量的前提下减少轮次？**
   提示：三个方向。① **工具合并**——把 `query_labs` + `query_equipment` 合成 `query_available_labs(date, require_equipment)`，3 轮变 1 轮；② **工具预执行**——某些信息每次都要用（比如当前用户身份、今天日期），直接在 prompt 或 state 里注入，别让模型用工具去查；③ **few-shot**——在 prompt 里给一个"多工具一次性调用"的示例，模型会模仿。**第三个成本最低，通常收益最明显。**

3. **如果 token 预算砍半，你会砍哪部分？**
   提示：按"每 token 的信息价值"排。① 先砍**冗余的检索上下文**（`FINAL_CONTEXT_K` 3→2，或 rerank 后只留最相关的）；② 砍**历史摘要**（把早期轮次压成一句话，第 19 章的 `summary` 策略）；③ 砍**工具结果的完整 JSON**（改成"前 3 条 + 总数"）；④ **最后才砍 system prompt**（它承载工具描述和安全规则，砍了会引发行为退化）。**顺序背后的原则：砍数据，不砍指令。**

4. **成本优化和评测指标冲突怎么办？**（比如砍 `FINAL_CONTEXT_K` 让 context_recall 下降）
   提示：这本质是一个**多目标决策**，需要显式定义"可接受的质量损失换多少成本"。实务做法：① 先测出 **Pareto 前沿**——把 `FINAL_CONTEXT_K` 从 1 到 10 都跑一遍，画出 (成本, context_recall) 曲线；② 选**拐点**（边际收益开始急剧下降的那个 K），而不是"成本最低"或"质量最高"；③ 把拐点写进配置注释，让下一个改这个参数的人知道为什么。**没有曲线的调参都是拍脑袋。**
