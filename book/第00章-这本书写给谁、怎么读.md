# 第 00 章 · 这本书写给谁、怎么读

## 开篇：一个真实的困境

假设你是一个刚学完 Python 基础、看过几篇 LangChain 教程的开发者。你把官方 Quickstart 跑通了，能问「今天天气怎么样」并让模型调用一个假函数。你很兴奋，把项目写进了简历。

然后面试时发生了这些对话：

> **面试官**：你的 Agent 多轮对话状态存在哪？
> **你**：呃……存在变量里？
>
> **面试官**：服务重启了还能接着聊吗？
> **你**：……不能。
>
> **面试官**：那如果模型要执行一个写数据库的操作，你怎么保证它是安全的？
> **你**：我在 prompt 里写「请谨慎操作」？
>
> **面试官**：对话聊了 50 轮，上下文爆了怎么办？
> **你**：……

这不是你不够聪明，是**教程没教你这些**。

官方 Quickstart 的目标是「让你在 5 分钟内看到效果」，所以它把所有真实工程问题都藏起来了：持久化用内存、工具是假的、没有鉴权、没有并发、没有成本、没有评测。

而这本书的目标正好相反：**把那些被藏起来的东西全部摊开，一个一个解决**。

## 二、这本书的方法论：从代码长出来

### 传统教程的结构

```
概念定义 → 原理解释 → 一个小例子 → 下一章
```

问题：例子之间不连贯，学完是一堆散点，脑子里没有一张网。

### 这本书的结构

```
真实项目里遇到了一个问题
  ↓
为什么会有这个问题（原理）
  ↓
最小骨架：50 行代码复现它
  ↓
项目里是怎么解决的（真实代码 + 行号）
  ↓
这么解决还留下了什么坑
  ↓
面试时怎么讲
```

**每一个知识点都能指着一个真实文件说「在这里，第 XX 行」**。这就是你能讲出来的底气——不是背的，是你真看过、真改过。

### 举个例子：上下文裁剪

传统教程会说：「长对话要裁剪历史，可以用滑动窗口。」

这本书会说：

1. **问题现场**：`agent_service.py:269` 这行原本是 `llm.ainvoke([SystemMessage(...), *state["messages"]])`，全量塞给模型。一个用户聊 30 轮，每轮检索回来 3 段父上下文，累计 4 万 token，模型直接报 `context_length_exceeded`。
2. **原理**：为什么必须保护 tool_calls 和 ToolMessage 的配对？因为 OpenAI 的 API 要求 `tool` 角色的消息必须紧跟在含 `tool_calls` 的 `assistant` 消息后面，拆散了会报 400。
3. **最小骨架**：50 行代码，用一个假的消息列表演示裁剪。
4. **真实实现**：`_trim_messages` 函数，两个策略（滑动窗口 / 摘要），带配对保护。
5. **坑**：中文按字符/4 估算是偏高的，宁可多剪不可越界。
6. **面试**：「你怎么处理长对话？」「为什么不能简单粗暴地删最老的 N 条？」

看到区别了吗？**后者你能讲三分钟，前者你只能讲十秒。**

## 四、贯穿全书的项目：智能实验室预约系统

### 它是什么

一个高校实验室的预约管理系统，核心特色是**用对话的方式完成预约**。

```
用户：下周周三下午有没有空闲的显微镜实验室？
Agent：（调用工具 search_labs）→ 找到 3 个
       （调用工具 check_availability）→ 只有 A301 周二下午空
       李教授的《细胞生物学》实验需要用到 confocal 显微镜，对吗？
用户：对，帮我预约 A301，周三下午 2 点到 5 点
Agent：（调用 create_reservation）→ ⏸️ 暂停，弹出确认卡片
用户：确认
Agent：（执行）→ ✅ 预约成功，单号 R20250117001
```

### 为什么选它做主线

因为它**刚好覆盖 Agent 开发的全部难点**，不多不少：

| 难点 | 项目里怎么体现的 |
|---|---|
| 工具调用 | 查实验室、查设备、查时段、创建预约 |
| 写操作安全 | 创建预约必须人工确认（HITL） |
| 并发冲突 | 两个人同时抢一个时段 |
| 多轮状态 | 「它」指代什么、上周说的偏好 |
| 私有知识 | 实验室规章制度问答（RAG） |
| 引用溯源 | 回答规章制度要能点回原文 |
| 角色权限 | 学生只能预约，管理员能建知识库 |
| 流式体验 | 回答要一个字一个字出来 |

如果选一个「聊天机器人」当主线，上面这些一个都覆盖不到。

### 项目真实规模（这些数字面试可以直接说）

| 指标 | 数值 |
|---|---|
| 后端 Python 代码 | 约 4200 行 |
| 前端 Vue 代码 | 2776 行 / 15 个视图 |
| REST 接口 | 31 个 |
| 数据库表 | 5 张（users / labs / equipments / reservations / kb_documents） |
| 单元/集成测试 | 37 个（全绿） |
| Alembic 迁移 | 2 个版本 |
| 技术文档 | 23 份（课程式）+ 9 份（面试速成） |

> ⚠️ **诚实提示**：31 个接口里只有 5 个是 `async def`，简历上不要写「全异步」。这个坑是写这本书时实测发现的，第 7 章会详细讲 sync/async 怎么取舍。

## 六、怎么读才有效

### 三种常见失败姿势

**姿势一：从头读到尾，不跑代码**
→ 结果：眼睛会了，手不会。面试官一追问「那你说说 tool_calls 的结构」，答不上来。

**姿势二：只抄代码，不想为什么**
→ 结果：能复刻，不能变通。面试官换个场景就卡住。

**姿势三：只看「最小骨架」，跳过「项目代码定位」**
→ 结果：懂原理，但讲不出「我做过」，简历没说服力。

### 推荐姿势：三遍法

**第一遍（理解）**：读原理 + 最小骨架，**必须跑起来**。
每章的最小骨架都是自包含的，复制到一个 `.py` 文件直接 `python xxx.py` 就能看到输出。看到输出才算过。

**第二遍（对照）**：读「项目代码定位」，打开真实项目文件，找到那一行。
**用自己的话**在代码旁写一行注释，解释为什么这么写。写不出来说明没懂。

**第三遍（输出）**：盖住书，把这一章讲给一个假想的面试官听，讲 3 分钟。
卡住的地方就是没掌握的地方。

## 七、关于「几十万字」的说明

这本书确实很长，但不是灌水。长度的来源是三个「不省略」：

### 1. 不省略「为什么」

大多数教程只写「这样做」，这本书要写清楚「不这样做会怎样」。比如：

> 不说「用 `SELECT FOR UPDATE` 加行锁」就完事，
> 而是要说明：不加锁的话，两个事务同时读到「时段空闲」，同时插入，就会**超卖**；
> 而如果用的是 SQLite，行锁是**整库锁**，并发测试会假通过。

### 2. 不省略「完整代码」

每个最小骨架都是**能直接跑的完整文件**，不是代码片段。你会看到：

```python
# 完整可运行，不是伪代码
import asyncio

async def main():
    ...

if __name__ == "__main__":
    asyncio.run(main())
```

### 3. 不省略「真实行号」

每个知识点后面都跟着「项目里在哪」。这不是炫技，是为了让你能**真的打开文件看一眼**。

## 面试问答：关于项目和自学

### Q1：「你这个项目是自己做的还是跟着教程做的？怎么证明？」

**满分答法**：

> 核心的 Agent 部分是我自己设计的。我能说清楚每一个决定背后的取舍，比如：
>
> 持久化我选了 LangGraph 的 checkpointer 而不是自己写 Redis 存 messages，因为 LangGraph 的 `thread_id` 语义天然和「一个会话」对应，而且它能把 interrupt 的状态一并持久化——自己存的话，中断恢复要额外设计状态机。
>
> 另外这个项目里有一半内容是**踩坑踩出来的**，教程不会教你这些。比如 langchain-mcp-adapters 0.3.2 把 `__aenter__` 移除了，`async with` 会抛 `NotImplementedError`，我是翻源码才发现的。再比如 RAGAS 评测里判官模型的噪声会让 faithfulness 虚高，我是做了对照实验才定位的。

**追问防线**：
- 「那你怎么证明 RAGAS 是你自己接的？」→ 讲三个评测陷阱（第 37 章）
- 「代码有多少是抄的？」→ 分层架构是通用模式，但工具定义、审批节点、裁剪策略都是自己写的

### Q2：「Agent 开发和普通后端开发最大的区别是什么？」

**满分答法**：

> 三个根本区别：
>
> **第一，控制流不确定。** 普通后端的执行路径是编译期就定死的，Agent 的执行路径是模型在运行时决定的。这意味着你没法用传统的单测覆盖所有分支，必须靠**确定性注入假模型**来做集成测试（我项目里 37 个测试有一半是这么做的）。
>
> **第二，失败是常态且不可预测。** 普通后端的失败是网络超时、DB 挂了这种明确错误；Agent 的失败是「模型理解错了」「工具参数编错了」「上下文爆了」，这些都要**在运行时兜住并反馈给模型自纠**。所以我给每个工具加了超时 + 重试，失败时把错误 JSON 回填给模型，而不是抛异常中断整个图。
>
> **第三，成本是一等公民。** 普通后端一次请求几毫秒几 KB；Agent 一次对话可能几十秒、几万 token、几毛钱。所以 token 预算、缓存、模型分级（裁判模型和被测模型分离）都变成了架构决策，而不是优化项。

**追问防线**：
- 「那测试怎么做？」→ 假 LLM + 状态断言（第 17 章有实例）
- 「成本控制具体做了什么？」→ 第 41 章

---

### Q3：「你觉得现在 Agent 开发最大的难点是什么？」

**满分答法**（这个问题考深度，要分层答）：

> 我分三层说：
>
> **工程层**：状态管理和可观测性。Agent 的执行是有状态的、循环的、可能中断的，传统 APM 工具看不懂「这一轮对话模型思考了 3 次、调用了 2 个工具、第 2 次失败重试成功」这种链路。我在项目里是用结构化日志 + 关键节点埋点解决的，但说实话这不够，生产上应该接 Langfuse 这类专用工具。
>
> **效果层**：评测难。RAG 的效果不像分类任务有准确率，它依赖 LLM-as-judge，而 judge 本身有噪声。我在项目里踩过：用同一个模型既当被测又当裁判，faithfulness 会虚高，因为模型倾向于认同自己的输出。解决办法是裁判模型和被测模型分离。
>
> **产品层**：什么时候该用 Agent，什么时候不该。我现在的判断标准是：**如果任务路径可以被穷举成流程图，就不要用 Agent**。比如「用户上传发票 → 提取金额 → 入库」，这三步是确定的，写死比让模型规划更可靠更便宜。Agent 适合的是「用户意图发散、路径不可穷举」的场景，比如我项目里「帮我找个下周能做细胞实验的实验室」——这个要查哪些东西，取决于实验室的实际情况。

**追问防线**：
- 「那你项目里有没有不该用 Agent 的地方？」→ 诚实承认：预约确认流程其实可以写死，用 Agent 是为了演示 HITL
- 「Langfuse 怎么接？」→ 第 40 章

### Q4：「你怎么保持技术更新的？AI 领域变化太快了」

**满分答法**：

> 我有两个习惯：
>
> 一是**读源码而不是读博客**。比如这次项目里 langchain-mcp-adapters 版本升级导致 `async with` 失效，中文社区几乎搜不到，我是直接看它的 `__aenter__` 实现才确认是 `NotImplementedError`。这比看二手教程可靠得多。
>
> 二是**用评测来锚定变化**。新技术出来我不马上换，而是把它接到我已有的评测集上跑一遍，看指标是不是真的涨了。比如查询改写这个功能，我做了 A/B 对照才敢用——不然「感觉变好了」是自欺欺人。

**追问防线**：
- 「举个例子说明你读了源码解决了什么问题？」→ MCP 异步加载（第 30 章）
- 「你的评测集怎么建的？」→ 第 37-39 章

---

### Q5：「如果让你重新做这个项目，你会改什么？」

**满分答法**（这题考反思能力，一定要说具体）：

> 三个地方：
>
> **第一，持久化会直接上 PostgreSQL。** 我现在是 SQLite / PG 双后端抽象，但生产环境 SQLite 的行锁是整库锁，并发测试其实是假通过。当时是为了本地跑测试方便，现在看这个便利性不值得。
>
> **第二，评测会一开始就建。** 我是项目做完了才补 RAGAS，导致很多检索参数的调整没有对照数据，只能凭感觉。应该先建评测集，再调参数。
>
> **第三，会拆出独立的工具服务。** 现在工具是进程内函数，MCP 只是可选加载。如果要做真正的工具复用和多语言接入，应该把工具层独立成服务，Agent 只通过 MCP 协议调用——这样工具可以被其他 Agent 甚至其他语言的项目复用。

**追问防线**：
- 「SQLite 行锁具体什么问题？」→ 第 11 章有实测
- 「为什么先建评测集？」→ 第 37 章三个陷阱

## 常见坑

### 坑 1：把「用过」当成「懂了」

很多人的简历写「熟悉 LangChain」，问他「`bind_tools` 之后消息流怎么变的」答不上来。

**这本书的解法**：每个知识点都要求你能讲出「不这么做会怎样」。

### 坑 2：Demo 跑通就以为会了

官方 Quickstart 跑通只需要 20 行代码，但那 20 行里没有任何一个真实工程问题。

**这本书的解法**：每章的「项目代码定位」都是真实项目里处理过问题的代码。

### 坑 3：不敢承认没做过的

简历写 Milvus、Docker，面试官一问「Milvus 的索引类型有哪几种」就露馅。

**这本书的解法**：全书明确标注 ✅实跑 / ⚠️未实跑，面试按这个口径答，任何追问都不虚。

### 坑 4：只学不练

看别人的代码看懂了 ≠ 自己能写。

**这本书的解法**：每章有动手练习，至少做完第 1 题。
