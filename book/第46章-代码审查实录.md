## 46.1 为什么需要：代码审查审的是什么

### 46.1.1 三个层次

大多数人以为代码审查是"看代码写得规不规范"。实际上它要回答三个递进的问题：

```
层次 1：它能不能跑？        → 单测、接口自测（大多数人的审查止步于此）
层次 2：它会不会坏？        → 边界、并发、异常、外部依赖故障
层次 3：它会不会被搞？      → 越权、注入、成本攻击、数据污染
```

**这六个缺陷的分布正好对应这三层**：

| 缺陷 | 层次 | 类型 |
|---|---|---|
| B1 知识库接口越权 | 3 会不会被搞 | 垂直越权（安全） |
| B2 前端无角色守卫 | 3 会不会被搞 | 权限断层 |
| C1 事务边界缺失 | 2 会不会坏 | 异常路径未处理 |
| C2 工具无超时重试 | 2 会不会坏 | 外部依赖故障 |
| C3 MCP 静默失效 | 1 能不能跑 | **防御性代码写反了** |
| C4 上下文无保护 | 2 会不会坏 | 规模增长后崩溃 |

**注意 C3 落在层次 1**——它连"能不能跑"这关都没过，却被埋在最深的防御逻辑里。**这说明：层次 1 的问题也可能藏得非常深。**

### 46.1.2 为什么自己审自己很难

这六个缺陷，有五个是**我自己写的代码**。为什么自己没发现？

**原因一：你测试的是"你预期的路径"**

我测过 kb 接口——用管理员账号测的，一切正常。我从来没想过"用学生账号打这个接口会怎样"，因为**在我的心智模型里，kb 管理页就是管理员用的**。

**审查的价值就是打破这个心智模型。**

**原因二：防御性代码不会被执行到，所以测不出来**

C3 里那段 `if asyncio.get_running_loop(): return None`——它是为了"防止在 async 环境里误调 asyncio.run"而写的。它在同步场景下走的是另一条分支，测试通过；**async 场景下它走了 `return None`，而那条路径我从来没验证过"返回值是不是我想要的"**。

**防御性代码是最容易被漏测的代码**，因为它"看起来"在保护系统。

**原因三：有些问题要"规模"才暴露**

C4 的上下文膨胀，对话 3 轮时完全没问题。要聊 20 轮才炸——而我从来没聊过 20 轮。

**审查就是要在脑子里模拟"规模放大 10 倍"的场景。**

## 46.2 方法论：五维度 × 三级分类

### 46.2.1 五维度（这是审查这个项目的框架）

```
1. 后端分层与工程规范   → 分层是否清晰、异常是否统一、配置是否外置
2. 业务逻辑正确性       → 边界条件、并发、事务
3. 前后端连桥           → 协议对齐、鉴权是否两头都有
4. 核心知识应用         → Agent/RAG 的设计是否合理、有没有更好的做法
5. 测试                 → 覆盖了什么、漏了什么、测试是否真的在测
```

**第 3 条（前后端连桥）是最容易被忽略的维度**——因为前端和后端分属两个心智区域，审查时容易各自看各自的。B2 就是在这个维度上发现的：**后端鉴权做得很好，前端完全没有**，断层了。

### 46.2.2 三级分类

```
阻断级（Blocker）  → 必须修，面试会被直接抓      B1、B2
重要级（Critical） → 影响健壮性，会被追问         C1、C2、C3、C4
建议级（Suggest）  → 加分项，讲出来是亮点         D1~D5
```

**分类的关键是"后果"不是"难度"**。B1（改四个依赖）技术上最简单，但后果最严重（任何登录用户能删知识库），所以是阻断级。

### 46.2.3 审查的六个提问模板

我自己审查时用的六个问题，按这个顺序过一遍每个模块：

```
1. 这个接口谁可以访问？换一个角色会怎样？（→ 抓越权）
2. 如果这一步失败，系统处于什么状态？（→ 抓事务/回滚）
3. 如果它依赖的外部服务挂了/变慢呢？（→ 抓超时/降级）
4. 这条防御分支真的会被执行吗？执行了返回值对吗？（→ 抓 C3 这类）
5. 数据量/对话轮次放大 10 倍呢？（→ 抓 C4 这类）
6. 这个测试在测什么？如果代码错了它会红吗？（→ 抓假测试）
```

**第 6 条很少有人问，但它能抓出"看起来有测试实际上没测到"的情况。**

## 46.3 六个缺陷实录

### 缺陷 B1 · 知识库接口无管理员权限（阻断级）

**怎么发现的**

按提问模板第 1 条逐个接口过。看到 `backend/app/api/kb.py` 的四个接口：

```python
@router.post("/documents/upload")
def upload_document(..., current_user=Depends(get_current_user)):

@router.get("/documents")
def list_documents(..., current_user=Depends(get_current_user)):

@router.delete("/documents/{document_id}")
def delete_document(..., current_user=Depends(get_current_user)):
```

**用的是 `get_current_user`，不是 `get_current_admin`。**

**后果**

任何登录的**普通学生**都可以：

- 上传一个文档，往 RAG 语料里注入内容（**间接提示词注入的入口**，第 36 章）
- 删除全部知识库文档，让 AI 失去所有知识
- 遍历所有文档

**这是一条完整的攻击链**：注入 → 所有用户的 AI 回答被污染。

**根因**

写这批接口时，我心智模型里"知识库管理页 = 管理员用的页面"，所以**下意识用了 `get_current_user`**（反正前端不会给普通用户看到这个入口）。

**忘了根本原则：前端的隐藏不是安全。**

**修法**

四个接口的依赖全部从 `get_current_user` 换成 `get_current_admin`。

**这里有个容易搞错的点**：知识库的**检索**能力不受影响。Agent 的 `search_lab_docs` 工具走的是 `kb_service`，**不经过这个 HTTP 接口**。这个 `/documents/{id}/search` 是管理后台的"单文档内检索"，纯管理功能。

**验证**

新增 `tests/test_auth.py`（2 个用例）：

```python
def test_admin_passes():      # admin 角色放行
def test_student_rejected():  # student 角色抛 403
```

**面试怎么讲**

> "我在自检时发现知识库的四个接口用的是 `get_current_user` 而不是 `get_current_admin`——意味着任何登录学生能上传文档污染 RAG 语料，或者删掉全部知识库。这是我写的时候的默认假设错了——我以为前端不给普通用户看到入口就行，忘了前端隐藏不算安全。改成 admin 依赖并补了两个权限测试。"

**★这句话的价值在于它同时暴露了两件事**：你能发现安全问题，**并且**你能诚实地说出自己当时的错误假设。

### 缺陷 B2 · 前端路由无角色守卫（阻断级）

**怎么发现的**

审查"前后端连桥"维度。后端鉴权看了一遍——很好，每个管理接口都有 admin 依赖。然后看前端 `router/index.js` 的 `beforeEach`：

```javascript
router.beforeEach((to, from, next) => {
  const token = getToken()
  if (to.meta.requiresAuth && !token) {
    next('/login')
  } else {
    next()
  }
})
```

**只判断 token，不判断角色。**

**后果（分两层）**

**表层**：普通学生手动输入 `/kb-manage` 能看到知识库管理页（虽然调用接口会被 403 拒绝，页面会报错）。这是 UX 问题。

**深层**：**前后端鉴权断层**。后端做了 100% 的保护，前端 0%。如果将来有人"顺手"把某个后端接口的 admin 依赖去掉（这种事在迭代中很常见），**前端完全没有第二道防线**。

**纵深防御的意义就在这里**——单靠一层，只要那一层被改坏就全崩。

**修法**

给三个管理页加 `meta: { admin: true }`，`beforeEach` 里加角色判断：

```javascript
if (to.meta.admin && getUser()?.role !== 'admin') {
  next('/')
  return
}
```

**注意 `getUser()` 从 token 解析出 role**——这个信息本来就在 JWT payload 里，前端读得到（第 32 章讲过 JWT 是签名不是加密，payload 可读）。

**验证**

手工验证：用学生账号登录后手动访问 `/kb-manage` → 重定向回首页。

**面试怎么讲**

> "我发现前后端鉴权断层——后端每个管理接口都有 admin 依赖，但前端的 `beforeEach` 只判断 token 不判断角色。虽然单看后端是安全的，但这就是单点防御。我给管理页加了 `meta.admin` 并在守卫里判断角色，形成双重鉴权。不过要说清楚：**前端守卫只是 UX 和纵深防御，真正的防线始终在后端**——删掉前端守卫用 curl 直接打，后端依然 403。"

**★要主动说出最后那句**。很多候选人加了前端守卫就以为安全了，能说清"真正防线在哪"是分水岭。

### 缺陷 C1 · 事务边界缺失（重要级）

**怎么发现的**

按提问模板第 2 条："如果这一步失败，系统处于什么状态？"

看 `reservation_service.create_reservation`：

```python
db.add(reservation)
db.commit()          # ← 如果这里抛异常呢？
db.refresh(reservation)
return reservation
```

**`commit()` 失败没有 `rollback()`。**

**后果**

`commit()` 失败（约束冲突、连接断开、磁盘满）时，Session 处于**脏状态**——未提交的事务还在。这个 Session 如果在连接池里被复用（取决于 SQLAlchemy 的配置和 `get_db` 的实现），**后续请求会带着一个残留的事务**，表现为各种诡异的数据不一致。

而且 `get_db` 只做了 `close()`：

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()      # ← 没有 rollback
```

**根因**

"happy path 思维"——`commit()` 在我的测试里从来没失败过，所以没想过失败路径。

**修法（两层）**

**第一层：service 四处写库**（创建/取消/审核/过期扫描）的 commit 全部包 try/except：

```python
try:
    db.commit()
except Exception:
    db.rollback()
    raise
```

**第二层：`get_db` 兜底**，在 except 分支加 rollback：

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    except Exception:
        db.rollback()      # ← 兜底：覆盖所有请求会话
        raise
    finally:
        db.close()
```

**为什么要两层？** 第一层是"精确处理"（能给出业务级的错误信息），第二层是"兜底"（**防止未来新增的 service 漏写**）。

**这是一个通用的工程模式：精确处理 + 全局兜底。** 只做前者，总有一天有人会漏；只做后者，错误粒度太粗。

**验证**

新增 `test_create_reservation_rolls_back_on_commit_failure`：模拟 commit 失败，断言数据库中没有落库。

**面试怎么讲**

> "我原来的 `commit()` 没有 `rollback()`，`get_db` 也只 close 不 rollback。commit 失败时 Session 会带着未提交事务回到连接池，后续请求可能出现诡异的不一致。修了两层：service 里四处写库的 commit 都包了 try/except 回滚并抛出；`get_db` 里加了 except 分支的 rollback 兜底，防止以后新增 service 时漏写。补了一个测试专门验证 commit 失败后不落库。"

### 缺陷 C2 · 工具调用无超时、无重试（重要级）

**怎么发现的**

按提问模板第 3 条："如果它依赖的外部服务变慢呢？"

看 `tool_node`：

```python
for tool_call in tool_calls:
    try:
        result = await tool.ainvoke(...)
    except Exception as exc:
        result = json.dumps({"error": str(exc)})   # ← 只有错误回填
```

**没有超时，没有重试。**

**后果**

- **超时缺失**：某个工具里的慢查询跑 60 秒，整张图会卡 60 秒。用户等到网关超时（也是 60s）才失败——**而且这时候钱已经烧了**（如果前面已经调过 LLM）。
- **重试缺失**：一次网络抖动就导致整个工具调用失败。虽然错误回填给模型能让它换个思路，但**网络抖动本来重试一次就好了**。

**修法**

新增模块级 `_invoke_tool_with_retry`（`agent_service.py:155-173`）：

```python
async def _invoke_tool_with_retry(tool, args):
    # 1. to_thread：工具里的 DB 查询是同步的，不阻塞事件循环
    # 2. wait_for：单次 30 秒超时
    # 3. 有限重试：TOOL_MAX_RETRIES 次，指数退避 0.2s / 0.4s
```

三个设计点：

1. **`asyncio.to_thread`**——工具内部是同步 SQLAlchemy 调用，直接 await 会阻塞事件循环
2. **`asyncio.wait_for`**——超时 30 秒（`TOOL_TIMEOUT_SECONDS`）
3. **有限重试**——默认 1 次，指数退避。**只重试 1 次**，因为每次重试都是一轮完整的 LLM 调用，成本翻倍

**关于"要不要区分可重试错误"**：第 20 章讲过要分类（网络抖动可重试、参数错误不可重试）。这个实现是**统一重试**，严格来说参数错误也重试了一次——**这是一个未优化的点，面试时可以主动说**。

**验证**

新增 3 个测试：一次成功 / 连续失败重试后回填错误 JSON / 第二次恢复成功。

**面试怎么讲**

> "原来工具执行只有错误回填，没有超时也没有重试。修法是用 `asyncio.to_thread` 把同步的 DB 调用丢到线程池（不阻塞事件循环），`wait_for` 加 30 秒超时，有限重试 1 次加指数退避。失败后回填结构化错误 JSON 给模型让它自纠——这是 ReAct 的核心机制，不能抛异常，抛了模型就没机会修正了。
>
> 有个未优化点：现在是统一重试，没区分错误类型。**参数错误其实不该重试**，重试浪费钱。要改的话是在工具返回的错误里加一个 `retryable` 标记。"

### 缺陷 C3 · MCP 工具在流式场景下永远加载不到（重要级，最隐蔽）

**这是全书最有教学价值的一个缺陷。** 它展示了"看起来正确的防御性代码"如何导致功能静默失效。

**怎么发现的**

按提问模板第 4 条："这条防御分支真的会被执行吗？执行了返回值对吗？"

原来的代码（大意）：

```python
def _load_mcp_tools():
    global _mcp_cache
    if _mcp_cache["tried"]:
        return _mcp_cache["tools"]

    try:
        # 探测当前是否在 async 上下文里
        asyncio.get_running_loop()
        # 在 async 里，不能用 asyncio.run（会报错），所以放弃加载
        return None                      # ★ 问题在这
    except RuntimeError:
        # 不在 async 里，可以安全地用 asyncio.run
        _mcp_cache["tools"] = asyncio.run(_fetch_mcp_tools())
        _mcp_cache["tried"] = True
        return _mcp_cache["tools"]
```

**看出问题了吗？** 这段代码的意图是：

> "如果我在 async 环境里，就不能用 `asyncio.run()`（会抛 RuntimeError），所以放弃加载 MCP。"

但**调用它的 `build_agent` 恰恰是一个 `async def` 函数**——也就是说，**它永远在 async 环境里**，所以 **MCP 工具永远加载不到，永远返回 None**。

**而系统有降级**：MCP 加载失败 → 用本地工具。所以**没有任何报错**，只是"MCP 工具从来没生效过"。

**这就是"静默失效"**：功能 100% 失效，但系统看起来 100% 正常。

**为什么会被写出来？**

因为当时 `langchain-mcp-adapters` 的 `MultiServerMCPClient` 需要用 `async with` 上下文管理器，而有些版本的实现在 async 环境里调用会出问题。所以作者（我）加了这段探测**试图避免在 async 里调用**——**但探测的结果处理反了**：

```
正确的逻辑应该是：在 async 里 → 用 await
                不在 async 里 → 用 asyncio.run
实际写成了：    在 async 里 → 放弃
                不在 async 里 → 用 asyncio.run
```

**"防御"变成了"禁用"。**

**第二个问题：`tried` 标志有竞态**

```python
if _mcp_cache["tried"]:     # ← 检查
    return ...
_mcp_cache["tried"] = True  # ← 赋值
```

两个并发请求同时进来，都能通过检查，**重复建立 MCP 连接**。

**修法**

**① 改成真正的 async**：`_load_mcp_tools` 改成 `async def`，直接 `await client.get_tools()`。`build_tools` 同步改 async，`build_agent` 里 `await` 调用。

**不再需要"探测环境"**——因为在 async 函数里，你本来就该用 `await`，不需要判断。

**关键佐证**：本版本 `langchain-mcp-adapters 0.3.2` 的 `MultiServerMCPClient` **已经移除了上下文管理器**（`__aenter__` 直接抛 `NotImplementedError`），连接是自管理的。所以原来担心的"async 里调用会出问题"**根本不成立**——**这是通过一个依赖升级就消失了的前提**。

**② 用 `asyncio.Lock` + 双重检查替代 `tried` 标志**：

```python
async def _load_mcp_tools():
    global _mcp_cache
    if _mcp_cache["tools"] is not None:
        return _mcp_cache["tools"]
    async with _mcp_lock:               # ← 加锁
        if _mcp_cache["tools"] is None:  # ← 双重检查
            _mcp_cache["tools"] = await _fetch()
    return _mcp_cache["tools"]
```

**"双重检查锁定"（double-checked locking）**是并发初始化的标准模式：第一次检查避免每次都加锁（快路径），第二次检查避免重复初始化。

**验证**

新增 `test_load_mcp_tools_works_in_async_context`——**专门验证在 async 上下文里能拿到工具**。

**注意这个测试的命名**：它不是"测试 MCP 加载"，是"测试**在 async 上下文里**能加载"。**测试名字要指向你真正担心的那个条件。**

**面试怎么讲**

> "这是我踩过最隐蔽的一个坑。原来的 MCP 加载函数用 `asyncio.get_running_loop()` 探测是否在 async 环境里——如果在，就 `return None`，理由是'async 里不能用 asyncio.run'。但调用它的 `build_agent` 本身是 async 函数，所以**它永远走 return None 那条分支，MCP 工具从来没生效过**。而系统有降级到本地工具的逻辑，所以完全没有报错，只是功能静默失效。
>
> 修法是把它改成真正的 async 函数直接 await——因为根本不需要探测环境，在 async 函数里本来就该用 await。后来发现依赖升级后 `MultiServerMCPClient` 已经移除了上下文管理器，原来担心的前提就不存在了。另外 `tried` 标志有竞态，换成了 `asyncio.Lock` + 双重检查。补了一个专门验证 async 上下文的测试。"

**★这个故事的三个价值点**：
1. 你写过**防御性代码**（说明你想过边界）
2. 你能发现它**写反了**（说明你会审查自己的代码）
3. 你能定位到**依赖版本变化**这个根因（说明你查到底了）

---

### 缺陷 C4 · 上下文窗口无上限保护（重要级）

**怎么发现的**

按提问模板第 5 条："对话轮次放大 10 倍呢？"

看 `agent_node`（`agent_service.py:264-270`）：

```python
async def agent_node(state: AgentState):
    messages = state["messages"]        # ← 全量
    response = await model.ainvoke(messages)
```

**没有任何预算管理、没有裁剪。**

**后果（三个，逐个恶化）**

```
第 1 阶段：成本失控    每轮重发完整历史 → O(N²)（第 41 章）
第 2 阶段：延迟变长    prompt 越长 TTFB 越长
第 3 阶段：直接崩溃    超出模型 context window → API 报错 → 整个会话废掉
```

而且**检索返回的父上下文会加速这个过程**——每轮往历史里塞 3 块 × 约 400 token。

**修法**

三个新增（`agent_service.py:176-246`）：

**① `_estimate_tokens`**：`(len+3)//4` 轻量估算，不引入 tiktoken 依赖。

**② `_trim_messages`**：两种策略——
- `sliding_window`：保留最新，丢最早
- `summary`：把丢弃的压成一条摘要占位

**③ 配对保护**：裁剪时**不能拆散 `tool_calls` ↔ `ToolMessage`**，否则 API 报 400（第 19 章讲过索引左移的处理）。

配置：`MAX_CONTEXT_TOKENS = 4000` / `TRIM_STRATEGY = "sliding_window"`。

**验证**

新增 5 个单元测试：估算、裁剪、配对保护、摘要策略。

**已知偏差**（第 41 章讲过，这里重申）：`(len+3)//4` 是英文经验值，**对中文低估 3-4 倍**。所以 `MAX_CONTEXT_TOKENS=4000` 实际可能放行 12000+ token。注释里写的"对中文更友好"其实不准确。

**面试怎么讲**

> "原来的 agent 节点直接把全部 messages 塞给 LLM，没有预算也没有裁剪。多轮对话加上每轮检索返回的父上下文，会一路涨到超出模型窗口。修法是加了 token 估算和裁剪，两种策略——滑动窗口和摘要，默认用滑动窗口因为它更稳（摘要要多一次 LLM 调用，LLM 挂了连裁剪都做不了）。
>
> 最关键的一点是**裁剪不能拆散 tool_calls 和 ToolMessage 的配对**——拆散了 API 直接 400。这个我专门写了单测。
>
> 有个已知偏差：估算用的 `(len+3)//4` 是英文经验值，对中文会低估 3-4 倍，所以 4000 的预算实际可能放行更多。"

## 46.4 一个"审查误报"：幂等性

这一节很重要——**它教你如何对待审查结论本身**。

### 46.4.1 原审查结论

最初审查时，我列了一条：

> **写库工具无幂等键**：`create_lab_reservation` 被模型重复调用（重试或模型行为）会导致重复落库。建议加幂等键（如 `request_id`）。

**看起来完全合理**——第 20 章讲过工具重试，重试就可能导致重复写库。

### 46.4.2 核实后发现：不成立

修复 C2 时逐行核实，发现：

**`create_reservation` 的时段冲突检测已经覆盖了这个问题**：

```python
# 冲突判断覆盖 status in [0, 1] 的重叠（pending + approved）
# 配合 with_for_update() 行锁
```

也就是说：**模型用相同参数重复调用 → 第一次已经写入 → 第二次命中"该时段已预约"→ 被拒绝**。

**不会重复落库。幂等性被现有的并发控制天然覆盖了，不需要额外改表或加幂等键。**

### 46.4.3 还试过一个方案，但放弃了

尝试加应用层"同用户同参数查重"。结果发现：

> 它会破坏并发测试里"两线程抢同一时段应返回 busy"的互斥语义。

也就是说，加了查重之后，**两个不同用户抢同一时段的场景反而处理错了**。

**这是一个典型的"修复引入新 bug"**——如果没有那个并发测试，这个改动会被当成"改进"合进去。

### 46.4.4 这一节的三个教训

**① 审查结论也要验证。** 审查是"怀疑"，不是"判决"。每一条都要回到代码里确认。

**② 已有的防护可能已经覆盖了新问题。** 加防护之前先看现有的机制——**重复防护会互相干扰**（这个例子里查重就破坏了互斥语义）。

**③ 测试是验证审查结论的唯一手段。** 这个误报能被发现，靠的是那个已经存在的并发测试。**没有测试，我就真的会加一个错误的"幂等键"。**

**面试怎么讲**

> "审查时我列了一条'写库工具无幂等键'，但修的时候核实发现**不成立**——`create_reservation` 的时段冲突检测已经覆盖了 status 0/1 的重叠，配合行锁，模型重复调用同样参数会被拒绝，不会重复落库，幂等性被并发控制天然覆盖了。
>
> 我一度加了应用层的同参数查重，**结果发现它破坏了并发测试里'两线程抢同一时段应返回 busy'的语义**，所以放弃了。这件事让我意识到两点：审查结论也要验证；以及**加防护之前先看现有机制，重复防护会互相干扰**。"

**★这是全书最"高级"的一个故事**——它展示的不是"我修了 bug"，是"我推翻了自己的审查结论"。**这是资深工程师的行为模式。**

## 46.5 还没修的五项（诚实清单）

审查还列了五条建议级，都没修。逐条说明**为什么不修**——这个"为什么"本身就是工程判断。

### D1 · 无 LLM 调用日志与可观测性

**状态**：未修（第 40 章给了完整方案）
**为什么不修**：需要引入追踪平台（LangSmith/Langfuse），涉及 prompt 数据出境问题。本地日志方案的骨架我写了（第 40 章），没接进项目是因为这会改动多处代码，而我当时的优先级是先把评测跑通。
**如果做**：优先选**可自部署的 Langfuse**，避免 prompt 出网。

### D2 · 输入校验依赖业务层，schema 层过松

**状态**：未修
**问题**：`ReservationCreateRequest` 的 `date/start_time/end_time` 是裸 `str`，格式没在 Pydantic 层约束。
**为什么不修**：service 层已经做了字符串比较和校验，功能是**正确的**，只是**分层不优雅**。
**如果要改**：用 `field_validator` 加格式约束。**这是一个纯重构，风险低收益中等**——属于"有空就做"的类别。

### D3 · CORS 全开放 + 静态文件无鉴权

**状态**：未修
**问题**：`allow_origins=["*"]`；`/uploads` 挂载的静态文件**完全无鉴权**，任何人猜到 URL 就能访问。
**为什么这个其实更严重**：上传的文档可能是敏感内容（实验数据、个人信息）。**无鉴权静态目录 = 信息泄露**。
**为什么不修**：需要给静态文件加鉴权中间件（`StaticFiles` 本身不支持），要改成自定义路由 + 鉴权依赖。工作量中等。
**面试时怎么说**："这是我知道但没修的一项，风险是上传文件可被任意访问。要修的话是把 `/uploads` 从 StaticFiles 改成带鉴权的路由，或者给文件名加不可猜测的随机前缀（后者改动小，但属于 security by obscurity，不是正解）。"

### D4 · pgvector 里的 SQL 字符串拼接

**状态**：未修（低危）
**问题**：`PgVectorStore` 里有 `f"DROP TABLE {table}"`、`f"CREATE INDEX ... {table}"`，`table` 来自内部常量 `kb_chunks`，**当前不可注入**。
**为什么不修**：不可注入——`table` 是代码里的常量，不是用户输入。
**但风格不统一**：同一段代码里 `existing_dim` 判断用了参数化 `{"t": table}`，建表/删表却没用。**面试容易被追问"为什么这里拼字符串"**。
**如果要改**：加白名单校验，或者加注释说明来源。**最低成本是加注释**——这已经能挡住大部分追问。

### D5 · 查询改写无 A/B 对比数据

**状态**：未修
**问题**：`QUERY_REWRITE_ENABLED=False`，且没有"改写 vs 不改写"的召回对比。
**为什么不修**：要跑 A/B 需要两组评测（第 38 章的检索指标），而每次评测都要调 LLM。优先级低于其它项。
**面试时怎么说**：**如实说这是没有数据支撑的功能**。"改写逻辑写好了有测试有降级，默认关闭，但我没有做改写前后的召回对比，所以不能声称它一定提升效果。"

```

## 46.7 面试问答

### Q1：你的项目做过代码审查吗？发现了什么？

**答**：做过一次完整的五维度审查（后端分层、业务逻辑、前后端连桥、Agent/RAG 核心、测试），发现 6 个真实缺陷，全部修复并补了测试。

**★要给数量（6 个）和分类**——比"发现了一些问题"有说服力得多。

**★这个故事的杀伤力在于"静默失效"四个字**——它说明你理解降级设计的副作用。

这件事让我意识到：**审查结论也要验证**，以及**加防护之前要看现有机制，重复防护会互相干扰**。

**★主动讲自己推翻自己的结论**——这是这一章最加分的一个回答。

### Q4：修复缺陷时怎么保证不引入新问题？

**答**：每个缺陷都配了测试，而且测试要**指向我真正担心的那个条件**。比如 MCP 那个测试叫 `test_load_mcp_tools_works_in_async_context`——不是"测试 MCP 加载"，是"测试**在 async 上下文里**能加载"。

### Q5：有没有发现但没修的？

2. 加防护前先看现有机制，重复防护会互相干扰
```

**未修五项**：D1 可观测性 / D2 schema 校验 / **D3 uploads 无鉴权** / D4 SQL 拼接 / D5 改写无 A/B

## 46.9 全书结语

写到这里，46 章、约 38 万字就结束了。

回顾一下这本书想给你的东西——**不是一份可以背的知识点清单，而是一套"遇到问题时怎么想"的框架**。

全书反复出现的其实是同一个动作：

```
看到一个现象 → 问"它为什么这样" → 找到根因 → 给出可验证的方案 → 说清边界
```

这个动作在每一章都发生过：

- 第 11 章：并发抢时段 → 根因是"检查"和"插入"之间有窗口 → `FOR UPDATE` → 边界是行锁的粒度
- 第 18 章：审批后代码执行两次 → 根因是 interrupt 的"重放"语义 → 幂等化 → 边界是 checkpoint 的结构
- 第 26 章：两路召回分数不可比 → 根因是量纲不同 → RRF 用排名 → 边界是 k=60 的经验性
- 第 39 章：拒答类分数恒为 0 → 根因是指标机制 → 分类打分 → 边界是裁判噪声未根治
- 第 46 章：MCP 不生效 → 根因是防御代码写反 → 改 async → 边界是降级掩盖了失效

**你会发现这些章的"答案"都不是最精彩的部分——"怎么想到"才是。**

最后说三句实话，作为这本书的结尾：

**第一句**：这本书里所有标了 ⚠️ 的地方（Milvus 未实跑、Redis 未配置、token 估算对中文不准、`uploads` 无鉴权、compose 没跑迁移），**都是这个项目真实的未做项**。我没有把它们藏起来，因为**知道自己没做什么，比做了什么更能决定你能走多远**。

**第二句**：你读完这本书，不等于你会了。**唯一能证明你会了的，是你自己敲一遍、跑一遍、然后被一个 bug 卡住两天。** 第 43 章那 21 天路线图存在的意义就是这个——它逼你产出"卡住过"的经验，而那正是面试时唯一有价值的东西。

**第三句**：Agent 这个领域变化极快。你现在学的 LangGraph API 半年后可能就变了（第 39 章坑 6 讲过 RAGAS 0.3→0.4 的大改）。**但底层的东西不会变**：状态机、上下文预算、工具的错误处理、检索的评估口径、降级的副作用。**这本书真正想教的，是那些不会变的部分。**

祝你在面试里被追问时，能笑着说出那句：

> "这个我真的跑过，而且我踩过坑。"
