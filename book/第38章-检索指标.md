# 第 38 章 · 检索指标：Hit@K、MRR、nDCG 到底在衡量什么

> **这一章要回答的核心问题**：三个指标各自的"性格"是什么？为什么有了 Hit@3 还要 MRR？nDCG 的那个 `log₂` 从哪来？本项目的实现有什么简化？

---

## 38.1 引子：为什么需要三个指标

假设两次检索结果（✅ = 正确文档）：

```
查询A: [✅, ❌, ❌, ❌, ❌]     正确答案排第 1
查询B: [❌, ❌, ✅, ❌, ❌]     正确答案排第 3
```

**只看 Hit@3**：两个都是 1.0（在 Top-3 里）。**但它们显然不一样** —— 查询 A 的体验好得多（第一个就是对的）。

**所以需要一个"考虑排名"的指标**。这就是 MRR 和 nDCG 存在的理由。

**三个指标的分工**：

| 指标 | 回答的问题 | 是否考虑排名 |
|---|---|---|
| **Hit@K** | 前 K 条里**有没有**正确答案？ | ❌ 不考虑 |
| **MRR** | 正确答案**平均排第几**？ | ✅ 考虑（但只看第一个） |
| **nDCG@K** | 前 K 条**整体排序质量**如何？ | ✅ 考虑（且有多级相关性） |

---

## 38.2 Hit@K：最简单也最粗暴

### 38.2.1 定义

```
Hit@K = 1  如果正确答案在 Top-K 里
Hit@K = 0  否则
```

整体分数 = 所有查询的平均值（等价于"命中率"）。

### 38.2.2 含义与局限

**含义**：召回能力的最粗粒度衡量 —— "我有没有找到？"

**局限**：
- 不区分第 1 名和第 K 名
- 不区分"找到 1 个"和"找到 K 个"（多答案场景）
- **K 的选择很主观**（K=1? 3? 5? 10?）

### 38.2.3 K 怎么选

**取决于下游用了几条**：

```
如果最终只把 Top-1 送进 prompt → 应该关注 Hit@1
如果送 Top-5 → 关注 Hit@5
```

**本项目**：`FINAL_CONTEXT_K=5`，但评测用的是 `Hit@1` 和 `Hit@3`。

> ⚠️ **这是一个轻微的不一致**：生产用 5 条，评测看 1 和 3。**更合理的是评 Hit@5**（或者直接评 Hit@1/3/5 都看，画一条曲线）。
>
> 不过 Hit@1 有独立价值——它衡量"最好的那条对不对"，这对 RAG 很关键（第 27 章讲过 rerank 主要提升的就是第一名）。

## 38.3 MRR：正确答案排第几

### 38.3.1 定义

```
MRR = (1/|Q|) × Σ  1 / rankᵢ
                i∈Q
```

其中 `rankᵢ` 是第 i 个查询里**第一个**正确答案的名次（从 1 开始）。没找到就是 0。

### 38.3.2 例子

```
查询A: 正确答案排第 1  → 1/1 = 1.0
查询B: 正确答案排第 3  → 1/3 = 0.33
查询C: 没找到          → 0
MRR = (1.0 + 0.33 + 0) / 3 = 0.44
```

### 38.3.3 为什么要"倒数"

因为**排名越靠前，价值增长是超线性的**。第 1 名和第 2 名的差距，远大于第 10 名和第 11 名。

`1/rank` 曲线：

```
rank=1  → 1.00
rank=2  → 0.50   （掉了 50%）
rank=3  → 0.33   （又掉 33%）
rank=5  → 0.20
rank=10 → 0.10
```

**这个衰减曲线符合直觉**：从"第 2 变第 1"是巨大提升，从"第 11 变第 10"几乎无感。

### 38.3.4 项目实现

`evaluate_rag.py:31-35`：

```python
def _mrr(expected: str, sources: list[str]) -> float:
    for rank, source in enumerate(sources, start=1):
        if source == expected:
            return 1 / rank
    return 0.0
```

**注意 `sources` 是去重后的**（`_sources()` 函数）：

```python
def _sources(hits: list[dict]) -> list[str]:
    """按顺序取出每个命中的源文档名，并去重。"""
    seen = []
    for hit in hits:
        source = (hit.get("meta") or {}).get("source") or ""
        source = source.replace(".md", "")
        if source and source not in seen:
            seen.append(source)
    return seen
```

**为什么要去重？**

因为检索命中的是**块**，多个块可能来自同一份文档。如果按块算名次：

```
[文档甲#0, 文档甲#1, 文档甲#2, 文档乙#0]  → 文档乙排第 4
```

但**从"文档"的角度看，文档乙其实是第 2 个不同文档**。

**本项目的标注粒度是"文档"**（`expected_source` 是文档名），所以指标要在文档粒度算 → 去重。

> **这是一个重要的细节**：**标注粒度和指标粒度必须一致**。如果标注"应该命中哪个块"，就按块算；标注"哪份文档"，就按文档算。混着算会得到无意义的数字。

### 38.3.5 MRR 的局限

**只看第一个正确答案**，忽略后续。

对于"只有一个正确答案"的场景（比如 FAQ），MRR 很合适。
对于"多个相关文档"的场景（比如开放性问题需要综合多份资料），MRR 会低估。

## 38.4 nDCG：考虑多级相关性的排序质量

### 38.4.1 从 CG 到 nDCG

**CG（Cumulative Gain，累积增益）**：

```
CG@K = Σ relᵢ        （前 K 条的相关性分数之和）
```

不考虑位置。**问题**：[高, 低] 和 [低, 高] 得分一样。

**DCG（Discounted CG，折扣累积增益）**：

```
DCG@K = Σ  relᵢ / log₂(i + 1)
```

**加了"位置折扣"**：排得越靠后，同样的相关性贡献越小。

**那个 `log₂(i+1)` 的由来**：

```
i=1: log₂(2) = 1     → 折扣 1/1 = 1.0
i=2: log₂(3) = 1.58  → 折扣 1/1.58 = 0.63
i=3: log₂(4) = 2     → 折扣 1/2 = 0.5
i=4: log₂(5) = 2.32  → 折扣 0.43
```

**为什么用 log 而不是线性（1/i）？** 因为 log 的衰减更平缓，更符合用户"往下翻几屏"的实际行为（用户会看前几条，但不会严格只看第 1 条）。这是信息检索领域几十年的经验选择。

**nDCG（normalized DCG）**：

```
nDCG@K = DCG@K / IDCG@K
```

`IDCG`（Ideal DCG）是"完美排序"下的 DCG。**归一化到 [0, 1]**，让不同查询可比。

### 38.4.2 本项目的实现（简化版）

`evaluate_rag.py:38-42`：

```python
def _ndcg_at_k(expected: str, sources: list[str], k: int) -> float:
    for rank, source in enumerate(sources[:k], start=1):
        if source == expected:
            return 1 / math.log2(rank + 1)
    return 0.0
```

**这是一个高度简化的版本**，值得说清楚：

| 简化 | 说明 |
|---|---|
| **相关性只有 0/1** | 没有多级相关性（真实 nDCG 支持 rel=0/1/2/3） |
| **只找第一个正确答案** | 和 MRR 的逻辑几乎一样 |
| **没有除以 IDCG** | 因为只有 1 个正确答案时，IDCG = 1/1 = 1，除法等于不变 |

**所以在"只有一个正确答案 + 二值相关性"的前提下，nDCG@K 就等于"带 log 折扣的倒数排名"**。

**它和 MRR 的唯一区别是折扣函数**：

```
MRR:     1 / rank          线性倒数
nDCG:    1 / log₂(rank+1)  log 折扣（衰减更慢）
```

对比：

| rank | MRR | nDCG |
|---|---|---|
| 1 | 1.00 | 1.00 |
| 2 | 0.50 | 0.63 |
| 3 | 0.33 | 0.50 |
| 5 | 0.20 | 0.39 |
| 10 | 0.10 | 0.29 |

**nDCG 对"排得靠后"更宽容**（第 10 名还有 0.29，MRR 只有 0.10）。

> **面试可以说**："我们的 nDCG 是简化版——因为标注里每个问题只有一个期望文档、相关性是二值的，此时 IDCG=1，nDCG 就退化成'带 log 折扣的倒数排名'。它和 MRR 的唯一区别是折扣函数：MRR 用 1/rank（线性倒数），nDCG 用 1/log₂(rank+1)（log 折扣，衰减更慢，对靠后位置更宽容）。
>
> 完整的 nDCG 支持多级相关性（rel=0/1/2/3）和多个相关文档，我们的简化在单答案场景下是等价的。"

### 38.4.3 什么时候必须用完整 nDCG

- **多个相关文档**（需要综合多份资料）
- **多级相关性**（有些文档非常相关，有些只是沾边）
- **需要跨数据集对比**（因为不同数据集的"理想排序"不同，必须归一化）

## 38.5 三个指标的选型建议

| 场景 | 推荐指标 |
|---|---|
| 快速看"找没找到" | **Hit@K** |
| 单答案、强调"第一个要对" | **MRR** |
| 多答案、多级相关性 | **nDCG@K** |
| 生产监控 | Hit@K（简单、稳定）+ 一个考虑排名的 |
| 论文/对外汇报 | nDCG@K（最"标准"、可比性强） |

**实务建议：三个都看**，因为它们从不同角度反映问题：

```
Hit@3 高但 MRR 低   → 能找到，但总是排在后面 → 该上 rerank
Hit@3 低            → 召回有问题 → 该扩大召回宽度 / 改切块 / 加混合检索
Hit@1 低但 Hit@3 高 → 第一名不准 → 典型的 rerank 收益场景
```

**三种策略的定义**：

```python
STRATEGIES = {
    "vector": lambda q: kb_service._vector_search(q, top_k=5),
    "hybrid": lambda q: kb_service._rrf_fusion(
        kb_service._vector_search(q, top_k=5),
```

**注意**：这三个是**递进**的，正好构成一个消融实验：

```
vector          基线
hybrid          加了 BM25 + RRF
hybrid+rerank   再加交叉编码器
```

**对比它们，就能量化每一层的贡献**（虽然第 37 章讲了当前评测集饱和，区分度不够）。

> ⚠️ **注意 `kb_service.retrieve` 会做查询改写**（`QUERY_REWRITE_ENABLED`），所以 `hybrid+rerank` 这一路实际上**包含了改写**。如果想严格对比"rerank 的贡献"，应该关掉改写。
> **这是一个实验设计的不严谨之处** —— 变量没有隔离。第 37 章讲的"A/B 实验"原则在这里没完全做到。

### 拒答用例的处理

```python

```

`labeled_pairs()` 返回的是 `(question, expected_source)` 对，**拒答用例（`expected_source=None`）被过滤掉了**（在 `eval_dataset.labeled_pairs()` 里）。

**这是正确的处理** —— 拒答问题没有"应命中的文档"，强制算检索指标会污染分数。

## 38.7 最小骨架：三个指标的手算

```python
"""
minimal_metrics.py —— Hit@K / MRR / nDCG 手算与对比
运行：python minimal_metrics.py  （纯 Python）
"""
import math


def hit_at_k(expected, retrieved, k=3):
    """前 K 条里有没有正确答案？不考虑名次。"""
    return 1.0 if expected in retrieved[:k] else 0.0


def mrr(expected, retrieved):
    """正确答案的平均倒数排名。只看第一个。"""
    for rank, item in enumerate(retrieved, start=1):
        if item == expected:
            return 1 / rank
    return 0.0


def ndcg_at_k(expected, retrieved, k=3):
    """简化版：单答案 + 二值相关性时，等于带 log 折扣的倒数排名。"""
    for rank, item in enumerate(retrieved[:k], start=1):
        if item == expected:
            return 1 / math.log2(rank + 1)
    return 0.0


def ndcg_full(rels, k=3):
    """完整版 nDCG：支持多级相关性。rels 是相关性分数列表。"""
    dcg = sum(r / math.log2(i + 2) for i, r in enumerate(rels[:k]))
    idcg = sum(r / math.log2(i + 2) for i, r in enumerate(sorted(rels, reverse=True)[:k]))
    return dcg / idcg if idcg else 0.0


# ── 演示 ────────────────────────────────────────────────────
CASES = [
    # (检索结果列表, 正确答案)
    (["甲", "乙", "丙", "丁"], "甲"),    # 第 1 名就对
    (["乙", "丙", "甲", "丁"], "甲"),    # 第 3 名
    (["乙", "丙", "丁", "甲"], "甲"),    # 第 4 名（Top-3 没命中）
    (["乙", "丙", "丁", "戊"], "甲"),    # 没找到
]

if __name__ == "__main__":
    print(f"{'结果':<24} {'Hit@3':>7} {'MRR':>7} {'nDCG@3':>8}")
    print("-" * 50)
    tot_h = tot_m = tot_n = 0
    for retrieved, expected in CASES:
        h = hit_at_k(expected, retrieved)
        m = mrr(expected, retrieved)
        n = ndcg_at_k(expected, retrieved)
        tot_h += h; tot_m += m; tot_n += n
        pos = retrieved.index(expected) + 1 if expected in retrieved else "未命中"
        print(f"{str(retrieved):<24} {h:>7.2f} {m:>7.2f} {n:>8.2f}   (第{pos}名)")

    n = len(CASES)
    print("-" * 50)
    print(f"{'平均':<24} {tot_h/n:>7.2f} {tot_m/n:>7.2f} {tot_n/n:>8.2f}")

    print("\n【★ 关键对比：Hit@3 相同的两条】")
    a = (["甲", "乙", "丙"], "甲")     # 第 1
    b = (["乙", "丙", "甲"], "甲")     # 第 3
    for name, (ret, exp) in [("第1名命中", a), ("第3名命中", b)]:
        print(f"  {name}: Hit@3={hit_at_k(exp, ret):.2f}  "
              f"MRR={mrr(exp, ret):.2f}  nDCG@3={ndcg_at_k(exp, ret):.2f}")
    print("  → Hit@3 都是 1.0，但 MRR/nDCG 差异明显 ★ 这就是需要它们的原因")

    print("\n【折扣函数对比】")
    print(f"  {'rank':<6}{'MRR(1/rank)':>14}{'nDCG(1/log2(r+1))':>20}")
    for r in (1, 2, 3, 5, 10):
        print(f"  {r:<6}{1/r:>14.2f}{1/math.log2(r+1):>20.2f}")
    print("  → nDCG 衰减更慢，对靠后位置更宽容")

    print("\n【完整版 nDCG（多级相关性）】")
    print(f"  rels=[3,2,1] 理想排序  nDCG={ndcg_full([3,2,1]):.3f}")
    print(f"  rels=[1,2,3] 最差排序  nDCG={ndcg_full([1,2,3]):.3f}")
```

**预期输出（关键部分）**：

```
【★ 关键对比：Hit@3 相同的两条】
  第1名命中: Hit@3=1.00  MRR=1.00  nDCG@3=1.00
  第3名命中: Hit@3=1.00  MRR=0.33  nDCG@3=0.50
  → Hit@3 都是 1.0，但 MRR/nDCG 差异明显 ★ 这就是需要它们的原因

【折扣函数对比】
  rank  MRR(1/rank)  nDCG(1/log2(r+1))
  1          1.00                1.00
  2          0.50                0.63
  3          0.33                0.50
  5          0.20                0.39
  10         0.10                0.29
```

## 38.8 面试问答

### Q1：Hit@K、MRR、nDCG 有什么区别？

**答**：三个指标从不同角度衡量。

**Hit@K** 只问"前 K 条里有没有正确答案"，**不考虑名次**。优点是简单直观，缺点是不区分第 1 名和第 K 名。

**MRR** 用倒数排名 `1/rank`，衡量"正确答案平均排第几"。考虑了名次，但**只看第一个正确答案**。

**nDCG@K** 用 log 折扣 `1/log₂(rank+1)`，衡量前 K 条的**整体排序质量**，完整版还支持**多级相关性**（rel=0/1/2/3）。

**为什么需要三个**：Hit@3 相同（都是 1.0）的两个结果，一个第 1 名命中、一个第 3 名命中，体验完全不同——MRR 是 1.0 vs 0.33，nDCG 是 1.0 vs 0.5。

### Q2：nDCG 的 log₂ 从哪来？

**答**：这是信息检索领域的经验选择。

DCG 的公式是 `Σ relᵢ / log₂(i+1)`，那个 `log₂(i+1)` 叫**位置折扣**——排得越靠后，同样的相关性贡献越小。

**为什么用 log 而不是线性 1/i？** 因为 log 衰减更平缓，更符合用户行为：用户会看前几条，但不会严格只看第 1 条。对比一下：第 10 名在 MRR 里只有 0.10，在 nDCG 里还有 0.29。

`n` 是 normalized——除以"完美排序"的 IDCG，归一化到 [0,1]，让不同查询可比。

### Q3：你们的 nDCG 实现有什么简化？

**答**：是简化版。因为我们的标注里**每个问题只有一个期望文档**、相关性是二值的（0/1），此时 IDCG = 1/1 = 1，除法等于不变，nDCG 就退化成"带 log 折扣的倒数排名"。

**它和 MRR 的唯一区别就是折扣函数**：MRR 用 `1/rank`（线性），nDCG 用 `1/log₂(rank+1)`（log，衰减更慢）。

完整的 nDCG 支持多级相关性和多个相关文档，我们的简化在单答案场景下是等价的。如果以后要支持"这个问题需要综合 3 份文档"这类场景，就要改用完整版。

### Q4：为什么 `_sources` 要去重？

**答**：因为**标注粒度和指标粒度要一致**。

我们的 `expected_source` 标注的是**文档名**，但检索命中的是**块**——多个块可能来自同一份文档。

如果不去重，结果是 `[文档甲#0, 文档甲#1, 文档乙#0]`，文档乙排第 3。但从"文档"的角度看它是第 2 个不同文档。

混着算会得到无意义的数字。所以先在文档粒度去重，再算名次。

### Q5：K 怎么选？

**答**：取决于下游用了几条。如果最终把 Top-5 送进 prompt，就该关注 Hit@5。

我们生产用 `FINAL_CONTEXT_K=5`，但评测用的是 Hit@1 和 Hit@3——**这是一个轻微的不一致**，更合理的做法是评 Hit@5 或者三个都看（画一条曲线）。

不过 Hit@1 有独立价值：它衡量"最好的那条对不对"，而 rerank 主要提升的就是第一名。所以 Hit@1 对评估 rerank 收益特别敏感。

### Q6：三个指标怎么组合看问题？

**答**：它们的组合能定位问题类型：

- **Hit@3 低** → 召回有问题 → 扩大召回宽度、改切块、加混合检索
- **Hit@3 高但 MRR 低** → 能找到但总排后面 → **该上 rerank**
- **Hit@1 低但 Hit@3 高** → 第一名不准 → 典型的 rerank 收益场景
- **nDCG 和 MRR 差距大** → 说明很多答案排在 3-5 名，Top-3 截断损失大

### Q7：你们的实验设计有没有不严谨的地方？

**答**：有。三种策略的对比里，`hybrid+rerank` 走的是 `kb_service.retrieve`，而它会做**查询改写**（如果 `QUERY_REWRITE_ENABLED=true`）。所以这一路实际上包含了改写的影响，**变量没有隔离**。

严谨的做法是：要测 rerank 的贡献，应该在**关闭改写**的条件下对比 `hybrid` 和 `hybrid+rerank`。

另外第 37 章讲了评测集饱和的问题——三种策略分数几乎一样，说明当前评测集区分度不够，需要先扩充语料和难例，再做消融实验。

## 38.9 速记卡

> **Hit@K（有没有）/ MRR（第几名）/ nDCG（整体排序质量）。**

**Hit@K**：`1 if expected in top_k else 0`，**不考虑名次**

**MRR**：`1/rank`（只看第一个正确答案），衰减快

**nDCG@K**：`1/log₂(rank+1)`（简化版），衰减慢、对靠后宽容
- 完整版支持**多级相关性** + 归一化（除以 IDCG）

**折扣对比**（第 10 名）：MRR=0.10，nDCG=0.29

**★ 标注粒度 = 指标粒度**：标文档就按文档去重后算，标块就按块算

**K 的选择**：跟随下游实际用几条

**组合诊断**：
```
Hit@3 低            → 召回问题 → 扩宽度/改切块/混合检索
Hit@3 高 MRR 低     → 排序问题 → rerank
Hit@1 低 Hit@3 高   → 第一名不准 → rerank 收益场景
```

**★ 本项目简化**：单答案 + 二值相关性 → nDCG 退化为"log 折扣倒数排名"
**★ 实验不严谨**：`hybrid+rerank` 含查询改写，变量未隔离

**代码位置**：`evaluate_rag.py:22-52`

## 38.10 延伸思考

1. **如果要支持"这个问题需要综合 3 份文档"，指标要怎么改？**
   提示：改成多答案标注（`expected_sources: list`），用**完整 nDCG**（多级相关性）或 **Recall@K**（K 条里召回了几个应召回的）。Hit@K 也要改成"至少命中一个"还是"全部命中"的口径约定。**标注的变化会牵动整个评测实现**。

2. **检索指标好，但用户还是不满意，可能是什么原因？**
   提示：① 检索对了但**生成错了**（模型没用好资料）→ 看 faithfulness；② 检索的块**上下文不完整**（第 29 章的父上下文问题）；③ 答案虽然对但**没引用出处**，用户无法验证；④ **UI 问题**（加载慢、Markdown 渲染错）。**检索指标只是全链路的一环。**

3. **能不能用"模型最终答对了吗"作为唯一指标？**
   提示：可以（这叫端到端指标），但它**无法定位问题**——答错了你不知道是检索错还是生成错。所以实务上是**分层评测**：检索指标定位检索问题、生成指标定位生成问题、端到端指标看最终结果。**三层都有价值。**
