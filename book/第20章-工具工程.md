# 第 20 章 · 工具工程：超时、重试、错误回填与身份注入

> **这一章要回答的核心问题**：`@tool` 装饰器背后做了什么？工具函数怎么拿到数据库会话和当前用户？为什么要放线程池里跑？超时和重试怎么实现才不会拖垮整个 Agent？MCP 工具为什么要用异步锁？

---

## 20.1 引子：一个工具卡死，整个服务跟着卡

想象这个场景。你的 `search_lab_docs` 工具内部有一个数据库查询，某天数据库慢了，一个查询要 60 秒。

你的 Agent 图在等它。而 FastAPI 的 worker 在等 Agent。用户在浏览器前等。

**一分钟过去，用户关掉页面。但请求还在跑，worker 还被占着。** 十个这样的请求同时进来，你的服务就耗尽了 worker 池，全部请求开始排队——**整个系统雪崩**。

再想象另一个场景：工具因为网络抖动失败了，抛了个异常。如果没处理好，整个 Agent 循环中断，用户看到"大模型调用失败"，但他根本不知道发生了什么，只能重新问一遍（再烧一遍 token）。

**工具工程要解决的就是这两类问题**：
1. **不让工具拖垮系统**（超时、并发隔离）
2. **不让工具失败毁掉会话**（重试、错误回填）

这一章我们把 `agent_tools.py` 和 `_invoke_tool_with_retry` 完整拆开。

## 20.2 `@tool` 装饰器：一行代码背后发生了什么

### 20.2.1 基本用法

`agent_tools.py:96-117`：

```python
@langchain_tool
def list_open_labs(keywords: str = "") -> str:
    """查询开放的实验室列表。"""
    try:
        keywords = keywords.strip() or None
        page = lab_service.get_lab_page_list(
            db, page=1, page_size=10, keywords=keywords, status=1
        )
        rows = [ {...} for item in page.list ]
        return json.dumps({"total": page.total, "labs": rows}, ensure_ascii=False)
    except Exception as exc:
        return json.dumps({"ok": False, "error": str(exc)}, ensure_ascii=False)
```

看起来就是一个普通函数加了个装饰器。但这个装饰器做了四件事：

### 20.2.2 ① 读取函数签名，生成 JSON Schema

LangChain 用 Python 的 `inspect` + 类型注解，自动生成给模型看的 schema：

```python
{
  "type": "function",
  "function": {
    "name": "list_open_labs",
    "description": "查询开放的实验室列表。",
    "parameters": {
      "type": "object",
      "properties": {
        "keywords": {"type": "string", "default": ""}
      },
      "required": []          # 有默认值 → 不 required
    }
  }
}
```

**这就是"docstring 即 prompt"的原理**。模型看到的是这段 JSON，不是你的 Python 代码。

**推论**：**docstring 和参数名直接决定模型会不会用对工具**。这是工具工程第一原则。

看几个对比：

```python
# ❌ 糟糕：模型不知道什么时候该用
@tool
def search(q: str) -> str:
    """搜索"""

# ❌ 一般：说了干什么，但没说什么时候用
@tool
def search_lab_docs(query: str) -> str:
    """检索知识库"""

# ✅ 好：说明了内容范围和使用时机
@tool
def search_lab_docs(query: str) -> str:
    """根据用户的提问检索知识库，包含系统内置文档和用户上传的文档。
    适用于询问实验室规则、安全须知、开放时间等问题。"""
```

本项目的做法更进一步——**docstring 是动态生成的**（`agent_tools.py:88-93`）：

```python
_search_lab_docs.__name__ = "search_lab_docs"
_search_lab_docs.__doc__ = (
    "根据用户的提问检索知识库，包含系统内置文档和用户上传的文档。"
    if include_uploaded
    else "根据用户的提问检索系统内置知识库，不包含用户上传的文档。"
)
search_lab_docs = langchain_tool(_search_lab_docs)
```

**为什么？** 因为用户可以在前端勾选"是否包含我上传的文档"（`include_uploaded`）。如果不改 docstring，模型就不知道当前检索范围是什么，可能给出错误回答（比如用户问"我上传的文档里说了什么"，而工具实际只检索了内置文档）。

> **这是一个很聪明的细节**：**让工具描述反映运行时状态**。面试时讲这个会很加分。

### 20.2.3 ② 参数类型注解决定入参校验

```python
def list_lab_equipments(lab_id: int, keywords: str = "") -> str:
```

`lab_id: int` → schema 里是 `{"type": "integer"}`。模型如果传了字符串 `"3"`，LangChain 的 Pydantic 校验会尝试转换，失败则报错。

**注意 `int | None` 的写法**（`agent_tools.py:151-152`）：

```python
equipment_id: int | None = None,
remark: str | None = None,
```

这是 Python 3.10+ 的联合类型语法。生成的 schema 是 `{"anyOf": [{"type": "integer"}, {"type": "null"}]}`。

**为什么要显式声明可选？** 因为预约实验室时不需要设备 ID，预约设备时才需要。如果不给默认值，模型会**被迫填一个值**（可能编造一个 equipment_id）。

### 20.2.4 ③ 返回值统一为 `str`

本项目所有工具都返回 `str`（JSON 序列化后的字符串）。为什么不让它们返回 dict？

因为 **ToolMessage 的 content 必须是字符串**（或者是可被模型理解的多模态结构）。返回 dict 会：

- 被 `str()` 强转成 Python 的 `{'a': 1}` 格式（单引号，模型解析困难）
- 或者报错

**统一 `json.dumps(..., ensure_ascii=False)`** 的好处：

| 好处 | 说明 |
|---|---|
| 模型好解析 | 标准 JSON，模型训练语料里大量出现 |
| 中文可读 | `ensure_ascii=False` 保留中文（否则 `\u4e2d\u6587`，模型也能懂但浪费 token） |
| 结构化 | 模型能提取 `ok`、`error`、`total` 等字段做判断 |

### 20.2.5 ④ 处理同步/异步

`@tool` 装饰同步函数 → 生成 `StructuredTool`，`.invoke()` 是同步的。

如果要异步工具，用 `async def` + `@tool`，LangChain 会生成支持 `.ainvoke()` 的版本。

**本项目全部用同步函数**，然后在调用时用 `asyncio.to_thread` 包装（见 20.4）。这个选择后面细说。

## 20.3 闭包注入：工具怎么拿到 db 和 user

这是本项目工具设计的核心模式。

### 20.3.1 问题：工具函数需要"请求级"的依赖

工具要查数据库，需要 `db: Session`；要校验权限，需要 `current_user: User`。但工具函数是**在 `build_tools` 里定义的**，而 LangChain 的工具签名只允许模型能填的参数（不能让模型传 `db`）。

**怎么把请求级对象传进工具？**

| 方案 | 做法 | 问题 |
|---|---|---|
| **全局变量** | 存到模块级变量 | 并发下必然串味 ❌ |
| **工具参数** | 让模型传 `db` | 模型不知道什么是 db ❌ |
| **LangGraph config** | 从 `config["configurable"]` 取 | 需要工具支持 RunnableConfig，稍复杂 |
| **✅ 闭包** | 在 `build_tools` 里定义函数，捕获外层变量 | 简单直接 |

### 20.3.2 项目实现

`agent_tools.py:68-98`（节选）：

```python
async def build_tools(db: Session, current_user: User, include_uploaded: bool = True):
    """根据当前请求的 db 和用户构建工具列表。

    把 db、current_user 用闭包传进去，工具函数内部就不用每次传 Session。
    include_uploaded=False 时，知识检索只在系统内置文档范围内进行。
    """
    if not TOOL_DECORATOR_AVAILABLE:
        raise BusinessException(message="未安装 langchain-core 依赖")

    scope_document_id = None if include_uploaded else "static"

    def _search_lab_docs(query: str) -> str:
        try:
            return (
                kb_service.search(query, document_id=scope_document_id)
                or "没有检索到相关的资料"
            )
        except Exception as exc:
            return json.dumps({"ok": False, "error": str(exc)}, ensure_ascii=False)
    ...

    @langchain_tool
    def create_lab_reservation(...):
        ...
        reservation_service.create_reservation(db, current_user, data)   # ★ 闭包捕获
```

**关键点**：`db` 和 `current_user` 不在工具函数的**参数列表**里，而是从**外层作用域**捕获的。

这意味着：

```
每次 HTTP 请求
  → build_agent(db, current_user)
  → build_tools(db, current_user)
  → 定义一批工具函数，它们"记住"了这次请求的 db 和 user
  → 绑定到 LLM
  → 模型调用时，工具内部用的是正确的 db/user
```

### 20.3.3 这个模式的代价

**代价 1：每次请求都要重建工具**

因为工具捕获了请求级对象，不能缓存复用。所以第 15 章讲过：**每次请求都要重建整个图**。

**代价 2：闭包变量的生命周期**

闭包捕获的是**对象引用**。如果请求结束后 db 会话被关闭，而工具还在被使用（异步场景），会出错。

本项目的调用是**同步的**（在一个请求内完成），所以安全。如果把工具丢到后台任务里，就要小心了。

**代价 3：测试时要构造这些对象**

看测试里怎么做的（`tests/test_agent_service.py:107`）：

```python
user = SimpleNamespace(id=1, role="student")
graph = await agent_service.build_agent(None, user)    # db 传 None！
```

用 `SimpleNamespace` 造一个假 user，`db` 直接传 `None`（因为测试用的假 LLM 不会真的调工具）。

### 20.3.4 权限控制：工具层的第一道防线

看 `create_lab_reservation`（`agent_tools.py:145-180`）：

```python
@langchain_tool
def create_lab_reservation(
    lab_id: int, date: str, start_time: str, end_time: str,
    equipment_id: int | None = None, remark: str | None = None,
) -> str:
    """创建预约单，预约实验室或设备。"""
    try:
        data = ReservationCreateRequest(
            lab_id=lab_id, equipment_id=equipment_id,
            date=date, start_time=start_time, end_time=end_time, remark=remark,
        )
        reservation_service.create_reservation(db, current_user, data)
        ...
```

注意 `create_reservation(db, current_user, data)` —— **用户身份是从闭包里来的，不是模型传的**。

**这非常重要**：如果 `current_user` 是模型传的参数，模型就可以伪造身份（"请以管理员身份预约"）。现在是闭包注入，模型**无法篡改**。

> **安全原则**：**任何涉及身份、权限的信息，都不能出现在工具的模型可填参数里**。这是防止 prompt injection 越权的基本功（第 36 章详述）。

## 20.4 为什么要放进线程池：`asyncio.to_thread`

### 20.4.1 问题：同步工具会阻塞事件循环

本项目所有工具都是 `def`（同步）。而 `tool_node` 是 `async def`。

如果在 async 函数里直接调用同步的阻塞操作：

```python
async def tool_node(state):
    result = tool.invoke(args)    # ❌ 同步阻塞！
```

**会发生什么？** `tool.invoke` 里面有数据库查询（IO 密集），它是同步的，会**阻塞整个事件循环**。也就是说，这个请求执行期间，**服务器上所有其他请求都卡住了**。

这就是第 3 章讲的 async 核心陷阱：**async 函数里不能直接调同步阻塞代码**。

### 20.4.2 解法：丢到线程池

`agent_service.py:155-173`：

```python
async def _invoke_tool_with_retry(tool, args: dict) -> str:
    """执行工具：线程池里跑（避免阻塞事件循环），带超时与有限重试。

    - 超时兜底：DB 慢查询或外部调用卡住时，不让它拖垮整张图。
    - 重试：只针对临时性故障重试有限次，最终失败再回填错误 JSON 给模型自纠。
    """
    last_error: Exception | None = None
    for attempt in range(settings.TOOL_MAX_RETRIES + 1):
        try:
            result = await asyncio.wait_for(
                asyncio.to_thread(tool.invoke, args),
                timeout=settings.TOOL_TIMEOUT_SECONDS,
            )
            return result.content if hasattr(result, "content") else str(result)
        except Exception as exc:
            last_error = exc
            if attempt < settings.TOOL_MAX_RETRIES:
                await asyncio.sleep(0.2 * (attempt + 1))
    return json.dumps({"ok": False, "error": str(last_error)}, ensure_ascii=False)
```

**两个 API 组合**：

**① `asyncio.to_thread(func, *args)`**

把同步函数丢到**默认线程池**执行，返回一个 awaitable。这样它就不会阻塞事件循环了。

```python
result = await asyncio.to_thread(tool.invoke, args)
# 等价于在某个 worker 线程里跑 tool.invoke(args)，await 等它完成
```

**为什么不用 `async def` 工具？** 三个理由：

| 理由 | 说明 |
|---|---|
| **依赖是同步的** | SQLAlchemy 的 `Session` 是同步的（本项目没用 `AsyncSession`）。要真异步得换成 async 驱动 + AsyncSession，改动很大 |
| **改造成本** | 所有 service 层都要改成 async |
| **够用** | `to_thread` 已经解决了阻塞问题，只是多一次线程切换（微秒级，相比 DB 查询可忽略） |

> **面试诚实答法**："我们的工具是同步函数，用 `asyncio.to_thread` 丢到线程池执行。这是因为我们的 ORM 用的是同步 Session。真正的异步需要换 async 驱动 + AsyncSession，改造成本较大；而 `to_thread` 已经解决了'阻塞事件循环'这个核心问题，线程切换的开销相比数据库查询可以忽略。如果要做高并发优化，换 async 全链路是明确的方向。"

**② `asyncio.wait_for(awaitable, timeout)`**

给 awaitable 加超时。超时后**取消**它并抛 `TimeoutError`。

```python
result = await asyncio.wait_for(
    asyncio.to_thread(tool.invoke, args),
    timeout=settings.TOOL_TIMEOUT_SECONDS,   # 默认 30 秒
)
```

**关键认知**：`wait_for` 可以取消 `asyncio` 的协程，但**取消不了线程池里的同步函数**。

也就是说：如果 `tool.invoke` 真的卡了 60 秒，`wait_for` 会在 30 秒时抛 `TimeoutError`，但**那个线程还在跑**，直到它自己结束。这是 Python 的固有限制（无法强制杀死线程）。

**实际影响**：
- ✅ 你的 Agent 不会被拖死（30 秒后继续走错误分支）
- ❌ 线程资源仍被占用（如果大量工具超时，线程池可能被耗尽）

**缓解**：可以配置更大的线程池：

```python
import asyncio
loop = asyncio.get_event_loop()
loop.set_default_executor(ThreadPoolExecutor(max_workers=50))
```

> ⚠️ **坑 1（真实）**：很多人以为 `wait_for` 会"杀掉"超时任务。对协程是的，对 `to_thread` 里的同步函数不是。这是 async 编程的经典误区。

## 20.5 重试策略：什么该重试，什么不该

### 20.5.1 项目实现

```python
for attempt in range(settings.TOOL_MAX_RETRIES + 1):   # 默认 TOOL_MAX_RETRIES=1 → 2 次尝试
    try:
        result = await asyncio.wait_for(...)
        return result.content if hasattr(result, "content") else str(result)
    except Exception as exc:
        last_error = exc
        if attempt < settings.TOOL_MAX_RETRIES:
            await asyncio.sleep(0.2 * (attempt + 1))    # 退避：0.2s, 0.4s
return json.dumps({"ok": False, "error": str(last_error)}, ensure_ascii=False)
```

三个设计点：

**① 重试次数是"额外次数"不是"总次数"**

```python
for attempt in range(TOOL_MAX_RETRIES + 1):
```

`TOOL_MAX_RETRIES = 1` → `range(2)` → 尝试 2 次（1 次原始 + 1 次重试）。

**② 指数退避**

```python
await asyncio.sleep(0.2 * (attempt + 1))
```

第 1 次失败后等 0.2s，第 2 次失败后等 0.4s。（真·指数退避应该是 `0.2 * 2**attempt`，这里是线性退避，但 2 次重试场景下差别不大。）

**③ 最终失败回填错误 JSON，不抛异常**

```python
return json.dumps({"ok": False, "error": str(last_error)}, ensure_ascii=False)
```

这是第 14 章讲的"错误变 Observation"原则的落地。

### 20.5.2 什么该重试，什么不该

**当前实现对所有异常都重试**，这是一个可以改进的点。更精细的分类：

| 异常类型 | 该重试？ | 理由 |
|---|---|---|
| 网络超时 / 连接重置 | ✅ 是 | 临时性故障 |
| 数据库死锁 / 锁等待超时 | ✅ 是 | 重试可能成功 |
| 限流（429） | ✅ 是（但要退避更久） | 需要等配额恢复 |
| 参数校验失败 | ❌ 否 | 重试也一样错，浪费时间 |
| 业务规则拒绝（时段冲突） | ❌ 否 | 应该由模型换个参数 |
| 权限不足 | ❌ 否 | 重试也不会有权限 |
| 404 资源不存在 | ❌ 否 | 同上 |

**改进方案**：

```python
RETRYABLE = (TimeoutError, ConnectionError, OperationalError)

except Exception as exc:
    last_error = exc
    if not isinstance(exc, RETRYABLE):
        break                      # 不可重试，直接跳出
    if attempt < settings.TOOL_MAX_RETRIES:
        await asyncio.sleep(0.2 * (attempt + 1))
```

> 📝 **简历优化点**：把"无差别重试"改成"按异常类型分类重试"。这是一个具体、有技术判断力的改进。

**为什么本项目没做分类？** 因为工具内部的 `except Exception` 已经把异常吞掉，转成 `{"ok": false, "error": ...}` 字符串了。所以 `_invoke_tool_with_retry` 层面**根本看不到原始异常类型**——它只会看到成功返回。

看 `agent_tools.py:116-117`：

```python
except Exception as exc:
    return json.dumps({"ok": False, "error": str(exc)}, ensure_ascii=False)
```

**工具内部已经捕获了所有异常**，所以 `_invoke_tool_with_retry` 的 `except` 只在两种情况触发：

1. `wait_for` 超时（`TimeoutError`）
2. LangChain 层面的参数校验失败

也就是说：**当前的重试实际上只对"超时"有效**。这倒是歪打正着——超时确实是最该重试的。

> **面试可以这样说**："工具内部已经把所有异常转成 `{"ok": false, "error": ...}` 返回了，所以外层重试实际上主要覆盖的是超时场景——而超时恰好是最值得重试的临时性故障。如果要做精细的重试分类，需要让工具层抛出可识别的异常类型而不是全部吞掉，这是一个明确的改进方向。"

## 20.6 MCP 工具加载与异步锁

### 20.6.1 项目实现

`agent_tools.py:27-65`：

```python
# MCP 工具缓存：连接失败回退本地工具。用 asyncio.Lock 防止并发请求重复加载。
_mcp_cache = {"tried": False, "tools": None}
_mcp_lock = asyncio.Lock()


async def _load_mcp_tools():
    """从独立 MCP Server 加载读工具。不可用时返回 None。

    这是异步函数：`build_tools` 在 `build_agent`（async）里被调用，
    而 MCP 客户端需要 asyncio 事件循环来建立连接，所以这里直接 `await`。
    之前的实现用 `asyncio.get_running_loop()` 探测 async 上下文，
    若在 async 里就 return None——导致流式场景下 MCP 工具永远加载不到。
    """
    if not settings.MCP_ENABLED:
        return None
    if _mcp_cache["tried"]:
        return _mcp_cache["tools"]
    async with _mcp_lock:
        # 双重检查：拿锁期间可能已被其它协程加载过。
        if _mcp_cache["tried"]:
            return _mcp_cache["tools"]
        try:
            from langchain_mcp_adapters.client import MultiServerMCPClient

            client = MultiServerMCPClient({
                "lab": {"url": settings.MCP_URL, "transport": settings.MCP_TRANSPORT}
            })
            tools = await client.get_tools()
            _mcp_cache["tools"] = tools
            _mcp_cache["tried"] = True
            return tools
        except Exception:
            _mcp_cache["tried"] = True
            return None
```

### 20.6.2 双重检查锁定（Double-Checked Locking）

```python
if _mcp_cache["tried"]:            # 第一次检查（无锁，快路径）
    return _mcp_cache["tools"]
async with _mcp_lock:              # 拿锁
    if _mcp_cache["tried"]:        # 第二次检查（有锁）
        return _mcp_cache["tools"]
    # 真正加载
```

**为什么要检查两次？**

- **第一次（锁外）**：99.9% 的请求走这条路，直接返回缓存，**零开销**（不拿锁）
- **第二次（锁内）**：防止并发竞态——多个线程同时通过第一次检查，第一个拿锁加载完，第二个拿锁后发现已经加载了，直接返回

这是经典的**双重检查锁定**模式（源自 Java 单例），在 Python asyncio 里同样适用。

**如果只检查一次会怎样？**

```python
async with _mcp_lock:              # 每次都拿锁
    if _mcp_cache["tried"]: ...
```

功能正确，但**每个请求都要拿一次锁**。虽然 asyncio 的锁很快（不涉及系统调用），但在高并发下仍有开销，而且会让请求串行化。

### 20.6.3 为什么用 `tried` 而不是检查 `tools is None`

```python
_mcp_cache = {"tried": False, "tools": None}
```

**关键**：MCP 加载失败时，`tools` 保持 `None`，但 `tried` 变成 `True`。

```python
except Exception:
    _mcp_cache["tried"] = True
    return None
```

如果只看 `tools is None`，失败后会**每次请求都重试连接 MCP**——对于一个不可用的服务，这是持续的浪费（每次都要等连接超时）。

用 `tried` 标记"已经尝试过了"，失败就**永久回退本地工具**（直到进程重启）。这是**失败快速降级**的设计。

> **权衡**：代价是 MCP 服务恢复后，需要重启应用才能重新连接。更完善的做法是加个 TTL（比如 5 分钟后允许重试一次）。

### 20.6.4 那个真实的 Bug（注释里记录的）

```python
"""
之前的实现用 `asyncio.get_running_loop()` 探测 async 上下文，
若在 async 里就 return None——导致流式场景下 MCP 工具永远加载不到。
"""
```

这是一个**极其典型**的 async bug。原代码大致是：

```python
def _load_mcp_tools():          # 同步版本
    try:
        loop = asyncio.get_running_loop()
        # 在 async 上下文里，没法同步等待 → 直接放弃
        return None             # ❌ 流式场景永远走不到这里想要的分支
    except RuntimeError:
        # 不在 async 上下文，可以同步加载
        return load_sync()
```

**问题**：`build_tools` 在 async 的 `build_agent` 里被调用，**永远**能拿到 running loop，于是**永远**返回 None，MCP 工具**永远**加载不到。而非流式路径可能不在 async 上下文，反而能加载——这就造成了"流式和非流式行为不一致"的诡异 bug。

**修复**：把整个链路改成 async（`build_tools` → `async def`，`_load_mcp_tools` → `async def`），直接用 `await`。

> ⚠️ **坑 2（真实，本项目踩过）**：**不要用 `get_running_loop()` 探测"能不能 await"**。判断能不能 await 的唯一标准是"你是不是在 async 函数里"——这是写代码时就确定的，不是运行时探测的。
> 正确做法：**把整条调用链都改成 async**。
> 这个 bug 是本项目代码审查里的 C3 缺陷，对应 `docs/23-代码审查报告.md`。

### 20.6.5 MCP 优先，本地兜底

`agent_tools.py:187-198`：

```python
# 优先使用 MCP 里的读工具，写工具和日期工具仍在本地（带鉴权）。
mcp_tools = await _load_mcp_tools()
if mcp_tools:
    return [*mcp_tools, create_lab_reservation, get_today]

return [
    search_lab_docs,
    list_open_labs,
    list_lab_equipments,
    create_lab_reservation,
    get_today,
]
```

**分工逻辑**：

| 工具类型 | 来源 | 理由 |
|---|---|---|
| **读工具**（检索、查询） | MCP（优先） | 可被其他系统复用；无鉴权要求 |
| **写工具**（预约） | 本地 | 需要 `db` + `current_user` 鉴权 |
| **日期工具** | 本地 | 无需外部依赖，本地最快 |

**为什么要区分？** 因为 **MCP 工具拿不到请求级的 `db` 和 `current_user`**——它是跨进程的，通过 HTTP/SSE 通信，你没法把数据库会话传过去。

所以：**需要身份鉴权的工具必须留在本地**。这是一个重要的架构判断，第 30 章会详述 MCP 的边界。

## 20.7 最小骨架：超时与重试的完整演示

```python
"""
minimal_tool_retry.py —— 工具超时/重试/错误回填最小实现
运行：python minimal_tool_retry.py  （纯 Python，无需依赖）
"""
import asyncio
import json
import time


# ── 模拟三个工具 ───────────────────────────────────────────
def quick_tool(args):
    """正常工具：100ms 返回。"""
    time.sleep(0.1)
    return json.dumps({"ok": True, "data": "查询成功"}, ensure_ascii=False)


def flaky_tool(args):
    """抖动工具：第一次失败，第二次成功。"""
    if not hasattr(flaky_tool, "n"):
        flaky_tool.n = 0
    flaky_tool.n += 1
    time.sleep(0.05)
    if flaky_tool.n == 1:
        raise ConnectionError("网络抖动")
    return json.dumps({"ok": True, "data": f"第 {flaky_tool.n} 次成功了"}, ensure_ascii=False)


def slow_tool(args):
    """慢工具：睡 5 秒，模拟 DB 慢查询。"""
    time.sleep(5)
    return json.dumps({"ok": True, "data": "终于查完了"}, ensure_ascii=False)


def always_fail_tool(args):
    """永远失败的工具。"""
    raise ValueError("参数不合法：lab_id 不存在")


class Result:
    """模拟 LangChain ToolMessage（有 content 属性）。"""
    def __init__(self, content):
        self.content = content


def tool_invoke(fn, args):
    """模拟 tool.invoke()。"""
    return Result(fn(args))


# ── 带超时和重试的执行器（本项目 _invoke_tool_with_retry 的等价实现） ──
async def invoke_with_retry(fn, args, timeout=1.0, max_retries=1):
    """在线程池里跑同步工具，带超时和有限重试。"""
    last_error = None
    for attempt in range(max_retries + 1):
        try:
            result = await asyncio.wait_for(
                asyncio.to_thread(tool_invoke, fn, args),
                timeout=timeout,
            )
            return result.content if hasattr(result, "content") else str(result)
        except Exception as exc:
            last_error = exc
            print(f"    ⚠ 第 {attempt + 1} 次尝试失败：{type(exc).__name__}: {exc}")
            if attempt < max_retries:
                wait = 0.2 * (attempt + 1)
                print(f"    等待 {wait}s 后重试…")
                await asyncio.sleep(wait)
    # 最终失败：回填错误 JSON（不抛异常）
    return json.dumps({"ok": False, "error": str(last_error)}, ensure_ascii=False)


async def main():
    print("=== 场景 1：正常工具 ===")
    t = time.time()
    print("  结果:", await invoke_with_retry(quick_tool, {}))
    print(f"  耗时: {time.time() - t:.2f}s\n")

    print("=== 场景 2：抖动工具（重试后成功）===")
    t = time.time()
    print("  结果:", await invoke_with_retry(flaky_tool, {}))
    print(f"  耗时: {time.time() - t:.2f}s  ← 含 0.2s 退避\n")

    print("=== 场景 3：慢工具（超时）===")
    t = time.time()
    print("  结果:", await invoke_with_retry(slow_tool, {}, timeout=1.0))
    print(f"  耗时: {time.time() - t:.2f}s  ← 1 秒超时 + 重试 1 次 = 约 2 秒")
    print("  ★ 注意：那个线程还在后台跑 5 秒，wait_for 杀不掉它\n")

    print("=== 场景 4：永远失败（重试耗尽）===")
    print("  结果:", await invoke_with_retry(always_fail_tool, {}, timeout=1.0))
    print("  ★ 异常没抛出去，而是变成 JSON 回填给模型自纠\n")

    print("=== 场景 5：并发 3 个慢工具（验证不阻塞）===")
    t = time.time()
    results = await asyncio.gather(
        invoke_with_retry(slow_tool, {}, timeout=1.0),
        invoke_with_retry(slow_tool, {}, timeout=1.0),
        invoke_with_retry(quick_tool, {}),
    )
    print(f"  总耗时: {time.time() - t:.2f}s  ← 若串行会 > 10s，并发后由超时决定")
    for r in results:
        print("   ", r[:60])


if __name__ == "__main__":
    asyncio.run(main())
```

**预期输出（关键行）**：

```
=== 场景 2：抖动工具（重试后成功）===
    ⚠ 第 1 次尝试失败：ConnectionError: 网络抖动
    等待 0.2s 后重试…
  结果: {"ok": true, "data": "第 2 次成功了"}
  耗时: 0.26s  ← 含 0.2s 退避

=== 场景 3：慢工具（超时）===
    ⚠ 第 1 次尝试失败：TimeoutError:
    等待 0.2s 后重试…
    ⚠ 第 2 次尝试失败：TimeoutError:
  结果: {"ok": false, "error": ""}
  耗时: 2.22s  ← 1 秒超时 × 2 次 + 0.2s 退避
  ★ 注意：那个线程还在后台跑 5 秒，wait_for 杀不掉它

=== 场景 4：永远失败（重试耗尽）===
  结果: {"ok": false, "error": "参数不合法：lab_id 不存在"}
  ★ 异常没抛出去，而是变成 JSON 回填给模型自纠
```

**四件事被验证**：
1. ✅ 重试能救回临时故障
2. ✅ 超时能防止拖死（2 秒而不是 5 秒）
3. ✅ 超时对线程内的同步函数无效（它还在跑）
4. ✅ 最终失败变成 JSON 而不是异常

## 20.9 面试问答

### Q1：工具超时了怎么办？

**答**：用 `asyncio.wait_for` 包一层，默认 30 秒超时。超时后抛 `TimeoutError`，走重试逻辑，最终还是失败就回填 `{"ok": false, "error": ...}` 给模型自纠。

这里有个容易误解的点：**`wait_for` 能取消协程，但取消不了线程池里的同步函数**。我们的工具是同步函数，用 `asyncio.to_thread` 跑在线程池里，所以超时后那个线程还在后台跑，直到它自己结束。

实际影响是：Agent 不会被拖死（30 秒后继续），但线程资源仍被占用。如果大量工具超时，要考虑调大线程池。

### Q2：为什么工具是同步函数而不是 async？

**答**：因为我们的 ORM 用的是同步 `Session`，整个 service 层都是同步的。要真异步需要换 async 驱动（asyncpg）+ `AsyncSession`，service 层全改，成本较大。

解决方案是用 `asyncio.to_thread` 把同步工具丢到线程池执行，这样就不会阻塞事件循环了。线程切换的开销是微秒级，相比数据库查询（毫秒级）可以忽略。

如果要做高并发优化，换 async 全链路是明确的方向。

### Q3：工具怎么拿到数据库会话和用户身份？

**答**：用闭包。`build_tools(db, current_user)` 内部定义工具函数，它们从外层作用域捕获 `db` 和 `current_user`，而这两个参数**不在工具的签名里**，模型看不到也传不了。

这个设计有个重要的安全意义：**模型无法通过 prompt injection 伪造身份**。如果 `current_user` 是工具参数，模型理论上可以传"以管理员身份执行"。现在是闭包注入，模型完全碰不到。

代价是每次请求都要重建工具（因为捕获的是请求级对象），所以我们的图也是每次请求重建的。

### Q4：为什么要重试？重试所有错误吗？

**答**：重试是为了应对**临时性故障**（网络抖动、数据库死锁、限流），这些重试一次很可能就成功了。

我们目前是"无差别重试"——所有异常都重试 1 次，退避 0.2 秒。但这里有个实际情况：工具内部已经把所有异常转成 `{"ok": false, "error": ...}` 字符串返回了，所以外层重试**实际上主要覆盖的是超时场景**——而超时恰好是最值得重试的。

如果要做精细分类（参数错误不重试、超时才重试），需要让工具层抛出可识别的异常类型而不是全部吞掉，这是明确的改进方向。

### Q5：MCP 工具加载为什么要用锁？

**答**：因为它是全局缓存 + 懒加载，高并发下多个请求会同时发现"还没加载"，然后并发建立 MCP 连接——浪费资源，还可能有竞态。

我们用 `asyncio.Lock` 加**双重检查锁定**：第一次检查在锁外（快路径，99.9% 的请求零开销直接返回缓存），拿锁后再检查一次（防止并发竞态）。

还有个细节：缓存的是 `{"tried": bool, "tools": ...}` 而不是直接判断 `tools is None`。因为 MCP 加载失败时 tools 是 None，如果只看 tools 就会每次请求都重试连接一个已知不可用的服务。用 `tried` 标记"试过了"，失败就永久回退本地工具。

### Q6：MCP 工具和本地工具怎么分工？

**答**：读工具优先走 MCP，写工具和日期工具留本地。

核心原因是 **MCP 是跨进程的，拿不到请求级的 `db` 和 `current_user`**。所以任何需要身份鉴权的工具（预约）必须留在本地——它能通过闭包拿到真实的用户身份。

读工具（检索知识库、查实验室、查设备）不需要鉴权，走 MCP 可以被其他系统复用，也更符合 MCP 的设计初衷。

### Q7：那个 MCP 加载的 bug 是什么？(加分题)

**答**：原实现用 `asyncio.get_running_loop()` 探测"当前是否在 async 上下文"，如果在就返回 None（因为同步函数没法 await）。

问题是 `build_tools` 是在 async 的 `build_agent` 里调用的，**永远**能拿到 running loop，所以 **MCP 工具永远加载不到**。而非流式路径可能不在 async 上下文反而能加载，导致流式和非流式行为不一致。

修复是把整条调用链改成 async——`build_tools` 和 `_load_mcp_tools` 都改成 `async def`，直接 `await`。

教训是：**不要用运行时探测来判断"能不能 await"**。能不能 await 是写代码时就确定的（你是不是在 async 函数里），不是运行时的事。正确做法是把整条链都改成 async。

## 20.11 延伸思考

1. **如果工具超时后线程还在跑，怎么才能真正"取消"它？**
   提示：Python 没有杀线程的 API。可行方案：把超时传给下游（比如 SQLAlchemy 的 `statement_timeout`、HTTP 客户端的 timeout），让**底层自己**超时。这是"超时下推"原则——每一层都要有自己的超时，不能只靠外层。

2. **工具返回值如果很大（比如 100KB 的检索结果），会有什么连锁问题？**
   提示：① 进 ToolMessage → 撑爆上下文（第 19 章）；② 进 checkpoint → 存储膨胀（第 17 章）；③ 进 SSE 流 → 前端卡顿（第 31 章）。**在工具层截断**是最经济的解法——本项目 `_tool_output_preview` 就是给前端预览做截断的。

3. **如果要给不同工具设不同超时（读 5 秒、写 30 秒），怎么设计？**
   提示：给工具加元数据（`tool.metadata = {"timeout": 5}`），`_invoke_tool_with_retry` 里读取。或者在工具名上做约定映射。思考：这个配置应该放在 `agent_tools.py` 还是 `config.py`？
