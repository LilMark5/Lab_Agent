# 第 40 章 · 可观测性：线上出问题时你怎么知道是哪一环坏的

> 前面 39 章我们一直在做一件事：**把系统做对**。
> 这一章开始做另一件事：**系统出错时你能看见**。
>
> 先说一句实话：这一章是全书里**唯一一章需要坦白"项目没做到位"**的。
> 目前项目只有标准库 `logging`，没有 trace_id、没有指标、没有链路追踪。
> 所以这一章的结构会有点不一样：先讲清楚**为什么这层必须存在**，再给一套**可以直接粘进项目的最小实现**，最后说明**哪些没做、为什么没做**。

---

## 40.1 为什么需要它：Agent 系统的故障长得不一样

传统 Web 服务的故障是可复现的：

```
用户报"订单提交失败"
→ 查日志，找到那条请求
→ 看到 SQL 报错 "duplicate key"
→ 复现：同样的参数再提交一次，必现
→ 修
```

Agent 系统的故障**不是这个形状**。

### 40.1.1 三种传统手段失效的场景

**场景一：不可复现**

用户说："我问'明天下午有空的实验室吗'，它给了我一个错的答案。"

你拿这句话重跑一次——**答案是对的**。

为什么？因为上一次的用户上下文里有前几轮对话，`_trim_messages`（第 19 章）裁剪后的窗口和这次不一样；或者那次查询改写（第 28 章）生成了不同的检索词；或者 LLM 本身有采样随机性。

**没有记录，你永远无法知道那一次到底发生了什么。**

**场景二：多跳链路，不知道坏在哪一环**

用户说："预约失败了。"

一条预约请求可能经过：

```
SSE 连接 → 鉴权 → 限流 → Agent 启动 → LLM 推理 → 工具调用
  → 冲突检测 SQL → 条件路由 → 人工审批 interrupt → 数据库写入
```

9 个环节。任何一环挂了，用户看到的都是"失败"。

**没有链路追踪，你只能从 9 个环节里第一个开始猜。**

**场景三：外部依赖静默降级**

这一条最阴险。看项目的实际代码（`kb_service.py:174`）：

```python
except Exception as exc:
    logger.warning("rerank 不可用，使用融合排序：%s", exc)
```

rerank 挂了，**系统不报错，继续用融合排序**。这是一个正确的降级设计（第 27 章讲过），但它带来一个副作用：

> **用户感觉"最近 AI 回答变差了"，但没有任何一条 ERROR 日志。**

你去看监控——全绿。你去看告警——没有。只有一条 WARNING 躺在日志里。

**降级设计做得越好，静默故障越难发现。** 这是可观测性里最反直觉的一条。

### 40.1.2 Agent 系统的四个"看不见"

把上面三种场景抽象一下，Agent 系统有四个传统监控看不见的东西：

| 看不见的东西 | 传统监控能测吗 | 后果 |
|---|---|---|
| **LLM 调用次数与延迟** | ❌（它只是个 HTTP 请求） | 慢了不知道是哪次调用慢 |
| **工具调用序列** | ❌（在进程内，没出口） | 不知道模型选了什么工具、参数对不对 |
| **上下文窗口膨胀** | ❌ | 突然超 token 才发现 |
| **检索质量退化** | ❌ | 召回变差了，系统照样返回 200 |

**这四个正是 Agent 系统最容易出问题的地方，而它们全在传统监控的盲区里。**

## 40.2 它到底是什么：四层可观测性

传统后端讲"三支柱"（日志、指标、链路追踪）。Agent 系统要加第四层。

```
┌────────────────────────────────────────────────────────────┐
│  第 4 层：LLM/Agent 追踪（Trace）                            │
│  每次 LLM 调用的 prompt/响应/token/耗时，工具调用序列，      │
│  图节点的执行顺序。LangSmith / Langfuse / Opik 做这层。      │
├────────────────────────────────────────────────────────────┤
│  第 3 层：链路追踪（Tracing）                                │
│  一个请求跨多少服务、每段耗时、在哪断的。OpenTelemetry。     │
├────────────────────────────────────────────────────────────┤
│  第 2 层：指标（Metrics）                                    │
│  聚合数值：QPS、P95 延迟、错误率、token 消耗。Prometheus。    │
├────────────────────────────────────────────────────────────┤
│  第 1 层：日志（Logging）                                    │
│  离散事件：什么时候、发生了什么。结构化日志 + trace_id。      │
└────────────────────────────────────────────────────────────┘
```

**四层的关系**：

- **日志**回答"某一次发生了什么"（点）
- **指标**回答"整体趋势怎么样"（面）
- **链路**回答"这一次慢在哪"（线）
- **LLM 追踪**回答"模型这一轮在想什么"（Agent 专属）

少任何一层都会出现特定的盲区：

```
只有日志      → 能查单次，看不到趋势，不知道"最近是不是变差了"
只有指标      → 知道变差了，查不到是哪条请求、哪个环节
只有日志+指标 → 知道哪个服务慢，不知道是 LLM 慢还是 SQL 慢
没有 LLM 追踪 → 知道 LLM 慢，不知道是哪一轮、prompt 多长、为什么慢
```

### 40.2.1 第一层：结构化日志 + trace_id

**普通日志的问题**：

```python
logger.warning("rerank 不可用，使用融合排序：%s", exc)
```

这条日志有三个致命缺失：

1. **不知道是哪个请求**——并发 100 个请求，日志全混在一起
2. **不知道是哪个用户**——无法关联到具体用户投诉
3. **不知道上下文**——这个问题问的是什么？召回了几个块？

**结构化日志的做法**：每条日志都带上一个 `trace_id`，同一次请求的所有日志都能串起来。

```
10:23:11 [trace=7f3a] INFO  agent.start      user=12 thread=t-9
10:23:11 [trace=7f3a] INFO  kb.retrieve      query="明天下午有空的实验室吗" hits=3
10:23:12 [trace=7f3a] WARN  kb.rerank_failed fallback=fusion  ← 问题在这
10:23:14 [trace=7f3a] INFO  llm.call         model=deepseek tokens=1840 ms=2100
10:23:14 [trace=7f3a] INFO  agent.tool_call  name=query_labs args={...}
```

**有了 trace_id，一次请求的完整故事是一条 grep 就能看完的。**

### 40.2.2 第二层：指标

指标是**聚合**的，它回答的是趋势问题：

| 指标类型 | 例子 | 回答什么问题 |
|---|---|---|
| **计数器**（Counter） | `agent_requests_total`、`llm_calls_total` | 量有多大 |
| **直方图**（Histogram） | `llm_latency_seconds`、`retrieval_latency` | 有多慢（能算 P95） |
| **仪表盘**（Gauge） | `context_tokens_used`、`active_streams` | 当前水位 |

**为什么必须是指标而不是日志？** 因为**你不可能"grep 出 P95"**。

日志能告诉你"这次请求 2.1 秒"，但"过去 24 小时的 P95 是多少"只有指标能回答。反过来，指标能告诉你"P95 从 1.2s 涨到 3.8s"，但"哪条请求这么慢"只有日志能回答。

**日志和指标不是替代关系，是互补关系。**

### 40.2.3 第三层：链路追踪

一个请求跨了多个组件，链路追踪把它画成一棵树：

```
POST /api/ai/chat/stream          总耗时 3420ms
├── auth.verify_jwt                  3ms
├── rate_limit.check                 1ms
├── agent.invoke                  3380ms   ← 慢在这
│   ├── llm.call                   2100ms
│   │   └── http POST /v1/chat    2080ms
│   ├── tool.query_labs             180ms
│   │   └── db SELECT labs         175ms
│   └── llm.call                   1050ms
└── sse.write                        36ms
```

**一眼看出问题在 LLM 调用，不在数据库。** 这是日志和指标都给不了的信息。

### 40.2.4 第四层：LLM/Agent 追踪（Agent 专属）

这是 Agent 系统特有的一层。它要记录的东西是传统追踪没有的：

```
LLM Span:
  model          = deepseek-chat
  prompt_tokens  = 1840
  completion     = 220
  temperature    = 0
  latency        = 2100ms
  prompt（脱敏后）= "你是智能实验室预约系统的助手..."
  response       = "..."
  
Tool Span:
  name     = query_labs
  args     = {"date": "2025-06-10"}
  result   = "[{...}]"  (前 500 字符)
  duration = 180ms
  status   = success
```

**为什么这一层不能省？** 因为 Agent 的"业务逻辑"在 prompt 里，不在代码里。

你看到 `llm.call` 慢了 2 秒，去查代码——代码没问题。真正的原因是**这一轮的 prompt 里有 8000 个 token 的历史对话**。这个信息只有 LLM 追踪能看到。

**LangSmith / Langfuse / Opik / Phoenix** 就是做这一层的。它们对 LangChain / LangGraph 有原生集成，通常一行环境变量就能接上。

## 40.3 最小可运行骨架

下面的 `minimal_observability.py` 是一个**零依赖**的可观测性最小实现：trace_id 中间件 + 结构化日志 + 计时器 + 内存指标。可以直接跑，也可以直接粘进 FastAPI 项目。

```python
"""可观测性最小骨架：trace_id + 结构化日志 + 计时 + 指标。

零第三方依赖（只用标准库），跑通后可直接粘进 FastAPI 项目。
四件事：
  1. trace_id：把一次请求的所有日志串起来
  2. 结构化日志：JSON 输出，可被日志系统索引
  3. 计时：拿到耗时分布（P95 的基础）
  4. 指标：计数器 + 直方图，暴露成文本供采集

局限（生产要补）：
  - 指标存内存，进程重启即丢 → 生产用 Prometheus client
  - 没有跨服务传播 → 生产用 OpenTelemetry 的 W3C traceparent
  - 没有采样 → 高 QPS 下要采样，否则日志量爆炸
"""
from __future__ import annotations

import contextvars
import json
import logging
import statistics
import time
import uuid
from collections import defaultdict
from contextlib import contextmanager
from dataclasses import dataclass, field

# ---------------------------------------------------------------- 1. trace_id

# contextvars 而不是 threading.local：async 环境下线程会切，thread-local 会串号。
# 这是 async 项目里最容易踩的坑，务必用 contextvars。
_trace_id: contextvars.ContextVar[str] = contextvars.ContextVar(
    "trace_id", default="-"
)


def new_trace_id() -> str:
    return uuid.uuid4().hex[:12]


def get_trace_id() -> str:
    return _trace_id.get()


def bind_trace_id(value: str) -> None:
    _trace_id.set(value)


# ------------------------------------------------------------ 2. 结构化日志


class JsonFormatter(logging.Formatter):
    """把日志输出成一行一个 JSON，带上 trace_id。"""

    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"),
            "level": record.levelname,
            "logger": record.name,
            "trace": get_trace_id(),          # ★ 每条日志自动带上
            "msg": record.getMessage(),
        }
        # 业务字段：logging.info("...", extra={"user_id": 12})
        for key, value in record.__dict__.items():
            if key not in logging.LogRecord.__dict__ and not key.startswith("_"):
                payload.setdefault(key, value)
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)


def setup_logging(level: int = logging.INFO) -> None:
    handler = logging.StreamHandler()
    handler.setFormatter(JsonFormatter())
    root = logging.getLogger()
    root.handlers = [handler]
    root.setLevel(level)


log = logging.getLogger("app")


# -------------------------------------------------------------- 3. 计时 span


@contextmanager
def span(name: str, **fields):
    """记录一段耗时，打一条日志 + 记一个直方图样本。"""
    start = time.perf_counter()
    try:
        yield
    except Exception as exc:
        duration_ms = (time.perf_counter() - start) * 1000
        log.warning(
            "span.error name=%s ms=%.1f err=%s", name, duration_ms, exc,
            extra={"span": name, "duration_ms": round(duration_ms, 1), **fields},
        )
        raise
    else:
        duration_ms = (time.perf_counter() - start) * 1000
        log.info(
            "span.ok name=%s ms=%.1f", name, duration_ms,
            extra={"span": name, "duration_ms": round(duration_ms, 1), **fields},
        )
        metrics.observe(f"span_{name}_ms", duration_ms / 1000)


# ---------------------------------------------------------------- 4. 指标


@dataclass
class Metrics:
    """内存指标：计数器 + 直方图。生产换 prometheus_client。"""

    counters: dict[str, float] = field(default_factory=lambda: defaultdict(float))
    histograms: dict[str, list[float]] = field(
        default_factory=lambda: defaultdict(list)
    )

    def inc(self, name: str, value: float = 1) -> None:
        self.counters[name] += value

    def observe(self, name: str, value: float) -> None:
        # 只留最近 1000 个样本，防止内存无限涨（真实项目踩过这个）
        hist = self.histograms[name]
        hist.append(value)
        if len(hist) > 1000:
            del hist[: len(hist) - 1000]

    def percentile(self, name: str, p: float) -> float | None:
        values = sorted(self.histograms.get(name, []))
        if not values:
            return None
        idx = min(len(values) - 1, int(len(values) * p))
        return round(values[idx], 4)

    def render(self) -> str:
        """暴露成 Prometheus 文本格式（简化版）。"""
        lines = []
        for name, value in self.counters.items():
            lines.append(f"# TYPE {name} counter")
            lines.append(f"{name} {value}")
        for name in self.histograms:
            lines.append(f"# TYPE {name} histogram")
            for p in (0.5, 0.95, 0.99):
                v = self.percentile(name, p)
                if v is not None:
                    lines.append(f'{name}{{quantile="{p}"}} {v}')
            if self.histograms[name]:
                lines.append(f"{name}_count {len(self.histograms[name])}")
        return "\n".join(lines)


metrics = Metrics()


# ------------------------------------------------------- 5. FastAPI 中间件


def make_middleware(app_type: str = "fastapi"):
    """返回一个 ASGI/FastAPI 中间件，给每个请求绑 trace_id 并记指标。

    FastAPI 用法：
        app.middleware("http")(make_middleware())
    """
    async def middleware(request, call_next):
        trace = request.headers.get("X-Trace-Id") or new_trace_id()
        bind_trace_id(trace)          # ★ 关键：绑到 contextvar，日志自动带上
        metrics.inc(f"{app_type}_requests_total")
        start = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            metrics.inc(f"{app_type}_errors_total")
            log.exception("request.failed path=%s", request.url.path)
            raise
        finally:
            ms = (time.perf_counter() - start) * 1000
            metrics.observe("request_duration_ms", ms)
        response.headers["X-Trace-Id"] = trace   # ★ 回给前端，用户报 bug 时能提供
        log.info(
            "request.done path=%s status=%s ms=%.1f",
            request.url.path, response.status_code, ms,
        )
        return response

    return middleware


# ------------------------------------------------------------------ 演示


def fake_llm_call(n_tokens: int) -> str:
    """模拟 LLM 调用：token 越多越慢。"""
    time.sleep(0.001 * n_tokens)
    return "根据《开放时间.md》，人工智能实验室周末 09:00 开放。"


def fake_retrieve(query: str) -> list[str]:
    time.sleep(0.02)
    return ["[开放时间#3] 人工智能实验室周末 09:00 开放，17:00 关闭。"]


def handle_chat(question: str, history_len: int) -> str:
    """模拟一次 RAG 问答：检索 → 拼 prompt → 调 LLM。"""
    with span("kb.retrieve", query=question):
        ctx = fake_retrieve(question)
        metrics.observe("retrieval_hits", len(ctx))

    # ★ 这一行是可观测性的核心价值：把"看不见的东西"变成指标
    prompt_tokens = 300 + history_len * 120
    metrics.observe("prompt_tokens", prompt_tokens)

    with span("llm.call", model="fake", prompt_tokens=prompt_tokens):
        answer = fake_llm_call(prompt_tokens)

    metrics.inc("agent_answers_total")
    return answer


if __name__ == "__main__":
    setup_logging()

    print("=" * 72)
    print("演示 1：trace_id 把一次请求的多条日志串起来")
    print("=" * 72)
    for i, (q, hist) in enumerate(
        [("周末几点开放？", 3), ("能预约吗？", 2)], start=1
    ):
        bind_trace_id(new_trace_id())
        answer = handle_chat(q, hist)
        print(f"  → 答案：{answer[:30]}...")

    print()
    print("=" * 72)
    print("演示 2：指标暴露（Prometheus 文本格式）")
    print("=" * 72)
    # 模拟 20 次请求，其中历史长度不同（模拟上下文膨胀）
    for i in range(20):
        bind_trace_id(new_trace_id())
        handle_chat("周末几点开放？", history_len=i)
    print(metrics.render())

    print()
    print("=" * 72)
    print("演示 3：从指标里读出'上下文膨胀'")
    print("=" * 72)
    p50 = metrics.percentile("prompt_tokens", 0.5)
    p95 = metrics.percentile("prompt_tokens", 0.95)
    print(f"  prompt_tokens  P50 = {p50}")
    print(f"  prompt_tokens  P95 = {p95}")
    print(f"  → P95/P50 = {p95 / p50:.2f} 倍")
    print("  → 这个比值越大，说明长对话用户的成本越失控（第 19 章的裁剪阈值该调了）")
```

### 40.3.1 三个必须记住的实现细节

**① 用 `contextvars`，不是 `threading.local`**

```python
_trace_id: contextvars.ContextVar[str] = contextvars.ContextVar("trace_id", default="-")
```

**为什么？** async 环境下，一个请求会在多个线程/协程间切换。`threading.local` 绑定的是线程，协程被调度到另一个线程执行时，取值会丢或串号。

这是 async 项目做 trace 传播的**头号坑**。第 03 章讲过 asyncio 的调度模型，这里是它的直接后果。

**② 直方图要限长**

```python
hist.append(value)
if len(hist) > 1000:
    del hist[: len(hist) - 1000]
```

内存里的直方图不限制长度就是内存泄漏。生产环境用 Prometheus 的直方图（分桶存储，O(1) 内存）没这个问题，但自己实现时必须限长。

**③ trace_id 要回给前端**

```python
response.headers["X-Trace-Id"] = trace
```

这样用户报 bug 时可以说"我的 trace 是 7f3a9c21b4de"，你直接 grep。没有这一步，用户只能说"刚才大概十点左右"，你还是得猜。

| `kb_service.py:174` | rerank 不可用，使用融合排序 | warning |
| `kb_service.py:190` | 查询改写：`%r -> %r` | info |
| `vector_store.py:476/488` | 向量库后端降级 | warning |
| `vector_store.py:499/501` | 预热完成/失败 | info/warning |

**值得肯定的地方**：所有**降级路径都打了日志**。这五条 warning：

```python
logger.warning("查询改写失败，回退原始问题：%s", exc)        # kb_service.py:63
logger.warning("从向量库读取块失败，回退静态文件：%s", exc)  # kb_service.py:82
logger.warning("向量检索失败：%s", exc)                     # kb_service.py:138
logger.warning("rerank 不可用，使用融合排序：%s", exc)       # kb_service.py:174
logger.warning("ChromaDB 不可用，RAG 功能降级为空实现")      # vector_store.py:488
```

**这是一个正确的工程习惯**：每次降级都留痕。很多项目的降级是静默的 `except: pass`，那才是灾难。

另外 `kb_service.py:190` 记了查询改写的前后对比：

```python
logger.info("查询改写：%r -> %r", query, search_query)
```

**这条日志价值很高**——查询改写是黑盒（第 28 章），有了它你能看到"用户问 A，系统实际检索的是 B"。排查召回问题时这是最关键的一条线索。

### 40.4.2 缺的：四层里的三层半

诚实清单：

| 层 | 状态 | 说明 |
|---|---|---|
| 日志 | ⚠️ 有，但**没有 trace_id**、**非结构化** | 并发下无法串联 |
| 指标 | ❌ 完全没有 | 没有 QPS、P95、错误率、token 消耗 |
| 链路追踪 | ❌ 完全没有 | 不知道慢在哪一环 |
| LLM 追踪 | ❌ 完全没有 | 没接 LangSmith / Langfuse |

### 40.4.3 ⚠️ 最严重的一处：兜底异常不记日志

`common/exceptions.py:50-55`：

```python
async def global_exception_handler(request: Request, exc: Exception):
    """兜底异常：捕获所有未处理的错误，避免把堆栈直接暴露给前端。"""
    return JSONResponse(
        status_code=500,
        content=Response.error(code=500, message="服务器内部错误").model_dump(),
    )
```

**看出问题了吗？这个函数捕获了所有未处理异常，然后直接返回 500，没有任何 `logger.exception`。**

后果是：

```
线上出现 500 → 用户看到"服务器内部错误"
            → 你去查日志 → 空的
            → 你不知道是什么错、在哪一行、谁的调用栈
            → 唯一的线索是"有个 500"
```

**这是可观测性里最致命的一类缺陷：错误被吞掉了。** 它比"没有指标"严重得多——没有指标是"看不见趋势"，吞掉异常是"发生了什么都不知道"。

**修复（三行）**：

```python
async def global_exception_handler(request: Request, exc: Exception):
    """兜底异常：捕获所有未处理的错误，避免把堆栈直接暴露给前端。"""
    # ★ 必须记日志：否则线上 500 无从排查，只能看到"有个 500"
    logger.exception(
        "未处理异常 method=%s path=%s trace=%s",
        request.method, request.url.path, get_trace_id(),
    )
    return JSONResponse(
        status_code=500,
        content=Response.error(code=500, message="服务器内部错误").model_dump(),
    )
```

**为什么原代码会漏？** 因为它把注意力放在了"不要把堆栈暴露给前端"这个正确的目标上，却忘了"但要在服务端记下来"。**安全和可观测性不是二选一，是两边都要做。**

> 这个缺陷值得你在面试时主动讲出来——能发现自己项目的兜底异常处理器没记日志，说明你真的看过代码、想过线上会怎样。

### 40.4.4 怎么把最小骨架接进项目

如果要补上这一层，改动只有三处（**这是本章给出的可执行方案，项目当前未实施**）：

**① 加 `app/common/observability.py`**——直接放 40.3 的骨架，去掉演示部分。

**② 在 `main.py` 挂中间件**（`main.py:61` 附近）：

```python
from app.common.observability import make_middleware, setup_logging

setup_logging()
app.add_middleware(...)   # 或用 app.middleware("http")(make_middleware())
```

注意顺序：**中间件要在 CORS 之后、路由之前**，这样 OPTIONS 预检请求不会污染指标。

**③ 在关键路径埋 span**：

```python
# kb_service.retrieve 里
with span("kb.retrieve", query=query, top_k=top_k):
    ...

# agent_service.agent_node 里

    ...

# agent_tools 的工具函数里

    ...
```

以及**把 token 数变成指标**（复用第 19 章已有的 `_estimate_tokens`）：

```python

```

这一条是 Agent 系统**最高性价比的指标**——它同时预警了成本、延迟、和上下文膨胀三个问题。

## 40.5 踩过的坑

### ⚠️ 坑 1：兜底异常处理器没记日志

见 40.4.3。这是项目里真实存在的问题，也是本章最重要的发现。

**通用教训**：**每一个 `except` 块都必须有出口——要么记日志、要么抛出去、要么计指标。三者都没有的 `except` 是bug 制造机。**

### ⚠️ 坑 2：降级日志是 WARNING，不触发告警

```python
logger.warning("rerank 不可用，使用融合排序：%s", exc)
```

**问题**：告警系统通常只盯 ERROR。rerank 全量挂了，系统只打 WARNING，告警不响，你只会感觉到"最近回答变差了"但查不到原因。

**正确做法**：**降级也要有指标**。

```python
metrics.inc("kb_rerank_fallback_total")      # 计数器
```

然后用指标配告警：`rate(kb_rerank_fallback_total[5m]) > 0`。

**核心原则**：**日志是给人看的，指标是给机器看的。想让机器帮你盯着，就必须是指标。**

### ⚠️ 坑 3：async 环境用 `threading.local` 传 trace_id 会串号

见 40.3.1。必须用 `contextvars`。

这个坑的隐蔽之处在于：**开发时不会暴露**（单请求、单线程），**上线后并发一高就开始串**，而且串出来的日志看起来完全合理（都是真实的日志，只是拼错了请求）——你会拿着错误的线索查半天。

### ⚠️ 坑 4：日志里打完整 prompt，等于把用户数据泄进日志系统

```python
logger.info("prompt: %s", full_prompt)   # ← 危险
```

**问题**：日志系统通常权限管控比数据库松得多（开发、运维、SRE 都能看）。把完整 prompt 打进去，等于把用户的预约信息、对话历史复制到了一个更不安全的地方。

**正确做法**：

```python
logger.info("llm.call model=%s prompt_tokens=%d prompt_sha=%s",
            model, tokens, hashlib.sha256(prompt.encode()).hexdigest()[:8])
```

只记**长度**和**哈希**：长度用于排查膨胀，哈希用于关联到 LLM 追踪平台（那边有权限管控）。

**想看完整 prompt？** 去 LangSmith / Langfuse 看，那边有访问控制和保留期设置。**日志不是存 prompt 的地方。**

### ⚠️ 坑 5：直方图不限制长度 = 内存泄漏

见 40.3.1。自己实现直方图必须限长，或直接用 Prometheus client 的分桶实现。

### ⚠️ 坑 6：高 QPS 下不采样，日志成本超过业务成本

SSE 流式接口（第 31 章）每个 token chunk 都可能打日志。1000 并发 × 每请求 200 chunk = 每秒 20 万条日志。

**日志系统的账单会比 LLM 账单还高。**

**正确做法**：分层采样——

```
错误/异常       → 100% 记
慢请求（>1s）   → 100% 记
正常请求        → 1% 采样
LLM prompt     → 0%（去追踪平台看）
```

### ⚠️ 坑 7：健康检查接口没有依赖检查

`main.py:84-87`：

```python
@app.get("/")
def root():
    """健康检查接口。"""
    return {"message": "智能实验室预约系统后端运行正常"}
```

**这个接口永远返回成功**，因为它不检查任何依赖。数据库挂了、向量库挂了、LLM API 挂了，它照样说"运行正常"。

后果：**负载均衡器认为实例健康，继续往一个已经废掉的实例上导流。**

**正确的健康检查要分两级**：

```python
@app.get("/healthz")
def liveness():
    """存活探针：进程还活着吗？不查依赖，挂了就重启。"""
    return {"status": "ok"}

@app.get("/readyz")
def readiness():
    """就绪探针：能接客吗？要查依赖，挂了就从 LB 摘掉。"""
    checks = {}
    try:
        with engine.connect() as conn:
            conn.execute(text("SELECT 1"))
        checks["db"] = "ok"
    except Exception as exc:
        checks["db"] = f"fail: {exc}"
    try:
        checks["vector"] = "ok" if kb_service.is_ready() else "empty"
    except Exception as exc:
        checks["vector"] = f"fail: {exc}"

    status = 200 if all(v == "ok" for v in checks.values()) else 503
    return JSONResponse(status_code=status, content={"checks": checks})
```

**这两个探针的区别面试常考**：
- **liveness 失败 → 重启容器**（进程死锁等情况）
- **readiness 失败 → 从负载均衡摘除**（依赖没准备好，但进程是好的）

用同一个接口做两件事是错的：数据库慢的时候你会不停重启健康的进程。

## 40.6 面试问答

### Q1：为什么 Agent 系统比普通 Web 服务更需要可观测性？

**答**：三个原因。

第一，**不可复现**。Agent 的输出依赖上下文窗口、查询改写结果、LLM 采样，同一个问题两次问可能不一样。没有记录就无法复现用户看到的那个错误。

第二，**多跳链路**。一次请求可能经过鉴权、限流、LLM 推理、工具调用、SQL、条件路由、人工审批等近十个环节，任何一环挂了用户看到的都是"失败"，没有链路追踪只能从头猜。

第三，**静默降级**。像 rerank 失败会回退融合排序，系统不报错、接口返回 200、监控全绿，但质量确实下降了。这类故障只有指标能抓到。

### Q2：日志、指标、链路追踪三者的区别？什么时候用哪个？

**答**：一句话区分——**日志查单点，指标看趋势，链路定位瓶颈**。

日志回答"某一次请求发生了什么"，指标回答"整体是不是变差了"（尤其是 P95 这种统计量，日志 grep 不出来），链路回答"这一次慢在哪个环节"。

三者互补：指标发现"P95 从 1.2s 涨到 3.8s" → 链路找到"是 LLM 调用慢了" → 日志看到"这一轮 prompt 有 8000 token"。缺任何一个，这个排查链都会断。

### Q3：trace_id 在 async 环境怎么传播？有什么坑？

**答**：用 `contextvars.ContextVar`，不能用 `threading.local`。

因为 async 环境下协程会在不同线程间切换，`threading.local` 绑的是线程，协程被调度到另一个线程时取值会丢或者串到别的请求上。

这个坑的隐蔽之处是开发时不暴露——单请求单线程跑得好好的，上线并发一高就开始串，而且串出来的日志看起来完全合理，你会拿着错误线索查很久。

### Q4：降级逻辑应该记日志还是记指标？

**答**：两个都要，但作用不同。日志给人排查用（为什么降级了），指标给机器告警用（降级了多少次）。

只记日志的典型后果是：**告警系统只盯 ERROR，降级打的是 WARNING，所以 rerank 全量挂了也没有告警**，你只能感觉到"最近回答变差了"却查不到原因。

正确做法是降级时同时 `metrics.inc("xxx_fallback_total")`，然后用指标配告警。**想让机器帮你盯着，就必须是指标。**

### Q5：能不能把完整 prompt 打进日志？

**答**：不能。日志系统的权限管控通常比数据库松得多，把完整 prompt 打进去等于把用户数据复制到一个更不安全的地方。

正确做法是只记**长度**和**哈希**：长度用于排查上下文膨胀，哈希用于关联到 LLM 追踪平台（LangSmith/Langfuse 那边有访问控制和保留期设置）。

**日志不是存 prompt 的地方，追踪平台才是。**

### Q6：liveness 和 readiness 探针有什么区别？能不能合成一个？

**答**：不能合成。它们的失败处理动作完全不同：

- **liveness 失败 → 重启容器**。用于检测进程死锁这种"进程活着但废了"的情况，所以它**不能查外部依赖**。
- **readiness 失败 → 从负载均衡摘除**。用于检测依赖没准备好，这时进程是好的，重启没用。

如果合成一个，数据库变慢时 readiness 会失败，而如果你按 liveness 处理就会不停重启一个健康的进程，把偶发抖动放大成全面故障。

我们项目现在只有一个 `GET /` 返回"运行正常"，不检查任何依赖，实际上连最弱的探针都算不上——这是已知待补的项。

### Q7：兜底异常处理器应该记日志吗？我们项目有没有这个问题？

**答**：必须记。我们项目**确实有这个问题**——`common/exceptions.py:50-55` 的 `global_exception_handler` 捕获了所有未处理异常，直接返回 500，但没有 `logger.exception`。

后果是线上出现 500 时，日志里什么都没有，你只知道"有个 500"，不知道是什么错、在哪一行。

修复就是在返回前加一行 `logger.exception(...)`，带上方法、路径、trace_id。安全和可观测性不是二选一：不把堆栈暴露给前端是对的，但服务端必须自己留一份。

### Q8：Agent 系统要额外观测什么传统系统没有的东西？

**答**：四个——**LLM 调用次数、工具调用序列、上下文窗口大小、检索质量**。

前三个是传统监控看不到的（它们只是普通 HTTP 请求或进程内调用），第四个连"错误"都算不上（检索变差了接口照样返回 200）。

具体指标建议：`llm_calls_per_request`（多轮 ReAct 会放大成本）、`prompt_tokens` 分布（预警上下文膨胀）、`tool_call_error_rate`（工具参数填错率）、`retrieval_hits`（召回为空的比例）。

其中 **`prompt_tokens` 的 P95/P50 比值**是最高性价比的一个——它同时预警成本、延迟、上下文膨胀三个问题。

### Q9：怎么接入 LangSmith / Langfuse？

**答**：对 LangChain / LangGraph 项目通常是环境变量级别的配置，比如 LangSmith 是 `LANGCHAIN_TRACING_V2=true` + `LANGCHAIN_API_KEY` + `LANGCHAIN_PROJECT`，配好后 `@tool` 和图的每次调用会自动上报。

**但我们项目没接**，这是明确的未做项。原因是要引入外部依赖和一个有数据出境问题的 SaaS（prompt 会发到第三方），毕业设计项目里我选择了本地日志方案。生产上如果做，我会优先选**可自部署的 Langfuse**，避免 prompt 数据出网。

### Q10：SSE 流式接口怎么观测？

**答**：三个要点。

第一，**总耗时要包含最后一个 chunk**，不能在 LLM 返回就结束计时，要等流写完。

第二，**要区分"首字延迟"和"总耗时"**——用户感知的是首字延迟（TTFB），成本相关的是总耗时，两个都要记。

第三，**断流要能观测**——客户端读了一半断开，服务端要知道（否则你会以为请求成功了）。我们项目在 `agent_service.py:490` 有 `logger.exception("Agent 流式执行失败")`，能覆盖服务端异常，但**客户端主动断开的情况没有计数**，这是可以补的一个指标。

## 40.7 速记卡

**四层**

| 层 | 回答什么 | 工具 |
|---|---|---|
| 日志 | 某一次发生了什么 | 结构化日志 + trace_id |
| 指标 | 整体趋势（P95） | Prometheus |
| 链路 | 这一次慢在哪 | OpenTelemetry |
| LLM 追踪 | 模型这一轮在想什么 | LangSmith / Langfuse |

**★ 日志查单点、指标看趋势、链路定位瓶颈**

**trace_id 要点**
- **用 `contextvars`，不用 `threading.local`** ← async 头号坑
- 从请求头 `X-Trace-Id` 接管（跨服务传播）
- **回写到响应头**（用户报 bug 能提供）

**★ 每个 except 必须有出口**：记日志 / 抛出去 / 计指标，三者全无就是 bug

**★ 降级要计指标**：`xxx_fallback_total` → 否则 WARNING 不触发告警

**★ 不打完整 prompt**：只记长度 + 哈希，完整内容去追踪平台看

**★ liveness ≠ readiness**：前者失败重启、后者失败摘流量；**不能查依赖 / 必须查依赖**

**Agent 专属四指标**
```
llm_calls_per_request    多轮 ReAct 成本放大器
prompt_tokens (P95/P50)  同时预警成本 + 延迟 + 上下文膨胀 ★最高性价比
tool_call_error_rate     工具参数填错率
retrieval_hits           召回为空比例
```

**采样**：错误 100% / 慢请求 100% / 正常 1% / prompt 0%

**项目现状（诚实）**
- ✅ 5 处降级都有 warning 日志，查询改写记了前后对比（`kb_service.py:190`）
- ❌ 无 trace_id、无结构化、无指标、无链路、无 LLM 追踪
- ⚠️ **`global_exception_handler` 不记日志**（`exceptions.py:50-55`）← 最严重
- ⚠️ **`GET /` 健康检查不查依赖**（`main.py:84-87`）

## 40.8 延伸思考

1. **如果只能加一个指标，加哪个？**
   提示：`prompt_tokens` 的 P95。理由：它同时是成本指标（token 直接计费）、延迟指标（prompt 越长越慢）、质量指标（上下文膨胀会导致中间信息丢失，第 19 章的 "lost in the middle"）。一个指标能预警三类问题，性价比最高。**选指标的思路是"覆盖面"，不是"看起来专业"。**

2. **告警应该怎么配才不会把人吵死？**
   提示：三条原则。① **告警要可执行**——收到告警必须有明确的下一步动作，否则就是噪音（"CPU 80%" 不可执行，"P95 超过 3s 持续 5 分钟"可执行）。② **分级**——P0 打电话（服务不可用）、P1 即时消息（错误率超阈值）、P2 工单（降级次数上升）。③ **要有持续时间条件**（`for: 5m`），瞬时抖动不算故障，否则你的告警会在每次发布时响一遍，然后所有人都开始忽略它。**一个被忽略的告警系统比没有告警系统更糟。**

3. **LLM 追踪平台把 prompt 发到第三方，合规上要注意什么？**
   提示：三个层面。① **数据出境**——如果用户在境内、SaaS 在境外，涉及数据出境合规；② **保留期**——追踪平台默认可能永久保存，要设保留期和脱敏规则；③ **访问控制**——谁能看 prompt 决定了谁能看到用户数据。所以生产上优先选**可自部署方案**（Langfuse 有开源自部署版），并在上报前做 PII 脱敏。**这一条在金融、医疗行业是硬性要求。**

4. **有了完整的可观测性，还需要离线评测吗？**
   提示：**需要，两者测的东西不一样**。可观测性测的是"系统运行得怎么样"（延迟、错误率、成本），离线评测测的是"系统做得对不对"（faithfulness、Hit@K）。**一个质量退化的系统可以运行得非常健康**——召回变差了，接口照样 200，延迟照样 200ms，只有离线评测能发现。反过来，一个评测分很高的系统可能线上根本跑不起来。**可观测性是体检，评测是考试，都要。**
