# 第 16 章 · 工具节点与条件路由：循环是怎么"停下来"的

> **这一章要回答的核心问题**：`tool_node` 里那个 `for tc in tool_calls` 循环到底在干什么？多次工具调用怎么保证消息配对？路由函数怎么写才不会让图跑飞？"停下来"这个看似简单的动作，工程上有哪些坑？

---

## 16.1 引子：一个"停不下来"的 Agent 有多可怕

先看一个真实的故障场景。

某天你上线了一个 Agent，用户问："帮我预约明天的显微镜实验室。"然后：

```
Step 1: 模型调 create_lab_reservation → 时段冲突
Step 2: 模型看错误，换时段再调 → 实验室不存在
Step 3: 模型换个实验室再调 → 参数格式错
Step 4: ...继续
Step 5: ...继续
Step 10: 撞上 recursion_limit，抛异常
```

用户等了 40 秒，看到一句"大模型调用失败"。而这 10 步里，你烧掉了：**10 次 LLM 调用 + 10 次工具调用 + 累积约 3 万 token**。

更糟的情况：如果没有 `recursion_limit`，或者你的工具是收费的外部 API，这就是一个**无上限的烧钱循环**。

**"让循环停下来"看起来是最简单的事（不就是个 if 判断吗），但它实际上是 Agent 工程里最容易出事的地方。**这一章我们把"停下来"这件事拆开看清楚。

---

## 16.2 停下来有三条路，缺一不可

| 停止方式 | 触发条件 | 谁决定 | 用户体验 |
|---|---|---|---|
| **正常收敛** | 模型不再产生 `tool_calls` | 模型 | ✅ 最好 |
| **人工拦截** | 命中写库工具 → `interrupt` | 系统 | ✅ 好（可控） |
| **兜底熔断** | 撞上 `recursion_limit` / 工具超时 | 框架 | ❌ 差（要兜底文案） |

本项目三条全做了。我们一个个看。

---

## 16.3 第一条路：正常收敛（模型决定停）

### 16.3.1 判定逻辑

`agent_service.py:147-152`：

```python
def _route_after_agent(state: AgentState) -> str:
    """模型返回 tool_calls 则先进审批节点，否则结束本轮。"""
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "approval"
    return "end"
```

判定依据只有一个：**最后一条消息有没有 `tool_calls`**。

- 有 → 模型还想做事 → 继续循环
- 没有 → 模型认为信息够了 → 结束

### 16.3.2 为什么是"最后一条"？

因为 `state["messages"]` 是**按时间顺序累积**的，`[-1]` 永远是最新产生的消息。在 `agent` 节点刚执行完时，最后一条一定是刚返回的 `AIMessage`。

**这里有个隐含假设**：`agent` 节点是最后一个写入 messages 的节点。如果图结构改了（比如在 agent 后插入别的节点），这个假设就失效了。

更防御的写法是**从后往前找最后一条 AIMessage**：

```python
def _route_after_agent(state: AgentState) -> str:
    for msg in reversed(state["messages"]):
        if isinstance(msg, AIMessage):
            return "approval" if getattr(msg, "tool_calls", None) else "end"
    return "end"
```

本项目用的是简化版，因为在当前图结构下 `[-1]` 一定正确。**这是一个"已知约束下的简化"，面试时可以主动指出，说明你理解边界。**

### 16.3.3 `getattr` vs 直接访问

```python
if getattr(last, "tool_calls", None):     # ✅ 本项目
if last.tool_calls:                        # ❌ 会崩
```

为什么要 `getattr`？因为 `AnyMessage` 是个联合类型，可能是：

- `HumanMessage` —— **没有** `tool_calls` 属性
- `AIMessage` —— 有（默认为 `[]` 或 `None`）
- `ToolMessage` —— 没有
- `SystemMessage` —— 没有

访问不存在的属性会抛 `AttributeError`，直接让整个请求 500。`getattr(obj, name, default)` 成本几乎为零，但消灭了一整类崩溃。

> 这是 Python 处理"鸭子类型 + 联合类型"的标准防御写法。面试时提到这个细节会很加分。

### 16.3.4 如何让模型"更愿意停下来"？

有时候模型会过度调用工具——明明知道答案了还要再查一次。三个优化手段：

**① System Prompt 约束**（本项目已用）

`agent_service.py:64-88` 的 SYSTEM_PROMPT 里明确写了：

```
## 必须遵守
当用户提到今天、明天、后天等日期问题时，请先调用 get_today 获取日期，
不要直接返回"我需要确定明天的具体日期"。

提交预约前必须向用户复述：实验室ID与名称（或设备ID和名称）、日期、开始时间、结束时间，
并得到用户确认后再调用 create_lab_reservation。系统会在真正落库前再次弹出确认，
这是最后一道保护，用户没有明确确认时不要硬调工具。
```

注意最后这句："**系统会在真正落库前再次弹出确认，这是最后一道保护**"。这是**显式告诉模型有兜底机制**，减少模型因为"怕出错"而反复确认的倾向。

**② 工具返回里给明确的"够了"信号**

比如检索工具在返回内容时附带 `{"has_more": false, "total": 3}`，让模型知道没有更多可查了。

**③ `temperature=0`**

`agent_service.py:256-262`：

```python
llm = ChatOpenAI(
    api_key=settings.LLM_API_KEY,
    base_url=settings.LLM_BASE_URL,
    model=settings.LLM_MODEL,
    temperature=0,
    streaming=True,
).bind_tools(tools)
```

`temperature=0` 让输出更确定，减少"这轮要不要调工具"的随机抖动。Agent 场景**强烈建议 temperature=0**（或极低），因为我们要的是可靠的工具调用决策，不是创造性。

## 16.4 第二条路：人工拦截（系统决定停）

### 16.4.1 为什么要插一个 approval 节点

本项目的图有个不寻常的地方：

```python
graph.add_conditional_edges(
    "agent", _route_after_agent, {"approval": "approval", "end": END}
)
graph.add_edge("approval", "tools")
```

**只要模型想调工具，就先进 `approval`，再进 `tools`。**哪怕是要调只读的 `search_lab_docs`。

这看起来有点浪费（15.6.4 讨论过），但它换来了一个极其重要的性质：

> **写库操作和读操作走同一条路径，因此"拦截"只需要在一个地方实现。**

### 16.4.2 approval 节点的实现

`agent_service.py:272-287`：

```python
async def approval_node(state: AgentState) -> dict:
    """审批节点：命中写库工具时 interrupt 暂停，等用户确认。"""
    last = state["messages"][-1]
    tool_calls = getattr(last, "tool_calls", None) or []
    write_calls = [tc for tc in tool_calls if tc.get("name") in WRITE_TOOLS]
    if not write_calls:
        return {"approval": None}

    payload = {
        "tool": write_calls[0].get("name"),
        "args": write_calls[0].get("args") or {},
    }
    decision = interrupt(payload)
    if not isinstance(decision, dict):
        decision = {"approved": bool(decision)}
    return {"approval": decision}
```

关键逻辑三步：

**① 筛选写库工具**

```python
write_calls = [tc for tc in tool_calls if tc.get("name") in WRITE_TOOLS]
```

`WRITE_TOOLS` 是一个模块级集合（`agent_service.py:100`）：

```python
WRITE_TOOLS = {"create_lab_reservation"}
```

**用集合而不是列表**，因为 `in` 判断是 O(1)。更重要的是：**这是一个"白名单"设计**——只有显式声明为写库的工具才会被拦截。新增工具时如果忘了加进这个集合，它就是"不受保护的"，这是一个安全隐患，也是为什么这个常量要放在显眼位置并加注释。

**② 只处理第一个写库调用**

```python
payload = {"tool": write_calls[0].get("name"), "args": write_calls[0].get("args") or {}}
```

注意取的是 `write_calls[0]`。如果模型一次返回多个写库调用怎么办？**目前只拦第一个**。

这是一个已知的简化。更严谨的做法是把**所有**写库调用打包成一个 payload 让用户一次性确认：

```python
payload = {"calls": [{"tool": tc["name"], "args": tc.get("args")} for tc in write_calls]}
decision = interrupt(payload)
```

> **面试可以这么说**："目前审批节点只拦截第一个写库调用。这是简化：因为我们的写库工具只有一个（create_lab_reservation），且 System Prompt 已经要求一次只提交一个预约。如果后续要支持批量操作，需要改成批量确认的 payload 格式。"——承认边界 + 说明改进方向，比假装完美更可信。

**③ `interrupt()` 是魔法发生的地方**

```python
decision = interrupt(payload)
```

这一行看起来平平无奇，但它做了极其不平凡的事：

1. 抛出一个特殊的 `GraphInterrupt` 异常
2. LangGraph 捕获它，**保存当前 state 到 checkpointer**
3. `ainvoke` 返回，result 里带着 `__interrupt__` 字段
4. 下次用 `Command(resume=...)` 调用时，**从这一行继续执行**，`decision` 拿到 resume 的值

也就是说：**同一个函数，第一次执行到 `interrupt` 就"冻结"，第二次从冻结处"解冻"并继续往下走。**

这是 LangGraph 最反直觉也最强大的能力。第 18 章会完整拆解它的实现原理。这里你只需要记住：

> `interrupt()` 之前的变量都还在（因为 state 被完整保存），`interrupt()` 的返回值是用户传进来的决策。

**④ 类型防御**

```python
if not isinstance(decision, dict):
    decision = {"approved": bool(decision)}
```

用户（前端）可能传 `true`/`false`，也可能传 `{"approved": true}`。统一归一化成 dict，后面 `tool_node` 就能统一用 `approval.get("approved")` 读取。

### 16.4.3 `{"approval": None}` 的作用

再强调一次这个易漏点：

```python
if not write_calls:
    return {"approval": None}
```

不是 `return {}`，而是**显式置 None**。因为如果上一次对话留下了 `approval={"approved": True}`，而这次不需要审批，残留的 `True` 会让后续的写库工具被"自动放行"。

虽然在当前图结构下 `tool_node` 只在 `approval` 节点之后执行，看似不会有问题，但**防御性地清空状态是好习惯**——尤其当图结构变化时。

## 16.5 第三条路：兜底熔断

### 16.5.1 recursion_limit

```python
{"configurable": {"thread_id": thread_id}, "recursion_limit": 10}
```

撞上后抛 `GraphRecursionError`。在 `run_agent` 里会被 `except Exception` 捕获，变成"大模型调用失败，请稍后重试"。

**这个文案其实不准确**。更好的做法是对 `GraphRecursionError` 单独处理：

```python
from langgraph.errors import GraphRecursionError

try:
    result = await agent.ainvoke(inputs, _make_config(thread_id))
except GraphRecursionError:
    raise BusinessException(message="这个问题的处理步骤过多，请换个更具体的问法")
except BusinessException:
    raise
except Exception:
    raise BusinessException(message="大模型调用失败，请稍后重试")
```

> 📝 **这是一个可以改进的点**，如果你想在简历里加一条优化，这是个不错的选择：区分异常类型，给出准确的错误提示。

### 16.5.2 工具超时与重试

`agent_service.py:155-173`（第 20 章详述）：

```python
async def _invoke_tool_with_retry(tool, args: dict) -> str:
    last_error: Exception | None = None
    for attempt in range(settings.TOOL_MAX_RETRIES + 1):
        try:
            result = await asyncio.wait_for(
                asyncio.to_thread(tool.invoke, args),
                timeout=settings.TOOL_TIMEOUT_SECONDS,
            )
            return result.content if hasattr(result, "content") else str(result)
        except Exception as exc:
            last_error = exc
            if attempt < settings.TOOL_MAX_RETRIES:
                await asyncio.sleep(0.2 * (attempt + 1))
    return json.dumps({"ok": False, "error": str(last_error)}, ensure_ascii=False)
```

**这是循环能在"工具卡住"时仍然推进的关键**：不会因为一次 DB 慢查询把整张图挂死 30 秒以上。

## 16.6 tool_node 深入：一次执行多个工具

现在仔细看 `tool_node`（`agent_service.py:289-315`）：

```python
async def tool_node(state: AgentState) -> dict:
    """工具节点：执行模型请求的工具，写库工具遵守审批结果。"""
    last = state["messages"][-1]
    tool_calls = getattr(last, "tool_calls", None) or []
    approval = state.get("approval")
    messages: list[ToolMessage] = []

    for tc in tool_calls:
        name = tc.get("name")
        args = tc.get("args") or {}
        tool = tools_by_name.get(name)

        if name in WRITE_TOOLS and (not approval or not approval.get("approved")):
            content = "用户取消了本次操作，未执行。"
        elif tool is None:
            content = f"未找到工具：{name}"
        else:
            content = await _invoke_tool_with_retry(tool, args)

        messages.append(
            ToolMessage(content=content, tool_call_id=tc.get("id"), name=name)
        )
    return {"messages": messages}
```

### 16.6.1 为什么用 for 而不是 gather？

模型可能一次返回多个 tool_calls（parallel tool calling）。这里用 `for ... await` 是**串行**执行。

如果要并行：

```python
results = await asyncio.gather(*[
    _invoke_tool_with_retry(tools_by_name.get(tc["name"]), tc["args"])
    for tc in tool_calls
])
```

本项目为什么选择串行？三个理由：

| 理由 | 说明 |
|---|---|
| **数据库事务安全** | 工具大量涉及 DB 读写。并行执行同一个 `Session` 会导致事务竞争（第 11 章） |
| **错误定位清晰** | 串行下，出错的一目了然；并行下异常聚合较复杂 |
| **实际收益有限** | 我们的场景多数只调 1 个工具，并行加速用不上 |

> **面试标准答法**："我们支持接收 parallel tool calling（模型一次返回多个调用），但执行层选择了串行。因为工具主要是同一个数据库 Session 上的读写操作，并行会带来事务竞争和连接池压力。对于纯读且无状态的工具（比如独立 HTTP 查询），可以考虑用 asyncio.gather 并行，这是后续优化方向。"

### 16.6.2 三分支的错误降级

```python
if name in WRITE_TOOLS and (not approval or not approval.get("approved")):
    content = "用户取消了本次操作，未执行。"
elif tool is None:
    content = f"未找到工具：{name}"
else:
    content = await _invoke_tool_with_retry(tool, args)
```

判断顺序有讲究：**审批检查在最前**。因为即便工具存在，用户没批准也不能执行。这是安全优先的排序。

**三种降级文案的设计意图**：

| 文案 | 意图 |
|---|---|
| `"用户取消了本次操作，未执行。"` | 让模型知道"不是工具失败，是用户拒绝"，从而**不要重试**，而是告知用户 |
| `"未找到工具：{name}"` | 给模型一个明确的信号，让它换个名字（模型偶尔会拼错工具名） |
| `{"ok": false, "error": ...}` | 结构化错误，让模型能提取原因自纠 |

注意第一条和其他两条的区别：**它不带"请重试"的暗示**。如果写成"操作失败"，模型可能会以为要重试，然后再次触发审批——用户就会被反复弹窗。文案措辞直接影响模型行为，这是 Prompt 工程在工具层的延伸。

### 16.6.3 ToolMessage 的三个字段

```python
ToolMessage(content=content, tool_call_id=tc.get("id"), name=name)
```

| 字段 | 作用 | 不填会怎样 |
|---|---|---|
| `content` | 工具结果，模型实际读到的内容 | 模型看不到结果 |
| `tool_call_id` | **必须**与 `AIMessage.tool_calls[i].id` 一致 | OpenAI 协议报 400 |
| `name` | 工具名，帮助模型区分结果来源 | 不影响协议，但提升模型理解 |

**`tool_call_id` 配对是硬性协议约束**。完整的消息序列必须长这样：

```json
[
  {"role": "user", "content": "预约显微镜实验室"},
  {"role": "assistant", "content": null, "tool_calls": [
      {"id": "call_abc", "type": "function",
       "function": {"name": "create_lab_reservation", "arguments": "{...}"}}
  ]},
  {"role": "tool", "tool_call_id": "call_abc", "content": "{\"ok\": true}"},   ← id 必须匹配
  {"role": "assistant", "content": "预约成功"}
]
```

> ⚠️ **坑 1（真实）**：如果你把 `tool_call_id` 写死成错误值，API 会立刻返回：
> ```
> BadRequestError: An assistant message with 'tool_calls' must be followed by
> tool messages responding to each tool_call_id.
> ```
> 这是 Agent 开发最常见的 400 错误之一。第 19 章讲上下文裁剪时会再遇到它——**裁剪时如果把 ToolMessage 删了但留下 AIMessage 的 tool_calls，就会触发这个错**。

### 16.6.4 一次执行多个工具的完整示例

假设模型一次返回两个调用：

```python
tool_calls = [
    {"id": "call_1", "name": "list_open_labs", "args": {"keywords": "显微镜"}},
    {"id": "call_2", "name": "get_today", "args": {}},
]
```

`tool_node` 会产生：

```python
[
    ToolMessage(content='{"total":1,"labs":[...]}', tool_call_id="call_1", name="list_open_labs"),
    ToolMessage(content="2026-10-17", tool_call_id="call_2", name="get_today"),
]
```

**两条都追加到 messages**，然后回 `agent`，模型一次性看到两个结果。

注意：**审批逻辑对多个写库调用的处理**——如果两个都是写库工具，两个都会被拦（因为 `name in WRITE_TOOLS` 对每个都成立），但 `approval` 只记录了第一个的决策。这就是 16.4.2 提到的简化带来的边界。

## 16.7 路由设计的五个模式

除了本项目的 `_route_after_agent`，LangGraph 里常见的路由模式还有这些。了解它们能让你在设计复杂 Agent 时有更多工具。

### 模式 1：二元路由（本项目）

```python
def route(state) -> str:
    return "continue" if need_more(state) else "end"
```

最简单，覆盖 80% 场景。

### 模式 2：多分支路由

```python
def route(state) -> str:
    intent = classify(state)
    if intent == "search":
        return "search_node"
    if intent == "book":
        return "approval"
    if intent == "chitchat":
        return "chat_node"
    return "end"

graph.add_conditional_edges("router", route, {
    "search_node": "search_node",
    "approval": "approval",
    "chat_node": "chat_node",
    "end": END,
})
```

### 模式 3：带重试计数的路由（防跑飞）

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]
    retry_count: int

def route(state) -> str:
    if not state["messages"][-1].tool_calls:
        return "end"
    if state.get("retry_count", 0) >= 3:
        return "fallback"        # 重试 3 次还不行 → 走降级节点
    return "tools"

async def tool_node(state) -> dict:
    ...
    return {"messages": [...], "retry_count": state.get("retry_count", 0) + 1}
```

**这是比单纯 `recursion_limit` 更精细的控制**：不是硬崩，而是**优雅降级**到"基于已有信息给出阶段性答复"。

### 模式 4：基于模型判断的路由（LLM-as-Router）

```python
def route(state) -> str:
    last = state["messages"][-1].content
    verdict = llm.invoke(f"这句话是不是已经完整回答了用户？只回答 yes/no。\n{last}")
    return "end" if "yes" in verdict.content.lower() else "tools"
```

灵活但慢且贵（多一次 LLM 调用），一般不建议。

### 模式 5：Send 动态并行（LangGraph 高级特性）

```python
from langgraph.types import Send

def route(state) -> list[Send]:
    """根据 state 动态决定并行派发几个任务。"""
    return [Send("process_lab", {"lab_id": lid}) for lid in state["lab_ids"]]
```

返回 `Send` 列表而不是字符串，可以**把同一个节点并行派发多次**，每次带不同状态。适合 map-reduce 型任务。

## 16.8 最小骨架：一个带审批和熔断的完整图

下面这个例子把本章所有概念串起来，**可直接运行**（用假 LLM，不需要 API Key）：

```python
"""
minimal_guard.py —— 带审批拦截和熔断的 LangGraph 最小骨架
运行：pip install langgraph langchain-core && python minimal_guard.py
"""
import asyncio
import json
from typing import Annotated, TypedDict

from langchain_core.messages import AIMessage, AnyMessage, HumanMessage, ToolMessage
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.types import interrupt

# ── State ─────────────────────────────────────────────────
class State(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]
    approval: dict | None
    tool_calls_count: int          # 用于熔断计数

WRITE_TOOLS = {"create_reservation"}

# ── 假 LLM：前两轮调工具，第三轮给答案 ────────────────────
_call_count = 0

async def fake_llm_node(state: State) -> dict:
    global _call_count
    _call_count += 1
    print(f"  [agent] 第 {_call_count} 次调用模型")

    if _call_count == 1:
        # 第一次：要查一下
        return {"messages": [AIMessage(
            content="",
            tool_calls=[{"id": "c1", "name": "query_lab", "args": {"lab": "显微镜"}}],
        )]}
    if _call_count == 2:
        # 第二次：要写库（会被拦截）
        return {"messages": [AIMessage(
            content="",
            tool_calls=[{"id": "c2", "name": "create_reservation",
                         "args": {"lab": "显微镜", "time": "14:00"}}],
        )]}
    # 第三次：给答案
    return {"messages": [AIMessage(content="已为您预约显微镜实验室 14:00")]}


# ── 审批节点 ──────────────────────────────────────────────
async def approval_node(state: State) -> dict:
    last = state["messages"][-1]
    calls = getattr(last, "tool_calls", None) or []
    writes = [tc for tc in calls if tc.get("name") in WRITE_TOOLS]

    if not writes:
        print("  [approval] 非写库工具，放行")
        return {"approval": None}          # ★ 显式清空，不留残值

    print(f"  [approval] ⏸ 拦截写库工具：{writes[0]['name']}，等待用户确认")
    decision = interrupt({"tool": writes[0]["name"], "args": writes[0]["args"]})
    if not isinstance(decision, dict):
        decision = {"approved": bool(decision)}
    print(f"  [approval] ▶ 收到决策：{decision}")
    return {"approval": decision}


# ── 工具节点 ──────────────────────────────────────────────
TOOLS = {
    "query_lab": lambda args: json.dumps({"available": True}, ensure_ascii=False),
    "create_reservation": lambda args: json.dumps({"ok": True, "id": 99}, ensure_ascii=False),
}

async def tool_node(state: State) -> dict:
    last = state["messages"][-1]
    calls = getattr(last, "tool_calls", None) or []
    approval = state.get("approval")
    out = []

    for tc in calls:
        name, args = tc.get("name"), tc.get("args") or {}
        if name in WRITE_TOOLS and (not approval or not approval.get("approved")):
            content = "用户取消了本次操作，未执行。"
        elif name not in TOOLS:
            content = f"未找到工具：{name}"
        else:
            content = TOOLS[name](args)
        print(f"  [tools] {name}({args}) → {content}")
        out.append(ToolMessage(content=content, tool_call_id=tc.get("id"), name=name))

    return {"messages": out, "tool_calls_count": (state.get("tool_calls_count") or 0) + 1}


# ── 路由：二元 + 计数熔断 ─────────────────────────────────
def route(state: State) -> str:
    last = state["messages"][-1]
    if not getattr(last, "tool_calls", None):
        print("  [route] 无 tool_calls → end")
        return "end"
    if (state.get("tool_calls_count") or 0) >= 3:
        print("  [route] ⚠ 工具调用已达 3 次 → 强制结束")
        return "end"
    print("  [route] 有 tool_calls → approval")
    return "approval"


def build():
    g = StateGraph(State)
    g.add_node("agent", fake_llm_node)
    g.add_node("approval", approval_node)
    g.add_node("tools", tool_node)
    g.add_edge(START, "agent")
    g.add_conditional_edges("agent", route, {"approval": "approval", "end": END})
    g.add_edge("approval", "tools")
    g.add_edge("tools", "agent")
    return g.compile()


async def main():
    from langgraph.types import Command
    graph = build()
    cfg = {"configurable": {"thread_id": "demo"}, "recursion_limit": 12}

    print("=== 第一次调用（会撞上 interrupt）===")
    result = await graph.ainvoke({"messages": [HumanMessage("预约显微镜")]}, cfg)
    print(f"  __interrupt__ = {result.get('__interrupt__')}")

    print("\n=== 第二次调用（用户批准，从断点继续）===")
    result = await graph.ainvoke(Command(resume={"approved": True}), cfg)
    for i, m in enumerate(result["messages"]):
        c = m.content or f"<tool_calls:{len(getattr(m,'tool_calls',[]) or [])}>"
        print(f"  [{i}] {type(m).__name__}: {c}")


if __name__ == "__main__":
    asyncio.run(main())
```

**预期输出**（关键部分）：

```
=== 第一次调用（会撞上 interrupt）===
  [agent] 第 1 次调用模型
  [route] 有 tool_calls → approval
  [approval] 非写库工具，放行
  [tools] query_lab({'lab': '显微镜'}) → {"available": true}
  [agent] 第 2 次调用模型
  [route] 有 tool_calls → approval
  [approval] ⏸ 拦截写库工具：create_reservation，等待用户确认
  __interrupt__ = [Interrupt(value={'tool': 'create_reservation', 'args': {...}})]

=== 第二次调用（用户批准，从断点继续）===
  [approval] ▶ 收到决策：{'approved': True}
  [tools] create_reservation(...) → {"ok": true, "id": 99}
  [agent] 第 3 次调用模型
  [route] 无 tool_calls → end
  [0] HumanMessage: 预约显微镜
  [1] AIMessage: <tool_calls:1>
  [2] ToolMessage: {"available": true}
  [3] AIMessage: <tool_calls:1>
  [4] ToolMessage: {"ok": true, "id": 99}
  [5] AIMessage: 已为您预约显微镜实验室 14:00
```

**从这个输出确认四件事**：

1. **interrupt 真的停在了原地**：第一次调用在 approval 节点冻结，第二次从那里继续（注意第二次没有重新执行 agent 节点）。
2. **`__interrupt__` 携带 payload**：前端就是靠它渲染确认框的。
3. **消息序列严格配对**：`AIMessage(tool_calls)` 后面紧跟同 id 的 `ToolMessage`。
4. **循环靠 `tools → agent` 边驱动**，出口靠路由返回 `end`。

## 16.10 面试问答

### Q1：你的 Agent 怎么保证不会无限循环？

**答**：三层防护。

第一层是**模型自主收敛**：路由函数检查最后一条消息有没有 `tool_calls`，没有就结束。这是正常路径，占绝大多数情况。

第二层是**人工拦截**：命中写库工具（白名单 `WRITE_TOOLS`）时 `interrupt` 暂停，等用户确认。这既防了不可逆操作，也天然打断了可能的重试循环——因为用户看到弹窗，可以拒绝。

第三层是**兜底熔断**：`recursion_limit=10` 硬限制，加上工具层 30 秒超时 + 1 次重试。工具卡住不会拖死整张图。

补充一点：`recursion_limit` 是按**超步**计数的，本项目一轮完整循环是 4 个超步，所以 10 大约支持 2-3 轮工具调用。

### Q2：工具调用失败了，你怎么处理？

**答**：核心原则是**不抛异常，把错误变成一条 Observation 消息回喂给模型**。

具体分三种情况：用户拒绝 → 返回"用户取消了本次操作，未执行。"（措辞不带重试暗示，避免模型反复触发审批）；工具不存在 → 返回"未找到工具：xxx"（让模型换个名字）；执行报错 → 返回 `{"ok": false, "error": "..."}` 结构化 JSON（让模型提取原因自纠，比如时段冲突就换个时段）。

工具层还有超时和有限重试：30 秒超时通过 `asyncio.wait_for` 实现，失败重试 1 次，最终失败才回填错误。

这样设计的原因是：抛异常会中断整个循环，用户只能重来；而把错误变成 Observation，模型有机会自己救回来。

### Q3：`tool_call_id` 有什么用？不填会怎样？

**答**：它是 `AIMessage.tool_calls` 和 `ToolMessage` 之间的关联键，OpenAI 消息协议要求**每个 tool_call 必须有一条同 id 的 tool_message 回应**。不填或填错，API 会返回 400：

```
An assistant message with 'tool_calls' must be followed by tool messages
responding to each tool_call_id.
```

这个约束还有个连带影响：做上下文裁剪时，不能孤立地删掉 `ToolMessage` 而保留对应的 `AIMessage`，否则下次调用模型就会报这个错。所以我们的裁剪逻辑里专门保护了"AI 带 tool_calls + 其后紧邻的 ToolMessage"这个配对（第 19 章）。

### Q4：模型一次返回多个 tool_calls，你怎么执行？

**答**：`tool_node` 里用 `for` 循环遍历，串行执行，每个调用产生一条独立的 `ToolMessage`，全部追加到 messages 后一起回给模型。

选择串行而不是 `asyncio.gather` 并行，是因为我们的工具主要是同一个数据库 Session 上的读写操作，并行会带来事务竞争和连接池压力。对于纯读且无状态的工具可以考虑并行，这是后续优化方向。

另外有个边界：如果多个调用里都有写库工具，目前审批只拦截第一个。这是简化——我们的写库工具只有一个，且 prompt 已要求一次只提交一个预约。要支持批量操作的话，需要改成批量确认的 payload。

### Q5：`approval` 字段为什么在不需要审批时返回 `{"approval": None}` 而不是 `{}`？

**答**：为了**显式清空上一次的审批决策**。如果返回空 dict，`approval` 字段保持上次的值（比如 `{"approved": True}`），这个残留值可能在后续流程里意外放行某个写库操作。

虽然当前图结构下 `tool_node` 只在 approval 之后执行，看似安全，但图结构一旦调整就可能出问题。防御性地清空状态成本很低，价值很高。

### Q6：条件边的路由函数有什么设计原则？

**答**：三条。

第一，**路由函数只做判断，不做计算**。它是纯函数，读 state、返回字符串，不应该有副作用。业务逻辑都在节点里。

第二，**返回值用业务语义而不是节点名**（"approval"/"end" 而不是 "node_2"），然后通过映射字典关联到节点。这样重构图结构时不用改路由逻辑，路由函数也更好测试。

第三，**用 `getattr` 做防御**。state 里的消息是联合类型，`HumanMessage`/`ToolMessage` 都没有 `tool_calls` 属性，直接访问会 `AttributeError` 让整个请求 500。

## 16.11 速记卡

> **停下来有三条路：模型收敛（最好）、人工拦截（可控）、兜底熔断（保命）。缺一不可。**

**路由判定**：`getattr(last, "tool_calls", None)` → 有则继续，无则 END

**审批三步**：筛写库 → `interrupt(payload)` → 归一化 decision

**工具三降级**：
```python
用户拒绝 → "用户取消了本次操作，未执行。"   # 措辞不带重试暗示
工具不存在 → f"未找到工具：{name}"          # 让模型换名字
执行失败 → {"ok": false, "error": ...}      # 让模型自纠
```

**ToolMessage 三字段**：`content`（结果）/ `tool_call_id`（**必须配对**）/ `name`（来源）

**为什么串行不并行**：同一 DB Session 并行会事务竞争

**recursion_limit 换算**：一轮完整循环 = 4 超步，`10` ≈ 2-3 轮

**五种路由模式**：二元 / 多分支 / 带重试计数（优雅降级）/ LLM-as-Router / Send 动态并行

**代码位置**：
- 路由：`agent_service.py:147-152`
- 审批：`agent_service.py:272-287`
- 工具：`agent_service.py:289-315`
- 熔断：`agent_service.py:332-333`
- 工具定义：`agent_tools.py:68-198`

## 16.12 延伸思考

1. **如果想让"撞上 recursion_limit"也给用户一个好体验，你会怎么做？**
   提示：捕获 `GraphRecursionError`，然后把已有轨迹交给模型，让它"基于目前掌握的信息给出阶段性答复"。这是从"失败"到"降级"的转变，可以写进简历。

2. **多个写库调用的批量确认，payload 应该怎么设计？前端怎么渲染？**
   提示：payload 用列表，前端渲染成"以下 3 项操作需要确认"的清单，支持单独勾选。

3. **`tool_node` 里 `await` 在循环中，如果某个工具耗时 25 秒（未超时），整轮请求会很慢。怎么优化？**
   提示：给不同工具设不同超时（读工具 5 秒、写工具 30 秒）；或者对无依赖的工具用 `gather` 并行；或者加缓存。
