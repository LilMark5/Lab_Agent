# 第 35 章 · 记忆系统：短期记忆与长期记忆

> **这一章要回答的核心问题**：Agent 的"记忆"到底是什么？对话历史算记忆吗？为什么"记住用户偏好"比"记住对话"难得多？本项目做了哪一层？

---

## 35.1 引子：Agent 的三种"失忆"

用户和你的 Agent 有过这些交互：

| 场景 | 用户期望 | 当前是否支持 |
|---|---|---|
| **同一次会话第 5 轮**，用户说"它几点关" | Agent 知道"它"指什么 | ✅ 支持（checkpointer） |
| **隔了一天，新会话**，"上次我预约的是哪个实验室？" | Agent 记得历史 | ❌ 不支持 |
| **任何会话**，"我喜欢上午做实验" | Agent 记住这个偏好 | ❌ 不支持 |

**这三种对应三层记忆**：

| 层次 | 名称 | 时间跨度 | 本项目 |
|---|---|---|---|
| **短期记忆** | 对话内上下文 | 单次会话 | ✅ checkpointer |
| **中期记忆** | 跨会话历史 | 天~月 | ❌ 未实现 |
| **长期记忆** | 用户画像/知识沉淀 | 永久 | ❌ 未实现 |

## 35.2 第一层：短期记忆（对话内上下文）

**这就是第 17 章讲的 checkpointer**，但放在"记忆"的框架下理解会更完整。

### 35.2.1 它解决什么

```
轮次1: 用户："显微镜实验室在哪？"
       Agent："实验楼 A 座 301。"
轮次2: 用户："里面有什么设备？"          ← "里面" 依赖轮次1
       Agent："有扫描电镜、离心机……"
轮次3: 用户："离心机明天有空吗？"        ← "离心机" 依赖轮次2
```

每一轮依赖前面的上下文。checkpointer 保存完整 messages，每轮自动加载。

### 35.2.2 它的局限

| 局限 | 说明 |
|---|---|
| **按 thread_id 隔离** | 新 thread 就是新会话，旧的一概不知 |
| **会膨胀** | 第 19 章的 token 问题、第 17 章的存储问题 |
| **无语义检索** | 只能"全量带上"，不能"按需取用" |
| **无压缩** | 早期对话只能是原始文本（或有损裁剪） |

**本质上，短期记忆 = "把全部历史塞进上下文"**。这个策略在轮次少时有效，轮次多时崩塌。

## 35.3 第二层：跨会话记忆（中期）

**目标**：用户在周一的会话里预约了实验室，周五问"我上次预约的是哪个"，Agent 要能答。

### 35.3.1 三种实现方案

**方案 A：从业务数据库查**

```
用户问"我上次预约的是哪个实验室？"
  → Agent 调 query_my_reservations 工具
  → 查 reservations 表（按 user_id + 时间排序）
  → 返回最近的预约
```

**这是最简单也最可靠的方案** —— 因为数据本来就在数据库里（结构化）。

> **本项目其实有这个能力**：`reservation_service` 有查询用户预约的方法，只是**没暴露成 Agent 工具**。加一个 `query_my_reservations` 工具就能支持。
>
> 📝 **这是一个低成本高价值的改进**，可以写进简历。

**方案 B：会话摘要 + 检索**

```
每次会话结束 → LLM 生成一段摘要 → 存入向量库（关联 user_id）
新会话开始 → 检索相关的历史摘要 → 注入上下文
```

**优点**：能记住非结构化的内容（"上次我们讨论了离心机的维护周期"）
**缺点**：多一次 LLM 调用、摘要有信息损失

**方案 C：结构化事实抽取**

```
会话中 → 抽取事实三元组 → 存入图数据库/关系表
  (用户, 预约了, 显微镜实验室@2026-10-18)
  (用户, 偏好, 上午做实验)
```

这是"知识图谱"路线，最强大也最复杂。

### 35.3.2 方案对比

| 方案 | 实现成本 | 适用 | 本项目 |
|---|---|---|---|
| **A：查业务库** | **低** | 结构化历史（预约、订单） | ⚠️ 有能力未暴露 |
| B：摘要检索 | 中 | 非结构化对话 | ❌ |
| C：事实图谱 | 高 | 复杂关系推理 | ❌ |

**务实建议**：**先用方案 A**（能把 80% 的问题解决），确实需要再上 B。

## 35.4 第三层：长期记忆（用户画像）

**目标**：Agent 知道"这个用户喜欢上午做实验""他是物理系的""他常用离心机"。

### 35.4.1 为什么这层最难

三个难点：

**难点 1：什么值得记？**

用户说了 100 句话，哪些是"稳定偏好"，哪些是"一次性需求"？

```
"帮我预约明天下午的实验室"     → 一次性需求，不该进长期记忆
"我一般是上午做实验"           → 稳定偏好，该记
"离心机怎么用？"               → 一次性问题
"我是物理系三年级的"           → 稳定属性，该记
```

**判断需要 LLM 参与**（或用规则 + LLM 混合）。

**难点 2：怎么更新？**

用户今天说"喜欢上午"，下个月说"最近改成下午了"。**新旧冲突怎么办？**

需要：时间戳 + 置信度 + 更新策略。

**难点 3：怎么用？**

记住了"喜欢上午"，在什么时机注入上下文？**每次都注入会浪费 token**，只在相关时（用户要预约时）注入才合理。

### 35.4.2 一个务实的简化方案

不需要做完整画像系统，一个**轻量的偏好表**就能解决大部分场景：

```python
class UserProfile(Base):
    __tablename__ = "user_profiles"
    user_id = Column(Integer, primary_key=True)
    preferences = Column(JSON)      # {"preferred_time": "morning", "dept": "物理系"}
    updated_at = Column(DateTime)
```

**写入**：用户在设置页填写（或 Agent 观察到后询问确认）
**读取**：System Prompt 里注入

```python
SYSTEM_PROMPT = f"""...
## 当前用户
{profile_text}       # ← "该用户偏好上午时段，物理系三年级"
"""
```

**关键**：**让用户显式设置，比让 Agent 猜更可靠**。这也是很多产品的做法（"偏好设置"页面）。

## 35.5 记忆的一个关键认知：写入比读取难

大部分人讨论记忆时想到的是"怎么取出来用"，但真正的难点是**"什么时候写、写什么"**。

```
会话进行中
  → 用户说了一句话
  → ★ 判断是否值得记？（难点 1）
  → ★ 归到哪个类别？（难点 2）
  → ★ 和已有记忆冲突怎么办？（难点 3）
  → 写入
```

**一个常见的错误**：让 Agent 自己决定记什么，结果它记了一堆垃圾（"用户说'你好'"也被记成偏好）。

**更可靠的做法**：
1. **显式收集**（设置页、表单）
2. **关键动作触发**（用户预约成功 → 记录"常用实验室"）
3. **定期批量总结**（会话结束后用 LLM 抽取，人工/规则过滤）
4. **让用户确认**（"我注意到你常在上午预约，要记住这个偏好吗？"）—— **最可靠**

> **面试金句**："记忆系统真正的难点不是'怎么取出来用'，而是'什么时候写、写什么'。让 Agent 自己判断记录什么会产生大量噪声。更可靠的做法是四个层次：显式收集（设置页）、关键动作触发（预约成功记常用实验室）、会话后批量抽取、以及**让用户确认**（'我注意到你常在上午预约，要记住吗？'）。最后一种最可靠，因为它把不确定性交还给人。"

## 35.6 本项目的记忆能力盘点

| 层次 | 能力 | 实现 | 状态 |
|---|---|---|---|
| **短期** | 多轮上下文 | checkpointer（第 17 章） | ✅ **已实现** |
| **短期** | 上下文裁剪 | `_trim_messages`（第 19 章） | ✅ 已实现 |
| **中期** | 查我的预约 | `reservation_service`（有方法） | ⚠️ **未暴露成工具** |
| **中期** | 跨会话摘要 | — | ❌ 未实现 |
| **长期** | 用户画像 | — | ❌ 未实现 |
| **长期** | 知识库（系统级） | RAG（卷三） | ✅ **已实现** |

**注意最后一行**：**RAG 其实是一种"系统级长期记忆"** —— 它记的不是用户个人，而是领域知识。这是 Agent 系统里最先该做的"长期记忆"，因为它的价值最直接。

> **面试可以说**："我们的记忆分三层看：**短期记忆**用 checkpointer 实现（多轮上下文 + 裁剪）；**系统级长期记忆**用 RAG 实现（知识库文档）；**用户级长期记忆**（偏好画像）目前没做。
>
> 如果要补，我的优先级是：① 先把已有的 `query_my_reservations` 暴露成工具（成本最低，能回答'我上次预约了什么'）；② 再做会话摘要检索；③ 最后才是用户画像——因为它最难（判断什么值得记、冲突怎么解决），而且可以用'设置页显式收集'来简化。"

## 35.7 最小骨架：一个两层记忆系统

```python
"""
minimal_memory.py —— 短期记忆（会话）+ 中期记忆（跨会话摘要检索）
运行：python minimal_memory.py  （纯 Python，无需依赖）
"""
import json
import math
from datetime import datetime


# ══════════════════════════════════════════════════════════
# 第一层：短期记忆（对应 checkpointer）
# ══════════════════════════════════════════════════════════
class ShortTermMemory:
    """按 thread_id 隔离的会话记忆。= 本项目的 checkpointer。"""

    def __init__(self, max_tokens: int = 4000):
        self._threads: dict[str, list[dict]] = {}
        self.max_tokens = max_tokens

    def append(self, thread_id: str, role: str, content: str):
        self._threads.setdefault(thread_id, []).append(
            {"role": role, "content": content, "ts": datetime.now().isoformat()}
        )

    def get(self, thread_id: str) -> list[dict]:
        """取历史（含裁剪，对应 _trim_messages）。"""
        msgs = self._threads.get(thread_id, [])
        total = sum(len(m["content"]) // 4 for m in msgs)
        if total <= self.max_tokens:
            return msgs
        # 从最老开始丢
        keep = list(msgs)
        while keep and sum(len(m["content"]) // 4 for m in keep) > self.max_tokens:
            keep.pop(0)
        return keep


# ══════════════════════════════════════════════════════════
# 第二层：中期记忆（跨会话摘要 + 语义检索）
# ══════════════════════════════════════════════════════════
class LongTermMemory:
    """把历史会话摘要存起来，新会话时按语义检索注入。"""

    def __init__(self):
        self._summaries: list[dict] = []      # {user_id, text, vector, ts}

    def _embed(self, text: str, dim: int = 64) -> list[float]:
        """玩具 embedding（真实项目用 bge-small-zh）。"""
        v = [0.0] * dim
        for i, ch in enumerate(text):
            v[(ord(ch) * (i + 1)) % dim] += 1
        n = math.sqrt(sum(x * x for x in v))
        return [x / n for x in v] if n else v

    def save_summary(self, user_id: int, text: str):
        self._summaries.append({
            "user_id": user_id,
            "text": text,
            "vector": self._embed(text),
            "ts": datetime.now().isoformat(),
        })
        print(f"  💾 已保存会话摘要（user={user_id}）：{text[:40]}...")

    def recall(self, user_id: int, query: str, top_k: int = 2) -> list[str]:
        """★ 语义检索历史摘要（这就是"中期记忆"的取用方式）。"""
        qv = self._embed(query)
        scored = []
        for s in self._summaries:
            if s["user_id"] != user_id:
                continue                      # ★ 用户隔离
            sim = sum(a * b for a, b in zip(qv, s["vector"]))
            scored.append((sim, s))
        scored.sort(key=lambda x: x[0], reverse=True)
        return [s["text"] for _, s in scored[:top_k] if _ > 0.05]


# ══════════════════════════════════════════════════════════
# 第三层（简化版）：用户画像
# ══════════════════════════════════════════════════════════
class UserProfileStore:
    """显式收集的偏好（比让 Agent 猜可靠）。"""

    def __init__(self):
        self._profiles: dict[int, dict] = {}

    def set_preference(self, user_id: int, key: str, value: str):
        self._profiles.setdefault(user_id, {})[key] = {
            "value": value, "updated_at": datetime.now().isoformat()
        }

    def render(self, user_id: int) -> str:
        """渲染成注入 prompt 的文本。"""
        p = self._profiles.get(user_id)
        if not p:
            return ""
        items = "，".join(f"{k}={v['value']}" for k, v in p.items())
        return f"## 当前用户偏好\n{items}\n"


# ══════════════════════════════════════════════════════════
# 演示
# ══════════════════════════════════════════════════════════
if __name__ == "__main__":
    short = ShortTermMemory(max_tokens=100)     # 故意设小，演示裁剪
    long = LongTermMemory()
    profiles = UserProfileStore()

    USER = 1

    print("=" * 62)
    print("【第一次会话】（thread-A）")
    tid_a = "thread-A"
    for role, content in [
        ("user", "显微镜实验室在哪？"),
        ("assistant", "在实验楼 A 座 301。"),
        ("user", "里面有什么设备？"),
        ("assistant", "有扫描电镜、离心机、超净工作台。"),
    ]:
        short.append(tid_a, role, content)
    print(f"  短期记忆条数：{len(short.get(tid_a))}")

    # 会话结束 → 生成摘要 → 存入长期记忆
    long.save_summary(USER, "用户询问了显微镜实验室的位置和设备，关注离心机。")
    profiles.set_preference(USER, "常用实验室", "显微镜实验室")

    print("\n【第二次会话】（新 thread-B，隔了一天）")
    tid_b = "thread-B"
    short.append(tid_b, "user", "我上次问的那个实验室，离心机怎么用？")

    # ★ 新会话时检索长期记忆
    recalled = long.recall(USER, "离心机 显微镜实验室")
    print(f"  🔍 回忆到的历史：")
    for r in recalled:
        print(f"    - {r}")

    profile_text = profiles.render(USER)
    print(f"  👤 用户画像：\n{profile_text}")

    # 组装 prompt
    context = ""
    if recalled:
        context += "## 相关历史\n" + "\n".join(f"- {r}" for r in recalled) + "\n"
    context += profile_text
    print("  📝 注入到 prompt 的记忆部分：")
    print("   " + context.replace("\n", "\n   "))

    print("\n【★ 用户隔离验证】")
    print(f"  user=2 检索「离心机」：{long.recall(2, '离心机')}")
    print("  ✅ 空。不同用户的记忆互不可见")

    print("\n【★ 短期记忆裁剪演示】")
    for i in range(10):
        short.append(tid_a, "user", f"第{i}条很长的消息" * 8)
    print(f"  写入 10 条长消息后，取回 {len(short.get(tid_a))} 条（被裁剪了）")
```

**预期输出（关键部分）**：

```
【第二次会话】（新 thread-B，隔了一天）
  🔍 回忆到的历史：
    - 用户询问了显微镜实验室的位置和设备，关注离心机。
  👤 用户画像：
## 当前用户偏好
常用实验室=显微镜实验室

【★ 用户隔离验证】
  user=2 检索「离心机」：[]
  ✅ 空。不同用户的记忆互不可见
```

## 35.8 面试问答

### Q1：Agent 的记忆分几层？你们实现了哪层？

**答**：三层。

**短期记忆**（单次会话内的上下文）：我们用 LangGraph 的 checkpointer 实现，按 `thread_id` 隔离，每轮自动加载历史，并做了 token 预算裁剪。

**中期记忆**（跨会话）：目前没做。但有低成本的方案——我们的 `reservation_service` 已经有查询用户预约的方法，只要暴露成一个 `query_my_reservations` 工具，就能回答"我上次预约了什么"。更进一步是会话摘要 + 语义检索。

**长期记忆**（用户画像）：也没做。这一层最难——要判断"什么值得记""冲突怎么解决""什么时候注入"。务实的简化是用设置页显式收集。

**另外要说**：**RAG 是一种系统级长期记忆**——它记的不是用户个人，而是领域知识。这是最先该做的长期记忆，我们做了。

### Q2：短期记忆有什么局限？

**答**：四个。

一是**按 thread_id 隔离**——新会话就是全新开始，旧的完全不知道。

二是**会膨胀**——token 平方级增长（第 19 章）和存储线性膨胀（第 17 章）。

三是**无语义检索**——只能"全量带上"，不能"按需取用"。聊了 50 轮之后，早期内容虽然还在，但可能挤不进上下文。

四是**无压缩**——早期对话只能是原始文本，裁剪是有损的（直接丢弃）。

本质上短期记忆就是"把全部历史塞进上下文"，轮次少时有效，多了就崩塌。

### Q3：跨会话记忆怎么做？

**答**：三种方案，我按成本从低到高说。

**方案 A：从业务数据库查** —— 结构化历史（预约记录、订单）本来就在库里，暴露成工具即可。**成本最低，能解决 80% 的问题**，优先做这个。

**方案 B：会话摘要 + 语义检索** —— 每次会话结束用 LLM 生成摘要存入向量库，新会话时按语义检索注入。适合非结构化内容。代价是多一次 LLM 调用 + 摘要有信息损失。

**方案 C：结构化事实抽取** —— 抽取三元组（用户, 预约了, 显微镜实验室）存入知识图谱。最强大也最复杂，适合需要关系推理的场景。

**我的优先级是 A → B → C。**

### Q4：用户画像为什么难做？

**答**：三个难点。

**一是"什么值得记"**。用户说 100 句话，哪些是稳定偏好（"我一般上午做实验"）、哪些是一次性需求（"帮我预约明天下午"）？判断需要 LLM 参与，而 LLM 自己判断会产生大量噪声。

**二是"怎么更新"**。今天说喜欢上午，下个月改成下午，新旧冲突怎么办？需要时间戳 + 置信度 + 更新策略。

**三是"什么时候用"**。记住了"喜欢上午"，每次都注入浪费 token，只在相关时（要预约时）注入才合理。

**我的结论是：写入比读取难。** 更可靠的做法不是让 Agent 猜，而是四个层次：显式收集（设置页）、关键动作触发（预约成功记录常用实验室）、会话后批量抽取、**让用户确认**（"我注意到你常在上午预约，要记住吗？"）。最后一种最可靠。

### Q5：记忆系统怎么保证用户隔离？

**答**：这是必须有的一层过滤。

存储和检索都要带 `user_id`：
- 存：摘要关联 `user_id`
- 取：`WHERE user_id = ?`（我用过滤实现，真实项目在 SQL 里过滤）

**这是水平越权的高发区**（第 32 章）——如果检索时忘了过滤 `user_id`，用户 A 就能看到用户 B 的记忆。**任何"用户数据"的查询都必须带归属条件。**

### Q6：如果要给本项目加记忆能力，你的优先级是什么？

**答**：三步。

**第一步（成本最低、收益最快）**：把已有的 `reservation_service` 查询方法暴露成 `query_my_reservations` 工具。这样 Agent 能回答"我上次预约了什么""我有哪些待审核的预约"。几乎零成本。

**第二步**：会话结束时生成摘要存向量库，新会话检索注入。解决"上次我们聊了什么"。

**第三步**：用户画像——但**先用设置页显式收集**（"常用实验室""偏好时段"），而不是让 Agent 自己猜。等有足够数据后再考虑自动抽取。

## 35.9 速记卡

> **记忆三层：短期（会话）/ 中期（跨会话）/ 长期（画像）。RAG 是系统级长期记忆。**

**短期**：checkpointer（第 17 章）+ 裁剪（第 19 章）
- 局限：thread 隔离 / 膨胀 / 无语义检索 / 无压缩

**中期三方案**：**A 查业务库（最优先）** / B 摘要检索 / C 事实图谱

**长期三难点**：什么值得记 / 怎么更新（冲突） / 什么时候用

**★ 核心认知**：**写入比读取难** —— 别让 Agent 自己猜
- 可靠做法：显式收集 / 关键动作触发 / 批量抽取 / **让用户确认**

**★ 必须做用户隔离**：任何用户数据查询都要带 `user_id`

**RAG = 系统级长期记忆**（记领域知识，不是个人）

**本项目盘点**：
- ✅ 短期（checkpointer）
- ✅ 系统级长期（RAG）
- ⚠️ 中期有能力未暴露（`query_my_reservations`）
- ❌ 用户画像

**代码位置**：`agent_service.py:45-53`（State 预留）、`reservation_service.py`

## 35.10 延伸思考

1. **如果 Agent 记住了用户的错误偏好（比如一次性的"帮我约下午"被记成"偏好下午"），怎么纠正？**
   提示：① 让偏好**可被用户查看和修改**（设置页）；② 记忆带置信度和来源（"根据 3 次预约推断"比"根据用户一句话"可信）；③ **提供遗忘机制**（用户可以删除某条记忆）。**GDPR 等法规也要求"被遗忘权"**。

2. **记忆注入 System Prompt 会破坏 prompt caching 吗？**
   提示：会。第 19 章讲过，prompt 变化会打破缓存。如果用户画像每次都变（比如加了时间戳），缓存就永远不命中。**解法：画像内容要稳定**（只在真正变化时更新），不要用动态内容（时间戳、随机数）。

3. **"记住"和"检索"的边界在哪？**
   提示：RAG 检索知识库是"系统级记忆"，记忆系统检索用户历史是"个人级记忆"。**技术上可以统一**（都是"存储 + 语义检索"），但**隔离要求不同**（用户数据必须隔离，知识库可以共享）。设计时要分清。
