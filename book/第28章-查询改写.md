# 第 28 章 · 查询改写：把"那个啥几点关"变成"实验室开放时间"

> **这一章要回答的核心问题**：用户问得口语化、指代不清、甚至带错别字，检索怎么办？查询改写和多轮对话的指代消解有什么关系？为什么改写失败要"静默回退"？

---

## 28.1 引子：用户不会按你的检索式说话

先看你设计的检索系统期待什么：

> **理想查询**："实验室开放时间 规定"

再看真实用户怎么问：

| 真实提问 | 问题 |
|---|---|
| "那个啥，实验室几点关啊？" | 口语、指代词 |
| "昨天说的那个离心机能用不？" | **跨轮指代**（"那个"指上一轮提到的） |
| "预约了明天下午的，能改时间吗？" | 省略主语 |
| "实验式安全规定" | **错别字**（实验式 → 实验室） |
| "嗯...我想问一下...就是那个..." | 大量寒暄 |

用这些原始问题去做向量检索，会发生什么？

**向量检索**：口语化的长句里，真正有检索价值的关键词被大量"噪声词"稀释，embedding 向量的语义重心偏移。

**BM25**：更糟。"那个啥"、"啊"、"呢" 这些词在文档里不存在，匹配为 0；而真正的关键词"关"可能匹配到一堆无关文档。

**这就是查询改写（Query Rewriting）要解决的问题**：

> **把用户的自然语言提问，转换成"检索友好"的查询式。**

---

## 28.2 改写的四种类型

### 类型 1：去噪（Denoise）

```
输入："那个啥，我想问一下，实验室一般几点关门啊？"
输出："实验室开放时间 闭馆时间"
```

去掉：寒暄（"我想问一下"）、指代词（"那个啥"）、语气词（"啊"）
保留：实体（"实验室"）、意图（"开放时间/闭馆"）

### 类型 2：纠错（Spell Correct）

```
输入："实验式安全规定"
输出："实验室安全规定"
```

LLM 有能力识别明显的错别字（尤其是拼音输入法常见的同音字错误）。

### 类型 3：指代消解（Coreference Resolution）

```
上一轮："离心机怎么预约？"
本轮："它明天有空吗？"
改写后："离心机明天是否可预约"
```

**这需要多轮上下文**——单看"它明天有空吗？"不知道"它"是什么。

> ⚠️ **本项目的一个重要限制**：`_rewrite_query` 接收的参数**只有 `question`**，没有历史消息：
> ```python
> def _rewrite_query(question: str) -> str:
> ```
> 所以它**只能做类型 1 和 2，做不了类型 3**（指代消解）。
>
> 这是一个真实的边界。要支持指代消解，需要把 `state["messages"]` 传进来。
> **面试时主动指出这一点会很加分。**

### 类型 4：扩展（Expansion）

```
输入："离心机怎么用"
输出："离心机 使用方法 操作流程 注意事项"
```

补充同义词和相关概念，提高召回。

**风险**：扩展可能引入噪声（"注意事项"可能召回一堆无关内容）。**本项目没做扩展**，因为后面有混合检索兜底。

## 28.3 项目实现

`kb_service.py:26-64`：

```python
# 查询改写用的 prompt：把口语化问句压缩成适合检索的关键词/短语，
# 去掉寒暄与多余修饰，保留实体。输出纯文本，不要解释。
_REWRITE_PROMPT = """把下面的问题改写成一个适合做检索的简短查询。
要求：
1. 只输出改写后的查询文本，不要解释、不要引号、不要序号。
2. 保留关键实体（实验室名、设备名、日期、规则类别等）。
3. 去掉寒暄和多余修饰词。

问题：{question}
"""


def _rewrite_query(question: str) -> str:
    """把口语化问句改写成检索友好的查询；失败或未启用时原样返回。"""
    global _rewrite_client
    if not settings.QUERY_REWRITE_ENABLED:
        return question
    if not settings.LLM_API_KEY:
        return question
    try:
        if _rewrite_client is None:
            from openai import OpenAI

            _rewrite_client = OpenAI(
                api_key=settings.LLM_API_KEY, base_url=settings.LLM_BASE_URL
            )
        resp = _rewrite_client.chat.completions.create(
            model=settings.LLM_MODEL,
            messages=[
                {"role": "user", "content": _REWRITE_PROMPT.format(question=question)}
            ],
            temperature=0,
            max_tokens=128,
        )
        rewritten = (resp.choices[0].message.content or "").strip()
        return rewritten or question
    except Exception as exc:
        logger.warning("查询改写失败，回退原始问题：%s", exc)
        return question
```

### 七个设计点

**① 三重前置检查**

```python
if not settings.QUERY_REWRITE_ENABLED:
    return question
if not settings.LLM_API_KEY:
    return question
```

- 功能开关
- **API Key 检查**（没有 Key 就没法调 LLM）

这两个检查让改写成为**纯可选功能**：关掉或没配 Key 时，系统行为完全不变（只是少了改写）。

**② 全局单例客户端**

```python
global _rewrite_client
if _rewrite_client is None:
    from openai import OpenAI
    _rewrite_client = OpenAI(...)
```

`OpenAI` 客户端持有 HTTP 连接池，复用它避免重复建连。

**③ 用原生 OpenAI SDK 而不是 LangChain**

```python
from openai import OpenAI
resp = _rewrite_client.chat.completions.create(...)
```

**为什么不用 `ChatOpenAI`（LangChain 的封装）？**

| 理由 | 说明 |
|---|---|
| **同步 vs 异步** | `kb_service` 全是同步函数，用同步 SDK 最自然 |
| **轻量** | 改写只需要最简单的 chat completion，不需要 LangChain 的消息抽象 |
| **明确** | `resp.choices[0].message.content` 直观 |

如果用 LangChain 的 `ChatOpenAI.invoke()`，需要构造 `HumanMessage`、处理返回对象，反而绕。

**这是一个务实的判断：不是所有地方都要用框架。**

**④ `temperature=0`**

改写要**确定性**，不要创造性。同一个问题每次改写结果应该一致（否则检索结果会抖动）。

**⑤ `max_tokens=128`**

改写后的查询应该很短（几个词到一句话）。限制 128 token：

- 省钱
- 防止模型输出一大段解释（虽然 prompt 里要求了不要解释，但双保险）
- 降低延迟

> ⚠️ **注意**：如果用了**推理模型**（如 DeepSeek-R1），`max_tokens=128` 会不够——因为模型的思考过程（reasoning tokens）也消耗 token 预算。这在第 38 章讲 RAGAS 评测时踩过同样的坑（裁判模型的 `max_tokens` 太小导致输出被截断）。

**⑥ 双重兜底**

```python
rewritten = (resp.choices[0].message.content or "").strip()
return rewritten or question
```

- 模型返回 `None` → `or ""`
- 改写结果为空 → `or question`（**回退原始问题**）

**⑦ 异常静默回退**

```python
except Exception as exc:
    logger.warning("查询改写失败，回退原始问题：%s", exc)
    return question
```

**这是整个函数最重要的设计。**

**查询改写是"锦上添花"的功能，不是"必须"的功能。** 它失败不应该影响主流程：

- 不抛异常（否则整个检索失败）
- 只打 warning（便于排查）
- 返回原始问题（系统降级到"不改写"，仍然可用）

> **面试金句**："查询改写我设计成'失败静默回退'——异常时只打 warning 并返回原始问题，不抛异常。因为它是一个增强功能而不是必需功能，**它的失败不应该让检索失败**。这是'可选增强'类功能的通用设计原则：不能因为它挂了就整个不可用。"

### 28.3.1 为什么不用便宜的小模型？

```python
model=settings.LLM_MODEL,     # 和主 Agent 同一个模型
```

改写用的是**主模型**（DeepSeek），而不是便宜的小模型。

**权衡**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 主模型 | 改写质量高 | 贵、慢（多一次完整 LLM 调用） |
| 小模型（gpt-4o-mini、qwen-turbo） | 便宜、快 | 质量略低 |
| 规则/模型微调 | 最快 | 覆盖面窄 |

**本项目的选择**：用主模型，简单（不用配第二个模型）。

**代价**：**每次检索都多一次 LLM 调用**，增加延迟（200-500ms）和成本。

> 📝 **优化方向**（简历素材）：
> 1. **用便宜的小模型**做改写（改写是简单任务，不需要强模型）
> 2. **缓存改写结果**（相同问题不重复改写）
> 3. **只在需要时改写**：短查询（< 10 字）不改写，长查询才改写
> 4. **异步化**：改写和向量检索并行？不行（改写结果是检索的输入）。但可以和其他路并行。

## 28.4 改写在链路中的位置

`kb_service.py:188-190`：

```python
search_query = _rewrite_query(query.strip())
if search_query != query.strip():
    logger.info("查询改写：%r -> %r", query, search_query)
```

**注意日志**：改写发生时打 info 日志。这是**可观测性**的实践——你能看到改写到底做了什么，便于调试"为什么检索结果不对"。

然后**改写后的查询用于所有下游**：

```python
vector_hits = _vector_search(search_query, ...)      # 用改写后的
keyword_hits = _bm25_search(search_query, ...)       # 用改写后的
merged = _rrf_fusion(vector_hits, keyword_hits)
if settings.RERANK_ENABLED:
    merged = _rerank(search_query, merged)           # 用改写后的
```

**关键**：**rerank 也用改写后的查询**。

这合理吗？想一想：rerank 要判断"查询和文档是否相关"。如果用**原始口语化查询**，可能更贴近用户真实意图；如果用**改写后的**，可能更贴近检索语义。

**没有标准答案**，取决于改写质量。本项目用改写后的（一致性更好）。

> ⚠️ **一个值得思考的问题**：如果改写**改错了**（比如把"实验室几点关"改成"实验室关门流程"，语义偏移了），那么 rerank 也会沿着错误方向走。
>
> **改进方案**：rerank 用**原始查询**（更贴近用户真实意图），检索用改写查询（更适合匹配）。这是一个可以 A/B 测试的设计选择。

### 28.4.1 一个重要的架构观察

```
用户原始问题 ──→ 改写 ──→ 检索 ──→ 生成
                  ↑
              唯一入口
```

**改写发生在最前端，影响所有下游。** 这意味着：

- ✅ 好处：一次改写，全链路受益
- ❌ 风险：一次改错，全链路受影响

**对比另一种设计**：不改写原始问题，而是**同时用原始和改写做两路检索**，然后 RRF 融合三路（原始向量 + 改写向量 + BM25）。

这样更鲁棒，但成本更高（多一次检索）。

## 28.5 为什么不改写的替代方案

除了 LLM 改写，还有几种处理方式：

### 方案 1：不做改写，靠混合检索兜底

BM25 对口语化查询效果差，但向量检索有一定鲁棒性。**如果改写的收益不明显，不如不做。**

### 方案 2：HyDE（假设性文档嵌入）

```
原问题 → LLM 生成一段"假设的答案" → 用这段答案去做向量检索
```

原理：**答案和答案的相似度，比问题和答案的相似度更高**。

```
问题："实验室几点关？"
HyDE 生成："实验室的开放时间是 8:00-22:00，闭馆前需要..."
用这段文本去检索 → 能匹配到真实的"开放时间"文档
```

**优点**：不需要训练，效果通常比简单改写好
**缺点**：多一次 LLM 调用（生成完整答案，比改写贵），而且生成的"假设答案"可能是错的（幻觉）会带偏检索

### 方案 3：多查询扩展（Multi-Query）

```
原问题 → LLM 生成 3-5 个不同角度的查询 → 分别检索 → RRF 融合
```

```
"实验室几点关？"
→ ["实验室开放时间", "实验室闭馆时间", "实验室非工作时间能否进入"]
```

**优点**：召回覆盖更全（这是主流 RAG 框架的做法，如 LlamaIndex 的 MultiQueryRetriever）
**缺点**：N 次检索，成本高

### 方案 4：Step-back Prompting

```
原问题 → LLM 生成一个"更抽象、更高层"的问题 → 用抽象问题检索
```

```
"SP-2000 光谱仪的功率上限是多少？"
→ step-back: "光谱仪的技术参数有哪些？"
```

**原理**：抽象问题的答案通常包含具体问题的答案。

**本项目用的是方案 1 的增强版（简单改写）**，没有用 HyDE / Multi-Query。

> **面试可以说**："我们做的是最基础的 LLM 查询改写。更高级的方案有 HyDE（生成假设答案再检索）、Multi-Query（生成多个角度的查询并行检索再融合）、Step-back（抽象化问题）。它们各有适用场景，但都会增加 LLM 调用次数和延迟。我们选简单改写是因为在这个场景够用，且成本可控。如果要进一步提升召回，Multi-Query 是首选——它能和我们的 RRF 天然结合（多路融合）。"

## 28.6 最小骨架：带缓存和降级的改写器

```python
"""
minimal_rewrite.py —— 查询改写（带缓存、降级、开关）
运行：python minimal_rewrite.py  （纯 Python，无需依赖）
用规则模拟 LLM 改写，重点演示工程结构而非改写算法
"""
import re
import time


# ── 1. 配置（模拟 settings）────────────────────────────────
class Settings:
    QUERY_REWRITE_ENABLED = True
    LLM_API_KEY = "sk-fake"           # 改成 "" 可测"无 Key 降级"
    LLM_MODEL = "deepseek-chat"


settings = Settings()


# ── 2. 规则版"改写模型"（真实项目里是 LLM 调用）─────────────
NOISE_WORDS = ["那个", "啥", "啊", "呢", "吧", "我想问一下", "请问",
               "帮我查一下", "能不能告诉我", "麻烦问一下", "就是说"]

TYPO_MAP = {
    "实验式": "实验室",
    "离心基": "离心机",
    "光谱义": "光谱仪",
}


def fake_llm_rewrite(question: str) -> str:
    """模拟 LLM：去噪 + 纠错 + 压缩。真实项目里是一次 chat completion。"""
    text = question.strip()

    # ① 纠错（错别字映射）
    for wrong, right in TYPO_MAP.items():
        text = text.replace(wrong, right)

    # ② 去噪（去掉寒暄和语气词）
    for noise in NOISE_WORDS:
        text = text.replace(noise, "")

    # ③ 压缩（多个空格合并、去掉句尾语气标点）
    text = re.sub(r"\s+", " ", text).strip()
    text = re.sub(r"[？?。！!，,、]+$", "", text).strip()

    # ④ 模拟 LLM 偶尔返回空（用于测试降级）
    if not text:
        return ""

    return text


# ── 3. 缓存（真实项目里是 Redis，见 kb_service._cache_get）──
_rewrite_cache: dict[str, str] = {}


def cached_rewrite(question: str) -> str:
    if question in _rewrite_cache:
        return _rewrite_cache[question]
    result = fake_llm_rewrite(question)
    _rewrite_cache[question] = result
    return result


# ── 4. 核心：带三重检查 + 静默降级 ─────────────────────────
_client = {"inited": False, "calls": 0}


def rewrite_query(question: str, use_cache: bool = True) -> str:
    """把口语化问句改写成检索友好的查询；失败或未启用时原样返回。"""
    # 检查①：功能开关
    if not settings.QUERY_REWRITE_ENABLED:
        return question
    # 检查②：API Key
    if not settings.LLM_API_KEY:
        return question

    try:
        if not _client["inited"]:
            _client["inited"] = True          # 模拟：初始化客户端（建连接池）
        _client["calls"] += 1

        # 真实项目：resp = client.chat.completions.create(model=..., temperature=0, max_tokens=128)
        fn = cached_rewrite if use_cache else fake_llm_rewrite
        rewritten = (fn(question) or "").strip()

        # 兜底：改写结果为空 → 回退原始问题
        return rewritten or question
    except Exception as exc:
        # ★ 静默降级：只 warning，不抛异常
        print(f"    ⚠ 查询改写失败，回退原始问题：{exc}")
        return question


# ── 5. 演示 ────────────────────────────────────────────────
CASES = [
    "那个啥，我想问一下，实验室一般几点关门啊？",
    "实验式安全规定有哪些",
    "请问离心基怎么预约呢？",
    "帮我查一下光谱义的功率",
    "开放时间",                    # 短查询，不需要改写
]

if __name__ == "__main__":
    print("=== ① 正常改写 ===")
    for q in CASES:
        r = rewrite_query(q)
        flag = "（未变化）" if r == q else ""
        print(f"  原文：{q}")
        print(f"  改写：{r}  {flag}\n")

    print(f"  LLM 调用次数：{_client['calls']}")

    print("\n=== ② 缓存效果 ===")
    before = _client["calls"]
    for q in CASES:
        rewrite_query(q)
    print(f"  重复 5 次后，新增 LLM 调用：{_client['calls'] - before}  ← 应为 0")

    print("\n=== ③ 关闭开关（降级）===")
    settings.QUERY_REWRITE_ENABLED = False
    print(f"  {CASES[0]}")
    print(f"  → {rewrite_query(CASES[0])}  ← 原样返回")
    settings.QUERY_REWRITE_ENABLED = True

    print("\n=== ④ 无 API Key（降级）===")
    settings.LLM_API_KEY = ""
    print(f"  → {rewrite_query(CASES[1])}  ← 原样返回")
    settings.LLM_API_KEY = "sk-fake"

    print("\n=== ⑤ 改写结果为空（兜底）===")
    weird = "那个啥啊啊啊"
    print(f"  原文：{weird}")
    print(f"  → {rewrite_query(weird)}  ← 空结果回退原始问题")

    print("\n=== ⑥ 异常降级 ===")
    def boom(q):
        raise RuntimeError("模拟：LLM 服务超时")
    original = fake_llm_rewrite
    globals()["fake_llm_rewrite"] = boom
    globals()["cached_rewrite"] = boom
    print(f"  → {rewrite_query(CASES[0])}  ← 异常时静默回退，不抛异常")
    globals()["fake_llm_rewrite"] = original
```

**预期输出（关键部分）**：

```
=== ① 正常改写 ===
  原文：那个啥，我想问一下，实验室一般几点关门啊？
  改写：实验室一般几点关门  ← 去噪成功

  原文：实验式安全规定有哪些
  改写：实验室安全规定有哪些  ← 纠错成功

=== ③ 关闭开关（降级）===
  → 那个啥，我想问一下，实验室一般几点关门啊？  ← 原样返回

=== ⑤ 改写结果为空（兜底）===
  原文：那个啥啊啊啊
  → 那个啥啊啊啊  ← 空结果回退原始问题

=== ⑥ 异常降级 ===
    ⚠ 查询改写失败，回退原始问题：模拟：LLM 服务超时
  → 那个啥，我想问一下，实验室一般几点关门啊？  ← 异常时静默回退，不抛异常
```

1. ✅ 去噪 + 纠错生效
2. ✅ 缓存避免重复调用
3. ✅ 开关关闭 → 原样返回
4. ✅ 无 Key → 原样返回
5. ✅ 异常/空结果 → 静默回退

## 28.8 面试问答

### Q1：什么是查询改写？解决什么问题？

**答**：把用户的自然语言提问转换成"检索友好"的查询式。

解决的是**用户说话方式和检索系统期待不匹配**的问题。用户会问"那个啥，实验室几点关啊"，里面有大量寒暄、指代、语气词，这些词在文档里不存在，BM25 匹配为 0；而且噪声词会稀释 embedding 的语义重心，向量检索也变差。

改写做四件事：去噪（去掉寒暄和语气词）、纠错（"实验式"→"实验室"）、指代消解（"它明天有空吗"→"离心机明天是否可预约"）、扩展（补充同义词）。

**我们实现了去噪和纠错，没做指代消解**——因为 `_rewrite_query` 只接收 `question` 一个参数，拿不到历史消息。要支持多轮指代，需要把 `state["messages"]` 传进去。这是明确的改进方向。

### Q2：改写失败了怎么办？

**答**：静默回退——只打 warning 日志，返回原始问题，不抛异常。

理由是**查询改写是增强功能而不是必需功能**。**它的失败不应该让检索失败**。这是"可选增强"类功能的通用设计原则。

实现上有三层兜底：配置开关关闭时原样返回、没有 API Key 时原样返回、改写结果为空或抛异常时返回原始问题。

### Q3：改写用什么模型？成本怎么控制？

**答**：我们用的是主模型（和 Agent 同一个），`temperature=0` 保证确定性，`max_tokens=128` 限制输出长度。

成本控制上有几个可以改进的点：一是**用便宜的小模型**（改写是简单任务，不需要强模型）；二是**缓存改写结果**（相同问题不重复调用）；三是**短查询不改写**（< 10 字的查询通常已经是关键词了）。

当前每次检索都多一次完整 LLM 调用，会增加 200-500ms 延迟，这是明确的成本。

另外要注意：如果用的是**推理模型**（如 DeepSeek-R1），`max_tokens=128` 会不够——因为模型的思考过程也消耗 token 预算。我们在 RAGAS 评测里踩过这个坑。

### Q4：改写后的查询会影响 rerank 吗？

**答**：会，我们的实现里 rerank 也用改写后的查询。

这个选择有争议：用原始查询更贴近用户真实意图，用改写查询更贴近检索语义。没有标准答案，取决于改写质量。

**风险是**：如果改写改错了（语义偏移），rerank 会沿着错误方向走。

一个可以 A/B 测试的方案是：**检索用改写查询（更适合匹配），rerank 用原始查询（更贴近意图）**。

### Q5：除了简单的 LLM 改写，还有哪些方案？

**答**：三种进阶方案。

**HyDE**：让 LLM 生成一段"假设的答案"，用这段答案去做向量检索。原理是"答案和答案的相似度高于问题和答案的相似度"。效果通常比简单改写好，但多一次生成调用（更贵），而且如果生成的假设答案是幻觉，会带偏检索。

**Multi-Query**：让 LLM 生成 3-5 个不同角度的查询，分别检索再融合。召回覆盖更全，能和我们的 RRF 天然结合（多路融合）。代价是 N 次检索。

**Step-back**：把具体问题抽象成更高层的问题（"SP-2000 功率上限"→"光谱仪的技术参数"），用抽象问题检索。

我们选简单改写是因为在这个场景够用且成本可控。如果要进一步提升召回，Multi-Query 是首选。

### Q6：你怎么验证改写有没有用？

**答**：诚实说，我们还没有做量化的 A/B 实验。

正确做法是：固定其他条件（同样的评测集、同样的召回和 rerank 配置），只开关 `QUERY_REWRITE_ENABLED`，对比 Hit@K、MRR 和最终答案质量。

**特别要注意测"口语化问题"的子集**——改写对"开放时间"这类本身就是关键词的查询没有帮助，甚至可能有损；它的价值体现在"那个啥几点关啊"这类口语查询上。所以评测集要按查询类型分组统计。

这个实验做出来，"量化了查询改写对口语查询的召回提升"会比"接入了查询改写"有说服力得多。

## 28.9 速记卡

> **查询改写 = 把用户的话翻译成检索式。增强功能，失败要静默回退。**

**四类型**：去噪 / 纠错 / **指代消解（本项目未做）** / 扩展

**为什么需要**：口语、指代、错别字 → BM25 匹配为 0，向量语义被稀释

**项目实现**（`kb_service.py:38-64`）：
```python
if not QUERY_REWRITE_ENABLED: return question     # 开关
if not LLM_API_KEY: return question               # 无 Key
... temperature=0, max_tokens=128 ...
return rewritten or question                     # 空结果兜底
except: logger.warning(...); return question      # ★ 静默回退
```

**★ 设计原则**：增强功能失败 → **不抛异常**，降级到原始问题

**用原生 OpenAI SDK 而非 LangChain**：同步场景、轻量、直观

**⚠️ 限制**：只接收 `question`，**拿不到历史** → 做不了指代消解

**⚠️ 坑**：推理模型（R1）的 `max_tokens` 要考虑 reasoning tokens

**进阶方案**：HyDE（假设答案）/ **Multi-Query（多角度 + RRF）** / Step-back（抽象化）

**改写在最前端**：一次改写影响检索 + rerank 全链路（风险与收益并存）

**优化方向**：小模型 / 缓存 / 短查询跳过 / rerank 用原始查询

**代码位置**：`kb_service.py:28-64`、调用点 `:188-190`

## 28.10 延伸思考

1. **如果要支持指代消解（"它明天有空吗"），架构上要改哪些地方？**
   提示：`_rewrite_query(question)` → `_rewrite_query(question, history)`；`search()` 和 `retrieve()` 都要传历史；而调用方 `search_lab_docs` 工具**拿不到对话历史**（工具签名只有 query）。
   **真正的解法**：把改写提到 Agent 层（在 `agent_node` 里做），或者让工具能访问 state。思考哪种更合理？

2. **改写的缓存 key 应该包含什么？**
   提示：`question` + **模型版本** + **prompt 版本**。改了 prompt 就要让旧缓存失效（参考第 21 章的 `_corpus_version` 版本号方案）。如果做了指代消解，还要包含历史摘要。

3. **如果改写把"实验室几点关"改成了"实验室关门流程"，语义偏移了怎么办？**
   提示：这是改写的固有风险。缓解：① prompt 里强调"保持原意，不要推断意图"；② 用原始 + 改写**双路检索**再融合（更鲁棒但更贵）；③ 靠评测集监控。**没有银弹，只能靠数据验证。**
