# 第 22 章 · 文档解析：把 PDF 变成模型能读的文本

> **这一章要回答的核心问题**：为什么文档解析是 RAG 里最脏最累的活？PDF 到底难在哪？表格、多栏、扫描件怎么处理？为什么解析质量直接决定 RAG 的上限？

---

## 22.1 引子：RAG 的第一原则是"垃圾进，垃圾出"

有一个残酷的事实：**RAG 系统的上限，由解析质量决定。**

无论你的向量模型多先进、rerank 多精准、prompt 多巧妙——如果解析出来的文本是乱的，一切白搭。

看一个真实的例子。一份实验室安全手册 PDF，用最朴素的 `pypdf` 解析出来：

```
实 验 室 安 全 手 册
第 1 页

第一章 总则
1.1 为 加 强 实 验 室 安 全 管 理 ， 保 障
人 身 安 全 ， 特 制 定 本 手 册 。
1.2 本 手 册 适 用 于 全 校 各 类 实 验 室
。

设备名称        数量    负责人
离心机           2       张 三
光谱仪           1       李 四
```

**四个问题**：

1. **字符间被插入空格**（PDF 排版导致的）
2. **句子被断行切断**（"保障\n人身安全"）
3. **表格变成了一堆空格分隔的碎片**
4. **页眉页脚混进正文**（"第 1 页"）

然后你把它切成块，向量化，检索。用户问"离心机负责人是谁"，检索到的块里是"离心机           2       张 三"——**模型能不能看懂？能，但很勉强。而且表格的语义关系（哪列对应哪个字段）已经丢失了。**

这就是为什么业界有句话：

> **RAG 项目 80% 的工作量在数据处理，只有 20% 在模型和算法。**

## 22.2 三种文档格式，三种难度

### 22.2.1 Markdown / TXT：最容易

本项目（`kb_parser.py:14-15`）：

```python
if ext in {".md", ".txt"}:
    return data.decode("utf-8", errors="replace")
```

**为什么这么简单？** 因为纯文本本身就是"所见即所得"——你看到什么，文本里就是什么。

唯一的坑：**编码**。

```python
data.decode("utf-8", errors="replace")
```

- `utf-8`：最通用的编码。但 Windows 上很多 txt 是 GBK 的，直接 decode 会报错
- `errors="replace"`：遇到无法解码的字节，用 `�` 替代而**不是抛异常**

这是一个**务实的选择**：宁可得到带几个乱码的文本，也不要整个文件解析失败。因为一个知识库里有几十份文档，不能因为一份编码不对就让整个索引构建失败。

> **改进方向**：用 `chardet` 或 `charset-normalizer` 自动检测编码：
> ```python
> import chardet
> detected = chardet.detect(data)
> return data.decode(detected["encoding"] or "utf-8", errors="replace")
> ```
> 这是可以写进简历的小优化。

### 22.2.2 PDF：最难，没有之一

**为什么 PDF 难？** 因为 PDF 的**设计目标不是"存储文本"，而是"精确还原打印效果"**。

PDF 内部存的不是"一段文字"，而是一堆**绘制指令**：

```
BT                          % begin text
/F1 12 Tf                   % 用 F1 字体，12 号
100 700 Td                  % 移动到坐标 (100, 700)
(实验室安全手册) Tj          % 在这里画"实验室安全手册"
ET                          % end text
```

**它记录的是"在哪个坐标画什么字符"，而不是"这是一段话"。** 所以：

| 问题 | 原因 |
|---|---|
| 字符间空格 | 每个字符可能有独立的坐标 |
| 断行 | 换行是坐标变化，不是 `\n` 字符 |
| 阅读顺序乱 | 多栏排版时，pypdf 可能按"绘制顺序"而不是"阅读顺序"输出 |
| 表格丢失 | 表格是线条 + 分散的文字块 |
| 扫描件无文本 | 整页是图片，没有任何文本层 |
| 页眉页脚 | 和正文混在一起 |

本项目（`kb_parser.py:17-22`）：

```python
if ext == ".pdf":
    from pypdf import PdfReader

    reader = PdfReader(io.BytesIO(data))
    pages = [page.extract_text() or "" for page in reader.pages]
    return "\n\n".join(pages).strip()
```

**三个细节**：

**① `io.BytesIO(data)`**

`pypdf` 需要一个"文件对象"，而我们从上传拿到的是 `bytes`。`BytesIO` 把 bytes 包装成内存文件对象，避免写临时文件：

```python
reader = PdfReader(io.BytesIO(data))     # ✅ 内存操作
# vs
with open("tmp.pdf", "wb") as f: f.write(data)   # ❌ 要清理临时文件
```

**② `page.extract_text() or ""`**

某些页（比如纯图片页）`extract_text()` 可能返回 `None`。`or ""` 兜底，避免后面 `"\n\n".join()` 报错。

**③ `"\n\n".join(pages)`**

**用两个换行连接每一页**。这是一个有意的决定：

- 单换行 → 页与页之间可能被合并成一个段落，切块时跨页混在一起
- 双换行 → 形成明确的段落分隔，切块器（第 23 章）会优先在这里切

**这体现了"解析要为下游服务"的思路**——解析不是孤立的一步，它的输出格式要考虑切块器怎么处理。

### 22.2.3 DOCX：中等难度

本项目（`kb_parser.py:24-29`）：

```python
if ext == ".docx":
    from docx import Document

    document = Document(io.BytesIO(data))
    paragraphs = [p.text for p in document.paragraphs if p.text.strip()]
    return "\n".join(paragraphs).strip()
```

**为什么 DOCX 比 PDF 容易？** 因为 docx 是**结构化格式**（本质是 zip 包裹的 XML）。它有明确的"段落"概念：

```xml
<w:p><w:r><w:t>实验室开放时间为 8:00-22:00</w:t></w:r></w:p>
```

`python-docx` 直接把它解析成 `paragraphs` 列表。

**但有两个已知缺陷**：

1. **表格内容丢失**：`document.paragraphs` **不包含**表格里的文字！表格在 `document.tables` 里。本项目没处理，所以 Word 里的表格内容会丢失。
2. **页眉页脚丢失**：`document.paragraphs` 也不含页眉页脚（这反而是好事）。

> **改进方向**（简历优化点）：
> ```python
> def _docx_text(document) -> str:
>     parts = [p.text for p in document.paragraphs if p.text.strip()]
>     for table in document.tables:              # ★ 补上表格
>         for row in table.rows:
>             cells = [c.text.strip() for c in row.cells]
>             parts.append(" | ".join(cells))
>     return "\n".join(parts)
> ```

## 22.3 解析的六个真实难题

这一节是本章最有价值的部分——**面试时讲出这些，说明你真的处理过真实文档**。

### 难题 1：扫描件（图片 PDF）

**表现**：`extract_text()` 返回空字符串，整页没内容。

**原因**：这份 PDF 是扫描仪生成的，本质是图片，没有文本层。

**解法**：OCR。

```python
# 方案 A：pdfplumber + pytesseract（开源）
# 方案 B：云 OCR（腾讯云 OCR、Azure Form Recognizer）
# 方案 C：多模态大模型直接"看"页面（GPT-4V / Gemini）
```

**本项目的现状**：不支持扫描件。上传扫描件会得到空文本，然后切块得到 0 个块，索引为空。

> **面试诚实说法**："目前不支持扫描件 OCR。这是明确的边界——如果要支持，我倾向于用云 OCR 服务而不是自己搭 Tesseract，因为中文 OCR 的准确率自己调很费劲；或者用多模态模型直接读页面，效果更好但成本高。"

### 难题 2：多栏排版

**表现**：双栏 PDF 解析出来是"左栏第1行 右栏第1行 左栏第2行 右栏第2行"——**左右栏内容交错**。

**原因**：pypdf 按绘制顺序输出，而绘制顺序可能是"先画完左栏再画右栏"，也可能是逐行交替。

**解法**：
- 用 `pdfplumber`（能拿到每个字符的坐标，可以按坐标聚类分栏）
- 用 `unstructured`、`LlamaParse` 这类专门的文档解析库
- 用版面分析模型（LayoutLM 系列）

### 难题 3：表格

**表现**：表格变成空格分隔的碎片，或者干脆丢失列关系。

**为什么表格对 RAG 特别致命？** 因为表格的信息是**结构化的关系**：

```
| 设备 | 数量 | 负责人 |
| 离心机 | 2 | 张三 |
```

如果变成"离心机 2 张三"，模型可能还能猜。但如果表格有 10 列，或者数字没有表头，就完全没法理解了。

**解法**：
| 方案 | 做法 |
|---|---|
| **Markdown 化** | 把表格转成 `\| a \| b \|` 格式，模型对 Markdown 表格理解不错 |
| **行级切块** | 每一行作为一个块，并**重复表头** |
| **自然语言化** | 用 LLM 把表格转成"离心机的数量是 2，负责人是张三" |
| **专用模型** | 表格解析模型（如 Table Transformer） |

**"重复表头"这个技巧很实用**：

```python
# 原表格行
"离心机 | 2 | 张三"
# 转成块时带上表头
"设备: 离心机, 数量: 2, 负责人: 张三"
```

### 难题 4：断行与连字符

**表现**：
```
为加强实验室安全管
理，保障人身安全
```

**解法**：中文场景可以直接去掉换行（中文没有单词边界的概念）：

```python
text = re.sub(r"(?<=[\u4e00-\u9fff])\n(?=[\u4e00-\u9fff])", "", text)
# 把"中文\n中文"中间的换行去掉
```

**英文要小心**：英文的换行可能是真的换行，而连字符（`manage-\nment`）需要还原成 `management`。

### 难题 5：页眉页脚与水印

**表现**：每一页都有"第 N 页"、"机密文件"、"XXX公司"，混进正文。

**危害**：这些重复内容会被检索到（因为它们在很多块里出现），稀释真正的语义。

**解法**：
- 去掉每页开头/结尾的 N 行（简单粗暴但有效）
- 统计跨页重复的行，识别为页眉页脚
- 用规则匹配（"第 \d+ 页"）

### 难题 6：公式、图表、图片说明

**表现**：数学公式变成乱码，图片完全丢失，图注混在正文里。

**解法**：
- 公式：转成 LaTeX（`nougat` 这类工具）
- 图片：多模态模型生成描述，作为文本块存入（"图1：离心机结构示意图"）
- 图注：保留，但标记为图注

## 22.4 解析质量的评估：怎么知道解析得好不好？

这是一个常被忽略但极其重要的问题。四个层次的检查：

### 层次 1：字符层

```python
def check_char_quality(text: str) -> dict:
    """检查字符层质量。"""
    total = len(text)
    if total == 0:
        return {"ok": False, "reason": "空文本"}
    cjk = sum(1 for c in text if "\u4e00" <= c <= "\u9fff")
    spaces = text.count(" ")
    return {
        "total_chars": total,
        "cjk_ratio": cjk / total,                    # 中文文档的汉字占比应 > 30%
        "space_ratio": spaces / total,               # > 20% 可能是 PDF 空格问题
        "replacement_chars": text.count("\ufffd"),   # 乱码字符数
    }
```

**判据**：
- 空文本 → 可能是扫描件
- `space_ratio > 0.2` → 可能被插入了大量空格
- `replacement_chars > 0` → 编码问题

### 层次 2：结构层

```python
# 检查是否有明确的段落分隔
paragraphs = [p for p in text.split("\n\n") if p.strip()]
# 块数太少 → 可能整篇糊在一起
# 块数太多 → 可能被过度切碎
```

### 层次 3：语义层（最重要）

**抽样人工检查**：随机抽 10 个块，人眼看是否通顺、语义是否完整。

**自动化近似**：用一个小模型判断"这段文本是否通顺自然"。

### 层次 4：端到端（终极检验）

**用 RAG 的效果反推**：构造 10 个已知答案的问题，看检索能不能召回。

**如果召回率低，先怀疑解析，而不是先怀疑向量模型。** 这是排查顺序的原则：

```
检索效果差
  → 先看命中的块内容对不对（解析 + 切块问题？）
  → 再看相关资料有没有被索引（覆盖问题？）
  → 最后才调模型和参数
```

## 22.5 最小骨架：一个带质量检查的解析器

```python
"""
minimal_parser.py —— 带质量检查的文档解析器
运行：pip install pypdf python-docx && python minimal_parser.py
（无依赖部分纯 Python 也能跑，用于理解结构）
"""
import io
import re
from pathlib import Path

SUPPORTED = {".md", ".txt", ".pdf", ".docx"}


# ── 1. 分格式解析 ──────────────────────────────────────────
def parse_bytes(filename: str, data: bytes) -> str:
    ext = Path(filename).suffix.lower()
    if ext not in SUPPORTED:
        raise ValueError(f"不支持的文件类型：{ext}")

    if ext in {".md", ".txt"}:
        return data.decode("utf-8", errors="replace")

    if ext == ".pdf":
        from pypdf import PdfReader
        reader = PdfReader(io.BytesIO(data))
        pages = [page.extract_text() or "" for page in reader.pages]
        return "\n\n".join(pages).strip()

    if ext == ".docx":
        from docx import Document
        document = Document(io.BytesIO(data))
        parts = [p.text for p in document.paragraphs if p.text.strip()]
        # ★ 改进：把表格也解析进来
        for table in document.tables:
            for row in table.rows:
                cells = [c.text.strip() for c in row.cells]
                if any(cells):
                    parts.append(" | ".join(cells))     # Markdown 表格行
        return "\n".join(parts).strip()

    raise ValueError(f"暂不支持解析：{ext}")


# ── 2. 清洗：处理 PDF 常见的四种脏数据 ─────────────────────
def clean_text(text: str) -> str:
    """针对中文 PDF 的常见清洗。"""
    # ① 中文之间的换行去掉（中文没有单词边界，换行通常是排版导致的）
    text = re.sub(r"(?<=[\u4e00-\u9fff])\n(?=[\u4e00-\u9fff])", "", text)

    # ② 英文连字符断词还原：manage-\nment → management
    text = re.sub(r"(\w)-\n(\w)", r"\1\2", text)

    # ③ 多个空格压缩成一个（PDF 常见"字 字 字"）
    text = re.sub(r"[ \t]{2,}", " ", text)

    # ④ 去掉页眉页脚（简单规则：形如"第 N 页"的独立行）
    text = re.sub(r"^\s*第\s*\d+\s*页\s*$", "", text, flags=re.M)

    # ⑤ 三个以上连续换行压成两个（保留段落分隔）
    text = re.sub(r"\n{3,}", "\n\n", text)

    return text.strip()


# ── 3. 质量检查 ────────────────────────────────────────────
def check_quality(text: str) -> dict:
    """解析质量自检：早发现早处理，别让脏数据进索引。"""
    total = len(text)
    if total == 0:
        return {"ok": False, "level": "fatal", "reason": "空文本（可能是扫描件）"}

    cjk = sum(1 for c in text if "\u4e00" <= c <= "\u9fff")
    spaces = text.count(" ")
    replacement = text.count("\ufffd")
    paragraphs = [p for p in text.split("\n\n") if p.strip()]

    issues = []
    if replacement > 0:
        issues.append(f"存在 {replacement} 个乱码字符（编码问题）")
    if spaces / total > 0.2:
        issues.append(f"空格占比 {spaces/total:.1%} 偏高（可能是 PDF 字间距问题）")
    if len(paragraphs) < 3 and total > 2000:
        issues.append("段落数过少，整篇可能糊在一起")
    if total < 50:
        issues.append("文本过短，可能解析失败")

    return {
        "ok": not issues,
        "level": "warn" if issues else "ok",
        "total_chars": total,
        "cjk_ratio": round(cjk / total, 3),
        "space_ratio": round(spaces / total, 3),
        "paragraphs": len(paragraphs),
        "issues": issues,
    }


# ── 4. 完整流程 ────────────────────────────────────────────
def parse_and_check(filename: str, data: bytes) -> tuple[str, dict]:
    raw = parse_bytes(filename, data)
    cleaned = clean_text(raw)
    report = check_quality(cleaned)
    return cleaned, report


if __name__ == "__main__":
    # 造几份"脏"文档测试
    samples = {
        "正常.md": "实验室开放时间为 8:00 至 22:00。\n\n进入实验室必须穿戴实验服。".encode(),
        "带页眉.txt": "第 1 页\n实验室规定第一条。\n第 2 页\n实验室规定第二条。".encode(),
        "字间距.txt": "实 验 室 安 全 手 册 。 进 入 必 须 穿 戴 实 验 服 。".encode(),
        "断行.txt": "为加强实验室安全管\n理，保障人身安全，特制定\n本手册。".encode(),
        "空.txt": b"",
    }

    for name, data in samples.items():
        text, report = parse_and_check(name, data)
        print(f"\n{'='*56}\n📄 {name}")
        print(f"   质量：{'✅' if report['ok'] else '⚠️'} {report.get('issues') or report.get('reason') or 'OK'}")
        print(f"   清洗后：{text[:60]}...")
        print(f"   统计：{report.get('total_chars', 0)} 字 / "
              f"{report.get('paragraphs', 0)} 段 / 空格占比 {report.get('space_ratio', 0)}")
```

**预期输出（关键部分）**：

```
📄 字间距.txt
   质量：⚠️ ['空格占比 45.5% 偏高（可能是 PDF 字间距问题）']
   清洗后：实 验 室 安 全 手 册 。 进 入 必 须 穿 戴 实 验 服 。
   统计：25 字 / 1 段 / 空格占比 0.455

📄 断行.txt
   质量：✅ OK
   清洗后：为加强实验室安全管理，保障人身安全，特制定本手册。
   统计：25 字 / 1 段 / 空格占比 0.0
   ← ★ 断行被正确还原了

📄 空.txt
   质量：❌ 空文本（可能是扫描件）
```

**注意"字间距"那份没被修好**——因为我们的清洗规则只压缩**连续空格**，`"实 验 室"` 是单空格分隔的。要修这个需要更复杂的规则（判断单字+空格的模式）。

> 这个例子说明了解析的现实：**规则能解决一部分，剩下的要靠更好的工具或接受损失**。

## 22.6 项目代码定位

`backend/app/services/kb_parser.py` 全文只有 31 行，但每一行都有讲究：

```python
"""知识库文档解析：把上传的文件字节解析成纯文本。"""

import io
from pathlib import Path

SUPPORTED_EXTENSIONS = {".md", ".txt", ".pdf", ".docx"}     # ① 白名单


def parse_bytes(filename: str, data: bytes) -> str:
    ext = Path(filename).suffix.lower()                      # ② 大小写不敏感
    if ext not in SUPPORTED_EXTENSIONS:
        raise ValueError(f"不支持的文件类型：{ext}")            # ③ 快速失败

    if ext in {".md", ".txt"}:
        return data.decode("utf-8", errors="replace")        # ④ 容错解码

    if ext == ".pdf":
        from pypdf import PdfReader                          # ⑤ 延迟导入
        reader = PdfReader(io.BytesIO(data))                 # ⑥ 内存文件对象
        pages = [page.extract_text() or "" for page in reader.pages]   # ⑦ None 兜底
        return "\n\n".join(pages).strip()                    # ⑧ 双换行分页

    if ext == ".docx":
        from docx import Document
        document = Document(io.BytesIO(data))
        paragraphs = [p.text for p in document.paragraphs if p.text.strip()]
        return "\n".join(paragraphs).strip()                 # ⑨ 表格未处理

    raise ValueError(f"暂不支持解析：{ext}")
```

### 九个点逐个说

| # | 代码 | 为什么 |
|---|---|---|
| ① | `SUPPORTED_EXTENSIONS` 集合 | 白名单设计，防止上传 `.exe`、`.sh` 等危险文件 |
| ② | `.suffix.lower()` | `PDF` 和 `pdf` 都要能识别 |
| ③ | `raise ValueError` | 快速失败，让上层能明确提示用户"不支持的类型" |
| ④ | `errors="replace"` | 一份文档编码不对不该让整体失败 |
| ⑤ | 函数内 `import` | **延迟导入**——pypdf/python-docx 只在用到时才加载，加快启动 |
| ⑥ | `io.BytesIO(data)` | 避免写临时文件，也避免了清理问题 |
| ⑦ | `or ""` | 图片页 `extract_text()` 返回 None |
| ⑧ | `"\n\n".join` | 双换行形成段落分隔，方便下游切块 |
| ⑨ | 只有 paragraphs | **表格内容会丢失**（已知缺陷） |

### 延迟导入的价值

```python
from pypdf import PdfReader    # 放在函数内而不是文件顶部
```

**为什么？** 因为 `pypdf` 和 `python-docx` 是**重依赖**。如果放顶部，每次启动 FastAPI 都要导入它们，即使这次请求根本不解析 PDF。

延迟导入让：
- 启动更快
- 没装这些包时**其余功能仍可用**（比如只处理 Markdown 的场景）

这是本项目的一贯风格——看 `agent_tools.py` 和 `kb_service.py` 里也是这样（`from rank_bm25 import ...` 在 try 里）。

## 22.7 上游：文件上传怎么到解析器的

解析不是孤立的，看一下它在整条链路里的位置。

```
前端上传（KbManage.vue）
  ↓ multipart/form-data
POST /files/upload 或 /kb/documents
  ↓
kb.py API 层
  ├─ 校验文件类型（白名单）
  ├─ 校验文件大小
  ├─ 读 bytes
  ↓
kb_parser.parse_bytes(filename, data)     ← 本章主角
  ↓
kb_chunking.chunk_document_text(document_id, filename, text)    ← 第 23 章
  ↓
vector_store 写入向量库                    ← 第 25 章
  ↓
kb_service.invalidate_cache()              ← 第 21 章
  ↓
返回成功
```

**两个上游要注意的点**：

1. **文件大小限制**：要在 API 层限制（比如 20MB），否则一个 500MB 的 PDF 会打爆内存
2. **类型校验要在两处做**：前端（体验）+ 后端（安全）。前端的校验可以绕过

## 22.8 面试问答

### Q1：你们支持哪些文档格式？PDF 解析有什么坑？

**答**：支持 md、txt、pdf、docx。用白名单，不支持的类型直接报错。

PDF 是最难的格式，因为它的设计目标是"精确还原打印效果"而不是"存储文本"——内部存的是绘制指令（在哪个坐标画什么字符），不是文本流。所以会有几个典型问题：字符间被插入空格、句子被断行切断、多栏排版阅读顺序乱、表格丢失、扫描件没有文本层、页眉页脚混进正文。

我们的做法是用 pypdf 逐页 `extract_text()`，用双换行连接每一页（形成段落分隔，方便下游切块）。这是最朴素的实现，对复杂 PDF 效果有限。

### Q2：扫描件你们支持吗？

**答**：不支持。扫描件本质是图片，`extract_text()` 返回空。

如果要支持，三条路：一是开源 OCR（pytesseract），中文准确率需要自己调，比较费劲；二是云 OCR 服务（腾讯云、Azure），准确率高但花钱；三是用多模态模型直接读页面，效果最好（还能理解图表），但成本最高。

我会倾向云 OCR，性价比最高。

### Q3：表格怎么处理？

**答**：坦白说这是个短板。docx 我用的是 `document.paragraphs`，它**不包含表格内容**，所以 Word 里的表格会丢失。PDF 的表格会变成空格分隔的碎片，列关系丢失。

改进方案有几种：把表格转成 Markdown 格式（模型对 Markdown 表格理解不错）；行级切块时**重复表头**（"设备: 离心机, 数量: 2, 负责人: 张三"）；或者用 LLM 把表格转成自然语言描述。

### Q4：怎么判断解析质量好不好？

**答**：四个层次。

字符层：检查空文本（可能是扫描件）、空格占比（>20% 说明可能有字间距问题）、乱码字符数。

结构层：段落数是否合理（太少说明糊在一起，太多说明被切碎）。

语义层：抽样人工看，这是最可靠的。

端到端：用 RAG 的召回率反推。**这是最重要的**——如果检索效果差，我的排查顺序是：先看命中的块内容对不对（解析/切块问题），再看资料有没有被索引（覆盖问题），最后才调模型参数。**先怀疑数据，再怀疑模型。**

### Q5：为什么用 `errors="replace"`？

**答**：务实考虑。一个知识库有几十份文档，如果一份是 GBK 编码而我按 UTF-8 解码，抛异常会导致整个索引构建失败。用 `replace` 会把它变成几个 `�`，**损失几个字符但整体可用**。

这是个权衡：宁可局部有损，不要整体失败。理想方案是用 `chardet` 自动检测编码，这是可以改进的点。

### Q6：为什么在函数里 import 而不是文件顶部？

**答**：延迟导入两个好处。

一是**启动快**：pypdf、python-docx 是重依赖，只有真正解析时才加载，其他请求不受影响。

二是**依赖可选**：如果环境没装这些包，只处理 Markdown 的场景仍然能正常工作。这是我们项目的一贯风格——BM25、rerank、MCP 客户端也都是延迟导入 + try/except 兜底。

### Q7：解析完的文本为什么要清洗？

**答**：因为解析出来的原始文本有很多"排版噪声"，会严重影响下游。

比如中文 PDF 的换行通常是排版导致的，不清洗的话切块时句子被切断，检索到的块语义不完整。页眉页脚在每一页重复出现，会被大量索引，稀释真正的语义。多个空格会让分词和 token 计算都不准。

清洗规则我列了五条：中文之间的换行去掉、英文连字符还原、多空格压缩、页眉页脚规则过滤、多余换行压缩。**注意中文和英文要分开处理**——中文没有单词边界可以直接去掉换行，英文不行。

## 22.9 速记卡

> **RAG 的上限由解析质量决定。垃圾进，垃圾出。**

**格式难度**：MD/TXT（易）< DOCX（中）< PDF（难，因为存的是绘制指令）

**PDF 六大坑**：字间距 / 断行 / 多栏乱序 / 表格丢失 / 扫描件 / 页眉页脚

**项目实现（31 行）**：
```python
if ext in {".md", ".txt"}: return data.decode("utf-8", errors="replace")
if ext == ".pdf":  PdfReader(io.BytesIO(data)) → "\n\n".join(pages)
if ext == ".docx": Document(...).paragraphs → "\n".join(...)
```

**九个点**：白名单 / lower() / 快速失败 / errors=replace / **延迟导入** / BytesIO / `or ""` / 双换行 / **表格丢失**

**清洗五规则**：中文换行合并 / 英文连字符还原 / 多空格压缩 / 页眉页脚 / 多余换行

**质量检查**：空文本 / 空格占比 >20% / 乱码字符 / 段落数

**排查原则**：**先怀疑数据，再怀疑模型**

**已知边界**：不支持扫描件 OCR；docx 表格丢失

**代码位置**：`backend/app/services/kb_parser.py`（全文 31 行）

## 22.10 延伸思考

1. **如果让你支持扫描件，你会怎么设计？成本和效果怎么权衡？**
   提示：先检测（文本层为空 → 判定为扫描件）→ 再决定走 OCR。云 OCR 按页计费，一本 300 页的手册成本不低。考虑：是否只对"检索失败"的页面做 OCR？

2. **表格转自然语言（用 LLM）会引入什么新问题？**
   提示：成本、延迟、以及**LLM 可能改写错误**。表格里的数字被改错是很危险的事。权衡：只在高价值表格上做，且保留原文对照。

3. **页眉页脚的过滤规则如果误伤了正文（比如正文里有一行"第 3 页"），怎么办？**
   提示：规则要更严格（必须是页首/页尾 N 行内 + 匹配模式）。或者统计法：在 >50% 的页面出现的行判定为页眉页脚。思考：统计法对小文档（3 页）有效吗？
