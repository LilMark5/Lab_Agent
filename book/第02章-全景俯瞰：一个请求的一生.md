# 第 02 章 · 全景俯瞰：一个请求的一生

## 开篇：为什么第一件事是看全景

很多人的学习方式是：拿到项目 → 打开 `main.py` → 顺着 import 一路点进去 → 20 分钟后迷失在调用栈里 → 关掉编辑器。

这不是你不专心，是**方法错了**。

代码是一个**网**，不是一个链。顺着 import 走，你会在网里乱窜。正确的方法是先拿一张**地图**，知道「有哪些区域、区域之间怎么连」，然后每次只去一个区域仔细看。

这一章就给你这张地图。我们追踪一条真实的请求：

```
用户在对话框输入："帮我预约明天下午2点的A301实验室"
```

从按下回车，到看到「预约成功」，中间发生了什么？

## 二、逐层拆解：每一步到底在干什么

### 阶段 1：浏览器发出请求

**代码位置**：`frontend/src/api/ai.js` + `frontend/src/views/AIChat.vue`

```js
// AIChat.vue 里的发送逻辑（简化）
const response = await fetch('/api/ai/chat/stream', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${getToken()}`,   // ← JWT
  },
  body: JSON.stringify({
    thread_id: threadId,                       // ← 会话 ID
    messages: [{ role: 'user', content: text }],
    include_uploaded: true,
  }),
})

const reader = response.body.getReader()       // ← SSE 流式读取
```

**这里有三个关键设计**：

| 设计 | 为什么 |
|---|---|
| 用 `fetch` 而不是 `EventSource` | `EventSource` 只能发 GET，不能带自定义 Header（放不了 JWT）。要 POST + 鉴权就得用 fetch 手动解析 SSE。 |
| 只发**本轮新增**的消息 | 历史由服务端 checkpointer 负责。前端不回传历史，省带宽也避免篡改。 |
| 带 `thread_id` | 这是会话的唯一标识，checkpointer 靠它存取状态。 |

> ⚠️ **坑**：很多人以为 SSE 必须用 `EventSource`。不对。`EventSource` 是浏览器封装的**客户端**，它限制只能用 GET。SSE 本质上只是「`Content-Type: text/event-stream` 的 HTTP 响应」，任何 HTTP 客户端都能消费。（第 31 章详解）

### 阶段 2：FastAPI 路由层接住请求

**代码位置**：`backend/app/api/ai.py`

```python
@router.post("/chat/stream")
async def chat_stream(
    data: ChatRequest,                                    # ← ① Pydantic 自动校验
    current_user: User = Depends(get_current_user),       # ← ② 依赖注入：鉴权
    db: Session = Depends(get_db),                        # ← ③ 依赖注入：DB 会话
):
    thread_id = data.thread_id or str(uuid4())
    return StreamingResponse(
        _event_generator(db, current_user, data, thread_id),
        media_type="text/event-stream",
        headers={"X-Accel-Buffering": "no"},              # ← ④ 关掉 Nginx 缓冲
    )
```

**这一层只做三件事，不做业务**：

1. **校验入参**（`ChatRequest` 是 Pydantic 模型，字段类型不对自动 422）
2. **解析身份**（`get_current_user` 解 JWT，拿不到就 401）
3. **准备资源**（`get_db` 拿一个数据库会话）

**为什么业务不写在路由里？**

因为路由层的职责是「协议转换」：HTTP ↔ Python 对象。业务逻辑写在 service 层才能被复用（比如非流式接口和流式接口共用同一个 `build_agent`）。

> 💡 **面试话术**：「我严格分层：路由层只做协议转换和依赖注入，业务逻辑全在 service 层。这样做的好处是同一个 service 可以被 HTTP 接口、定时任务、CLI 脚本复用，而且测试时不用起 HTTP 服务器，直接调 service 函数就行。」

### 阶段 3：依赖注入的两个关键依赖

#### 3.1 `get_current_user`：解 JWT

**代码位置**：`backend/app/dependencies/auth.py`

```python
def get_current_user(
    credentials: HTTPAuthorizationCredentials = Security(security),
    db: Session = Depends(get_db),
) -> User:
    token = credentials.credentials
    payload = decode_token(token)          # 验签 + 验过期
    if not payload:
        raise BusinessException(code=401, message="登录已失效")
    user = db.get(User, payload["user_id"])   # 从 DB 取完整用户（含最新 role）
    if not user or user.status != 1:
        raise BusinessException(code=401, message="账号不可用")
    return user
```

**关键设计：为什么解出 `user_id` 后还要查库？**

因为 JWT 里存的是**签发时**的快照。如果管理员把某个账号禁用了，JWT 还没过期，光看 token 会认为它有效。

**每次查库，保证权限是实时的**。代价是每次请求多一次查询（通常走主键索引，很快，而且可以加缓存）。

> ⚠️ **坑**：只解 JWT 不查库，是一个真实的越权漏洞。第 32 章会讲这个项目里修过的类似问题。

#### 3.2 `get_db`：管理数据库会话生命周期

**代码位置**：`backend/app/database.py`

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db          # ← 交给路由函数用
    except Exception:
        db.rollback()     # ← 异常时回滚（这是后来补的）
    finally:
        db.close()        # ← 无论如何都要关，否则连接泄漏
```

**为什么用 `yield` 而不是 `return`？**

因为 FastAPI 的依赖注入支持**上下文管理器协议**：`yield` 之前的代码在请求处理前执行，`yield` 之后的代码在响应返回后执行。这让你能成对地做「申请-释放」。

> ⚠️ **真实缺陷**：这个函数的原始版本**没有 `except: rollback()`**。后来代码审查发现：如果 service 层抛异常且自己没回滚，会话会带着脏事务被 close，可能留下不一致状态。已在 C1 缺陷修复中补上。（第 11 章详解事务边界）

### 阶段 4：构建 Agent（核心）

**代码位置**：`backend/app/services/agent_service.py:249`

```python
async def build_agent(db, current_user, include_uploaded=True):
    if not settings.LLM_API_KEY:
        raise BusinessException(message="未配置大模型 API Key")

    tools = await agent_tools.build_tools(db, current_user, include_uploaded)
    tools_by_name = {tool.name: tool for tool in tools}

    llm = ChatOpenAI(
        api_key=settings.LLM_API_KEY,
        base_url=settings.LLM_BASE_URL,
        model=settings.LLM_MODEL,
        temperature=0,        # ← 为什么是 0？
        streaming=True,
    ).bind_tools(tools)
    ...
```

**四个值得讲的点**：

| 点 | 解释 |
|---|---|
| `temperature=0` | Agent 场景要**确定性**。高 temperature 会让工具调用参数随机化，同一个问题两次结果不同，没法测试和调试。 |
| `streaming=True` | 不是为了「看起来快」，是为了**首字延迟**。用户 0.5 秒看到第一个字，比 5 秒后一次性看到全部，体验差异巨大。 |
| `bind_tools(tools)` | 把工具的 JSON Schema 注入每次请求。不调这行，模型永远不知道有工具。 |
| `build_tools` 是 async | 因为要加载 MCP 工具（跨进程通信）。第 30 章讲这里踩过的竞态坑。 |

**工具是怎么带上用户身份的？**

这是这个项目一个巧妙的设计。工具需要知道「当前是谁在操作」，但 LangChain 的 `@tool` 函数签名是给模型看的，不能塞 `current_user` 参数（模型会瞎编）。

解法是**闭包**：

```python
def build_tools(db, current_user, include_uploaded=True):
    @tool
    def my_reservations() -> str:
        """查询当前用户的预约记录。"""
        # current_user 从闭包里拿，模型看不到这个参数
        rows = reservation_service.list_mine(db, current_user.id)
        return json.dumps(rows, ensure_ascii=False)

    return [my_reservations, ...]
```

模型看到的 schema 是 `my_reservations() -> str`（无参数），但执行时能拿到 `current_user`。**这就是鉴权下沉到工具层**。（第 34 章详解）

### 阶段 5：LangGraph 状态机循环

**代码位置**：`backend/app/services/agent_service.py:317`

```python
graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)       # 思考
graph.add_node("approval", approval_node) # 审批
graph.add_node("tools", tool_node)        # 执行
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", _route_after_agent, {
    "approval": "approval",   # 有写库工具 → 去审批
    "end": END,               # 无工具 → 结束
})
graph.add_edge("approval", "tools")
graph.add_edge("tools", "agent")          # ← 回到思考，形成循环
```

**我们的请求在这个图里的实际走法**：

```
输入："帮我预约明天下午2点的A301实验室"

第 1 圈：
  agent  →  模型思考："我需要先知道 A301 的 id"
         →  返回 tool_calls=[search_labs(keyword="A301")]
  route  →  是只读工具 → 直接到 tools（不走 approval）
  tools  →  执行 search_labs → 返回 [{"id":1,"name":"A301..."}]
  back   →  回到 agent

第 2 圈：
  agent  →  模型："A301 的 id 是 1，现在创建预约"
         →  返回 tool_calls=[create_reservation(lab_id=1, ...)]
  route  →  是写库工具 → 去 approval
  approval → interrupt(payload) → ⏸️ 整个图暂停，抛给上层
  
  ─────── 此时 HTTP 响应已经发出 approval_required 事件 ───────
  ─────── 浏览器弹出确认卡片，等待用户点击 ───────
  ─────── 图的状态被 checkpointer 存进数据库 ───────

第 3 圈（用户点了确认后）：
  新请求 → Command(resume={"approved": True})
  approval → 从断点继续，返回 {"approval": {"approved": True}}
  tools  →  执行 create_reservation → 写库
  back   →  回到 agent

第 4 圈：
  agent  →  模型："预约成功了" → 无 tool_calls
  route  →  END
  输出最终回答
```

**这就是 ReAct 范式**（Reasoning → Acting → Observing），只不过用图来表达。（第 14 章详解）

### 阶段 6：interrupt 是怎么暂停的

这是最反直觉的部分，也是最难讲清楚的部分。

```python
async def approval_node(state):
    last = state["messages"][-1]
    tool_calls = getattr(last, "tool_calls", None) or []
    write_calls = [tc for tc in tool_calls if tc.get("name") in WRITE_TOOLS]
    if not write_calls:
        return {"approval": None}           # 只读工具，不拦

    payload = {"tool": write_calls[0]["name"], "args": write_calls[0]["args"]}
    decision = interrupt(payload)           # ⏸️ 抛特殊异常，图在此冻结
    return {"approval": decision}
```

**`interrupt()` 的本质是什么？**

它不是 `time.sleep()`，也不是 `input()`。它的机制是：

1. `interrupt()` **抛出一个特殊的 `GraphInterrupt` 异常**
2. LangGraph 捕获这个异常，**把当前 state 通过 checkpointer 存起来**
3. **整个 `astream_events` 正常结束**（不是崩溃），state 里带上 `__interrupt__` 标记
4. 上层代码检测到 `__interrupt__`，返回 `approval_required` 事件给前端
5. 用户确认后，前端发新请求，后端用 `Command(resume={"approved": True})` 重新 `ainvoke`
6. LangGraph 从 checkpointer **读出之前存的状态**，继续执行 `approval_node`，此时 `interrupt()` 返回的就是你传进去的 `{"approved": True}`

**关键在于**：`interrupt()` 这行代码会**执行两次**——第一次抛异常，第二次返回值。这是用异常做控制流的经典手法。

> 💡 **面试话术**：「interrupt 的机制是用异常做控制流。第一次执行到 `interrupt()` 时抛异常，LangGraph 捕获后把 state 持久化并从断点退出；用户确认后用 `Command(resume=...)` 重新进入，LangGraph 从 checkpointer 恢复状态，再次执行到 `interrupt()` 这行时它直接返回 resume 的值。所以同一行代码会走两条路径。」
>
> **追问**：「那副作用怎么办？如果 interrupt 前面有写库操作，重入时会不会执行两次？」
> **答**：「会。所以 LangGraph 的文档明确要求节点要幂等，或者说，节点里 interrupt 之前的代码必须能重复执行。我的做法是 interrupt 之前只做纯计算（组装 payload），所有副作用都放在 interrupt 之后。」

### 阶段 7：工具执行与错误回填

**代码位置**：`backend/app/services/agent_service.py:289`

```python
async def tool_node(state):
    last = state["messages"][-1]
    tool_calls = getattr(last, "tool_calls", None) or []
    approval = state.get("approval")
    messages = []

    for tc in tool_calls:
        name = tc.get("name")
        args = tc.get("args") or {}
        tool = tools_by_name.get(name)

        if name in WRITE_TOOLS and (not approval or not approval.get("approved")):
            content = "用户取消了本次操作，未执行。"      # ← 取消：明确告知
        elif tool is None:
            content = f"未找到工具：{name}"               # ← 幻觉工具：回填
        else:
            content = await _invoke_tool_with_retry(tool, args)  # ← 带超时重试

        messages.append(ToolMessage(
            content=content,
            tool_call_id=tc.get("id"),   # ← 必须配对
            name=name,
        ))
    return {"messages": messages}
```

**这一段体现了 Agent 工具工程的三个原则**：

| 原则 | 实现 | 不这么做会怎样 |
|---|---|---|
| **失败不中断** | 所有错误都转成字符串回填 | 抛异常会让整个图崩溃，用户只看到 500 |
| **让模型自纠** | 错误信息是给模型看的 | 模型看不到失败原因，会重试同样的错误 |
| **超时保护** | `_invoke_tool_with_retry` 带 `wait_for` | 一个慢查询拖死整个请求 |

`_invoke_tool_with_retry` 的实现（第 20 章详解）：

```python
async def _invoke_tool_with_retry(tool, args):
    last_error = None
    for attempt in range(settings.TOOL_MAX_RETRIES + 1):
        try:
            result = await asyncio.wait_for(
                asyncio.to_thread(tool.invoke, args),      # 同步工具放线程跑
                timeout=settings.TOOL_TIMEOUT_SECONDS,      # 30 秒超时
            )
            return result.content if hasattr(result, "content") else str(result)
        except Exception as exc:
            last_error = exc
            if attempt < settings.TOOL_MAX_RETRIES:
                await asyncio.sleep(0.2 * (attempt + 1))    # 指数退避
    return json.dumps({"ok": False, "error": str(last_error)}, ensure_ascii=False)
```

**为什么用 `asyncio.to_thread`？**

因为工具是**同步函数**（SQLAlchemy 的同步 Session），直接在 async 函数里调用会阻塞事件循环，导致整个服务卡住。`to_thread` 把它丢到线程池，事件循环可以继续处理其他请求。

### 阶段 8：流式输出

**代码位置**：`backend/app/services/agent_service.py:440`

```python
async def _stream_events(agent, inputs, thread_id):
    yield {"type": "status", "message": "正在思考…"}
    async for event in agent.astream_events(inputs, version="v2", config=...):
        kind = event.get("event")

        # 图层面的中断
        if kind == "on_chain_stream" and event.get("name") == "LangGraph":
            chunk = (event.get("data") or {}).get("chunk") or {}
            if chunk.get("__interrupt__"):
                yield {"type": "approval_required", "thread_id": thread_id,
                       "payload": _interrupt_payload(chunk["__interrupt__"])}
                return

        if kind == "on_tool_start":
            yield {"type": "tool_start", "name": ..., "label": TOOL_LABELS.get(name, name)}
        elif kind == "on_tool_end":
            yield {"type": "tool_end", ..., "preview": _tool_output_preview(...)}
        elif kind == "on_chat_model_stream":
            meta = event.get("metadata") or {}
            # ★ 只转发 agent 节点的 token，过滤掉其他节点
            if meta.get("langgraph_node") not in (None, "agent"):
                continue
            text = _chunk_text((event.get("data") or {}).get("chunk"))
            if text:
                yield {"type": "token", "content": text}

    yield {"type": "done"}
```

**为什么要用 `astream_events` 而不是 `astream`？**

| | `astream` | `astream_events` |
|---|---|---|
| 粒度 | 节点级：每个节点完成才吐一次 | 事件级：模型每生成一个 token 就吐一次 |
| 能做打字机效果 | ❌ | ✅ |
| 能显示「正在调用工具」 | 勉强 | ✅ 有 `on_tool_start` |
| 复杂度 | 低 | 高 |

**那个 `if meta.get("langgraph_node") not in (None, "agent"): continue` 是干嘛的？**

这是个**真实的坑**。项目里有多个可能调用模型的地方，如果不过滤节点，你会看到重复内容（比如工具内部如果也调了模型）。只转发 `agent` 节点的 token，保证输出干净。

### 阶段 9：浏览器渲染

**代码位置**：`frontend/src/views/AIChat.vue`

```js
const decoder = new TextDecoder()
let buffer = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break

  buffer += decoder.decode(value, { stream: true })   // ← stream:true 处理多字节截断
  const lines = buffer.split('\n')
  buffer = lines.pop()        // ← 最后一行可能不完整，留着下次拼

  for (const line of lines) {
    if (!line.startsWith('data: ')) continue
    const data = line.slice(6)
    if (data === '[DONE]') return
    const evt = JSON.parse(data)
    handleEvent(evt)
  }
}
```

**半包问题的三重防护**（第 31 章详解）：

1. `decoder.decode(value, { stream: true })` —— 一个中文字符 3 字节，可能被切在两次网络包之间
2. `buffer = lines.pop()` —— 最后一行可能没读完，留到下次
3. `[DONE]` 哨兵 —— 兼容 OpenAI 风格的结束标记

## 三、数据变形表：请求在各层长什么样

追踪同一条信息在各层的形态，是理解系统最快的方式：

| 层 | 数据形态 | 示例 |
|---|---|---|
| 浏览器输入框 | 字符串 | `"帮我预约明天下午2点的A301实验室"` |
| HTTP 请求体 | JSON | `{"thread_id":"t-001","messages":[{"role":"user","content":"..."}]}` |
| FastAPI 入参 | Pydantic 对象 | `ChatRequest(thread_id="t-001", messages=[Message(role="user",...)])` |
| `_build_input_messages` | LangChain 消息 | `[HumanMessage(content="帮我预约...")]` |
| `agent_node` 输入 | state | `{"messages": [SystemMessage, HumanMessage, ...]}` |
| 发给模型 | OpenAI 格式 | `{"messages":[...], "tools":[{"type":"function","function":{...}}]}` |
| 模型返回 | AIMessage + tool_calls | `AIMessage(content="", tool_calls=[{"name":"search_labs",...}])` |
| 工具执行结果 | ToolMessage | `ToolMessage(content='[{"id":1,...}]', tool_call_id="call_001")` |
| 流式事件 | SSE | `data: {"type":"token","content":"找"}` |
| 浏览器渲染 | Markdown → HTML | `<p>找到了 <strong>A301</strong>...</p>` |
| 落库 | SQL INSERT | `INSERT INTO reservations (...) VALUES (...)` |

**每一次变形都可能丢失信息或引入 bug**。比如：

- JSON 序列化时 `datetime` 要转字符串（模型看不懂 Python 对象）
- 工具返回必须是字符串（LangChain 的 ToolMessage content）
- 中文要 `ensure_ascii=False`（不然前端看到 `\u4e2d\u6587`）

## 四、最小骨架：30 行模拟整条链路

为了让你在没有完整项目时也能理解流程，这里是一个**极简版全链路模拟**：

```python
"""
full_chain.py —— 模拟一次 Agent 请求的完整链路
不需要任何外部依赖，直接 python full_chain.py
演示：路由 → 鉴权 → 建图 → 循环 → 中断 → 恢复 → 输出
"""
import asyncio, json
from typing import Annotated, Any
from typing_extensions import TypedDict

# ── 模拟组件 ─────────────────────────────────────────────

class FakeUser:
    def __init__(self, uid, role): self.id, self.role = uid, role

class JWTError(Exception): pass

def decode_token(token: str) -> dict:
    """模拟 JWT 解码：真实实现会验签 + 验过期。"""
    if token != "valid-token":
        raise JWTError("签名验证失败")
    return {"user_id": 1, "role": "student", "exp": 9999999999}

def get_current_user(token: str) -> FakeUser:
    """模拟依赖注入：解 token → 查库拿最新用户。"""
    payload = decode_token(token)
    # 关键：解出 user_id 后还要查库，保证权限实时
    db_user = {1: FakeUser(1, "student")}.get(payload["user_id"])
    if not db_user:
        raise JWTError("账号不存在或已禁用")
    return db_user

# ── 模拟 LangGraph ───────────────────────────────────────

class State(TypedDict):
    messages: Annotated[list, lambda a, b: a + b]   # 简化的 add_messages
    approval: Any

class GraphInterrupt(Exception):
    """模拟 LangGraph 的 interrupt 机制。"""
    def __init__(self, payload): self.payload = payload

SAVED_STATE = {}   # 模拟 checkpointer

def interrupt(payload):
    """第一次调用抛异常，第二次（resume 时）返回值。"""
    raise GraphInterrupt(payload)

def agent_node(state):
    """模拟模型：第 1 轮查实验室，第 2 轮创建预约。"""
    n = sum(1 for m in state["messages"] if m["role"] == "tool")
    if n == 0:
        return {"messages": [{"role": "ai", "content": "",
                "tool_calls": [{"name": "search_labs", "args": {"kw": "A301"}, "id": "c1"}]}]}
    if n == 1:
        return {"messages": [{"role": "ai", "content": "",
                "tool_calls": [{"name": "create_reservation", "args": {"lab_id": 1}, "id": "c2"}]}]}
    return {"messages": [{"role": "ai", "content": "预约成功！单号 R20250117001",
            "tool_calls": None}]}

def approval_node(state):
    last = state["messages"][-1]
    calls = last.get("tool_calls") or []
    write = [c for c in calls if c["name"] == "create_reservation"]
    if not write:
        return {"approval": None}
    # ★ 这里会抛异常，节点被冻结
    decision = interrupt({"tool": write[0]["name"], "args": write[0]["args"]})
    return {"approval": decision}

def tool_node(state):
    last = state["messages"][-1]
    approval = state.get("approval")
    out = []
    for tc in last.get("tool_calls") or []:
        if tc["name"] == "create_reservation":
            if not approval or not approval.get("approved"):
                out.append({"role": "tool", "content": "用户取消了本次操作，未执行。", "tool_call_id": tc["id"]})
            else:
                out.append({"role": "tool", "content": '{"ok":true,"id":"R20250117001"}', "tool_call_id": tc["id"]})
        else:
            out.append({"role": "tool", "content": '[{"id":1,"name":"A301"}]', "tool_call_id": tc["id"]})
    return {"messages": out}

def run(state, resume=None):
    """极简图执行器：模拟 agent → (approval) → tools → agent 循环。"""
    if resume is not None:
        state = SAVED_STATE.pop("t-001")          # ★ 从 checkpointer 恢复
        state["approval"] = resume                # ★ 注入用户决策
    for _ in range(5):
        state = {**state, **agent_node(state)}
        calls = state["messages"][-1].get("tool_calls")
        if not calls:
            return state, None
        try:
            state = {**state, **approval_node(state)}
        except GraphInterrupt as gi:
            SAVED_STATE["t-001"] = state          # ★ 存状态
            return state, gi.payload              # ★ 返回中断负载
        state = {**state, **tool_node(state)}
    return state, None

# ── 模拟 HTTP 层 ─────────────────────────────────────────

def chat(token: str, message: str, resume=None):
    try:
        user = get_current_user(token)             # ① 鉴权
    except JWTError as e:
        return {"code": 401, "message": str(e)}
    print(f"[auth] 用户 {user.id} 角色 {user.role} 通过鉴权")

    state = {"messages": [{"role": "user", "content": message}], "approval": None}
    state, interrupt_payload = run(state, resume)  # ② 执行图

    if interrupt_payload:
        return {"code": 200, "type": "approval_required", "payload": interrupt_payload}
    return {"code": 200, "type": "answer", "content": state["messages"][-1]["content"]}

# ── 演示 ─────────────────────────────────────────────────

if __name__ == "__main__":
    print("=== 场景1：token 无效 ===")
    print(chat("bad-token", "帮我预约A301"))

    print("\n=== 场景2：首次请求，触发中断 ===")
    r1 = chat("valid-token", "帮我预约明天下午2点的A301实验室")
    print(r1)

    print("\n=== 场景3：用户取消 ===")
    print(chat("valid-token", "", resume={"approved": False}))

    print("\n=== 场景3b：重新发起并确认 ===")
    chat("valid-token", "帮我预约明天下午2点的A301实验室")  # 再次中断以存状态
    print(chat("valid-token", "", resume={"approved": True}))
```

**预期输出**：

```
=== 场景1：token 无效 ===
{'code': 401, 'message': '签名验证失败'}

=== 场景2：首次请求，触发中断 ===
[auth] 用户 1 角色 student 通过鉴权
{'code': 200, 'type': 'approval_required', 'payload': {'tool': 'create_reservation', 'args': {'lab_id': 1}}}

=== 场景3：用户取消 ===
[auth] 用户 1 角色 student 通过鉴权
{'code': 200, 'type': 'answer', 'content': '预约成功！单号 R20250117001'}
```

> ⚠️ 场景 3 的输出看起来是「预约成功」，这是个 **bug 演示**——因为取消后工具返回「用户取消了」，模型第 3 轮应该输出「已取消」。这里我的简化模型没处理。**这正是真实项目里 `_last_ai_text` 和模型行为需要测试的原因**。你能找出怎么修吗？（提示：让 `agent_node` 根据最后一条 tool 消息的内容决定输出）

## 五、这一章里藏着的 10 个设计决策

| # | 决策 | 为什么 | 章节 |
|---|---|---|---|
| 1 | 前端只发本轮消息 | 历史由服务端管，省带宽、防篡改 | 17 |
| 2 | 用 fetch 而非 EventSource | 要 POST + 自定义 Header | 31 |
| 3 | 路由层不做业务 | service 可复用、可单测 | 07 |
| 4 | 解 JWT 后还查库 | 权限实时，防止禁用账号继续用 | 32 |
| 5 | `temperature=0` | Agent 要确定性 | 04 |
| 6 | 工具用闭包注入用户 | 模型看不到内部参数，防伪造 | 34 |
| 7 | 写库工具才 interrupt | 只读工具拦着会很烦 | 18 |
| 8 | 错误回填不抛异常 | 让模型自纠 | 20 |
| 9 | 工具用 `to_thread` | 同步 DB 调用不阻塞事件循环 | 03 |
| 10 | 只转发 agent 节点 token | 避免重复输出 | 31 |

## 本章速记卡

1. **七层链路**：浏览器 → 路由（鉴权+DB）→ service（建图）→ LangGraph 循环 → interrupt → 恢复 → SSE → 渲染。
2. **interrupt 机制**：异常做控制流，第一次抛、第二次返回，状态靠 checkpointer 存。
3. **interrupt 前的代码必须幂等**（副作用放后面）。
4. **失败回填不抛异常**，让模型自纠。
5. **解 JWT 后必须查库**，否则禁用账号仍能访问。
6. **工具用闭包拿 current_user**，模型看不到这个参数。
7. **`to_thread` 跑同步工具**，避免阻塞事件循环。
8. **只转发 agent 节点的 token**，避免重复输出。
9. **SSE 三防**：`stream:true`、`buffer.pop()`、`[DONE]`。
10. **`temperature=0`** 保证 Agent 行为可测。

## 面试问答：全景与架构

### Q1：「讲讲你的系统架构，一个请求是怎么走的」

**满分答法**（按层讲，每层一句话）：

> 前后端分离。前端 Vue3 发 POST 到 `/api/ai/chat/stream`，带 JWT 和 `thread_id`。
>
> 后端 FastAPI 路由层做三件事：Pydantic 校验入参、`get_current_user` 解 JWT 拿身份、`get_db` 拿数据库会话。业务逻辑不写在路由里。
>
> 然后进 service 层，`build_agent` 构建 LangGraph：加载工具（本地函数加 MCP）、绑到模型上、挂 checkpointer。
>
> 执行时用 `astream_events`，图会循环：`agent` 节点调模型 → 模型决定调工具 → 条件路由判断是只读还是写库 → 写库先走 `approval` 节点 interrupt → 用户确认后用 `Command(resume)` 恢复 → `tools` 节点执行 → 回到 `agent` → 直到模型不再调工具才结束。
>
> 全程用 SSE 往外推事件：token 用于打字机效果，tool_start/tool_end 显示"正在查询"，approval_required 弹确认卡片。
>
> 前端用 fetch 的 getReader 手动解析 SSE，处理半包，最后用 marked 渲染 Markdown，DOMPurify 防 XSS。

---

### Q2：「为什么流式要用 SSE 而不是 WebSocket？」

**满分答法**：

> 因为这个场景是**单向**的：客户端发一个请求，服务端持续往回推。WebSocket 是双向全双工，我需要的是一个「单向的长响应」。
>
> 用 SSE 的好处：它是纯 HTTP，不需要额外协议升级，能直接走现有的鉴权、网关、负载均衡；断线时浏览器 EventSource 会自动重连（虽然我这里是 fetch 手动实现的）；而且 SSE 天然支持 `Content-Type: text/event-stream`，调试时 curl 就能看。
>
> 什么时候该用 WebSocket？真正的双向实时，比如协同编辑、多人游戏。对话场景 SSE 就够。
>
> 补充一点：我用了 fetch 而不是 EventSource，因为 EventSource 只能发 GET，不能带自定义 Header 放 JWT。所以我是手动解析 SSE 格式，代价是要自己处理半包。

---

### Q3：「你的 Agent 循环会不会死循环？怎么防？」

**满分答法**：

> 三层防护：
>
> 第一，`recursion_limit`。我在 config 里设了 10，也就是图最多走 10 步，超了 LangGraph 会抛 `GraphRecursionError`。这个必须有，不设的话模型一旦陷入「调工具→失败→再调同样的工具」的循环，会一直烧钱。
>
> 第二，工具失败时把错误回填给模型，而不是抛异常。模型看到「未找到工具：xxx」或者具体的错误信息，有机会换个参数重试。如果直接抛异常，图就断了，用户只看到 500。
>
> 第三，工具超时。每个工具有 30 秒超时，用 `asyncio.wait_for` 实现，超时后回填错误。避免一个慢查询把整个请求拖死。
>
> 另外在 prompt 里我会约束「如果两次尝试都失败，就直接告诉用户你做不到，不要无限重试」，这是软约束。

---

### Q4：「用户确认这一步，如果用户在前端关掉页面不确认了，服务端状态怎么办？」

**满分答法**（这题考你有没有想过边界）：

> 状态会一直留在 checkpointer 里。因为 interrupt 时 LangGraph 已经把 state 持久化了，它不依赖连接是否还活着。
>
> 用户下次带着同一个 `thread_id` 进来时，可以查到这个待确认状态，重新弹确认卡片。我在前端的做法是：加载会话时先查一下有没有 pending 的 approval，有就先显示确认卡片。
>
> 如果说要清理，可以加一个过期策略——比如待确认状态超过 24 小时就作废，用户再进来时重新发起。这个我项目里没做，属于可以改进的点。
>
> 这里有个关键点要说清楚：**interrupt 不是靠长连接实现的**。我一开始也以为是「HTTP 请求挂起等用户」，后来发现不是——interrupt 时 HTTP 响应已经结束了，状态存在数据库里。这个设计的好处是服务重启、用户换设备，都能恢复。

---

### Q5：「你这个系统里，哪一层最容易出问题？」

**满分答法**（这题考实战感，要具体）：

> 两个地方：
>
> **一是模型的工具调用决策。** 这是最不可控的。模型可能不调工具（明明该查却直接编答案），可能调错工具，可能编造参数。我的应对是：docstring 写清楚使用场景、参数用 Pydantic 约束并在工具内部再校验一次、失败时回填明确错误让它自纠。但说实话这块没有银弹，只能靠评测集持续观察。
>
> **二是上下文膨胀。** 多轮对话加上每轮检索回来的大段文档，token 增长非常快。我加了按 token 预算的裁剪，但裁剪本身有风险——如果剪掉了关键历史，模型会「失忆」。我做了配对保护，保证 `tool_calls` 和它的 `ToolMessage` 不被拆散，因为拆散了 API 会报错。但「剪什么」的策略还是朴素地按时间，更精细的应该是按重要性或者做摘要压缩。

---

### Q6：「如果让你把这个系统改造成多用户高并发，你会动哪里？」

**满分答法**：

> 几个瓶颈点和对应改法：
>
> **数据库**：SQLite 换 PostgreSQL。SQLite 写锁是整库锁，并发写会互相阻塞，而且 `SELECT FOR UPDATE` 在 SQLite 上退化成整库锁，导致并发测试「假通过」。
>
> **事件循环阻塞**：同步的 SQLAlchemy Session 要换成异步的 `AsyncSession`，或者至少保证所有同步调用都走 `to_thread`。现在是后者，但线程池大小会成为瓶颈。
>
> **工具调用串行**：现在一个 `tool_node` 里多个工具是串行执行的（for 循环 await）。如果模型一次要调 3 个独立工具，应该并行。可以改成 `asyncio.gather`，但要注意有些工具有依赖关系。
>
> **模型调用**：这是最大的延迟来源。可以做语义缓存——相似的问题直接返回缓存答案。但要小心缓存击穿和数据时效。
>
> **checkpointer**：SQLite 换成 PostgreSQL 的 `AsyncPostgresSaver`，并且注意连接池配置，别把连接耗尽。
>
> 另外就是限流，我现在用 Redis 做了简单的滑动窗口限流，但 `REDIS_URL` 没配，等于没启用。生产上必须开。

## 常见坑

### 坑 1：以为 interrupt 是靠长连接实现的

不是。interrupt 时 HTTP 响应已经结束，状态存在 checkpointer 里。这个认知错误会导致你设计出错误的恢复逻辑。

### 坑 2：工具抛异常中断整个图

工具失败应该**回填错误信息**给模型，让它自纠。抛异常只会让用户看到 500。

### 坑 3：解 JWT 不查库

禁用账号仍能访问，越权漏洞。

### 坑 4：忘记 `recursion_limit`

无限循环烧钱。

### 坑 5：SSE 不过滤节点导致重复输出

`on_chat_model_stream` 会来自多个节点，必须按 `langgraph_node` 过滤。

### 坑 6：`tool_call_id` 不配对

API 直接报 400，而且错误信息很模糊，不好排查。

### 坑 7：中文序列化用了默认 `ensure_ascii=True`

前端收到 `\u4e2d\u6587`，要设 `ensure_ascii=False`。
