# 第 43 章 · 从零复刻这个项目：21 天路线图

> 前面 42 章是"讲清楚"，这一章是"带你做"。
>
> 这一章的目标很具体：**21 天后，你有一个自己写的、能跑的、面试能讲的项目。**
> 不是Fork，不是Copy，是你自己一行行敲出来的——因为**只有自己敲过的代码，你才答得出追问**。
>
> 先给你一个数：这个项目的实际体量是
> **后端 52 个 Python 文件 / 4216 行，测试 681 行，前端 2776 行**。
> 平均到 21 天是**每天约 230 行后端代码**——这个强度对有 Python 基础的人是可行的，
> 但前提是**每天都有明确的验收标准**。所以这一章的核心是"每天做什么 + 怎么算做完"。

## 43.1 为什么需要一份路线图

### 43.1.1 自学 Agent 开发的三个典型死法

**死法一：教程收藏家**

看了 20 篇 LangGraph 教程，每篇都"懂了"，但打开编辑器不知道第一行写什么。

**原因**：教程给你的是**结论**（"用 StateGraph 就对了"），没给你**过程**（"为什么需要状态机、不用会怎样"）。收藏结论不产生能力。

**死法二：Demo 玩家**

跑通了官方 Quickstart，能改改参数。面试时被问"如果工具超时怎么办"，答"应该要处理吧"。

**原因**：Demo 是**无菌环境**——没有并发、没有鉴权、没有上下文膨胀、没有成本。你在无菌环境里学到的东西，一碰真实场景就露馅。

**死法三：完美主义者**

第 3 天在纠结"到底该用 Chroma 还是 Milvus"，查了两天资料，然后放弃了。

**原因**：**在不知道全貌时做技术选型，必然纠结**。正确做法是先用最简方案跑通全链路，回头再替换——这也是本章路线图的排法。

### 43.1.2 这份路线图的三个设计原则

```
原则 1：先跑通全链路，再回头加深
        第 7 天你就有一个能对话的系统（很粗糙），之后 14 天逐层加固。
        理由：早期反馈 > 早期完美。

原则 2：每一层都先写"会坏的版本"
        先写会超时的工具，再写超时处理；先写会膨胀的上下文，再写裁剪。
        理由：没见过故障的人，写不出正确的防护。

原则 3：每天有可验证的产出
        "看完第 15 章"不是验收标准，"能断点看到第二次调用时 state 里有几条消息"才是。
```

### 43.1.3 开始之前：你的起点在哪

三条路径，先对号入座：

| 起点 | 特征 | 建议 |
|---|---|---|
| **A. 有 Python + Web 基础** | 写过 Flask/FastAPI，用过 SQL | 按 21 天走，每天 3-4 小时 |
| **B. 会 Python，没写过 Web** | 只写过脚本/数据分析 | 先花 3 天补第 07-11 章，再走 21 天 |
| **C. 只要面试能讲** | 时间紧，项目已存在 | 走"压缩版"：只看每章的面试问答 + 速记卡，7 天 |

**B 路径特别提醒**：不要跳过 FastAPI 和 SQLAlchemy。很多 Agent 岗位面试会问"你的 Agent 怎么和业务系统结合"——**答不出分层架构和事务控制，Agent 部分再强也像玩具。**

## 43.2 它到底是什么：21 天的三层结构

```
第 1 周（Day 1-7）  地基：让一个"假 AI"跑起来
  目标：Day 7 结束时，你能在浏览器里和一个后端对话（AI 部分先硬编码）
  为什么先做地基：Agent 的一切能力都要挂在真实的业务系统上

第 2 周（Day 8-14） Agent 内核：让它真的会思考、会调工具、会停下来
  目标：Day 14 结束时，Agent 能查数据库、能让人审批、重启后不失忆
  为什么第二周才做 Agent：没有业务系统，Agent 没有工具可调

第 3 周（Day 15-21） RAG + 生产：让它有知识、能流式、可评测、能部署
  目标：Day 21 结束时，全套系统跑在 Docker 里，评测跑得通
  为什么最后做 RAG：它是"增强"，不是"基础"，先有主干再加增强
```

**为什么是这个顺序？** 因为**依赖方向**：

```
RAG 依赖 → 检索管线 依赖 → 文档解析
                    依赖 → 向量库（可以是 SQLite 起家）

Agent 依赖 → 工具（= 业务系统的 Service 层）
        依赖 → 持久化（= 数据库）
        依赖 → 鉴权（= JWT）

业务系统 依赖 → FastAPI + SQLAlchemy
```

从底往上做，**每一步都能跑**。从顶往下做（先搞 RAG），你会发现没有地方挂。

## 43.3 第 1 周：地基（Day 1-7）

### Day 1 · 环境 + 第一个接口

**做什么**

- Python 3.12 + venv + 依赖安装
- FastAPI 起一个 `GET /` 返回 `{"message": "ok"}`
- 加上统一响应格式 `{code, message, data}`

**验收标准**

```
✅ 访问 http://127.0.0.1:8000/docs 能看到 Swagger
✅ 所有接口返回统一格式（不是裸 dict）
```

**对应章节**：第 01 章、第 07 章（前半）

**常见卡点**

- 装 `chromadb` / `sentence-transformers` 时网络超时 → 配 `HF_ENDPOINT=https://hf-mirror.com`（`config.py:74`）
- 想一次装完所有依赖 → **不要**。第一周只需要 `fastapi` `uvicorn` `sqlalchemy` `pydantic-settings`

### Day 2 · 分层架构 + 数据契约

**做什么**

- 建 `api/`、`services/`、`models/`、`schemas/`、`common/` 五层
- 用 Pydantic 写请求/响应模型
- 实现统一异常处理（4 个 handler）

**验收标准**

```
✅ 接口层不出现任何 SQL
✅ 参数错误返回 422 且格式统一
✅ 抛 BusinessException 时返回 200 + code（不是 500）
```

**对应章节**：第 07 章、第 08 章

**⚠️ 必踩的坑**：异常处理器的注册顺序。`Exception` 兜底必须**最后注册**，否则会吃掉前面的（第 07 章讲过）。

### Day 3 · 依赖注入 + JWT 鉴权

**做什么**

- `get_db` 生成器依赖
- `get_current_user` → `get_current_admin` 嵌套依赖
- JWT 签发与校验、bcrypt 密码哈希

**验收标准**

```
✅ 不带 token 访问受保护接口 → 401
✅ 普通用户访问管理员接口 → 403
✅ 手改 token payload 的一个字符 → 校验失败（篡改可检测）
```

**对应章节**：第 09 章、第 32 章

**⚠️ 必踩的坑**：`bcrypt` 4.x 对密码有 72 字节限制，超长密码直接报错。以及 `Depends` 的嵌套顺序。

### Day 4 · 数据建模 + 事务与并发

**做什么**

- SQLAlchemy 2.0 语法写 5 张表（user / lab / equipment / reservation / kb_document）
- 实现预约创建：时段重叠检测
- 用 `SELECT ... FOR UPDATE` 解决并发冲突

**验收标准**

```
✅ 同一时段重复预约 → 业务报错，不是脏数据
✅ 两个并发请求抢同一时段 → 只有一个成功（写个并发脚本验证）
✅ 事务失败时回滚干净
```

**对应章节**：第 10 章、第 11 章

**⚠️ 必踩的坑**：时段重叠的判断条件是 `new_start < exist_end AND new_end > exist_start`，不是 `>=`。边界相等（A 10-12，B 12-14）**不算冲突**。

**这一天的验收必须写并发测试脚本**——因为单线程测试永远发现不了并发 bug。

### Day 5 · 前端骨架 + 打通登录

**做什么**

- Vue3 + Vite + Element Plus
- axios 拦截器（自动带 token、统一错误提示）
- 登录页 + 路由守卫

**验收标准**

```
✅ 登录后 token 存起来，刷新页面不丢
✅ 未登录访问 /admin → 自动跳登录
✅ 普通用户看不到管理员菜单
```

**对应章节**：第 33 章、第 32 章（后半的角色守卫）

**⚠️ 必踩的坑**：前端路由守卫只是 UX，不是安全。**真正的鉴权必须在后端**——删掉前端守卫，用 curl 直接打管理员接口，必须依然 403。

### Day 6 · 业务页面 + 预约流程

**做什么**

- 实验室列表、预约列表、预约创建页
- 管理员审核页（通过/拒绝）
- 完整跑通"用户预约 → 管理员审核 → 状态变更"

**验收标准**

```
✅ 一条预约从 pending → approved 全流程走通
✅ 取消已通过的预约有业务校验
```

**对应章节**：第 11 章、第 33 章

### Day 7 · 第一个"AI 接口"（硬编码）+ 全链路打通

**做什么**

- 加 `/api/ai/chat` 接口，**先返回硬编码的假答案**
- 前端加一个对话页面，能发消息、能看到回复

**验收标准**

```
✅ 浏览器里发一句话，能看到（假的）回复
✅ 消息列表能正常渲染
```

**对应章节**：第 12 章（前半）

**为什么第 7 天要做假 AI？** 因为**全链路打通的心理价值极大**。你已经有一个"能对话的系统"了，剩下 14 天只是把假的换成真的。如果你第 7 天还在搭地基，很容易在第 10 天放弃。

**第一周小结**：到今天你有了一个**没有 AI 的完整业务系统**（约 1200 行后端 + 800 行前端）。这本身就够写一个普通 Web 项目的简历了。

## 43.4 第 2 周：Agent 内核（Day 8-14）

### Day 8 · Function Calling 最小闭环

**做什么**

- 直接调 OpenAI 兼容 API，传 `tools` 参数
- 拿到 `tool_calls` 后手动执行，把结果作为 `tool` 消息发回去
- **不要上 LangGraph**，先手写循环

**验收标准**

```
✅ 问"有哪些实验室" → 模型返回 tool_call → 你执行 → 模型给出自然语言答案
✅ 打印出完整的 messages 列表，看懂每一条的角色
```

**对应章节**：第 13 章

**⚠️ 必踩的坑**：`tool` 消息的 `tool_call_id` 必须和 `AIMessage.tool_calls` 里的 id **完全一致**，否则 API 报 400。这是第 14 章讲的"硬配对约束"。

**为什么先手写循环？** 因为 LangGraph 帮你封装了这一步。**没手写过的人，看 LangGraph 会觉得它是魔法；手写过的人，会觉得它是省事。**

### Day 9 · ReAct 循环 + 上 LangGraph

**做什么**

- 手写 2-3 轮的 ReAct 循环（Thought → Action → Observation）
- 然后改写成 `StateGraph`：agent 节点 → 条件边 → tool 节点 → 回到 agent

**验收标准**

```
✅ 断点/日志能看到 messages 随轮次增长
✅ 模型不调工具时，图能走到 END（不会死循环）
✅ 能画出你的图（print(graph.get_graph().draw_ascii())）
```

**对应章节**：第 14 章、第 15 章、第 16 章

**⚠️ 必踩的坑**：节点返回的是**增量**不是全量（第 15 章的 Reducer）。如果你在每个节点里 `return {"messages": all_messages}`，消息会翻倍——因为 `add_messages` 是追加语义。

### Day 10 · 条件路由 + 三条终止路径

**做什么**

- 实现 `_route_after_agent`：无工具调用 → END；写库工具 → 审批节点；只读工具 → 工具节点
- 工具节点的三分支降级（成功 / 失败重试 / 超限）

**验收标准**

```
✅ 问"有哪些实验室" → 直接执行，不弹审批
✅ 说"帮我预约" → 触发审批，返回 interrupt
✅ 工具抛异常 → 以 Observation 形式回填，模型换个思路（不是整个请求失败）
```

**对应章节**：第 16 章、第 20 章

**⚠️ 必踩的坑**：工具里**不要 raise**，要返回错误字符串。第 20 章讲过"错误即 Observation"——模型看到错误会自己修正，抛出去了就整条链断掉。

### Day 11 · Checkpointer 持久化 + thread_id

**做什么**

- 接入 `AsyncSqliteSaver`（先 SQLite，后面换 PG）
- 前后端打通 `thread_id`：新会话前端生成并带上，后续复用

**验收标准**

```
✅ 重启服务后，用同一个 thread_id 继续对话，AI 记得之前说的
✅ 换一个 thread_id → 全新的会话
✅ 打印出 checkpoint 的内容，看懂 messages 是怎么存的
```

**对应章节**：第 17 章

**⚠️ 必踩的坑**：checkpointer 必须是**全局单例**。每次请求 new 一个，等于没存。第 17 章讲过这个坑，而且它会表现为"重启后能恢复，但第二次请求又失忆"。

### Day 12 · Human-in-the-Loop

**做什么**

- `approval_node` 里 `interrupt()` 返回审批负载
- `/chat/resume` 接口用 `Command(resume=...)` 恢复
- 前端渲染审批卡片，点"同意"调用 resume

**验收标准**

```
✅ 触发写库工具 → 前端出现审批卡片
✅ 点同意 → 真正写入数据库
✅ 点拒绝 → 不写入，且 AI 给出"已取消"的回复
✅ 审批前的代码执行两次也不产生副作用（幂等性验证）
```

**对应章节**：第 18 章

**⚠️ 必踩的坑**：**`interrupt()` 前的代码会被重放**。第 18 章讲过——`interrupt()` 本质是抛异常 + 恢复时重放整个节点。所以 `interrupt()` 之前不能有写库、发消息这类副作用。**写个计数器验证它确实执行了两次。**

### Day 13 · 上下文工程

**做什么**

- 实现 `_estimate_tokens` 和 `_trim_messages`
- 保护 `tool_calls` ↔ `ToolMessage` 的配对（裁剪不能拆散它们）
- 配 `MAX_CONTEXT_TOKENS` 和 `TRIM_STRATEGY`

**验收标准**

```
✅ 连续对话 20 轮，token 数被控制在预算内（打印每轮的估算值）
✅ 裁剪后 messages 里不存在"有 tool_calls 但没有对应 ToolMessage"的情况
✅ 写一个单测专门验证配对完整性
```

**对应章节**：第 19 章

**⚠️ 必踩的坑**：裁剪时如果先删了 `AIMessage`（含 tool_calls）而留下 `ToolMessage`，**API 直接报 400**。第 19 章讲过"索引左移"的处理。

### Day 14 · 工具工程 + 单元测试

**做什么**

- 工具超时（`asyncio.wait_for`）+ 重试分类
- `asyncio.to_thread` 包裹同步阻塞调用
- 写 `test_agent_service.py`：用假 LLM 测试图和审批流程

**验收标准**

```
✅ 工具执行超过 30 秒 → 超时，错误回填给模型
✅ 单测覆盖：interrupt 审批流、路由分支、裁剪配对
✅ 所有测试通过（此时约 7-10 个测试）
```

**对应章节**：第 20 章、以及各章的测试部分

**⚠️ 必踩的坑**：`asyncio.get_running_loop()` 在同步上下文里调用会抛异常（第 20 章讲过这个真实 bug）。

**第二周小结**：到今天你的 Agent **会思考、会调工具、会让人审批、重启不失忆、长对话不崩**。这已经是市面上 80% Agent Demo 达不到的完成度了。

## 43.5 第 3 周：RAG + 生产（Day 15-21）

### Day 15 · 文档解析 + 切块

**做什么**

- 支持 `.md` / `.txt` / `.pdf` / `.docx`
- 递归字符切块 + 重叠

**验收标准**

```
✅ 上传一个 Markdown，能看到切出来的块（打印出来检查语义完整性）
✅ 块大小 200 / 重叠 40 生效
✅ 写一个单测：验证重叠区确实存在
```

**对应章节**：第 22 章、第 23 章

**⚠️ 必踩的坑**：切块大小不是越小越好。**打印出来看**——如果一个"开放时间 09:00-17:00"被切成两半，你的块就太小了。

### Day 16 · Embedding + 向量库（先用 Chroma）

**做什么**

- 本地 `bge-small-zh-v1.5`（512 维，`normalize_embeddings=True`）
- Chroma 存向量、检索
- **模型单例 + 启动预热**

**验收标准**

```
✅ 入库 10 个块，检索"开放时间"能召回正确的块
✅ 第二次启动检索速度正常（预热生效，不重新加载模型）
✅ 打印向量维度 = 512
```

**对应章节**：第 24 章、第 25 章

**⚠️ 必踩的坑**：模型不复用单例的话，每次检索 +3 秒。以及**换 embedding 模型必须重新向量化**（第 42 章延伸思考讲过）。

### Day 17 · 混合检索 + RRF + Rerank

**做什么**

- BM25（中文 unigram + bigram）+ 向量 + RRF 融合（k=60）
- 可选 rerank（cross-encoder）

**验收标准**

```
✅ 纯关键词问题（如"Wi-Fi"）向量检索召回差、BM25 召回好 → 混合后命中
✅ 打印两路召回的排名，看 RRF 怎么融合的
✅ rerank 失败 → 自动回退融合排序（拔网线验证）
```

**对应章节**：第 26 章、第 27 章

**⚠️ 必踩的坑**：中文 BM25 必须做分词，**按字切会退化**。项目用 unigram + bigram（第 26 章）。

### Day 18 · RAG 接入 Agent + 引用溯源

**做什么**

- 把检索做成 Agent 的一个工具（`search_knowledge_base`）
- Small-to-Big：存小块、送大模型时展开父上下文
- 答案里带 `[source#chunk_index]` 引用

**验收标准**

```
✅ 问知识库里的问题 → Agent 主动调用检索工具
✅ 答案里有引用标注，能点开对应文档
✅ 打印送进 LLM 的上下文，确认是"父上下文"不是"原始小块"
```

**对应章节**：第 21 章、第 29 章

**⚠️ 必踩的坑**：`_expand_context` 的双条件过滤（同文档 + 相邻索引）。写错了会把别的文档的块拼进来。

### Day 19 · SSE 流式 + 前端打字机

**做什么**

- `astream_events(version="v2")` 逐事件推送
- 前端 fetch + getReader（不用 EventSource，因为要带 header）
- marked → DOMPurify 渲染

**验收标准**

```
✅ 回答逐字出现（打字机效果）
✅ 工具调用过程可见（"正在查询实验室…"）
✅ nginx 反代下流式正常（proxy_buffering off）
✅ XSS 测试：<img src=x onerror=alert(1)> 被净化
```

**对应章节**：第 31 章

**⚠️ 必踩的坑**：marked 和 DOMPurify 的**顺序**。先 marked 再 DOMPurify，反过来会把 Markdown 语法破坏掉。

### Day 20 · 评测体系

```
✅ 拒答类用例的 answer_relevancy 被正确排除（METRIC_CATEGORIES 生效）
✅ 报告落盘，含 config（可复现）
✅ 人为把 FINAL_CONTEXT_K 改成 1，能看到指标下降（验证评测有区分度）
```

**对应章节**：第 37 章、第 38 章、第 39 章

**⚠️ 必踩的坑**：RAGAS 0.4.x 的 API 和教程不一样（第 39 章坑 6）。推理模型当裁判要调 `max_tokens`（坑 1）。

## 43.7 卡住了怎么办：四个自查清单

### 卡点 1：代码跑不起来

按顺序查：

```
1. 错误是什么？（完整读一遍 traceback，不是第一行）
2. 是配置问题还是代码问题？（环境变量有没有设：LLM_API_KEY / DATABASE_URL）
3. 最小复现：能不能用一个 10 行的脚本复现？
4. 看对应章节的"踩过的坑"小节
```

**90% 的"跑不起来"是配置问题**，尤其是 `LLM_API_KEY` 和 `HF_ENDPOINT`。

### 卡点 2：跑起来了但结果不对

```
1. 打印中间结果（不要只看最终输出）
2. Agent 类问题 → 打印 messages 列表
3. RAG 类问题 → 打印召回的块
4. 检索类问题 → 分别打印 BM25 排名和向量排名
```

**Agent/RAG 的调试核心是"看见中间过程"**。看不到中间过程的调试都靠猜。

### 卡点 3：不知道某个参数该设多少

**不要纠结，先用默认值跑通，再回来调**。默认值都在 `.env.example` 里，且都是项目实跑验证过的：

```bash
CHUNK_SIZE=200
CHUNK_OVERLAP=40
RETRIEVAL_TOP_K=5
FINAL_CONTEXT_K=3
CONTEXT_WINDOW=1
MAX_CONTEXT_TOKENS=4000
```

**这些不是最优值，是"能跑"的值。** 第 41 章延伸思考讲过怎么找拐点（跑一遍 1-10 画曲线）。

### 卡点 4：某个概念看不懂

判断标准：**这个概念会不会影响你写代码**？

- **会**（如 Reducer、interrupt、RRF）→ 回去读对应章节，跑最小骨架
- **不会**（如 HNSW 的数学原理、Transformer 的注意力公式）→ **先跳过**，标个 TODO

**第 04 章（大模型怎么思考）和第 25 章（HNSW 原理）都属于"知道了更好，不知道不影响写代码"的类型。** 别在这上面卡住。

## 43.8 面试问答

### Q1：这个项目是你自己做的吗？用了多久？

**答**：是，从搭 FastAPI 骨架到 RAG 评测体系跑通，主体代码花了 21 天，之后又迭代了大约两周做企业级改造（PG checkpointer、裁判模型分离、并发缺陷修复）。

如果问"21 天做这么多功能？"——如实说明是**全职投入**，而且是**分层的**：先做一个没有 AI 的完整业务系统（7 天），再把 AI 一层层加上去（14 天）。**不是 21 天从零写 4000 行，是 21 天每天 230 行且有明确的验收标准。**

### Q2：过程中最难的部分是什么？

**答**：三个。

**一是 Human-in-the-Loop**。`interrupt()` 的语义不是"暂停"，是"抛异常 + 保存状态 + **恢复时重放整个节点**"。我一开始在 interrupt 之前写了日志和计数，发现它们执行了两次才反应过来。后来把节点里 interrupt 之前的代码全部改成幂等的。

**二是并发缺陷**。时间段重叠的边界条件（`>=` 还是 `>`）和 `SELECT FOR UPDATE` 的位置，都是写了并发测试脚本才暴露的——单线程测试完全正常。

**三是评测的可信度**。一开始裁判模型和被测模型是同一个，同一段答案重复打分能在 0.5~1.0 之间抖动，这个噪声比我试图测量的优化差异大一个数量级。后来做了裁判分离，并且发现拒答类用例的 answer_relevancy 是机制性假低分，用指标分类解决了。

### Q3：如果重做一次，你会怎么改？

**答**：三件事会更早做。

**一是可观测性**。我最后才补，导致前面排查全靠 print。如果有 trace_id 和 token 指标，第 9 天发现"消息翻倍"会快得多。

**二是测试**。现在测试是后补的，覆盖率不够。如果从第 8 天开始每个节点配一个测试，第 13 天改裁剪逻辑时不会那么心虚。

**三是先定评测集再调参**。我一开始凭感觉调 `FINAL_CONTEXT_K`，后来才建评测集——等于前半个月的优化都没有基准。**应该 Day 8 就把 14 条评测集写好**，哪怕先不接 RAGAS，人工看也行。

### Q4：21 天路线图里，哪几天最重要？

**答**：Day 4（事务与并发）、Day 12（HITL）、Day 20（评测）。

Day 4 决定你的项目是不是"玩具"——能处理并发冲突的系统和不处理的，是两类东西。

Day 12 是 Agent 项目特有的难点，也是面试区分度最高的一块——大部分候选人没做过人工审批。

Day 20 决定你能不能证明自己的优化有效。**没有评测，你说的"我优化了检索"就只是说法。**

### Q5：做完这个项目能达到什么水平？

**答**：能完整讲清楚一个生产级 Agent 系统的每一层，包括它为什么这么设计、哪里会坏、坏了怎么修。

但也要清楚边界：**这是单体应用，没有做过真正的多租户、没有做过千级 QPS 的压测、Milvus 和 Redis 只是代码接入没有实跑、多 Agent 编排是设计没落地。**

**面试时把边界说清楚，比夸大更有说服力**——因为一追问就会露馅，而主动说明会显得你真的懂。

## 43.10 延伸思考

1. **21 天之后，下一步学什么？**
   提示：三个方向选一个深耕。① **深度**：把 Milvus 真正跑起来、做多租户隔离、做千级 QPS 压测——补工程深度；② **广度**：多 Agent 编排、Agent 自主学习、多模态——补技术广度；③ **业务**：找一个真实场景（客服、运维、数据分析）把这套架构套上去——补领域理解。**不要三个同时做**，面试时"一个方向深耕 + 两个方向了解"比"三个方向都略懂"更有说服力。

2. **怎么判断自己真的学会了？**
   提示：三个检验。① **能不能给别人讲明白**——找个不懂的人，用 5 分钟讲清楚 ReAct，他听懂了你就会了；② **能不能改对**——随机改一个需求（"预约要支持多人协作"），你能不能不改架构地实现；③ **能不能答出"为什么不用 X"**——每个技术选型都能说出被你否决的方案和否决理由。**第三点最难，也是面试官最在意的。**

3. **这个项目能不能直接写进简历？**
   提示：能，但要按第 45 章的方式写——**用动词 + 量化 + 技术点**的三段式，并且**如实标注边界**（Milvus/Redis 未实跑）。能直接抄的项目描述会撞车，而且一追问就露馅。**你亲手踩过的坑才是简历里最独特的部分。**

4. **如果是团队做，21 天怎么分工？**
   提示：按层分，不按功能分。一个人做业务系统 + 数据库（Week 1 全部 + 持续支持），一个人做 Agent 内核（Week 2），一个人做 RAG（Week 3 前半），最后两人合并做评测和部署。**关键是要有一个人从头到尾看全局**——否则第三周会出现"Agent 的工具定义和 RAG 的返回格式对不上"这类接口问题。
