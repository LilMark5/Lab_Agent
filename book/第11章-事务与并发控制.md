# 第 11 章 · 事务与并发控制

## 开篇：这是最能体现工程能力的一章

先说清楚为什么这章重要。

大部分 Agent 教程里的「预约」是这样的：

```python
def create_reservation(data):
    db.add(Reservation(**data))
    db.commit()
    return "预约成功"
```

**这段代码在生产上会超卖。**

场景：A301 实验室明天 14:00-17:00 只有一个位置。两个学生同时点「预约」。

```
时刻 T1: 用户A的请求 → 查询「14:00-17:00 有冲突吗？」→ 没有
时刻 T2: 用户B的请求 → 查询「14:00-17:00 有冲突吗？」→ 没有（A 还没提交！）
时刻 T3: 用户A → 插入预约 → 提交 ✅
时刻 T4: 用户B → 插入预约 → 提交 ✅
```

**结果：两个人预约了同一个时段的同一个实验室。**

这就是**并发超卖**。它是所有预约/库存/票务系统的头号问题。

**为什么面试官爱问这个？**

因为它能立刻区分：
- 只写过 CRUD 的人：答不出来，或者说「加个锁」（说不出加什么锁）
- 有工程能力的人：能说出行锁、区间重叠、隔离级别、以及不同数据库的差异

**这一章让你成为后者。**

## 一、事务的 ACID：先补基础

| 特性 | 含义 | 怎么保证 |
|---|---|---|
| **A**tomicity 原子性 | 要么全成功，要么全失败 | `rollback` |
| **C**onsistency 一致性 | 事务前后数据满足约束 | 约束、外键、业务规则 |
| **I**solation 隔离性 | 并发事务互不干扰 | 隔离级别、锁 |
| **D**urability 持久性 | 提交后不会丢 | WAL、redo log |

**并发问题主要出在 Isolation（隔离性）上。**

### 四种隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---|---|---|---|---|
| Read Uncommitted | ❌ 会 | ❌ 会 | ❌ 会 | 最高 |
| Read Committed（默认） | ✅ 不会 | ❌ 会 | ❌ 会 | 高 |
| Repeatable Read | ✅ | ✅ | ❌ 会 | 中 |
| Serializable | ✅ | ✅ | ✅ | 最低 |

**项目用的是默认的 Read Committed**（PostgreSQL / MySQL 默认）。

**这意味着什么？**

在同一个事务里，你读两次可能读到不同的结果（因为别的事务提交了）。对我们的场景：

```
事务A: SELECT 检查冲突 → 没有
       （事务B 提交了一条冲突记录）
事务A: INSERT 自己的记录
       → 超卖！
```

**Read Committed 无法防止这个问题。** 必须靠**锁**。

## 二、解法一：悲观锁 `SELECT FOR UPDATE`

### 2.1 原理

```sql
BEGIN;
SELECT * FROM labs WHERE id = 1 FOR UPDATE;   -- ← 锁住这一行
-- 其他事务也想 FOR UPDATE 这一行的话，会阻塞在这里等待
SELECT * FROM reservations WHERE ...;          -- 检查冲突
INSERT INTO reservations ...;
COMMIT;                                        -- ← 释放锁
```

`FOR UPDATE` 的含义：**「我要修改这行，别人不许动」**。

- 其他事务执行 `SELECT ... FOR UPDATE` 同一行 → **阻塞等待**
- 其他事务执行普通 `SELECT`（不带 FOR UPDATE）→ **不阻塞**（读不受影响）
- 其他事务执行 `UPDATE`/`DELETE` 这行 → **阻塞等待**

### 2.2 项目里的实现

**代码位置**：`backend/app/services/reservation_service.py`

```python
def create_reservation(db: Session, current_user: User, data: ReservationCreateRequest):
    # 1. 行锁：锁住实验室这一行
    lab = db.query(Lab).filter(Lab.id == data.lab_id).with_for_update().first()
    if not lab:
        raise BusinessException(message="实验室不存在")

    # 2. 时段冲突检测
    conflict = db.query(Reservation).filter(
        Reservation.lab_id == data.lab_id,
        Reservation.status.in_([0, 1]),           # 待审核 / 已通过 才算占用
        Reservation.start_time < data.end_time,   # ★ 区间重叠条件
        Reservation.end_time > data.start_time,   # ★ 区间重叠条件
    ).first()
    if conflict:
        raise BusinessException(message="该时段已被预约")

    # 3. 插入
    reservation = Reservation(...)
    db.add(reservation)

    # 4. 事务边界
    try:
        db.commit()
        db.refresh(reservation)
    except Exception:
        db.rollback()
        raise BusinessException(message="预约创建失败")

    return reservation
```

**关键点解读**：

| 行 | 作用 |
|---|---|
| `with_for_update()` | 行锁，序列化同一实验室的并发预约 |
| `status.in_([0, 1])` | 已拒绝(2)、已取消(3)的预约不占时段 |
| `start_time < end_time` | 区间重叠的两个条件 |
| `end_time > start_time` | （下一节详解） |
| `try/commit/except/rollback` | 事务边界 |

### 2.3 为什么锁「实验室」这一行，而不是锁「预约表」？

**这是设计的关键。**

| 方案 | 效果 | 问题 |
|---|---|---|
| 锁预约表 | 所有预约串行 | 不同实验室的预约也互相阻塞，性能极差 |
| 锁实验室行 | **同一实验室串行，不同实验室并行** | ✅ 正确 |

**粒度选择原则**：**锁的粒度要刚好覆盖竞争资源**。

预约 A301 和预约 B205 之间没有竞争，不该互相阻塞。锁 `labs` 表的第 1 行，只影响 A301 的预约。

> 💡 **面试话术**：「我锁的是实验室这一行，不是预约表。因为真正的竞争资源是『某个实验室的某个时段』，不同实验室之间没有竞争，不该互相阻塞。如果锁整张预约表，所有预约都串行了，并发能力归零。这是锁粒度选择的原则：刚好覆盖竞争资源，不要过度。」

### 2.4 区间重叠判断（重点，面试常考）

**为什么这两个条件能判断重叠？**

```python
Reservation.start_time < new_end_time   # 已有预约的开始 < 新预约的结束
Reservation.end_time > new_start_time   # 已有预约的结束 > 新预约的开始
```

**反着想更容易理解：什么时候「不重叠」？**

```
不重叠 = 已有预约完全在新预约之前  OR  已有预约完全在新预约之后
       = existing_end <= new_start  OR  existing_start >= new_end
```

取反：

```
重叠 = NOT (existing_end <= new_start OR existing_start >= new_end)
     = existing_end > new_start AND existing_start < new_end   （德摩根定律）
```

**验证所有情况**（假设已有 10:00-12:00）：

| 新预约 | `existing_start(10) < new_end` | `existing_end(12) > new_start` | 结果 | 期望 |
|---|---|---|---|---|
| 09:00-10:00 | 10 < 10:00? **False** | - | 不冲突 | ✅ 背靠背允许 |
| 09:00-10:30 | 10 < 10:30? True | 12 > 09:00? True | 冲突 | ✅ |
| 10:00-12:00 | 10 < 12:00? True | 12 > 10:00? True | 冲突 | ✅ |
| 11:00-13:00 | 10 < 13:00? True | 12 > 11:00? True | 冲突 | ✅ |
| 12:00-13:00 | 10 < 13:00? True | 12 > 12:00? **False** | 不冲突 | ✅ 背靠背允许 |
| 13:00-14:00 | 10 < 14:00? True | 12 > 13:00? **False** | 不冲突 | ✅ |
| 09:00-13:00 | 10 < 13:00? True | 12 > 09:00? True | 冲突 | ✅ 包含 |

**7 种情况全部正确。**

> ⚠️ **注意边界**：用的是严格 `<` 和 `>`，不是 `<=`。这保证了「背靠背」（10:00-12:00 和 12:00-14:00）**不算冲突**——因为前一个人 12:00 结束，后一个人 12:00 开始，理论上不冲突。
>
> 这是产品决策，不是技术问题。如果你们要求「两场之间留 15 分钟清洁时间」，就要改成 `existing_end > new_start - 15min`。

### 2.5 日期的处理

项目里 `date` 和 `time` 是分开的：

```python
Reservation.lab_id == data.lab_id,
Reservation.date == data.date,              # ★ 同一天
Reservation.start_time < data.end_time,
Reservation.end_time > data.start_time,
```

**必须加 `date` 条件**，否则「1月17日 14:00」的预约会和「1月18日 14:00」冲突。

## 三、解法二：乐观锁（不需要数据库锁）

悲观锁的问题是：**所有同实验室的预约都串行**，即使它们不冲突。

乐观锁的思路：**不加锁，靠版本号或唯一约束在提交时检测冲突**。

### 3.1 版本号方案

```python
class Lab(Base):
    version: Mapped[int] = mapped_column(default=0)   # 版本号

def create_reservation_optimistic(db, data, expected_version):
    result = db.execute(
        update(Lab)
        .where(Lab.id == data.lab_id, Lab.version == expected_version)  # ★
        .values(version=Lab.version + 1)
    )
    if result.rowcount == 0:
        raise BusinessException("数据已被修改，请重试")   # 版本不匹配
    # ... 检查冲突、插入
    db.commit()
```

**适合**：读多写少、冲突概率低的场景。

**不适合**：高频抢购（大量重试反而更慢）。

### 3.2 唯一约束方案（最优雅）

如果业务允许，可以让**数据库来保证不重叠**：

```sql
-- PostgreSQL 的排他约束（需要 btree_gist 扩展）
ALTER TABLE reservations
ADD CONSTRAINT no_overlap
EXCLUDE USING gist (
    lab_id WITH =,
    tsrange(start_at, end_at) WITH &&
) WHERE (status IN (0, 1));
```

这样数据库**物理上不可能**插入重叠的预约。应用层只需捕获唯一约束冲突异常。

**优点**：绝对可靠，不依赖应用逻辑正确。
**缺点**：需要数据库特性支持（PG 有，MySQL 没有）；约束变更成本高。

> 💡 **面试话术**：「防超卖有悲观锁和乐观锁两条路。我用的是悲观锁 `SELECT FOR UPDATE`，因为预约场景冲突概率不低（热门时段经常多人抢），悲观锁的『一次等待』比乐观锁的『失败重试』体验更好。
>
> 如果冲突概率很低，乐观锁更好——用版本号，提交时检查版本是否变化，变了就重试。
>
> 最彻底的是数据库约束：PostgreSQL 有 `EXCLUDE USING gist` 排他约束，能让重叠记录在物理上无法插入。这是最可靠的，因为不依赖应用逻辑正确。但 MySQL 不支持，而且约束变更成本高。我项目里没用这个，但知道它的存在。」

## 四、一个真实的坑：SQLite 的锁行为

**这是本项目实测发现的，也是简历上不能写「生产用 SQLite」的原因。**

### 4.1 现象

项目里的并发测试：

```python
def test_concurrent_reservation():
    """两个线程同时预约同一时段，应该只有一个成功。"""
    ...
```

**在 SQLite 上：测试通过，但通过得莫名其妙。**
**在 PostgreSQL 上：测试也通过，但通过的原因完全不同。**

### 4.2 原因

**SQLite 的写锁是「整库锁」**：

```
SQLite:  BEGIN IMMEDIATE → 锁住整个数据库文件
        所有其他写操作全部阻塞（不管是不是同一张表、同一行）

PostgreSQL: SELECT ... FOR UPDATE → 只锁住那一行
        其他行的操作不受影响
```

**所以 `with_for_update()` 在 SQLite 上退化成了「整库排他」**。

后果：

1. **并发测试「假通过」**：两个线程被 SQLite 串行化了，根本没真正并发，所以只有一个成功——但这不是你的代码起的作用，是 SQLite 的锁起的作用。
2. **性能假象**：本地测试很快，上生产（PG）后行为完全不同。
3. **掩盖 bug**：如果你的冲突检测逻辑有 bug，在 SQLite 上测不出来。

### 4.3 怎么验证这个差异

```python
# 在两个终端同时执行（SQLite）
import time, sqlite3
conn = sqlite3.connect("test.db")
conn.execute("BEGIN IMMEDIATE")
time.sleep(10)          # 持有锁 10 秒
conn.commit()

# 另一个终端
conn2 = sqlite3.connect("test.db")
conn2.execute("BEGIN IMMEDIATE")   # ← 阻塞 10 秒！
```

**结论**：

> ⚠️ **SQLite 只适合开发和单用户场景。生产必须换 PostgreSQL 或 MySQL。**
>
> 简历上可以说「开发用 SQLite 零配置，生产用 PostgreSQL」，但**不能说「生产用 SQLite」**。

### 4.4 项目里的双后端现状

```python
# config.py
DATABASE_URL: str = "sqlite:///./lab.db"
CHECKPOINT_DATABASE_URL: str = ""      # 空 = 用 SQLite
```

测试时可以切到 PostgreSQL：

```
DATABASE_URL=postgresql+psycopg2://user:pass@localhost/lab
```

> 💡 **面试话术**：「我项目里数据库支持 SQLite 和 PostgreSQL 双后端，开发用 SQLite 零配置，生产应该换 PG。
>
> 这里有个我实测发现的坑：**SQLite 的写锁是整库锁，`SELECT FOR UPDATE` 在它上面实际退化成锁整个数据库文件**。这导致并发测试会『假通过』——两个线程被 SQLite 串行化了，根本没真正并发，所以看起来只有一个成功，但这不是我的冲突检测逻辑起作用，是 SQLite 的锁起作用。
>
> 所以如果要验证并发逻辑，必须在 PostgreSQL 上测。这也是为什么生产一定要换 PG。」

## 五、事务边界：C1 缺陷的完整修复

### 5.1 原始代码

```python
def create_reservation(db, user, data):
    ...
    db.add(reservation)
    db.commit()              # ❌ 没有 rollback
    db.refresh(reservation)
    return reservation
```

### 5.2 问题

`commit()` 会真的执行 SQL。如果此时出错（约束冲突、连接断开、磁盘满），异常抛出，但**事务没有显式回滚**。

**后果有多严重？**

取决于连接池的行为：

1. **如果连接被归还池**：下一个请求拿到这个连接，事务可能还处于「未决」状态，后续操作的行为不可预测
2. **如果连接被丢弃**：数据库会在超时后回滚，但期间锁一直被持有，其他操作被阻塞

**即使 `get_db` 的 `finally: db.close()` 会隐式回滚**（SQLAlchemy 的 Session.close() 会 rollback 未完成的事务），但：

- 依赖隐式行为不如显式清晰
- 如果是长事务，close 可能来不及
- 代码审查时会质疑

### 5.3 修复后

```python
try:
    db.commit()
    db.refresh(reservation)
except Exception:
    db.rollback()                    # ✅ 显式回滚
    raise BusinessException(message="预约创建失败，请稍后重试")
```

**同时给 `get_db` 加了兜底**：

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    except Exception:
        db.rollback()                # ✅ 兜底回滚
    finally:
        db.close()
```

**两层保险**：

| 层 | 场景 |
|---|---|
| Service 层的 try/except | 业务逻辑自己捕获并处理 |
| `get_db` 的 except | 异常冒泡到依赖清理时兜底 |

> 💡 **面试话术**：「我项目里有四处 `commit` 没有 rollback 兜底，是代码审查时发现的。原本的写法是 `db.add(); db.commit()`，如果 commit 抛异常（约束冲突、连接断开），事务处于未决状态。
>
> 修复方式有两层：一是 service 层每个 commit 都包 try/except/rollback，失败时转成业务异常；二是给 `get_db` 的 except 分支也加了 rollback——因为如果异常从 service 冒泡到依赖清理那里，事务也应该回滚，这是最后一道保险。
>
> 虽然 SQLAlchemy 的 `Session.close()` 会隐式回滚，但依赖隐式行为不如显式清晰，而且代码审查时会被质疑。」

### 5.4 项目里修复的 4 处

`reservation_service.py` 里的：

1. `create_reservation` —— 创建预约
2. `audit_reservation` —— 审核（通过/拒绝）
3. `cancel_reservation` —— 取消
4. 其他写操作

## 六、并发测试怎么写

### 6.1 用线程模拟并发

```python
# tests/test_reservation.py（简化）
import threading
import time
from sqlalchemy.orm import sessionmaker

def test_concurrent_booking_no_oversell(engine):
    """两个线程同时预约同一时段，只能有一个成功。"""
    Session = sessionmaker(bind=engine)
    results = {}

    def worker(name: str, delay: float):
        db = Session()
        try:
            if delay:
                time.sleep(delay)
            try:
                r = reservation_service.create_reservation(
                    db, user, ReservationCreateRequest(
                        lab_id=1, date="2025-01-20",
                        start_time="14:00", end_time="17:00",
                    )
                )
                results[name] = ("ok", r.id)
            except BusinessException as e:
                results[name] = ("busy", e.message)
            finally:
                db.close()
        except Exception as e:
            results[name] = ("error", str(e))

    t1 = threading.Thread(target=worker, args=("A", 0))
    t2 = threading.Thread(target=worker, args=("B", 0.01))
    t1.start(); t2.start()
    t1.join(); t2.join()

    ok_count = sum(1 for v in results.values() if v[0] == "ok")
    assert ok_count == 1, f"应该只有 1 个成功，实际 {ok_count}：{results}"
```

**关键点**：

| 设计 | 为什么 |
|---|---|
| 每个线程独立的 Session | 模拟真实的并发请求（不同连接有不同事务） |
| `time.sleep(0.01)` 错开 | 确保两个线程都进入了临界区 |
| 断言「恰好 1 个成功」 | 不能断言「A 成功 B 失败」（顺序不确定） |
| `finally: db.close()` | 保证连接释放 |

### 6.2 断言要怎么写才稳定

```python
# ❌ 不稳定：依赖执行顺序
assert results["A"][0] == "ok"
assert results["B"][0] == "busy"

# ✅ 稳定：只断言业务结果
ok_count = sum(1 for v in results.values() if v[0] == "ok")
assert ok_count == 1
```

> ⚠️ **坑**：并发测试容易「flaky」（时好时坏）。常见的 flaky 来源：
> - 断言了执行顺序
> - sleep 时间不够，两个线程没真正重叠
> - 用了 SQLite（被串行化，测试假通过）
> - 没清理测试数据（上一个测试的残留影响下一个）

### 6.3 项目里的测试实际结果

```
tests/test_reservation.py::test_concurrent_booking_no_oversell PASSED
```

**但这个 PASSED 要分情况看**：

- 在 **SQLite** 上：被整库锁串行化，**没真正测到并发**
- 在 **PostgreSQL** 上：真正的并发测试，行锁起作用 ✅

> 💡 **面试话术**：「我有并发测试：两个线程同时预约同一时段，断言恰好一个成功。断言方式我特意写成统计成功数量，而不是断言『A 成功 B 失败』——因为并发下执行顺序不确定，断言顺序会导致测试 flaky。
>
> 但说实话，这个测试在 SQLite 上是『假通过』的——SQLite 的整库锁把两个线程串行化了，根本没真正并发。只有在 PostgreSQL 上跑才是真的验证了我的冲突检测逻辑。这也是我坚持生产要换 PG 的原因。」

## 七、死锁：并发的副作用

### 7.1 死锁怎么产生

```
事务A: 锁住 lab 1，想锁 lab 2
事务B: 锁住 lab 2，想锁 lab 1
→ 互相等待，死锁
```

**预约场景一般不会死锁**（每次只锁一个实验室），但**批量预约**（一次预约多个实验室）就会。

### 7.2 三种应对策略

| 策略 | 做法 | 代价 |
|---|---|---|
| **固定顺序加锁** | 按 lab_id 升序加锁 | 无（推荐） |
| **超时** | `with_for_update(nowait=False, timeout=5)` | 要处理超时 |
| **重试** | 捕获死锁异常，重试 | 复杂度 |

**最推荐的是固定顺序**：

```python
def create_batch_reservation(db, user, lab_ids, ...):
    for lab_id in sorted(lab_ids):     # ★ 固定顺序，避免死锁
        lab = db.query(Lab).filter(Lab.id == lab_id).with_for_update().first()
        ...
```

### 7.3 PostgreSQL 的死锁检测

PostgreSQL 有死锁检测（默认 1 秒后检测），检测到会杀掉一个事务并报错：

```
psycopg2.errors.DeadlockDetected: deadlock detected
```

应用层应该捕获并重试。

def create_naive(db, lab_id, user_name, date, start, end):
    """❌ 错误写法：先查后插，没有锁。"""
    # 检查冲突
    cnt = db.execute(
        select(func.count()).select_from(Reservation).where(
            Reservation.lab_id == lab_id,
            Reservation.date == date,
            Reservation.status.in_([0, 1]),
            Reservation.start_time < end,
            Reservation.end_time > start,
        )
    ).scalar()

    if cnt > 0:
        return "busy"

    # ⚠️ 关键：这里 sleep 一下，模拟"查询之后、插入之前"的时间窗口
    time.sleep(0.15)

    db.add(Reservation(lab_id=lab_id, user_name=user_name,
                       date=date, start_time=start, end_time=end, status=0))
    db.commit()
    return "ok"

def create_with_lock(db, lab_id, user_name, date, start, end):
    """✅ 正确写法：行锁 + 区间重叠 + 事务边界。"""
    try:
        # 1. 行锁：同一实验室串行化
        lab = db.execute(
            select(Lab).where(Lab.id == lab_id).with_for_update()
        ).scalar_one_or_none()
        if not lab:
            return "no_lab"

        # 2. 冲突检测（区间重叠）
        cnt = db.execute(
            select(func.count()).select_from(Reservation).where(
                Reservation.lab_id == lab_id,
                Reservation.date == date,
                Reservation.status.in_([0, 1]),
                Reservation.start_time < end,
                Reservation.end_time > start,
            )
        ).scalar()
        if cnt > 0:
            db.rollback()
            return "busy"

        # 同样 sleep，验证锁是否真的挡住了并发
        time.sleep(0.15)

        # 3. 插入
        db.add(Reservation(lab_id=lab_id, user_name=user_name,
                           date=date, start_time=start, end_time=end, status=0))
        db.commit()          # ← 释放锁
        return "ok"
    except Exception as e:
        db.rollback()        # ✅ 事务边界
        return f"error: {type(e).__name__}"

# ══════════════════════════════════════════════════════════
# 并发测试
# ══════════════════════════════════════════════════════════

def run_concurrent(engine, create_fn, label):
    """两个线程同时预约同一时段。"""
    # 重置数据
    Base.metadata.drop_all(engine)
    Base.metadata.create_all(engine)
    Session = sessionmaker(bind=engine)

    with Session() as db:
        db.add(Lab(id=1, name="A301"))
        db.commit()

    results = {}
    barrier = threading.Barrier(2)     # 保证两个线程同时开始

    def worker(name):
        db = Session()
        barrier.wait()                 # 等齐再一起跑
        try:
            results[name] = create_fn(db, 1, name, "2025-01-20", "14:00", "17:00")
        finally:
            db.close()

    t1 = threading.Thread(target=worker, args=("用户A",))
    t2 = threading.Thread(target=worker, args=("用户B",))
    t1.start(); t2.start()
    t1.join(); t2.join()

    ok_count = sum(1 for v in results.values() if v == "ok")
    total = 0
    with Session() as db:
        total = db.execute(select(func.count()).select_from(Reservation)).scalar()

    print(f"  [{label}]")
    print(f"    线程结果: {results}")
    print(f"    成功数:   {ok_count}")
    print(f"    数据库记录数: {total}")
    if total > 1:
        print(f"    ❌ 超卖了！同一时段有 {total} 条预约")
    else:
        print(f"    ✅ 没有超卖")
    print()
    return total

## 本章速记卡

1. **并发超卖的根源**：Read Committed 隔离级别下，「先查后插」两步之间有窗口。
2. **`SELECT FOR UPDATE` 行锁**：锁住竞争资源行，同一资源串行、不同资源并行。
3. **锁粒度原则**：刚好覆盖竞争资源。锁实验室行，不锁预约表。
4. **区间重叠公式**：`existing.start < new.end AND existing.end > new.start`（严格不等号 → 背靠背允许）。
5. **SQLite 写锁是整库锁**，`FOR UPDATE` 退化 → 并发测试假通过 → 生产必须用 PG。
6. **事务边界**：`try: commit() except: rollback()`，两层保险（service + get_db）。
7. **乐观锁适合低冲突**，悲观锁适合高冲突。PG 的 `EXCLUDE` 约束最彻底。
8. **死锁三策略**：固定顺序加锁（推荐）、超时、重试。
9. **并发测试断言「恰好 1 个成功」**，不要断言顺序（会 flaky）。
10. **项目修复**：4 处 commit 补 rollback + `get_db` 加兜底（C1 缺陷）。

## 面试问答：并发与事务

### Q1：「两个人同时预约同一个时段，你怎么保证不超卖？」

**满分答法**（这是高频题，要答得完整）：

> 这个问题的根源是：默认的 Read Committed 隔离级别下，「先查有没有冲突，再插入」这两步之间存在时间窗口。两个事务可能都查到「没冲突」，然后都插入。
>
> 我的解法是**悲观锁 + 区间重叠检测**：
>
> 第一步，用 `SELECT ... FOR UPDATE` 锁住实验室这一行（SQLAlchemy 里是 `with_for_update()`）。这样同一实验室的预约请求会被串行化，不同实验室不受影响。
>
> 第二步，在同一个事务里做区间重叠检测：`existing.start_time < new.end_time AND existing.end_time > new.start_time`。用的是严格不等号，所以「背靠背」（10:00-12:00 和 12:00-14:00）不算冲突。同时过滤 status，已拒绝和已取消的预约不占时段。还要限定同一天。
>
> 第三步，插入并 commit，释放锁。
>
> 锁粒度我选的是**锁实验室行而不是锁预约表**——因为真正的竞争资源是「某个实验室的某个时段」，不同实验室之间不该互相阻塞。锁整张表会让所有预约串行，并发能力归零。

**追问 1**：「为什么不用乐观锁？」
> 预约场景冲突概率不低（热门时段经常多人抢），悲观锁的「等待一下」比乐观锁的「失败重试」体验更好。冲突率低的场景（比如编辑个人资料）用乐观锁更合适。

**追问 2**：「那你的锁会不会导致性能问题？」
> 会。同一实验室的预约是串行的，如果某实验室特别热门，会形成排队。缓解手段有：缩短持锁时间（把校验移到锁外、减少锁内的 DB 查询）、给用户明确的等待反馈。真到了瓶颈，可以把热门资源拆分成更细的粒度（比如按小时分段而不是按实验室）。

---

### Q2：「区间重叠怎么判断？」

**满分答法**：

> 两个条件：`existing.start < new.end` 且 `existing.end > new.start`。
>
> 反着推更容易理解：不重叠的情况是「已有预约完全在新预约之前」或「已有预约完全在新预约之后」，也就是 `existing.end <= new.start OR existing.start >= new.end`。取反（德摩根定律）就得到重叠条件。
>
> 用严格不等号 `>` 和 `<`，保证背靠背不算冲突。如果业务要求两场之间留缓冲时间，就把条件改成 `existing.end > new.start - 缓冲时间`。
>
> 另外一定要加日期条件 `date = ?`，否则不同天的同一时段会误判为冲突。还要过滤状态——已取消、已拒绝的预约不占时段。

---

### Q3：「SQLite 和 PostgreSQL 在并发上有什么区别？」

**满分答法**（这是加分题，很多人不知道）：

> 最大的区别是**锁粒度**。SQLite 的写锁是**整库锁**——一个连接写的时候，整个数据库文件都被锁住，所有其他写操作全部阻塞。PostgreSQL 是**行级锁**，不同行的操作互不影响。
>
> 这导致 `SELECT FOR UPDATE` 在 SQLite 上**退化成锁整个数据库**。
>
> 我实测发现的一个坑：**并发测试在 SQLite 上会「假通过」**。两个线程同时预约，SQLite 把它们串行化了，根本没真正并发，所以看起来只有一个成功——但这不是我的冲突检测逻辑起作用，是 SQLite 的锁起作用。这样会掩盖真正的 bug。
>
> 所以我的结论是：开发可以用 SQLite（零配置方便），但生产必须换 PostgreSQL，而且**验证并发逻辑必须在 PG 上测**。

---

### Q4：「事务边界怎么把握？」

**满分答法**：

> 我的原则是：**commit 必须包 try/except/rollback**。
>
> 我项目里原本有四处 `db.add(); db.commit()` 没有 rollback，是代码审查时发现的（后来全部修了）。问题是如果 commit 抛异常（约束冲突、连接断开），事务处于未决状态。虽然 SQLAlchemy 的 `Session.close()` 会隐式回滚，但依赖隐式行为不清晰，而且如果是长事务，close 可能来不及。
>
> 修复做了两层：一是 service 层每个 commit 包 try/except/rollback，失败时转成业务异常；二是给 `get_db` 的 except 分支也加了 rollback——因为异常可能从 service 冒泡到依赖清理那里，这是最后一道保险。
>
> 另外一个概念要分清：**flush 和 commit**。flush 会发 SQL 但不提交事务，用它可以在同一个事务里拿到自增 ID 去做后续操作，最后一起 commit 保证原子性。我在需要关联插入时用这个。

---

### Q5：「死锁怎么避免？」

**满分答法**：

> 死锁发生在两个事务互相等待对方持有的锁。比如批量预约：事务A 锁了 lab1 想锁 lab2，事务B 锁了 lab2 想锁 lab1。
>
> 最有效的解法是**固定顺序加锁**——所有事务都按 lab_id 升序加锁，就不可能形成环。这是零成本的，我推荐这个。
>
> 另外两个策略：一是加超时（`with_for_update(timeout=5)`），超时就放弃并重试；二是捕获死锁异常后重试。PostgreSQL 有死锁检测（默认 1 秒），检测到会杀掉一个事务报 `DeadlockDetected`，应用层捕获后重试。
>
> 我的预约场景是单资源预约，不会死锁。但如果将来支持「一次预约多个实验室」，就必须按固定顺序加锁。

---

### Q6：「你的并发测试怎么写的？会不会 flaky？」

**满分答法**（这题考测试功底）：

> 我用两个线程同时预约同一时段，每个线程用独立的 Session（模拟真实的并发请求，不同连接有不同事务），用 `threading.Barrier` 保证两个线程同时开始。
>
> 断言方式我特意写成**统计成功数量**（`assert ok_count == 1`），而不是断言「A 成功 B 失败」——因为并发下执行顺序不确定，断言顺序会导致测试 flaky。
>
> flaky 的常见来源我都会避开：不断言执行顺序、用 Barrier 保证真正并发、每个测试前重置数据。
>
> 但说实话，这个测试在 SQLite 上是「假通过」的——被整库锁串行化了。我是在 PostgreSQL 上跑才能真验证逻辑。另外我会在测试里 sleep 一小段，确保两个线程都进入了临界区（查询之后、插入之前）。

## 常见坑

### 坑 1：先查后插，不加锁

必然超卖。这是最常见的错误。

### 坑 2：锁整张表而不是行

并发能力归零。

### 坑 3：在 SQLite 上验证并发逻辑

假通过，掩盖 bug。

### 坑 4：commit 没有 rollback

事务未决状态。

### 坑 5：区间重叠用了 `<=`

背靠背被误判为冲突。

### 坑 6：忘了过滤 status 或 date

已取消的预约仍占时段；不同天同时段误判。

### 坑 7：并发测试断言执行顺序

flaky test。

### 坑 8：持锁时间过长

在锁内做了不必要的耗时操作（网络调用、大量计算），导致排队严重。

### 坑 9：批量操作没按顺序加锁

死锁。
