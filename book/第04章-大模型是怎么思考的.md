# 第 04 章 · 大模型是怎么"思考"的

## 开篇：一个必须破除的误解

很多人对大模型有一个模糊的认知：「它像一个有知识的人，我问它问题，它想一下然后回答」。

这个认知会让你在 Agent 开发中反复踩坑，因为它暗示了三件**错误的事**：

| 误解 | 真相 |
|---|---|
| 模型「知道」事实 | 模型只是在预测「什么样的文字序列最像训练数据里的答案」 |
| 模型会「思考」 | 模型是逐 token 生成的，没有独立的思考阶段（除非是专门的推理模型） |
| 模型能「决定」 | 模型输出的是概率最高的 token 序列，不是理性决策 |

**正确的心智模型**：

> 大模型是一个**超强的模式匹配器**。给它一段文字（上下文），它输出「最可能接在这段文字后面的内容」。

这个认知转变是 Agent 开发的分水岭。理解它，你就能预判模型什么时候会出错、为什么 prompt 要那么写、为什么工具描述这么重要。

## 一、第一层：Token —— 模型看到的不是字

### 1.1 分词（Tokenization）

模型不能直接处理字符，它被训练时看到的是**数字序列**。把文字转成数字的过程叫分词。

```python
"我喜欢实验室" → [1546, 9821, 33081, 18923]  # 具体数值取决于词表
```

**分词的关键特性**：

| 特性 | 说明 | 对开发的影响 |
|---|---|---|
| 不是一字一 token | 常见词整体是一个 token | 中文通常 1 字 ≈ 1-2 token，英文 1 词 ≈ 1-3 token |
| 中英文差异大 | 中文 token 效率通常低 | 同样的内容中文更贵、更占上下文 |
| 数字常被拆开 | "2024" 可能是 ["20", "24"] | 模型算术差的部分原因 |
| 空格也算 | 英文的空格并入 token | 英文 prompt 的空格不是免费的 |

**一个真实的例子**：

```
"实验室预约" 可能被切成：["实验", "室", "预约"]  → 3 tokens
"laboratory reservation" 可能被切成：["lab", "oratory", " reservation"] → 3 tokens
```

**验证方法**（OpenAI 风格）：

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
print(enc.encode("帮我预约明天下午2点的A301实验室"))
# 输出：[...] 长度约 15
print(len(enc.encode("Hello, how are you?")))   # 5
```

> ⚠️ **项目里的真实做法**：`agent_service.py` 的 `_estimate_tokens` 用的是「字符数 / 4」的粗略估算，没有引入 tiktoken。为什么？因为项目用的是 DeepSeek，tokenizer 和 OpenAI 不完全一样，而且引入 tiktoken 要下载词表文件（国内可能失败）。字符/4 对中文是**保守偏高**的估计——宁可多剪一点，也不要超预算。（第 19 章详解）

### 1.2 为什么 token 数量这么重要

三个原因，每一个都直接影响你的系统：

**① 成本** —— API 按 token 计费，输入和输出都算。

**② 上下文窗口** —— 模型一次能「看到」的 token 上限（8k / 32k / 128k...）。超了直接报错。

**③ 延迟** —— 生成速度大致是 20-80 token/秒。输出 500 token 意味着 10-25 秒。

> 💡 **面试话术**：「我做上下文管理的时候，第一个要解决的问题是『怎么算 token 数』。理想是用官方 tokenizer，但我们用的是 DeepSeek，tokenizer 和 OpenAI 不完全一致，而且 tiktoken 要下载词表。所以我用了字符数除以 4 的近似——对中文来说这个估算是偏高的，也就是会多剪一点。我的判断是：裁剪宁可激进一点也不要超预算，因为超了是整个请求失败，多剪一点只是丢失一些早期历史。这是一个明确的取舍。」

## 二、第二层：模型是怎么生成下一个 token 的

### 2.1 本质：条件概率

模型做的事情，形式化地说：

```
P(下一个 token | 前面所有的 token)
```

它给词表里的每个 token 算一个概率，然后按策略选一个。

```
输入："今天天气很"
模型输出的概率分布：
  "好"    0.35
  "热"    0.22
  "不错"  0.18
  "冷"    0.12
  ...     ...
```

**这就是为什么同一个问题问两次可能得到不同答案** —— 因为选择是**采样**的，不是确定性的。

### 2.2 采样参数（面试必考）

#### temperature（温度）

控制概率分布的「平滑程度」。

```python
# 原理（简化）
logits = model_output / temperature
probs = softmax(logits)
```

| temperature | 效果 | 什么时候用 |
|---|---|---|
| 0 | 完全确定，总选最高概率 | **Agent 场景**（要确定性） |
| 0.3-0.7 | 轻微随机，自然但不胡说 | 一般对话 |
| 1.0+ | 高随机，创意但容易离谱 | 写作、头脑风暴 |

**项目里的选择**：`agent_service.py:259` 用的是 `temperature=0`。

**为什么 Agent 必须低温？**

因为 Agent 要做**工具调用**。温度高的话，模型可能：
- 这次调 `search_labs`，下次同样的问题调 `list_labs`
- 参数从 `{"lab_id": 1}` 变成 `{"labId": 1}`（编造字段名）
- 单元测试没法写（输出不确定）

> 💡 **面试话术**：「Agent 场景我固定用 temperature=0。因为工具调用的可靠性依赖于输出的确定性——温度一高，同样的问题模型可能调不同的工具、生成不同格式的参数，测试和调试都没法做。代价是回答会略显死板，但对于『查信息 + 执行操作』这类任务，可靠性远比文采重要。」

#### top_p（核采样）

不是按固定概率阈值，而是「从概率最高的 token 开始累加，直到累计概率超过 p，只在这部分里采样」。

```
top_p=0.9 → 只考虑累计概率前 90% 的 token
```

**和 temperature 的关系**：两者都在控制随机性，**通常只调一个**。OpenAI 官方建议：调 temperature **或** top_p，不要同时调。

#### 其他参数

| 参数 | 作用 | 项目里 |
|---|---|---|
| `max_tokens` | 限制输出长度 | 评测时设过（曾踩坑，见下） |
| `stop` | 遇到特定字符串停止 | 少用 |
| `presence_penalty` | 惩罚已出现过的 token，鼓励新话题 | 少用 |
| `frequency_penalty` | 按出现频率惩罚，减少重复 | 少用 |

> ⚠️ **真实踩坑**：项目在接 RAGAS 评测时，一开始设了 `max_tokens=1024`，结果 DeepSeek 的**思考 token**（reasoning）把预算吃光了，实际答案被截断，导致 `answer_relevancy` 分数虚低。后来把 `max_tokens` 提到很大才解决。
>
> 这个坑的教训是：**推理模型（如 DeepSeek-R1、o1）的输出 token 包含「思考过程」**，你看到的答案只是一部分。设 max_tokens 时要考虑这点。（第 38 章详解）

### 2.3 生成是一个一个 token 来的

这是一个关键的工程认知：

```
用户输入："帮我预约实验室"
模型生成：
  t1: "好"        → 推送给前端
  t2: "的"        → 推送给前端
  t3: "，"        → 推送给前端
  t4: "我"        → 推送给前端
  ...
```

**所以流式输出（SSE）在技术上完全可行**——模型本来就是逐个生成的，服务端拿到一个就推一个。（第 31 章）

**也解释了为什么长回答慢**：500 个 token × 50ms = 25 秒。

## 三、第三层：注意力机制（Attention）—— 工程直觉版

这一节不讲数学公式，讲**它解决了什么问题、对开发意味着什么**。

### 3.1 问题：怎么让每个词「知道」上下文

早期模型（RNN）的问题是：处理到句子末尾时，开头的词已经被「遗忘」了。

```
"我在清华大学计算机系读博士，研究方向是机器学习，___ 很有意思"
```

要填这个空，模型需要知道前面的「机器学习」。但 RNN 的长距离依赖会衰减。

### 3.2 Attention 的解法

**核心思想**：处理每个位置时，让模型「回头看」所有其他位置，并**动态决定看哪里、看多重**。

```
生成 "它" 这个词时，模型的注意力分布：
  "实验室"   0.45   ← 高注意力
  "预约"     0.20
  "明天"     0.15
  "我"       0.05
  ...        ...
```

### 3.3 对 Agent 开发的三个直接影响

**影响 1：位置越靠后，影响越大（大致上）**

虽然 attention 理论上能看到全部上下文，但实测中：

- **开头**的信息（system prompt）影响强
- **结尾**（最近的对话、刚检索回来的文档）影响强
- **中间**的信息容易被忽略 —— 这就是著名的 **"Lost in the Middle"** 现象

> 💡 **这个发现直接指导了 RAG 的设计**：检索回来的 3 段文档，最重要的应该放**最前面或最后面**，不要放中间。而且这也解释了为什么要 rerank —— 把最相关的排到最前。

**影响 2：上下文长度是硬约束**

Attention 的计算量是 **O(n²)**（n 是 token 数）。上下文从 4k 到 128k，计算量不是 32 倍，是 1024 倍。

这就是为什么长上下文模型更贵、更慢，也是为什么要做上下文裁剪。（第 19 章）

**影响 3：Prompt 的顺序真的有影响**

因为注意力是位置相关的，"把指令放在开头" 和 "放在结尾" 效果不同。经验规则：

```
[System Prompt]  ← 角色、规则
[检索到的文档]    ← 知识
[历史对话]        ← 上下文
[当前问题]        ← 最重要的，放最后
```

> ⚠️ **项目里的实际顺序**：`agent_service.py:269` 是 `[SystemMessage(SYSTEM_PROMPT), *history]` —— system 在最前，历史（含当前问题）在后。这是标准做法。

## 四、第四层：模型怎么「决定」调用工具

这是 Agent 开发的核心问题。很多人以为模型有某种「决策模块」，其实没有。

### 4.1 真相：工具也是「生成出来的文本」

当你在请求里带上 `tools` 参数时，API 服务端会做一件事：**把工具定义拼进 prompt**（用一种模型训练时见过的特殊格式），然后模型像生成普通文本一样，生成「调用工具的结构化文本」。

**你发的请求**（简化）：

```json
{
  "messages": [
    {"role": "system", "content": "你是实验室助手..."},
    {"role": "user", "content": "有哪些细胞相关的实验室？"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "search_labs",
        "description": "根据关键词搜索实验室。当用户想找某个实验室时调用。",
        "parameters": {
          "type": "object",
          "properties": {
            "keyword": {"type": "string", "description": "搜索关键词"}
          },
          "required": ["keyword"]
        }
      }
    }
  ]
}
```

**服务端实际给模型的东西**（概念上）：

```
你是实验室助手...

# 可用工具
- search_labs(keyword: string): 根据关键词搜索实验室。当用户想找某个实验室时调用。

# 用户问题
有哪些细胞相关的实验室？
```

**模型生成的「回答」**：

```
<tool_call>search_labs(keyword="细胞")</tool_call>
```

**API 服务端解析这段文本，返回成结构化的 `tool_calls`**：

```json
{
  "content": "",
  "tool_calls": [
    {"id": "call_001", "name": "search_labs", "args": {"keyword": "细胞"}}
  ]
}
```

### 4.2 这个真相带来的五个工程结论

**结论 1：工具描述（description/docstring）是「给模型看的 prompt」**

它决定了模型什么时候调用。**写得含糊 = 模型乱调用**。

```python
@tool
def search_labs(keyword: str) -> str:
    """搜索实验室。"""          # ❌ 太含糊，模型不知道什么时候用

@tool
def search_labs(keyword: str) -> str:
    """根据关键词搜索实验室。当用户想查找实验室、询问有哪些实验室、
    或需要知道某个实验室的 ID 时调用。只做查询，不做预约。"""   # ✅
```

**结论 2：参数描述同样重要**

```python
def create_reservation(lab_id: int, start_time: str, end_time: str) -> str:
    """创建预约..."""
    # 参数说明写在哪？
```

LangChain 的 `@tool` 支持用 Pydantic 模型声明参数，每个字段可以有 `description`：

```python
class CreateReservationInput(BaseModel):
    lab_id: int = Field(description="实验室 ID，必须是 search_labs 返回的 id 字段")
    start_time: str = Field(description="开始时间，格式 YYYY-MM-DD HH:MM:SS")
    end_time: str = Field(description="结束时间，格式 YYYY-MM-DD HH:MM:SS")

@tool(args_schema=CreateReservationInput)
def create_reservation(lab_id: int, start_time: str, end_time: str) -> str:
    """创建实验室预约..."""
```

这样模型看到的 schema 里会有格式说明，**大幅减少编造格式**。

**结论 3：模型可能不调工具（这是最大的坑）**

因为「调工具」只是模型生成的文本，它完全可以生成普通回答：

```
用户："有哪些实验室？"
模型："我们有 A301 细胞实验室、B205 材料实验室..."   ← 编的！没调工具
```

**为什么会这样？**
- 工具描述不够有吸引力
- 模型「觉得」自己知道答案（幻觉）
- System Prompt 没强调「必须使用工具获取真实数据」

**缓解手段**（第 34 章详解）：
- System Prompt 里明确「查询类问题必须调用工具，不要凭记忆回答」
- 工具描述写清楚「这是唯一的获取途径」
- 用 `tool_choice="required"` 强制（但会失去灵活性）

**结论 4：模型可能编造工具名或参数**

```
模型生成：<tool_call>search_laboratory(keyword="细胞")</tool_call>
          ↑ 编造的工具名
```

**必须处理**：`tool_node` 里的 `elif tool is None: content = f"未找到工具：{name}"`。

**结论 5：工具数量有上限，太多会退化**

经验值：**超过 10-20 个工具后，模型的选择准确率明显下降**。

原因：工具描述占用上下文，而且选项太多时模型更容易选错。

**解法**：
- 只给当前场景相关的工具（动态工具集）
- 工具分组，用路由 Agent 先选组
- 用 MCP 按需加载

## 五、第五层：推理模型（Reasoning Model）的新变量

2024 年后出现了一类新模型：DeepSeek-R1、OpenAI o1/o3、Qwen3-thinking。它们的特点是**先「思考」再回答**。

### 5.1 和普通模型的区别

```
普通模型：
  输入 → 直接生成答案

推理模型：
  输入 → 生成一大段"思考过程"（reasoning_content）→ 生成答案（content）
```

**思考过程是什么样的**（简化）：

```
用户：一个实验室有 3 台设备，每台每天可用 8 小时，一周 5 天。总共可用多少小时？

思考：
  让我算一下。3 台设备 × 8 小时 = 24 小时/天
  24 × 5 = 120 小时/周
  等等，题目问的是"总共可用多少小时"，应该是一周的总量
  所以是 120 小时

答案：120 小时
```

### 5.2 对 Agent 开发的四个影响

**影响 1：延迟大幅增加**

思考过程可能几千 token，生成要几十秒。**流式输出时要想清楚：推不推思考过程给用户看？**

- 推：用户看到模型在「思考」，体验更真实（很多产品这么做）
- 不推：用户等更久但只看答案

**影响 2：token 成本翻倍甚至更多**

思考 token 通常也计费。同样的问答，推理模型可能花 3-10 倍的 token。

**影响 3：`max_tokens` 要考虑思考部分**

> ⚠️ **真实踩坑**（前面提过）：RAGAS 评测时设 `max_tokens=1024`，DeepSeek 的思考过程吃光了预算，答案被截断。
>
> **教训**：用推理模型时，`max_tokens` 要给足，或者用模型提供的专门参数。

**影响 4：思考过程可能"过度思考"**

简单问题也推理 20 步。有些模型提供「思考强度」参数（如 Qwen3 的 `enable_thinking`），可以按需关闭。

### 5.3 项目里的选择

项目用的是 `deepseek-chat`（非推理版），`temperature=0`。

**为什么？**

| 考量 | 说明 |
|---|---|
| 延迟 | Agent 要多轮调用，推理模型每轮几十秒，用户体验崩了 |
| 确定性 | 推理模型的思考路径更不确定 |
| 成本 | 工具调用场景不需要深度推理 |
| 足够用 | 实验室预约的逻辑并不复杂，普通模型 + 好的 prompt 够用 |

> 💡 **面试话术**：「我没用推理模型，用的是 DeepSeek 的普通对话模型加 temperature=0。原因是 Agent 场景要多次调用模型，如果用推理模型，每轮几十秒的思考时间会让整个对话变得不可接受；而且工具调用这种任务，关键是『选对工具、填对参数』，不是深度推理，用好的工具描述和 prompt 就能解决。推理模型我留给了评测场景的判官——判官需要判断答案是否忠于原文，这个任务值得多花点 token。」

## 六、第六层：为什么模型会「幻觉」

幻觉（Hallucination）是 Agent 开发最大的敌人。理解它的成因才能对症下药。

### 6.1 幻觉的四个来源

**来源 1：训练数据的记忆被激活**

模型在训练时见过很多文本。问它「你们实验室的规定是什么」，它可能生成一段**看起来很像规定的文字**——但它从未见过你的实验室规定。

**本质**：模型不知道「自己不知道什么」。它只判断「这段文字像不像答案」。

**来源 2：上下文不足时的「补全冲动」**

```
System: 你是实验室助手
User: 实验室能不能带食物？
```

如果上下文里没有任何规定文档，模型仍然会「补全」一个答案——因为它被训练成「要给出看起来合理的回答」。

**这是为什么 RAG 至关重要**：给模型真实的文档，它就不用编了。

**来源 3：注意力分散（Lost in the Middle）**

你塞了 10 段文档，关键那段在第 5 段。模型可能没充分注意到它，转而依赖自己的记忆 → 幻觉。

**解法**：rerank + 只保留 top 3 + 把最相关的放前面（第 27 章）

**来源 4：工具结果和模型预期不符时，模型「修正」结果**

```
模型调工具 → 工具返回 "没有找到相关实验室"
模型回答 → "找到了 A301 实验室..."    ← 无视工具结果，自己编
```

**为什么？** 因为模型「觉得」应该有个答案。

**解法**：System Prompt 明确「工具返回什么就说什么，工具说没有就是没有，不要补充」。

### 6.2 项目里的防幻觉措施

| 措施 | 位置 | 效果 |
|---|---|---|
| RAG 提供真实文档 | `kb_service.py` | 让模型有据可依 |
| System Prompt 约束 | `SYSTEM_PROMPT` | 明确「不知道就说不知道」 |
| 引用溯源 | `kb_service.py` | 用户能验证 |
| 工具返回结果优先 | `SYSTEM_PROMPT` | 防止无视工具结果 |
| 评测集含拒答用例 | `eval_dataset.py` | 量化验证 |
| faithfulness 指标 | `evaluate_generation.py` | 测「是否忠于原文」 |

> ⚠️ **重要认知**：**幻觉不能被完全消除，只能被降低和检测**。任何声称「解决了幻觉」的方案都是营销话术。面试时这么说会显得你很清醒。

## 七、最小可运行骨架：亲眼看到 token 和概率

理论讲完了，用一个不需要 API Key 的 demo 把概念落地。

```python
"""
llm_intuition.py —— 理解模型的核心行为（无需 API Key）
运行：pip install numpy && python llm_intuition.py
演示：token 化、采样策略、注意力权重直觉、工具调用生成
"""
import random
import math

# ── 1. 模拟 tokenizer ────────────────────────────────────

class FakeTokenizer:
    """极简分词器演示：真实 tokenizer 用 BPE，这里用规则模拟。"""
    def __init__(self):
        # 模拟一个词表
        self.vocab = ["实验", "室", "预约", "实验", "的", "实验", "明天", "下午",
                      "A301", "B205", "有", "没有", "可以", "不能", "。", "？"]
        self.vocab = list(dict.fromkeys(self.vocab))

    def encode(self, text: str) -> list:
        """贪心最长匹配分词。"""
        tokens, i = [], 0
        while i < len(text):
            for length in range(min(4, len(text) - i), 0, -1):
                piece = text[i:i+length]
                if piece in self.vocab:
                    tokens.append(piece)
                    i += length
                    break
            else:
                tokens.append(text[i])   # 未登录字单独成 token
                i += 1
        return tokens

    def count(self, text: str) -> int:
        return len(self.encode(text))

tok = FakeTokenizer()

def demo_tokenize():
    print("【1. 分词】模型看到的不是字，是 token")
    for s in ["帮我预约明天下午的A301实验室", "实验室预约", "laboratory"]:
        t = tok.encode(s)
        print(f"  '{s}' → {t}  共 {len(t)} tokens")

    print("\n  ⚠️ 关键：同样语义，中文通常比英文占更多 token")
    print("  所以：中文 prompt 更贵、更占上下文窗口\n")

# ── 2. 模拟概率分布与采样 ────────────────────────────────

def softmax(logits):
    m = max(logits)
    exps = [math.exp(x - m) for x in logits]
    s = sum(exps)
    return [e / s for e in exps]

def sample(probs, temperature=1.0):
    """按温度调整后采样。"""
    if temperature == 0:
        return probs.index(max(probs))          # 贪心：总选最高
    # 温度缩放：temperature 越小，分布越尖锐
    logits = [math.log(p + 1e-9) / temperature for p in probs]
    adjusted = softmax(logits)
    r = random.random()
    cum = 0.0
    for i, p in enumerate(adjusted):
        cum += p
        if r <= cum:
            return i
    return len(probs) - 1

def demo_temperature():
    print("【2. temperature 的作用】同一个分布，不同温度采样 20 次")
    words = ["好", "热", "不错", "冷", "糟糕"]
    base_probs = [0.35, 0.25, 0.18, 0.12, 0.10]

    for temp in [0, 0.5, 1.0, 2.0]:
        picks = [sample(base_probs, temp) for _ in range(20)]
        counts = {w: picks.count(i) for i, w in enumerate(words)}
        top = max(counts, key=counts.get)
        print(f"  T={temp:<4} 分布: {counts}  最常见: '{top}'")

    print("\n  ✅ T=0 永远选概率最高的（确定性，Agent 需要这个）")
    print("  ⚠️ T 越高越随机，创意任务好，工具调用灾难\n")

# ── 3. 模拟注意力 ────────────────────────────────────────

def demo_attention():
    print("【3. 注意力：生成每个词时，模型在'看'哪里】")
    context = ["我在", "清华大学", "计算机系", "读博士", "，研究方向是", "机器学习"]
    # 模拟：生成"它"时，各位置的注意力权重
    query_word = "它"
    weights = [0.05, 0.08, 0.10, 0.12, 0.15, 0.50]   # 机器学习权重最高

    print(f"  上下文: {' '.join(context)}")
    print(f"  生成 '{query_word}' 时的注意力分布：")
    for w, a in zip(context, weights):
        bar = "█" * int(a * 40)
        print(f"    {w:<12} {a:.2f} {bar}")

    print("\n  ⚠️ Lost in the Middle：中间位置的信息容易被忽略")
    print("  这就是为什么 RAG 要把最相关的文档放在开头或结尾\n")

# ── 4. 模拟工具调用生成 ──────────────────────────────────

def demo_context_cost():

    print("\n  ⚠️ 不裁剪的话，第 5 轮就爆了（8000 窗口）")
    print("  ✅ 裁剪策略：保留 system + 最近 N 轮，早期历史摘要压缩")
```

### 8.3 token 估算：`agent_service.py` 的 `_estimate_tokens`

```python
def _estimate_tokens(messages) -> int:
    """粗略估算 token 数：字符数 / 4。
    不用 tiktoken 的原因：模型不是 OpenAI，tokenizer 不一致；
    且 tiktoken 要下载词表文件。字符/4 对中文偏高估，宁可多剪。"""
    total = 0
    for m in messages:
        content = m.content if isinstance(m.content, str) else str(m.content)
        total += (len(content) + 3) // 4 + 1
        # 工具调用的参数也要算进去
        for tc in getattr(m, "tool_calls", None) or []:
            total += (len(json.dumps(tc.get("args") or {}, ensure_ascii=False)) + 3) // 4
    return total
```

**注意 `len(json.dumps(...))`**：工具调用的参数也占 token，不能只算 `content`。

## 本章速记卡

1. **模型是模式匹配器**，不是「有知识的人」。它输出的是「最像答案的文字序列」。
2. **Token 不是字**。中文 1 字 ≈ 1-2 token，英文 1 词 ≈ 1-3 token。中文更贵。
3. **temperature=0** 用于 Agent（确定性）；创意任务才调高。
4. **生成是逐 token 的**，所以流式输出天然可行，也解释了长回答为什么慢。
5. **工具调用是「生成」出来的**，所以会：不调工具、编工具名、编参数格式。
6. **工具 docstring 是给模型看的 prompt**，决定调用时机。
7. **Lost in the Middle**：中间位置的信息容易被忽略 → RAG 要把最相关的放前/后。
8. **Attention 是 O(n²)** → 长上下文贵且慢 → 必须裁剪。
9. **幻觉不能被消除**，只能降低（RAG + prompt 约束）和检测（faithfulness）。
10. **推理模型的思考 token 也算钱**，设 `max_tokens` 要留足。

## 面试问答：模型原理

### Q1：「大模型是怎么工作的？用一句话解释」

**满分答法**：

> 它是一个超大规模的模式匹配器：给定一段文字，预测下一个最可能出现的 token，然后把这个 token 加到输入里继续预测，直到生成结束标记。
>
> 它之所以「看起来有知识」，是因为训练时见过海量文本，学会了「什么问题后面通常跟什么答案」的模式。但它并不真的「知道」事实，这也是幻觉的根源。
>
> 对工程来说，最重要的推论是：**模型的所有行为都是文本生成的副产品**，包括工具调用。所以工具调用会出错，需要工程兜底。

---

### Q2：「为什么 Agent 场景要用 temperature=0？」

**满分答法**：

> 因为 Agent 要做工具调用，可靠性依赖输出的确定性。
>
> 温度是控制采样随机性的参数。温度高了，同样的问题模型可能这次调 A 工具、下次调 B 工具，参数格式也可能变。这会带来三个问题：一是行为不可预测，用户同样的问法得到不同结果；二是单元测试没法写，断言不稳定；三是调试困难，bug 无法复现。
>
> 代价是回答略显死板。但对「查信息 + 执行操作」这类任务，可靠性远比文采重要。写作、头脑风暴这类场景我才考虑调高温度。

---

### Q3：「模型为什么会不调用工具？你怎么解决？」

**满分答法**（这题非常高频，要分层答）：

> 根本原因是：工具调用本质上是模型生成的一段结构化文本，它完全可以生成普通回答。
>
> 具体触发场景有三个：一是工具描述写得不清楚，模型不知道该用它；二是模型「觉得」自己知道答案，直接凭记忆回答（这其实是幻觉）；三是 System Prompt 没有强制约束。
>
> 我的应对分三层：
>
> **Prompt 层**：System Prompt 里明确写「涉及实验室、设备、预约的查询必须调用工具获取真实数据，不要凭记忆回答」。工具描述里也写清楚「这是获取该信息的唯一途径」。
>
> **工程层**：工具不存在或参数错误时，不抛异常中断，而是把错误信息回填成 ToolMessage 给模型，让它有机会修正。同时工具内部对参数再校验一次，不能信模型的输出。
>
> **评测层**：在评测集里放一些「必须调工具才能答对」的用例，定期跑，观察工具调用率有没有下降。
>
> 如果还不行，可以用 `tool_choice="required"` 强制必须调工具，但这会失去灵活性——比如用户说「你好」也要被迫调工具，所以我没用。

---

### Q4：「什么是幻觉？你怎么降低它？」

**满分答法**：

> 幻觉是模型生成了「看起来合理但不符合事实」的内容。
>
> 成因有四个：一是模型不知道自己不知道什么，它会补全一个「像答案」的东西；二是上下文里没有相关信息时，它仍有补全冲动；三是 Lost in the Middle——你塞了十段文档，关键那段在中间，模型没注意到；四是工具返回「没有找到」时，模型可能无视结果自己编。
>
> 我的降低手段：
>
> **RAG**：给模型真实文档，它就不用编了。这是最有效的。
>
> **Rerank 和精简**：不塞十段，只留最相关的三段，并把最相关的放最前面，对抗 Lost in the Middle。
>
> **Prompt 约束**：明确「只根据提供的资料回答，资料里没有就说不知道」。
>
> **引用溯源**：回答附带引用，用户可以点回原文验证，这既是产品功能也是约束——模型知道要给出处，就不敢乱编。
>
> **评测验证**：用 RAGAS 的 faithfulness 指标量化「回答是否忠于原文」，并在评测集里专门放拒答用例。
>
> 但要说清楚：**幻觉不能被完全消除，只能被降低和检测**。我现在能做的是把它的发生率压到可接受，并用评测持续监控。

---

### Q5：「工具太多会怎么样？怎么处理？」

**满分答法**：

> 经验上超过 10-20 个工具后，模型的选择准确率会明显下降。原因是工具描述占用大量上下文，而且选项太多时模型容易选错或者混淆。
>
> 处理方式有几种：
>
> **按需加载**：不一次性把所有工具都给模型，而是根据当前意图动态提供相关工具。我项目里 MCP 工具就是可选的，通过 `MCP_ENABLED` 控制。
>
> **分组路由**：用一个轻量的路由 Agent 先判断「这个问题属于哪一类」，再加载那一类的工具。
>
> **MCP 协议**：把工具拆到独立服务，Agent 只拿需要的。这是更彻底的解耦。
>
> **合并工具**：把功能相近的工具合并成一个，用参数区分。比如 `search(entity_type, keyword)` 而不是 `search_labs` / `search_equipments` 两个。
>
> 我项目里工具只有 6-8 个，还没到瓶颈，所以目前是全量注入。但 MCP 的架构已经留好了，将来工具多了可以按需加载。

---

### Q6：「推理模型（比如 R1）和普通模型有什么不同？你为什么没用？」

**满分答法**：

> 推理模型在生成答案前会先生成一段思考过程，这段思考也是 token，同样计费、同样耗时。
>
> 区别主要在三点：一是延迟，思考过程可能几千 token，生成要几十秒；二是成本，同样的问答可能花 3-10 倍 token；三是输出结构，响应里会多一个 reasoning_content 字段。
>
> 我没用在 Agent 主链路上，有三个原因：一是 Agent 要多轮调用模型，每轮几十秒的思考会让整个对话不可接受；二是工具调用这种任务，关键是选对工具填对参数，不是深度推理，好的工具描述和 prompt 就能解决；三是推理模型的输出更不确定，不利于测试。
>
> 但我把它用在了评测的判官模型上——判断答案是否忠于原文这个任务需要仔细比对，值得多花 token。而且判官和被测模型分离本身也是评测的最佳实践。
>
> 另外踩过一个坑：一开始评测设了 `max_tokens=1024`，结果思考过程把预算吃光，答案被截断，导致指标虚低。所以用推理模型时 max_tokens 要给足。

## 常见坑

### 坑 1：以为「模型知道答案」，不给它资料

模型不知道你的实验室规定。必须 RAG。

### 坑 2：工具 docstring 写成注释风格

`"""搜索实验室"""` 太短，模型不知道何时调用。要写清使用场景、边界、参数格式。

### 坑 3：推理模型设小 max_tokens

思考 token 吃光预算，答案被截断。

### 坑 4：忽略了 Lost in the Middle

把最相关的文档放在一堆文档中间，模型没注意到。

### 坑 5：用 tiktoken 估非 OpenAI 模型的 token

tokenizer 不一致，估算不准。用字符/4 的保守估算更实用。

### 坑 6：温度设高了还抱怨「模型行为不稳定」

Agent 场景就该 T=0。

### 坑 7：以为工具调用是「确定性决策」

它是生成出来的，会出错，必须兜底。
