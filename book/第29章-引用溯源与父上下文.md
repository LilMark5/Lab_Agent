# 第 29 章 · 引用溯源与父上下文：小块检索，大块生成

> **这一章要回答的核心问题**：检索用小块的精准 vs 生成要大块的完整，这个矛盾怎么解？`[文件名#块号]` 这个标记是怎么一路传递到模型回答里的？"根据《XX.md》"这句话凭什么可信？

---

## 29.1 引子：RAG 的两难

先明确一个贯穿前几章的矛盾：

| 需求 | 要求 |
|---|---|
| **检索要准** | 块要**小**（语义聚焦，向量匹配精准） |
| **生成要好** | 块要**大**（上下文完整，模型能理解） |

这是个**两难**：

- 块小（200 字）→ 向量匹配精准，但检索到的可能只是半句话，模型看不懂
- 块大（2000 字）→ 语义完整，但向量是"大杂烩"，匹配不准

**本项目的解法是"小规模检索 + 大规模生成"（Small-to-Big）**：

> **用小块的粒度做检索（保证精准），命中后再扩展成父上下文给模型（保证完整）。**

这就是本章的两个主角：
1. **父上下文扩展**（`_expand_context`）—— 解决"完整"
2. **引用溯源**（`[source#chunk_index]` 标记）—— 解决"可信"

## 29.2 父上下文扩展：命中块 → 前后各 N 块

### 29.2.1 项目实现

`kb_service.py:207-227`：

```python
def _expand_context(hit: dict, window: int | None = None) -> str:
    """把命中的小块扩展成父上下文：同源文档里前后各 window 块拼起来。"""
    window = window if window is not None else settings.CONTEXT_WINDOW
    source = hit.get("meta", {}).get("source")
    chunk_index = hit.get("meta", {}).get("chunk_index")
    if source is None or chunk_index is None:
        return hit.get("doc", "")

    document_id = hit.get("meta", {}).get("document_id")
    same_source = [
        c
        for c in _get_chunks()
        if c["meta"].get("source") == source
        and c["meta"].get("document_id") == document_id
    ]
    if not same_source:
        # 动态上传文档不在静态块缓存里，直接返回命中块本身。
        return hit.get("doc", "")
    low = max(0, int(chunk_index) - window)
    high = min(len(same_source), int(chunk_index) + window + 1)
    return "\n".join(c["doc"] for c in same_source[low:high])
```

### 29.2.2 逐步拆解

**① 取元数据**

```python
source = hit.get("meta", {}).get("source")        # 文件名
chunk_index = hit.get("meta", {}).get("chunk_index")   # 块序号
document_id = hit.get("meta", {}).get("document_id")   # 文档 ID
```

这三个字段是**第 23 章切块时就写进去的**。这里体现了元数据设计的前瞻性。

**② 防御：元数据缺失**

```python
if source is None or chunk_index is None:
    return hit.get("doc", "")
```

没有元数据（理论上不该发生）→ 直接返回命中块本身，**不报错**。

**③ 找同源同文档的所有块**

```python
same_source = [
    c for c in _get_chunks()
    if c["meta"].get("source") == source
    and c["meta"].get("document_id") == document_id
]
```

**注意用了两个条件**：`source`（文件名）+ `document_id`。

**为什么要两个？** 因为可能有**同名文件**：用户上传了一份叫"规定.md"的文档，静态库里也有"规定.md"。只用 `source` 会把两者的块混在一起，扩展出错误的上下文。

**④ 动态上传文档的兜底**

```python
if not same_source:
    # 动态上传文档不在静态块缓存里，直接返回命中块本身。
    return hit.get("doc", "")
```

**这是一个重要的边界处理**，值得细讲。

`_get_chunks()` 返回的是**缓存的块列表**（`kb_service.py:67-84`）：

```python
def _get_chunks() -> list[dict]:
    global _chunks_cache
    if _chunks_cache is None:
        store = vector_store.get_vector_store()
        if store is not None:
            try:
                chunks = store.list_chunks()      # ★ 从向量库读全部块
                if chunks:
                    _chunks_cache = chunks
                    return _chunks_cache
            except Exception as exc:
                logger.warning("从向量库读取块失败，回退静态文件：%s", exc)
        _chunks_cache = kb_chunking.load_kb_chunks()    # 兜底：只加载静态文件
    return _chunks_cache
```

**缓存优先从向量库读**（包含上传文档），失败才回退静态文件。

**但如果缓存是在上传文档之前建立的，或者向量库不可用导致回退到了静态文件**，那么上传文档的块就不在 `_get_chunks()` 里 → `same_source` 为空 → **无法扩展**。

**这时候怎么办？** 代码选择了：**返回命中块本身**（不扩展）。

**这是正确的降级**：虽然上下文不完整，但至少检索到的内容在，模型还能回答。比抛异常或返回空好得多。

> **面试可以说**："扩展父上下文时有个边界：如果块不在缓存里（比如上传文档但向量库不可用导致缓存回退到静态文件），`same_source` 会是空的。我们的处理是**直接返回命中块本身**——上下文不完整但内容还在，比抛异常或返回空好。这是又一次'降级而非失败'的设计。"

**⑤ 计算窗口**

```python
low = max(0, int(chunk_index) - window)
high = min(len(same_source), int(chunk_index) + window + 1)
return "\n".join(c["doc"] for c in same_source[low:high])
```

`window` 默认 1（`CONTEXT_WINDOW=1`）→ 取 `chunk_index-1` 到 `chunk_index+1`，**共 3 块**。

**边界处理**：
- `max(0, ...)`：不能在文档开头越界
- `min(len, ...)`：不能在文档末尾越界
- `high = idx + window + 1`：因为 Python 切片是**左闭右开**

### 29.2.3 一个具体例子

假设 `CONTEXT_WINDOW=1`，文档《规定.md》被切成 5 块：

```
[0] 实验室开放时间为每日 8:00 至 22:00
[1] 节假日另行通知，寒暑假按学校通知执行
[2] 进入实验室必须穿戴实验服和防护眼镜
[3] 禁止穿拖鞋、短裤进入实验区域
[4] 实验结束后必须关闭电源并填写记录
```

用户问"节假日怎么安排"，命中块 **#1**。

扩展后（`low=0, high=3`）：

```
[0] 实验室开放时间为每日 8:00 至 22:00
[1] 节假日另行通知，寒暑假按学校通知执行     ← 命中块
[2] 进入实验室必须穿戴实验服和防护眼镜
```

**模型现在看到的**：不只是"节假日另行通知"，还有前面的"开放时间 8:00-22:00"——**完整理解了"节假日另行通知"指的是开放时间的例外**。

**这就是父上下文的价值**：一个小块单独看是残缺的，加上前后文就完整了。

### 29.2.4 另一种方案：父文档检索（Parent Document Retriever）

对比两种 Small-to-Big 实现：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **窗口扩展**（本项目） | 取命中块前后各 N 块 | 上下文**紧贴**命中位置 | 可能超出文档边界就截断 |
| **父文档检索** | 存两层：小块用于检索，大块（整个章节/文档）用于生成 | 上下文**完整**（整个章节） | 大块可能很长（成本高）；大块的语义粒度粗 |

**父文档检索的做法**：

```python
# 索引时
small_chunks = split(text, 200)      # 用于检索
large_chunks = split(text, 2000)     # 用于生成
# 每个 small_chunk 记录它的 parent_id

# 检索时
hits = vector_search(query, small_chunks)
for hit in hits:
    parent = large_chunks[hit.parent_id]    # ★ 返回父块
```

**本项目的窗口扩展更简单**，且上下文紧贴命中位置（父文档检索可能返回一个 2000 字的大块，其中大部分不相关）。

**权衡**：窗口扩展在"文档结构清晰、相邻块语义连贯"时效果好；父文档检索在"大块本身就是完整语义单元"（比如一个 FAQ 对、一个小节）时更好。

> **面试可以说**："Small-to-Big 有两种实现：我们用的是**窗口扩展**（取命中块前后各 N 块），另一种是**父文档检索**（存两层块，小块检索、大块生成）。窗口扩展的好处是上下文紧贴命中位置、不会引入无关内容；父文档检索的好处是能保证语义单元完整（比如整个 FAQ 对）。我们的文档是连续的规章制度，相邻块语义连贯，窗口扩展更合适。"

## 29.3 引用溯源：让答案能追到出处

### 29.3.1 项目实现

`kb_service.py:287-296`：

```python
parts = []
for hit in hits:
    source = hit.get("meta", {}).get("source") or ""
    chunk_index = hit.get("meta", {}).get("chunk_index")
    context = _expand_context(hit)
    parts.append(f"[{source}#{chunk_index}]\n{context}")

result = "\n\n".join(parts)
```

**关键在这行**：

```python
parts.append(f"[{source}#{chunk_index}]\n{context}")
```

每个块前面加一个 **`[文件名#块号]`** 标记。

**最终送给模型的资料长这样**：

```
[实验室管理规定.md#0]
实验室开放时间为每日 8:00 至 22:00
节假日另行通知，寒暑假按学校通知执行
进入实验室必须穿戴实验服和防护眼镜

[量子实验室说明.md#3]
量子实验室的激光设备功率上限为 5W...
```

### 29.3.2 为什么用 `#` 分隔？

`[文件名#块号]` 这个格式的选择有讲究：

| 考虑 | 说明 |
|---|---|
| **唯一性** | 文件名 + 块号唯一确定一个块 |
| **模型熟悉** | `#` 在 Markdown 里是标题符号，在 URL 里是锚点，模型见过无数次 |
| **不会误解析** | 不会和正文混淆（用了方括号包裹） |
| **可解析** | 前端可以用正则提取，做"点击跳转到原文" |

**它和切块时的 `id` 格式一致**（`kb_chunking.py:119`）：

```python
"id": f"{path.stem}#{index}",
```

**从切块到检索到展示，同一个标识符贯穿全链路。** 这是数据设计一致性的体现。

### 29.3.3 System Prompt 里的硬要求

光有标记不够，**必须要求模型使用它**。`agent_service.py` 的 SYSTEM_PROMPT：

```
## 引用要求
search_lab_docs 返回的资料会带 [文件名#块号] 这样的来源标记。知识库同时包含系统内置文档
和用户上传的文档，回答时要注明依据的文件名，例如「根据《量子实验室说明.md》」，
不要只给结论而不说明出处。
```

**三句话，每句都有作用**：

| 句子 | 作用 |
|---|---|
| "资料会带 `[文件名#块号]` 这样的来源标记" | **告诉模型标记的格式和含义** |
| "回答时要注明依据的文件名，例如「根据《量子实验室说明.md》」" | **给出具体的示例**（few-shot 的作用） |
| "不要只给结论而不说明出处" | **硬性约束，堵住偷懒** |

**"给示例"这点很关键** —— 单纯说"要注明出处"，模型可能不知道用什么格式。给一个具体的例子（「根据《量子实验室说明.md》」），模型就会模仿。

### 29.3.4 引用溯源的价值

| 价值 | 说明 |
|---|---|
| **可验证** | 用户可以去查原文，确认 Agent 没编造 |
| **降幻觉** | 模型被要求"说出出处"，编造时更难自圆其说 |
| **可追责** | 出问题时能定位到是哪份文档的哪一段 |
| **可更新** | 文档更新后，能判断哪些答案需要重新生成 |

**在实验室安全、医疗、法律这类高风险领域，不可溯源 = 不可用。**

### 29.3.5 引用的三个层次（进阶）

本项目的引用是 **文档级**（"根据《XX.md》"）。更细的还有：

| 层次 | 形式 | 实现难度 |
|---|---|---|
| **文档级**（本项目） | "根据《量子实验室说明.md》" | 简单 |
| **块级** | "根据《说明.md》第 3 段" | 中（模型要能数块号） |
| **句级** | "激光功率上限为 5W（说明.md 第 12 行）" | 难（要精确定位） |

**句级引用最有价值**（能精确验证），但实现复杂（需要让模型输出精确的字符位置，或者后处理时做文本对齐）。

> 📝 **改进方向**：目前模型偶尔会引用"块号"，但不够稳定。可以：① 在 prompt 里明确要求输出块号；② 后处理时用正则提取 `[xxx.md#N]` 转成前端可点击的链接。**后者是很好的产品体验优化**。

## 29.4 完整链路：从检索到带引用的答案

把所有环节串起来（`kb_service.search()`）：

```python
def search(query: str, document_id: str | None = None) -> str:
    """检索并返回拼好的、带引用的资料文本。"""
    if not query.strip():
        return ""

    scope = document_id or "all"
    cache_key = (
        f"rag:v{_corpus_version}:{scope}:"
        + hashlib.md5(query.encode("utf-8")).hexdigest()
    )
    cached = _cache_get(cache_key)
    if cached:
        return cached

    hits = retrieve(query, top_k=settings.FINAL_CONTEXT_K, document_id=document_id)
    if not hits:
        return ""

    parts = []
    for hit in hits:
        source = hit.get("meta", {}).get("source") or ""
        chunk_index = hit.get("meta", {}).get("chunk_index")
        context = _expand_context(hit)                     # ★ 父上下文扩展
        parts.append(f"[{source}#{chunk_index}]\n{context}")   # ★ 引用标记

    result = "\n\n".join(parts)
    _cache_set(cache_key, result)
    return result
```

**完整流程**：

```
用户："实验室几点关门？"
  │
  ├─ 缓存检查（Redis，key 含 corpus_version）        ← 第 21 章
  │
  ├─ retrieve()
  │   ├─ _rewrite_query()          "实验室几点关门？" → "实验室开放时间 闭馆"
  │   ├─ _vector_search()          → [块A(0.82), 块C(0.71), ...]
  │   ├─ _bm25_search()            → [块A(12.4), 块B(8.1), ...]
  │   ├─ _rrf_fusion()             → [块A, 块C, 块B, ...]
  │   └─ _rerank()                 → [块A, 块B, 块C, ...]
  │
  ├─ 取前 FINAL_CONTEXT_K=5 条
  │
  ├─ 对每条：
  │   ├─ _expand_context()         小块 → 前后各 1 块
  │   └─ 拼 "[文件名#块号]\n{扩展后的内容}"
  │
  ├─ "\n\n".join(parts)            多条之间空一行
  │
  ├─ 写入 Redis 缓存（TTL 3600s）
  │
  └─ 返回给工具 → ToolMessage → 模型 → "根据《实验室管理规定.md》，开放时间是 8:00-22:00"
```

### 29.4.1 缓存的位置：在 search 层而不是 retrieve 层

```python
cached = _cache_get(cache_key)
if cached:
    return cached
...
_cache_set(cache_key, result)
```

**缓存的是"最终拼好的带引用文本"，不是中间的 hits。**

**为什么？** 因为：

- 省掉了**整条链路**（改写 + 双路检索 + 融合 + 重排 + 扩展）
- 缓存的值是**字符串**，序列化简单

**代价**：缓存粒度粗——如果 `include_uploaded` 变了，或者文档更新了，就要失效（靠 `corpus_version` 和 `scope` 处理）。

看 cache_key 的三个部分：

```python
f"rag:v{_corpus_version}:{scope}:" + md5(query)
```

| 部分 | 作用 |
|---|---|
| `v{_corpus_version}` | 文档变更时版本号 +1 → 全部失效（第 21 章） |
| `{scope}` | `document_id or "all"` → 检索范围不同，缓存隔离 |
| `md5(query)` | 查询内容的哈希 |

**注意 `{scope}` 已经涵盖了 `include_uploaded` 的影响** —— 因为 `include_uploaded=False` 时 `document_id="static"`，`scope` 就是 `"static"`；`True` 时 `document_id=None`，`scope` 是 `"all"`。两者 key 不同，**不会串**。✅

## 29.5 最小骨架：Small-to-Big + 引用

```python
"""
minimal_context_ref.py —— 父上下文扩展 + 引用溯源
运行：python minimal_context_ref.py  （纯 Python，无需依赖）
"""
import hashlib


# ── 1. 语料：模拟切块后的块（带元数据）──────────────────────
CHUNKS = [
    {"id": "规定.md#0", "doc": "实验室开放时间为每日 8:00 至 22:00",
     "meta": {"source": "规定.md", "chunk_index": 0, "document_id": "static"}},
    {"id": "规定.md#1", "doc": "节假日另行通知，寒暑假按学校通知执行",
     "meta": {"source": "规定.md", "chunk_index": 1, "document_id": "static"}},
    {"id": "规定.md#2", "doc": "进入实验室必须穿戴实验服和防护眼镜",
     "meta": {"source": "规定.md", "chunk_index": 2, "document_id": "static"}},
    {"id": "规定.md#3", "doc": "禁止穿拖鞋、短裤进入实验区域",
     "meta": {"source": "规定.md", "chunk_index": 3, "document_id": "static"}},
    # ★ 同名文件，不同 document_id（测试双条件过滤）
    {"id": "上传-42#0", "doc": "量子实验室规定.md 的补充：夜间需申请",
     "meta": {"source": "规定.md", "chunk_index": 0, "document_id": "upload-42"}},
]


# ── 2. 模拟检索（简单词元匹配，替代真实的向量+BM25）─────────
def fake_retrieve(query: str, top_k: int = 2) -> list[dict]:
    q = set(query)
    scored = []
    for c in CHUNKS:
        overlap = len(q & set(c["doc"]))
        if overlap:
            scored.append({**c, "score": overlap / len(q)})
    scored.sort(key=lambda x: x["score"], reverse=True)
    return scored[:top_k]


# ── 3. 父上下文扩展 ────────────────────────────────────────
def expand_context(hit: dict, chunks: list[dict], window: int = 1) -> str:
    """取同源同文档的前后各 window 块拼起来。"""
    source = hit.get("meta", {}).get("source")
    idx = hit.get("meta", {}).get("chunk_index")
    doc_id = hit.get("meta", {}).get("document_id")
    if source is None or idx is None:
        return hit.get("doc", "")

    # ★ 双条件：source + document_id（防止同名文件串味）
    same = [c for c in chunks
            if c["meta"].get("source") == source
            and c["meta"].get("document_id") == doc_id]
    if not same:
        return hit.get("doc", "")            # 降级：返回命中块本身

    low = max(0, int(idx) - window)
    high = min(len(same), int(idx) + window + 1)     # 切片右开
    return "\n".join(c["doc"] for c in same[low:high])


# ── 4. 拼装带引用 ──────────────────────────────────────────
def search(query: str, chunks: list[dict], window: int = 1) -> str:
    hits = fake_retrieve(query)
    if not hits:
        return ""
    parts = []
    for h in hits:
        src = h.get("meta", {}).get("source") or ""
        idx = h.get("meta", {}).get("chunk_index")
        ctx = expand_context(h, chunks, window)
        parts.append(f"[{src}#{idx}]\n{ctx}")        # ★ 引用标记
    return "\n\n".join(parts)
```

## 29.7 面试问答

### Q1：检索用小块的精准 vs 生成要大块的完整，你们怎么解决？

**答**：用 **Small-to-Big** 策略：**小块检索，命中后扩展成父上下文再生成**。

具体是：切块时每块 500 字符，用于向量检索（语义聚焦、匹配精准）；命中后按 `source` + `chunk_index` 找到同源文档里**前后各 N 块**（默认 N=1，共 3 块），拼起来再给模型。

这样既保证了检索精准（小块），又保证了上下文完整（扩展后的大块）。

对比另一种实现**父文档检索**（存两层块，小块检索、大块生成）：我们选窗口扩展是因为上下文**紧贴命中位置**，不会引入无关内容；父文档检索的好处是保证语义单元完整（比如整个 FAQ 对）。我们的文档是连续的规章制度，相邻块语义连贯，窗口扩展更合适。

### Q2：为什么过滤同名文件要用两个条件？

**答**：因为可能有**同名文件**。用户上传了一份叫"规定.md"的文档，静态知识库里也有"规定.md"。只用 `source`（文件名）会把两者的块混在一起，扩展出错误的上下文——比如把用户上传的补充规定和系统的规定拼在一起，语义就乱了。

所以过滤条件是 `source == 文件名 AND document_id == 文档ID`。`document_id` 在切块时就写入：静态库固定是 `"static"`，上传文档是真实的文件 ID。

### Q3：引用溯源怎么实现的？

**答**：两层。

**数据层**：检索结果的每个块前面拼一个 `[文件名#块号]` 标记。这个格式和切块时的 `id` 格式一致（`{文件名}#{块号}`），从切块到检索到展示用同一个标识符贯穿全链路。选 `#` 是因为它在 Markdown 里是标题符号、在 URL 里是锚点，模型非常熟悉。

**Prompt 层**：光有标记不够，必须要求模型使用它。System Prompt 里写了三句话——告诉模型标记的格式、给出具体的示例（「根据《量子实验室说明.md》」）、以及硬性约束"不要只给结论而不说明出处"。**给示例很关键**，单纯说"要注明出处"模型不知道用什么格式。

### Q4：引用溯源有什么价值？

**答**：四个。

一是**可验证**——用户可以去查原文确认 Agent 没编造；二是**降幻觉**——模型被要求说出出处，编造时更难自圆其说；三是**可追责**——出问题时能定位到哪份文档的哪一段；四是**可更新**——文档更新后能判断哪些答案需要重新生成。

在实验室安全、医疗、法律这类高风险领域，**不可溯源就等于不可用**。

### Q5：扩展时发现块不在缓存里怎么办？

**答**：返回命中块本身，不扩展、不报错。

这个边界是真实存在的：`_get_chunks()` 的缓存优先从向量库读（包含上传文档），如果向量库不可用会回退到只加载静态文件——这时上传文档的块就不在缓存里，`same_source` 为空。

我们的处理是返回命中块本身：上下文不完整但内容还在，模型仍能回答。比抛异常或返回空好得多。这是又一次"降级而非失败"的设计。

### Q6：缓存存在哪一层？key 怎么设计？

**答**：缓存在 `search()` 层，缓存的是**最终拼好的带引用文本**，不是中间的 hits。这样省掉整条链路（改写 + 双路检索 + 融合 + 重排 + 扩展），而且值是字符串，序列化简单。

key 是三段：`rag:v{corpus_version}:{scope}:{md5(query)}`。

- `corpus_version`：文档变更时 +1 → **所有旧缓存自动失效**（不需要遍历删除）
- `scope`：`document_id or "all"` → 检索范围不同则缓存隔离。它顺带涵盖了"是否包含上传文档"这个开关（`False` 时 scope 是 `"static"`，`True` 时是 `"all"`）
- `md5(query)`：查询内容哈希

代价是粒度粗——任何变化都会让整批失效。但对我们的场景够用。

## 29.8 速记卡

> **Small-to-Big：小块检索（精准），大块生成（完整）。引用让答案可信。**

**两难**：块小 → 检索准但语义残；块大 → 语义全但检索糊

**解法**：`_expand_context()` —— 命中后取前后各 N 块（默认 N=1，共 3 块）

**★ 双条件过滤**：`source`（文件名）+ `document_id`（防同名文件串味）

**★ 降级**：`same_source` 为空 → 返回命中块本身（不扩展、不报错）

**引用格式**：`[文件名#块号]` —— 和切块 `id` 格式一致，全链路贯穿

**Prompt 三句**：说明格式 + **给示例** + 硬性约束"不要只给结论"

**两种 Small-to-Big**：窗口扩展（本项目，紧贴命中位置）/ 父文档检索（两层块，语义单元完整）

**缓存**：在 `search()` 层，缓存最终文本
**key 三段**：`v{corpus_version}`（版本号失效）/ `{scope}`（范围隔离）/ `md5(query)`

## 29.9 延伸思考

1. **如果 `CONTEXT_WINDOW=2`（前后各 2 块，共 5 块），会发生什么？**
   提示：上下文更完整，但**每个命中块都变成 5 倍大小**。5 个命中 × 5 块 × 500 字 = 12.5K 字符 ≈ 4000+ token——**接近 `MAX_CONTEXT_TOKENS=4000` 的预算**！这会让第 19 章的裁剪频繁触发。
   **这揭示了一个连锁关系**：`CONTEXT_WINDOW` × `FINAL_CONTEXT_K` × `CHUNK_SIZE` 三者共同决定送入模型的 token 量，调参时要一起考虑。

2. **"块级引用"（"根据《说明.md》第 3 段"）怎么实现？**
   提示：模型已经看到了 `[说明.md#3]` 标记，理论上能引用块号。但**不够稳定**——模型经常只引用文件名。改进：prompt 里明确要求输出块号；或者后处理用正则提取。前端可以把它渲染成可点击链接（跳转到原文位置）。

3. **如果两份文档内容矛盾（旧规程 21:00 关门，新规程 22:00），引用溯源能帮上忙吗？**
   提示：**能**，这正是引用的价值之一——模型如果同时引用了两份文档，用户能看到矛盾所在。但更好的做法是：① 文档加时间元数据，检索时优先新文档；② prompt 要求模型在矛盾时明确指出"存在两个版本"。**这是一个真实且常见的生产问题**（第 21 章延伸思考提过）。
