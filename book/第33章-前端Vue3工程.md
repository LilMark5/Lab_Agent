# 第 33 章 · 前端 Vue3 工程：对话界面与审批联动

> **这一章要回答的核心问题**：Agent 的前端和普通 CRUD 页面有什么不同？流式消息怎么增量更新？审批确认框怎么和后端 `interrupt` 联动？为什么 `thread_id` 要前端生成？

---

## 33.1 引子：Agent 前端的三个特殊之处

普通 CRUD 前端的模式是：**发请求 → 等响应 → 渲染**。

Agent 前端完全不同：

| 维度 | 普通 CRUD | Agent 前端 |
|---|---|---|
| **响应** | 一次性 JSON | **流式事件流**（第 31 章） |
| **时长** | 毫秒~秒 | **秒~分钟** |
| **中间态** | 无（loading 就够） | **要展示"正在检索…""正在预约…"** |
| **交互** | 无 | **可能中途弹确认框**（第 18 章） |
| **状态** | 服务端无状态 | **会话状态**（`thread_id`） |

**这三点决定了 Agent 前端的架构**：

1. **事件驱动的状态机** —— 前端要处理多种事件类型
2. **消息对象的增量更新** —— 流式时不断往同一个对象追加
3. **双向交互** —— 不只展示，还要回应用户决策

## 33.3 消息的数据结构

`AIChat.vue:188-193`：

```javascript
const assistant = reactive({
  role: 'assistant',
  content: '',        // 流式追加的正文
  status: '正在思考…', // 当前状态提示
  steps: []           // 工具执行过程
})
messages.value.push(assistant)
```

**三个字段对应三种 UI**：

| 字段 | 展示 | 更新时机 |
|---|---|---|
| `content` | 回答正文（Markdown） | `token` 事件 |
| `status` | "正在思考…" | `status` / `tool_start` 事件 |
| `steps` | 工具执行记录 | `tool_start` / `tool_end` |

**为什么用 `reactive` 而不是 `ref`？**

```javascript
const assistant = reactive({...})
```

`reactive` 对**对象**做深层响应式，修改 `assistant.content` 会触发更新。如果用 `ref`，要写 `assistant.value.content`（多一层）。

**关键点**：这个对象被 `push` 进 `messages.value` 之后，**仍然持有引用**——所以后续修改 `assistant.content` 会直接反映到列表里。**这是流式增量更新的基础**。

> ⚠️ **坑**：如果用 `messages.value.push({ ...assistant })`（展开拷贝），后续修改原对象**不会**更新列表里的副本。必须是同一个对象引用。

## 33.4 事件处理：把 SSE 事件映射到 UI

`AIChat.vue` 的 `applyStreamEvents`（简化版逻辑）：

```javascript
function applyStreamEvents(assistant, evt) {
  switch (evt.type) {
    case 'status':
      assistant.status = evt.message
      break

    case 'tool_start':
      assistant.status = `正在${evt.label}…`
      assistant.steps.push({ label: evt.label, done: false })
      break

    case 'tool_end':
      const step = assistant.steps.find(s => s.label === evt.label)
      if (step) { step.done = true; step.preview = evt.preview }
      assistant.status = `已完成${evt.label}`
      break

    case 'token':
      // ★ 增量追加，不是替换
      assistant.content += evt.content
      scrollToBottom()
      break

    case 'approval_required':
      // ★ 需要用户决策 → 弹确认框
      handleApproval(evt, assistant)
      break

    case 'done':
      assistant.status = ''
      break

    case 'error':
      assistant.status = ''
      assistant.content = evt.message
      break
  }
}
```

**四个设计点**：

**① `token` 是追加不是替换**

```javascript
assistant.content += evt.content
```

这是流式 UI 的核心：**每个 token 追加到同一个字符串**。

**② `tool_start` / `tool_end` 配对**

用 `label` 作为 key 找到对应的步骤，标记完成。这让 UI 能显示：

```
✓ 检索实验室知识库    找到 3 条相关资料：开放时间 8:00-22:00…
⏳ 查询开放实验室
```

**③ `approval_required` 触发异步交互**

这是最特殊的一个——它不是一个"展示"事件，而是**要求用户做决策**。

**④ 滚动到底部**

```javascript
scrollToBottom()   // nextTick 后设置 scrollTop
```

流式输出时内容不断增长，要自动滚动让用户看到最新内容。

## 33.5 审批联动：前端如何响应 interrupt

这是本项目前端最有技术含量的部分。

### 33.5.1 完整流程

```
① 用户："帮我预约明天下午的显微镜实验室"
② 前端 POST /ai/chat/stream
③ 后端 Agent 走到 approval 节点 → interrupt
④ 后端发 SSE 事件：{"type":"approval_required","thread_id":"xxx","payload":{...}}
⑤ 前端收到 → 弹 Element Plus 确认框
⑥ 用户点"确认"或"取消"
⑦ 前端 POST /ai/chat/stream/resume {thread_id, approved}
⑧ 后端从断点继续 → 执行预约 → 流式返回结果
⑨ 前端继续接收 token，追加到**同一个** assistant 对象
```

**关键**：第 ⑨ 步的结果要追加到**第 ① 轮创建的那个 assistant 对象**上，而不是新建一条消息。

### 33.5.2 代码实现

`AIChat.vue:154-177`：

```javascript
const handleApproval = async (evt, assistant) => {
  const payload = evt.payload || {}
  const toolName = payload.tool || '未知工具'
  const label = TOOL_LABELS[toolName] || toolName
  const args = payload.args || {}
  const summary = Object.entries(args)
    .map(([key, value]) => `${key}: ${value}`)
    .join('，')

  try {
    await ElMessageBox.confirm(
      `即将执行「${label}」：${summary || '无参数'}。是否确认？`,
      '操作确认',
      {
        confirmButtonText: '确认',
        cancelButtonText: '取消',
        type: 'warning'
      }
    )
    await resumeStream(evt.thread_id, true, assistant)    // 确认
  } catch {
    await resumeStream(evt.thread_id, false, assistant)  // 取消（含关闭弹窗）
  }
}
```

**五个细节**：

**① 参数摘要的展示**

```javascript
const summary = Object.entries(args).map(([k, v]) => `${k}: ${v}`).join('，')
```

把 `{"lab_id": 1, "date": "2026-10-18", "start_time": "14:00"}` 转成：

```
lab_id: 1，date: 2026-10-18，start_time: 14:00
```

**让用户知道要执行什么。** 这是"知情同意"的基本要求。

> 📝 **改进方向**：`lab_id: 1` 对用户不友好（不知道是哪个实验室）。更好的做法是后端返回**名称**而不只是 ID（或者在前端做映射）。这是一个真实的体验问题。

**② 中文标签**

```javascript
const label = TOOL_LABELS[toolName] || toolName
```

前端维护一份和后端 `TOOL_LABELS` 一样的映射。显示"即将执行「提交预约」"而不是"即将执行「create_lab_reservation」"。

> ⚠️ **注意这是重复定义** —— 后端 `agent_service.py:89-97` 和前端各有一份。改动时要同步。更优雅的做法是后端在 payload 里直接带上 label（`agent_service.py` 的 `TOOL_LABELS` 已经在用了，但只用于 `tool_start`/`tool_end` 事件，**approval payload 里没带**）。
> **这是一个真实的可改进点。**

**③ `try/catch` 同时处理"确认"和"取消"**

```javascript
try {
  await ElMessageBox.confirm(...)
  await resumeStream(..., true, ...)    // 点确认
} catch {
  await resumeStream(..., false, ...)   // 点取消 或 关闭弹窗
}
```

`ElMessageBox.confirm` 在用户点"取消"或关闭时会 **reject**。所以用 try/catch 区分两种决策。

**两种"拒绝"都被归为取消**（关闭弹窗 = 拒绝），这是安全上的正确默认。

**④ 复用同一个 assistant 对象**

```javascript
await resumeStream(evt.thread_id, true, assistant)
```

把 `assistant` 传进去，让后续的事件继续追加到它上面。**用户看到的是一条连续的回复**，而不是"第一轮的回答 + 第二轮的新消息"。

**⑤ `thread_id` 从事件里拿**

```javascript
await resumeStream(evt.thread_id, ...)
```

后端在 `approval_required` 事件里回了 `thread_id`（`agent_service.py:455`），前端用它恢复。

**为什么不用自己的 `threadId.value`？** 理论上一样，但用后端返回的更可靠（万一前端的被改了）。**防御性写法**。

## 33.6 thread_id 的管理

`AIChat.vue:79-84`：

```javascript
// 一个页面会话一个 thread_id，后端 checkpointer 用它隔离和恢复多轮状态。
const threadId = ref(
  (typeof crypto !== 'undefined' && crypto.randomUUID
    ? crypto.randomUUID()
    : Date.now().toString(36) + Math.random().toString(36).slice(2))
)
```

**两个分支**：

| 环境 | 方法 |
|---|---|
| 现代浏览器 | `crypto.randomUUID()`（RFC 4122 v4 UUID） |
| 老浏览器 / 非 HTTPS | 降级：时间戳(36 进制) + 随机数 |

**为什么非 HTTPS 会降级？** 因为 `crypto.randomUUID()` 只在**安全上下文**（HTTPS 或 localhost）可用。HTTP 环境下它是 `undefined`。

**这是一个真实的兼容性处理**（本地开发用 HTTP 时会遇到）。

**生命周期**：组件创建时生成，页面刷新后重新生成 → **新会话**。

> 📝 **可改进**：存到 `localStorage` 让刷新后继续；或者后端建会话表支持"历史会话列表"（第 17 章讲过）。

## 33.7 请求层：axios 拦截器

`utils/request.js`：

```javascript
const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '',
  timeout: 30000
})

// 请求拦截：自动带 token
request.interceptors.request.use((config) => {
  const token = getToken()
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})

// 响应拦截：统一拆壳 + 401 处理
request.interceptors.response.use(
  (response) => {
    const res = response.data
    // 统一响应格式 {code, message, data}
    if (res.code === 0 || res.code === 200) {
      return res.data
    }
    ElMessage.error(res.message || '请求失败')
    return Promise.reject(new Error(res.message))
  },
  (error) => {
    if (error.response?.status === 401) {
      // 清除 token → 跳登录页
      removeToken()
      router.push('/login')
    }
    ElMessage.error(error.response?.data?.message || '网络异常')
    return Promise.reject(error)
  }
)
```

**三个价值**：

| 功能 | 好处 |
|---|---|
| **自动带 token** | 业务代码不用每次手写 header |
| **统一拆壳** | 业务代码拿到的是 `data`，不是 `{code,message,data}` |
| **401 统一处理** | 一处处理登录失效，不用每个页面写 |

**★ 为什么流式请求不用 axios？**

看 `api/ai.js:26` —— 流式用的是**原生 `fetch`**：

```javascript
return fetch(`${baseURL}${path}`, {...})
```

因为 axios（基于 XHR）对**流式响应**的支持不如 `fetch` + `getReader()` 直接。虽然 axios 也支持 `responseType: 'stream'`，但要处理的东西更多。

> **面试可以说**："普通请求用 axios（有拦截器统一管理 token 和错误），**流式请求用原生 fetch + getReader()**，因为流式需要逐块读取响应体，`fetch` 的 ReadableStream API 更直接。代价是要自己处理半包和错误响应。"

## 33.9 最小骨架：一个最小的对话页

用原生 HTML + JS 演示核心逻辑（不需要 Vue 环境）：

```html
<!-- minimal_chat.html —— Agent 对话页核心逻辑（原生 JS）
     用浏览器打开，配合第 31 章的 minimal_sse_server.py 使用 -->
<!DOCTYPE html>
<html lang="zh-CN">
<head><meta charset="UTF-8"><title>最小 Agent 对话页</title>
<style>
  body { font-family: sans-serif; max-width: 700px; margin: 40px auto; }
  #list { border: 1px solid #ddd; height: 350px; overflow-y: auto; padding: 12px; }
  .msg { margin: 8px 0; }
  .user { text-align: right; color: #409eff; }
  .assistant { text-align: left; }
  .status { color: #909399; font-size: 12px; }
  .steps { color: #67c23a; font-size: 12px; }
  button { padding: 8px 16px; }
</style>
</head>
<body>
  <h3>最小 Agent 对话页</h3>
  <div id="list"></div>
  <input id="input" style="width:80%" placeholder="输入消息…">
  <button id="send">发送</button>

<script>
// ── ① thread_id：一个页面会话一个 ────────────────────────
const threadId = (crypto.randomUUID
  ? crypto.randomUUID()
  : Date.now().toString(36) + Math.random().toString(36).slice(2))
console.log('thread_id =', threadId)

const listEl = document.getElementById('list')
let currentAssistant = null          // ★ 当前正在流式的消息对象（引用）

// ── ② 创建消息 DOM，返回可增量更新的对象 ──────────────────
function pushMessage(role) {
  const wrap = document.createElement('div')
  wrap.className = 'msg ' + role
  const status = document.createElement('div'); status.className = 'status'
  const steps = document.createElement('div'); steps.className = 'steps'
  const body = document.createElement('div')
  wrap.append(status, steps, body)
  listEl.append(wrap)
  listEl.scrollTop = listEl.scrollHeight
  return { status, steps, body, wrap }       // ★ 返回引用，后续直接改
}

// ── ③ 事件处理：把 SSE 事件映射到 UI ─────────────────────
function applyEvent(a, evt) {
  switch (evt.type) {
    case 'status':
      a.status.textContent = evt.message
      break
    case 'tool_start':
      a.status.textContent = `正在${evt.label}…`
      a.steps.textContent += `⏳ ${evt.label}  `
      break
    case 'tool_end':
      a.steps.textContent = a.steps.textContent.replace(`⏳ ${evt.label}`, `✓ ${evt.label}`)
      a.status.textContent = `已完成${evt.label}`
      break
    case 'token':
      // ★ 增量追加（流式 UI 的核心）
      a.body.textContent += evt.content
      listEl.scrollTop = listEl.scrollHeight
      break
    case 'approval_required':
      handleApproval(evt, a)
      break
    case 'done':
      a.status.textContent = ''
      break
    case 'error':
      a.status.textContent = ''
      a.body.textContent = evt.message
      break
  }
}

// ── ④ 审批：弹确认框 → 恢复执行 ─────────────────────────
async function handleApproval(evt, a) {
  const p = evt.payload || {}
  const args = Object.entries(p.args || {}).map(([k, v]) => `${k}: ${v}`).join('，')
  const ok = confirm(`即将执行「${p.tool}」：${args}。是否确认？`)
  a.status.textContent = ok ? '已确认，继续执行…' : '已取消'
  // ★ 复用同一个 assistant 对象，结果追加到同一条消息
  await stream('/api/ai/chat/stream/resume',
    { thread_id: evt.thread_id, approved: ok }, applyEvent, a)
}

// ── ⑤ SSE 解析（三重防护，见第 31 章）────────────────────
async function stream(path, data, onEvent, existing = null) {
  const a = existing || pushMessage('assistant')
  const res = await fetch(path, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Accept: 'text/event-stream' },
    body: JSON.stringify(data)
  })
  if (!res.ok || !res.body) throw new Error('请求失败')

  const reader = res.body.getReader()
  const decoder = new TextDecoder('utf-8')
  let buffer = ''

  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    buffer += decoder.decode(value, { stream: true })     // ① 防中文乱码
    const chunks = buffer.split('\n\n')
    buffer = chunks.pop() || ''                           // ② 保留不完整帧
    for (const chunk of chunks) {
      const line = chunk.split('\n').map(s => s.trim()).find(s => s.startsWith('data:'))
      if (!line) continue
      const raw = line.slice(5).trim()
      if (!raw || raw === '[DONE]') continue
      try { onEvent(a, JSON.parse(raw)) } catch {}        // ③ 脏数据跳过
    }
  }
  return a
}

// ── ⑥ 发送 ──────────────────────────────────────────────
document.getElementById('send').onclick = async () => {
  const input = document.getElementById('input')
  const text = input.value.trim()
  if (!text) return
  input.value = ''

  const u = pushMessage('user')
  u.body.textContent = text

  await stream('/api/ai/chat/stream', {
    messages: [{ role: 'user', content: text }],   // ★ 只发本轮消息
    thread_id: threadId
  }, applyEvent)
}
</script>
</body>
</html>
```

**五件事被演示**：
1. ✅ `thread_id` 前端生成与降级
2. ✅ **消息对象引用**（增量更新的基础）
3. ✅ 事件 → UI 的映射
4. ✅ 审批弹窗 → resume → 复用同一消息对象
5. ✅ SSE 三重防护

## 33.10 面试问答

### Q1：Agent 前端和普通前端有什么不同？

**答**：三点。

一是**响应是流式的**，要增量追加内容而不是一次性渲染。

二是**要展示中间状态**——"正在检索…""正在查询实验室…"，因为 Agent 执行可能要几十秒，用户需要知道它在干什么。

三是**可能发生双向交互**——后端 `interrupt` 时前端要弹确认框，用户决策后再恢复执行。

还有一点是**会话状态**：前端要维护 `thread_id`，后端 checkpointer 用它恢复多轮历史。

### Q2：流式消息怎么增量更新？

**答**：关键是**持有消息对象的引用**。

我们创建一个 `reactive` 的消息对象，`push` 进 messages 数组后**仍然持有它的引用**，之后每个 `token` 事件直接 `assistant.content += evt.content`，Vue 的响应式会自动更新视图。

**坑是**：如果用 `push({ ...assistant })` 展开拷贝，后续修改原对象不会更新列表里的副本。必须是同一个对象引用。

另外审批恢复时也要**复用同一个对象**——把 `assistant` 传进 resume 的回调，这样用户看到的是一条连续的回复，而不是两条消息。

### Q3：审批确认框怎么和后端 interrupt 联动？

**答**：流程是：后端 Agent 走到 approval 节点调用 `interrupt` → 发 SSE 事件 `{"type":"approval_required","thread_id":...,"payload":{tool, args}}` → 前端收到后弹确认框（展示"即将执行「提交预约」：lab_id: 1，date: ..."）→ 用户点确认或取消 → 前端调 `/ai/chat/stream/resume` 带 `{thread_id, approved}` → 后端从断点继续 → 流式返回结果。

**几个细节**：
- `ElMessageBox.confirm` 在取消/关闭时会 reject，所以用 try/catch 区分两种决策（**关闭弹窗 = 拒绝**，这是安全的默认）
- 恢复时**复用同一个 assistant 对象**，结果追加到同一条消息
- `thread_id` 用后端返回的（而不是前端自己的），更可靠
- 参数做了中文摘要展示，让用户"知情同意"

**可以改进的地方**：目前展示的是 `lab_id: 1`，用户不知道是哪个实验室。更好的做法是后端 payload 里带上名称，或者前端做映射。另外工具中文标签在前后端各定义了一份，更优雅的做法是后端 payload 里直接带 label。

### Q4：前端为什么要自己生成 thread_id？

**答**：因为前端需要在多轮对话中**复用同一个标识**，而前端是无状态的（刷新就没了）。

生成方式是优先 `crypto.randomUUID()`，老浏览器或非 HTTPS 环境降级到"时间戳 + 随机数"——因为 `randomUUID` 只在安全上下文（HTTPS/localhost）可用。

当前行为是页面刷新就生成新的（新会话）。可以改进成存 localStorage，或者后端建会话表支持历史会话列表。

### Q5：流式请求为什么不用 axios？

**答**：因为流式需要**逐块读取响应体**，`fetch` 的 `ReadableStream` + `getReader()` API 更直接。axios 基于 XHR，虽然也支持 `responseType: 'stream'`，但处理起来更绕。

代价是要自己实现半包处理、错误响应判断（后端可能返回 JSON 错误而不是流）、手动带 token。

所以我们的策略是**普通请求用 axios**（有拦截器统一管理 token 和 401），**流式请求用原生 fetch**。

### Q6：前端做了哪些安全/体验的防护？

**答**：安全方面，主要是 **DOMPurify 清洗模型输出的 Markdown**（第 31 章）——因为模型输出来自知识库和用户上传的文档，不完全可信，直接 `v-html` 会有 XSS 风险。

体验方面：路由守卫（第 32 章）、401 统一跳登录、请求超时设置（`timeout: 90000`，因为 Agent 可能执行很久）、自动滚动到底部。

**注意 timeout 设成 90 秒**——这是考虑了工具执行 + 多轮 LLM 调用的时间。普通 CRUD 设 10 秒就够，Agent 不行。

## 33.11 速记卡

> **Agent 前端 = 流式渲染 + 中间态展示 + 审批交互 + 会话标识。**

**消息对象三字段**：`content`（正文）/ `status`（状态）/ `steps`（工具过程）

**★ 增量更新靠引用**：`push(assistant)` 不改引用 → `assistant.content += token` 生效
- 坑：`push({...assistant})` 拷贝会导致更新失效

**事件映射**：status/tool_start/tool_end/token/approval_required/done/error

**审批联动**：
```
approval_required → ElMessageBox.confirm → resume(thread_id, approved, assistant)
```
- confirm 取消/关闭会 reject → try/catch 区分
- **复用同一 assistant 对象**（连续回复）
- **关闭弹窗 = 拒绝**（安全默认）

**thread_id**：前端 `crypto.randomUUID()`，非 HTTPS 降级

**请求层**：普通 axios（拦截器）/ 流式 fetch（ReadableStream）

**timeout=90s**：Agent 执行可能很久

**代码位置**：
- 对话页：`views/AIChat.vue`
- 流式请求：`api/ai.js:22-94`
- 拦截器：`utils/request.js`
- 路由守卫：`router/index.js:68-82`

**可改进**：payload 带中文名和 label / thread_id 持久化

## 33.12 延伸思考

1. **用户开两个标签页同时聊，会怎样？**
   提示：两个 `thread_id`，两个独立会话（因为 checkpointer 按 thread_id 隔离）。但如果刷新后 thread_id 变了，之前的会话就"找不回来"了——虽然数据还在 checkpointer 里。**这正是需要"历史会话列表"功能的理由**。

2. **流式输出时用户想中断（点"停止"），怎么实现？**
   提示：前端用 `AbortController` 中断 fetch。但**后端仍在跑**（HTTP 断开不代表 Agent 停止）——这会浪费 token。更好的做法是前端发一个"取消"请求，后端把取消信号写进 state，Agent 下一个节点检查到就退出。**这是一个真实的工程问题**。

3. **如果要做"重新生成"按钮，前端和后端要怎么配合？**
   提示：后端需要支持"回退到上一轮"—— LangGraph 的 `get_state_history` + 从某个 checkpoint 重新执行（第 17 章的时间旅行）。前端发起一个新请求带"从哪个 checkpoint 重跑"。**checkpointer 的版本链让这个功能成为可能**，这是它相对简单缓存的价值。
