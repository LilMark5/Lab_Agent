## 25.1 引子：为什么普通数据库存不了向量

先想一个朴素的问题：我把向量存成 PostgreSQL 的一个 `TEXT` 字段（JSON 数组），检索时全表扫描算相似度，不行吗？

```sql
SELECT id, text FROM chunks;   -- 取出全部
-- 然后在 Python 里循环算余弦相似度，排序取 Top-K
```

**小规模可以。大规模不行。**

算一笔账：

| 数据量 | 向量数 × 512 维 | 每次检索的计算量 | 耗时（Python） |
|---|---|---|---|
| 1 千条 | 512K 次乘法 | 还行 | ~10ms |
| 10 万条 | 51.2M 次乘法 | 明显慢 | ~1s |
| 100 万条 | 512M 次乘法 | 不可接受 | ~10s+ |

**这就是"暴力检索（brute force / flat search）"的问题：O(N) 复杂度，N 一大就崩。**

向量数据库要解决的就是：**用索引结构把 O(N) 降成 O(log N) 或近似常数时间。**

代价是：**近似**（Approximate Nearest Neighbor, ANN）——不保证找到**最**近的，但保证找得**又快又接近**。

> **核心权衡**：**召回率 vs 速度**。ANN 索引牺牲一点点召回率（比如 95% → 99% 可调），换来百倍加速。对 RAG 来说，这个取舍完全值得——因为后面还有 rerank（第 27 章）兜底。

## 25.2 ANN 索引的三种主流算法

### 25.2.1 IVFFlat（倒排文件索引）

**思路**：先聚类，再只在最近的几个簇里找。

```
1. 训练阶段：把所有向量聚成 100 个簇（k-means），记录每个簇的中心
2. 检索阶段：
   - 先算 query 和 100 个簇中心的距离
   - 只在最近的 N 个簇（比如 5 个）里做精确搜索
```

**复杂度**：从 O(N) 降到 O(N/100 × 5) ≈ O(N/20)。

**特点**：
- 快、内存小
- 需要**训练**（要有足够数据才能聚类好）
- 召回率对 `nprobe`（搜几个簇）敏感

### 25.2.2 HNSW（分层可导航小世界）⭐

**本项目用的**（`vector_store.py:322-324`）：

```sql
CREATE INDEX IF NOT EXISTS idx_lab_kb_chunks_embedding 
ON lab_kb_chunks USING hnsw (embedding vector_cosine_ops)
```

**思路**：建一张"多层导航图"。

```
第 2 层（最稀疏）：  A ──────────── D          ← 远距离"高速公路"
                    |               |
第 1 层（中等）：    A ── B ── C ── D ── E
                    |   |   |   |   |
第 0 层（最密）：   A─B─C─D─E─F─G─H─I─J       ← 全量数据，精细化搜索
```

**检索过程**：
1. 从最高层的某个入口点开始
2. 在当前层贪心地走向"更接近 query"的邻居
3. 走不动了，就下降一层继续
4. 到第 0 层精细搜索，返回 Top-K

**为什么快？** 高层的边很少（比如 16 条），但覆盖很远——相当于"跳"到了目标附近；然后逐层细化。整体复杂度约 **O(log N)**。

**优点**：
- 无需训练（可增量插入）✅
- 召回率高（通常 > 95%）✅
- 查询快 ✅

**缺点**：
- **内存占用大**（图结构要存）
- 构建慢（插入时要维护图）
- 删除不友好（图里的边要重建）

**HNSW 的两个关键参数**：

| 参数 | 含义 | 影响 |
|---|---|---|
| `m` | 每个节点连多少条边 | 大 → 召回高、内存大、构建慢 |
| `ef_construction` | 构建时的候选池大小 | 大 → 图质量高、构建慢 |
| `ef_search` | 查询时的候选池大小 | 大 → 召回高、查询慢 |

pgvector 默认值（16, 64, 40）对大多数场景够用。

### 25.2.3 乘积量化（PQ）

**思路**：把 512 维向量切成 64 段，每段 8 维，每段用一个"码本"（256 个聚类中心）量化成 1 字节。

```
512 维 float32 = 2048 字节
→ 64 段 × 1 字节 = 64 字节       ★ 压缩 32 倍
```

**特点**：
- **极省内存**（亿级向量也能装下）
- 精度损失较大（召回率下降）
- 常和 IVF 组合成 IVFPQ

**本项目没用**（数据量小，不需要）。

## 25.3 为什么选 pgvector

本项目支持三种后端，但**主推 pgvector**。为什么？

| 维度 | Chroma | pgvector | Milvus |
|---|---|---|---|
| **部署** | 嵌入式（pip 装） | PostgreSQL 扩展 | 独立服务（Docker） |
| **运维** | 零 | 和主库一起 | 独立集群 |
| **事务** | ❌ | ✅ **和主库同一事务** | ❌ |
| **混合查询** | 弱 | ✅ **向量 + SQL 条件** | 一般 |
| **容量** | 单机 | 中等 | **大规模（亿级）** |
| **成熟度** | 新 | 稳（PG 生态） | 稳 |

### 25.3.1 pgvector 的杀手锏：和主库同源

这是本项目选它的**决定性理由**。

看这个查询（`vector_store.py:417-426`）：

```sql
SELECT id, text, source, chunk_index, document_id,
       1 - (embedding <=> CAST(:vec AS vector)) AS score
FROM lab_kb_chunks
WHERE document_id = :doc          -- ★ 普通 SQL 条件
ORDER BY embedding <=> CAST(:vec AS vector)
LIMIT :k
```

**一次查询同时做了**：
1. 向量相似度排序
2. `document_id` 过滤（元数据）
3. 返回任意字段（text、source、chunk_index）

**如果用独立的向量库**，你需要：
- 向量库里搜 → 拿到 id 列表
- 再用 id 去主库查元数据 → **两次查询 + 一致性问题**

pgvector 让"向量检索"变成了一条普通的 SQL —— **可以用 JOIN、可以用事务、可以用所有 PostgreSQL 的能力**。

### 25.3.2 事务一致性

```python
with engine.begin() as conn:
    conn.execute(DELETE_OLD_CHUNKS)      # 删旧块
    conn.execute(INSERT_NEW_CHUNKS)      # 插新块
# 要么都成功，要么都回滚
```

**向量数据和业务数据在同一事务里** —— 不会出现"文档删了但向量还在"的不一致状态。

这对本项目很重要：知识库文档和业务表在同一个库，删除文档时要同时删向量和业务记录。

### 25.3.3 什么时候该换 Milvus？

| 信号 | 说明 |
|---|---|
| 向量数 > 千万级 | pgvector 性能下降 |
| QPS > 数千 | 需要专门的向量服务 |
| 需要分布式 | 单机装不下 |
| 需要 GPU 加速 | Milvus 支持 |

**诚实说明**：本项目的数据量（几百到几千个块）**远达不到**需要 Milvus 的程度。Milvus 的实现更多是**展示架构能力和接口抽象**（也是简历上的技术点）。

> ⚠️ **面试诚实口径**（很重要）："Milvus 我们实现了接口但没有实机验证——Windows 不支持 Milvus Lite，需要 Docker 部署服务，我在开发环境没起起来。所以简历上我写的是'Milvus 了解'，'实跑'的是 Chroma 和 pgvector。这是如实标注，不虚标。"
> 这个诚实度反而加分——面试官见过太多"用过 Milvus"实际只是 pip install 过的候选人。

## 25.4 三后端抽象：面向接口编程

### 25.4.1 统一接口

`vector_store.py:1-12` 的文档注释写得很清楚：

```python
"""向量库抽象层。

同一个 RAG 检索代码可以在 ChromaDB / Milvus / pgvector 之间切换，体现"面向接口编程"。
三者的共同接口：
    is_ready() -> bool
    count()    -> int
    add_chunks(chunks)            # 新增/更新块（按 id 幂等）
    delete_chunks(document_id)    # 删除某文档的全部块
    search(query, top_k, document_id=None) -> list[dict]
"""
```

**五个方法，覆盖了 RAG 的全部需求**：

| 方法 | 用途 | 调用方 |
|---|---|---|
| `is_ready()` | 健康检查 | 启动检查 |
| `count()` | 统计 | 健康检查、预热 |
| `add_chunks()` | 写入 | 文档上传、启动重建 |
| `delete_chunks()` | 删除 | 文档删除 |
| `search()` | 检索 | `kb_service._vector_search()` |
| `list_chunks()` | 列全部 | `kb_service._get_chunks()`（BM25 需要） |

> 注意：`list_chunks()` 不在文档注释里，但三个实现都有。它是 BM25 检索的数据源（第 26 章），因为 BM25 需要全部文本。

### 25.4.2 抽象的价值

`kb_service.py` 里**完全不知道用的是哪个后端**：

```python
def _vector_search(query, top_k=5, document_id=None):
    store = vector_store.get_vector_store()      # 拿接口
    if store is None:
        return []
    try:
        return store.search(query, top_k=top_k, document_id=document_id)   # 调接口
    except Exception as exc:
        logger.warning("向量检索失败：%s", exc)
        return []
```

**切换后端只改一个环境变量**：

```bash
VECTOR_BACKEND=chroma     # 或 pgvector / milvus
```

这就是**面向接口编程**的价值：**上层逻辑和具体实现解耦**。

> **面试话术**："向量库我抽象成统一接口（is_ready / count / add_chunks / delete_chunks / search / list_chunks），上层的检索代码完全不知道用的是哪个后端，切换只改一个环境变量。这是典型的面向接口编程——好处是可以在不同场景下选不同后端（开发用 Chroma 零配置，生产用 pgvector 和主库同源），而且接入新的向量库（比如 Qdrant、Weaviate）只需要实现这五个方法，不动上层。"

### 25.4.3 工厂函数：`get_vector_store()`

`vector_store.py:451-490`：

```python
def get_vector_store():
    """按配置选择向量库。"""
    global _store, _init_attempted
    if _store is not None:
        return _store

    preferred = settings.VECTOR_BACKEND.lower()

    if preferred == "pgvector":
        store = PgVectorStore()
        store._ensure()
        _store = store
        return store

    if _init_attempted:
        return None
    _init_attempted = True

    if preferred == "milvus":
        try:
            store = MilvusVectorStore()
            store._ensure()
            _store = store
            return store
        except Exception as exc:
            logger.warning(
                "Milvus 初始化失败，回退 ChromaDB（Windows 不支持 Milvus Lite，"
                "需用 Docker 部署 Milvus 服务）：%s", exc,
            )

    try:
        store = ChromaVectorStore()
        store._ensure()
        _store = store
        return store
    except Exception:
        logger.warning("ChromaDB 不可用，RAG 功能降级为空实现")
        _store = None
        return None
```

**四个设计点**：

**① 单例 + 懒加载**

```python
if _store is not None:
    return _store
```

向量库连接是重资源（Chroma 要读文件、pgvector 要建连接池），全局复用。

**② pgvector 优先且"硬失败"**

```python
if preferred == "pgvector":
    store = PgVectorStore()
    store._ensure()      # ← 没有 try/except！
```

**注意这里没有 try 包裹**。这是**有意的**：如果用户明确配置了 pgvector，初始化失败就应该**大声报错**，而不是悄悄降级——否则用户以为在用 pgvector，实际在跑 Chroma，数据不一致会造成困惑。

**③ Chroma / Milvus 会降级**

```python
except Exception:
    logger.warning("ChromaDB 不可用，RAG 功能降级为空实现")
    _store = None
```

**降级到 `None` 而不是抛异常** —— 因为 RAG 不是核心功能，向量库挂了系统仍应能用（Agent 还能查数据库、还能聊天）。

`kb_service._vector_search` 里处理了 `store is None`：

```python
store = vector_store.get_vector_store()
if store is None:
    return []      # 向量检索返回空，但 BM25 还能用
```

**这是"优雅降级"的典型实践**。

**④ `_init_attempted` 防止重复尝试**

```python
if _init_attempted:
    return None
_init_attempted = True
```

如果第一次初始化失败，后续请求**不再重试**（直接返回 None）。避免每个请求都去尝试连接一个已知不可用的服务（浪费时间和日志）。

> 这个模式在第 20 章的 MCP 缓存里见过一样的（`_mcp_cache["tried"]`）。**"失败了就记住，别反复试"** 是处理外部依赖的通用原则。

### 25.4.4 为什么删除按 `document_id` 而不是按 id

```python
def delete_chunks(self, document_id: str) -> None:
    col = self._ensure()
    col.delete(where={"document_id": document_id})     # Chroma
```

pgvector 侧：

```python
conn.execute(text(f"DELETE FROM {self.TABLE} WHERE document_id = :d"), {"d": document_id})
```

**为什么这样设计？**

因为一份文档会被切成**几十个块**，每个块有独立 id（`{document_id}#{index}`）。删除文档时要删掉**所有块**。

按 `document_id` 删除的好处：
- 一次操作删干净
- 不需要知道具体有多少块、id 是什么
- 幂等（删不存在的也无害）

**这体现了元数据设计的重要性**（第 23 章讲过）：`document_id` 这个字段从切块时就带上，一路贯穿到删除。

## 25.5 pgvector 实现细节

### 25.5.1 建表与索引

`vector_store.py:295-325`：

```python
# 检查已有表的维度（换模型时自动重建）
existing_dim = conn.execute(...).scalar()
if existing_dim and int(existing_dim) != dim:
    conn.execute(text(f"DROP TABLE {table}"))

conn.execute(text(f"""
    CREATE TABLE IF NOT EXISTS {table} (
        id VARCHAR(255) PRIMARY KEY,
        text TEXT NOT NULL,
        source VARCHAR(512) NOT NULL,
        chunk_index INTEGER NOT NULL,
        document_id VARCHAR(64),
        embedding vector({dim}) NOT NULL
    )
"""))
conn.execute(text(f"ALTER TABLE {table} ADD COLUMN IF NOT EXISTS document_id VARCHAR(64)"))
conn.execute(text(f"""
    CREATE INDEX IF NOT EXISTS idx_{table}_embedding 
    ON {table} USING hnsw (embedding vector_cosine_ops)
"""))
```

**四个点**：

**① `vector({dim})` 类型**

pgvector 提供的列类型，`{dim}` 是维度（本项目 512）。

**② `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`**

这是一个**简易的 schema 迁移**。为什么需要？因为 `document_id` 是后来加的列，老表没有。

> 📝 **这是一个"手工迁移"的例子**。更规范的做法是用 Alembic（本项目其他地方用了）。向量表的 schema 没纳入 Alembic 管理，是一个**已知的简化**。面试时可以说："向量表的 schema 我做在代码里用 `CREATE IF NOT EXISTS` + `ALTER ADD IF NOT EXISTS` 做兼容，没纳入 Alembic 统一管理，这是一处可以规范化的地方。"

**③ HNSW 索引 + `vector_cosine_ops`**

```sql
USING hnsw (embedding vector_cosine_ops)
```

`vector_cosine_ops` 表示用**余弦距离**算子。pgvector 还支持：
- `vector_l2_ops`（欧氏）
- `vector_ip_ops`（内积/点积）

**必须和你的向量归一化方式匹配**：我们用了 `normalize_embeddings=True`，所以余弦 == 点积，用 `vector_cosine_ops` 正确。

**④ `CREATE INDEX IF NOT EXISTS`**

幂等，重复调用不报错。

### 25.5.2 写入：upsert

`vector_store.py:340-364`：

```sql
INSERT INTO lab_kb_chunks (id, text, source, chunk_index, document_id, embedding)
VALUES (:id, :text, :source, :chunk_index, :document_id, CAST(:embedding AS vector))
ON CONFLICT (id) DO UPDATE SET
    text = EXCLUDED.text,
    source = EXCLUDED.source,
    chunk_index = EXCLUDED.chunk_index,
    document_id = EXCLUDED.document_id,
    embedding = EXCLUDED.embedding
```

**`ON CONFLICT (id) DO UPDATE` = upsert**（存在则更新，不存在则插入）。

**为什么需要 upsert？**

因为**重新上传同名文档**时，块的 id（`{document_id}#{index}`）可能和已有的重复。如果不是 upsert 而是 INSERT，会主键冲突报错。

**幂等性是索引构建的关键属性**：同一份操作执行多次，结果一致。这让"重新索引"这个操作可以安全重试。

**`CAST(:embedding AS vector)`**

pgvector 需要显式类型转换。Python 侧传的是向量的**字符串表示**：

```python
"embedding": str(vector),      # "[0.12, -0.33, ...]"
```

这是 pgvector 接受的格式。

### 25.5.3 检索

`vector_store.py:408-444`：

```python
def search(self, query, top_k=5, document_id=None):
    engine = self._ensure()
    vector = _embed_texts([query])[0]                    # ★ 查询也要向量化
    where = "WHERE document_id = :doc" if document_id else ""
    params = {"vec": str(vector), "k": top_k}
    if document_id:
        params["doc"] = document_id
    sql = text(f"""
        SELECT id, text, source, chunk_index, document_id,
               1 - (embedding <=> CAST(:vec AS vector)) AS score
        FROM {self.TABLE}
        {where}
        ORDER BY embedding <=> CAST(:vec AS vector)
        LIMIT :k
    """)
    ...
```

**三个关键点**：

**① 查询也要 embedding**

```python
vector = _embed_texts([query])[0]
```

**"用同一个模型"**（第 24 章要点 1）。这里是同一个 `_embed_texts` 函数。✅

**② `<=>` 是余弦距离算子**

pgvector 的算子：

| 算子 | 含义 | 范围 |
|---|---|---|
| `<->` | L2 距离（欧氏） | [0, ∞) |
| `<=>` | **余弦距离** | [0, 2] |
| `<#>` | 内积的负值 | |

`ORDER BY embedding <=> vec` = 按余弦距离升序 = 按相似度降序。✅

**③ `1 - distance` 转相似度**

```sql
1 - (embedding <=> CAST(:vec AS vector)) AS score
```

和第 24 章讲的统一分数方向一致。

> ⚠️ **注意**：`ORDER BY` 里用的是**距离**（升序），而 SELECT 里输出的是**相似度**（`1 - 距离`）。排序和输出的"方向"相反，但因为单调对应，结果正确。这是个小陷阱——如果写成 `ORDER BY score DESC` 也可以，但要确保索引能用到（pgvector 的索引只对 `ORDER BY embedding <=> vec` 生效，对 `ORDER BY score DESC` **用不上索引**！）
>
> **这是一个真实的性能陷阱**：`ORDER BY` 里必须写原始的算子表达式，才能让 HNSW 索引生效。写成包装后的表达式会导致**全表扫描**。

### 25.5.4 参数化查询：`text()` 与 SQL 注入

```python
params = {"vec": str(vector), "k": top_k}
sql = text(f"""... WHERE document_id = :doc ... """)
```

注意：
- **表名用 f-string 拼接**（`{self.TABLE}`）—— 表名不能参数化，但它是代码里的常量，不是用户输入 ✅
- **值用 `:param` 绑定** —— 用户输入走参数化 ✅

这是**安全的做法**：表名来自代码常量，用户输入全部参数化。

> ⚠️ **反例**：如果表名来自用户输入（`f"FROM {user_input}"`），就是 SQL 注入。本项目的表名是硬编码的 `self.TABLE`，安全。

## 25.6 最小骨架：用 SQLite 模拟一个向量库

这个例子**不需要装任何向量库**，用纯 Python + SQLite 演示"向量存储 + ANN 检索"的核心结构。

```python
"""
minimal_vectordb.py —— 用 SQLite 模拟向量库的接口与降级
运行：python minimal_vectordb.py  （纯 Python，无需依赖）
目的是理解：统一接口、幂等写入、按元数据删除、优雅降级
"""
import json
import math
import sqlite3
from abc import ABC, abstractmethod
from typing import Any


# ── 1. 统一接口（本项目的五个方法）─────────────────────────
class VectorStore(ABC):
    @abstractmethod
    def is_ready(self) -> bool: ...
    @abstractmethod
    def count(self) -> int: ...
    @abstractmethod
    def add_chunks(self, chunks: list[dict]) -> None: ...
    @abstractmethod
    def delete_chunks(self, document_id: str) -> None: ...
    @abstractmethod
    def search(self, query_vec, top_k=5, document_id=None) -> list[dict]: ...
    @abstractmethod
    def list_chunks(self) -> list[dict]: ...


# ── 2. 一个"假 embedding"（真实项目里是 bge-small-zh）──────
def embed(text: str, dim: int = 32) -> list[float]:
    """模拟 embedding：把文本哈希成定长向量并归一化。"""
    vec = [0.0] * dim
    for i, ch in enumerate(text):
        vec[(ord(ch) * (i + 1)) % dim] += 1.0
    norm = math.sqrt(sum(x * x for x in vec))
    return [x / norm for x in vec] if norm else vec


def cosine(a, b) -> float:
    return sum(x * y for x, y in zip(a, b))     # 已归一化 → 点积即余弦


# ── 3. SQLite 实现（模拟 pgvector）────────────────────────
class SqliteVectorStore(VectorStore):
    """暴力检索版：全表扫描算余弦。
    真实项目里 pgvector 用 HNSW 索引把 O(N) 降到 O(log N)。"""

    def __init__(self, path: str = ":memory:"):
        self.conn = sqlite3.connect(path)
        self.conn.row_factory = sqlite3.Row
        self._init()

    def _init(self):
        self.conn.execute("""
            CREATE TABLE IF NOT EXISTS chunks (
                id TEXT PRIMARY KEY,
                text TEXT NOT NULL,
                source TEXT NOT NULL,
                chunk_index INTEGER NOT NULL,
                document_id TEXT,
                embedding TEXT NOT NULL
            )
        """)
        self.conn.execute(
            "CREATE INDEX IF NOT EXISTS idx_doc ON chunks(document_id)")
        self.conn.commit()

    def is_ready(self) -> bool:
        return True

    def count(self) -> int:
        return self.conn.execute("SELECT count(*) FROM chunks").fetchone()[0]

    def add_chunks(self, chunks: list[dict]) -> None:
        """★ upsert：按 id 幂等，重复写入是更新而不是报错。"""
        for c in chunks:
            self.conn.execute("""
                INSERT INTO chunks (id, text, source, chunk_index, document_id, embedding)
                VALUES (?, ?, ?, ?, ?, ?)
                ON CONFLICT(id) DO UPDATE SET
                    text=excluded.text, source=excluded.source,
                    chunk_index=excluded.chunk_index,
                    document_id=excluded.document_id,
                    embedding=excluded.embedding
            """, (
                c["id"], c["doc"], c["meta"]["source"],
                int(c["meta"]["chunk_index"]),
                c["meta"].get("document_id") or "static",
                json.dumps(embed(c["doc"])),
            ))
        self.conn.commit()

    def delete_chunks(self, document_id: str) -> None:
        """★ 按 document_id 删：一份文档的所有块一次删干净。"""
        self.conn.execute("DELETE FROM chunks WHERE document_id = ?", (document_id,))
        self.conn.commit()

    def list_chunks(self) -> list[dict]:
        rows = self.conn.execute("SELECT * FROM chunks").fetchall()
        return [{"id": r["id"], "doc": r["text"], "meta": {
            "source": r["source"],
            "chunk_index": r["chunk_index"],
            "document_id": r["document_id"],
        }} for r in rows]

    def search(self, query_vec, top_k=5, document_id=None) -> list[dict]:
        """暴力检索：O(N)。真实向量库用 ANN 索引。"""
        sql = "SELECT * FROM chunks"
        params: list[Any] = []
        if document_id:
            sql += " WHERE document_id = ?"        # ★ 元数据过滤（向量库的价值之一）
            params.append(document_id)

        hits = []
        for r in self.conn.execute(sql, params).fetchall():
            score = cosine(query_vec, json.loads(r["embedding"]))
            hits.append({"id": r["id"], "doc": r["text"], "score": score,
                         "meta": {"source": r["source"],
                                  "chunk_index": r["chunk_index"],
                                  "document_id": r["document_id"]}})
        hits.sort(key=lambda x: x["score"], reverse=True)
        return hits[:top_k]


# ── 4. 工厂函数（含优雅降级）───────────────────────────────
_store = None
_init_attempted = False


def get_vector_store(backend: str = "sqlite", fail: bool = False) -> VectorStore | None:
    """按配置选后端，失败时降级为 None（RAG 可用但无向量召回）。"""
    global _store, _init_attempted
    if _store is not None:
        return _store
    if _init_attempted:
        return None
    _init_attempted = True
    try:
        if fail:
            raise RuntimeError("模拟：向量库不可用")
        _store = SqliteVectorStore()
        return _store
    except Exception as exc:
        print(f"  ⚠ 向量库初始化失败，RAG 降级：{exc}")
        return None


if __name__ == "__main__":
    store = get_vector_store()
    print(f"is_ready={store.is_ready()}  count={store.count()}")

    # ① 写入（静态库 + 上传文档）
    chunks = [
        {"id": "static#0", "doc": "实验室开放时间为 8:00 至 22:00",
         "meta": {"source": "规定.md", "chunk_index": 0, "document_id": "static"}},
        {"id": "static#1", "doc": "进入实验室必须穿戴实验服",
         "meta": {"source": "规定.md", "chunk_index": 1, "document_id": "static"}},
        {"id": "doc-42#0", "doc": "量子实验室的激光功率上限为 5W",
         "meta": {"source": "量子说明.md", "chunk_index": 0, "document_id": "doc-42"}},
    ]
    store.add_chunks(chunks)
    print(f"\n写入后 count={store.count()}")

    # ② upsert 幂等性验证
    store.add_chunks(chunks)
    print(f"重复写入后 count={store.count()}  ← 应为 3，说明是更新不是新增")

    # ③ 检索（全库）
    q = embed("实验室几点开门")
    print("\n【全库检索】")
    for h in store.search(q, top_k=3):
        print(f"  {h['score']:.3f}  [{h['meta']['source']}#{h['meta']['chunk_index']}] {h['doc'][:28]}")

    # ④ 检索（限定 document_id）
    print("\n【只搜静态库 document_id='static'】")
    for h in store.search(q, top_k=3, document_id="static"):
        print(f"  {h['score']:.3f}  [{h['meta']['source']}] {h['doc'][:28]}")
    print("  ← 上传文档被过滤掉了")

    # ⑤ 按 document_id 删除
    store.delete_chunks("doc-42")
    print(f"\n删除 doc-42 后 count={store.count()}  ← 应为 2")

    # ⑥ 优雅降级
    print("\n【模拟向量库不可用】")
    broken = get_vector_store(fail=True)
    print(f"  get_vector_store() 返回: {broken}")
    print("  ← 不抛异常，上层 _vector_search 返回空列表，BM25 仍能工作")
```

### 预热的价值

```python
def warmup() -> None:
    """启动时预热向量库和 embedding 模型。"""
    try:
        store = get_vector_store()
        if store and store.count() > 0:
            store.search("预热", top_k=1)
            logger.info("向量库预热完成，后端：%s", type(store).__name__)
    except Exception as exc:
        logger.warning("向量库预热失败，服务继续启动：%s", exc)
```

**为什么需要预热？** 因为第一个真实请求要承担：模型加载（几秒）+ 建连接 + 建索引。用户会感到"第一次特别慢"。

预热在启动时把这些做完，让第一个用户请求也很快。

**注意 `except` 后"服务继续启动"** —— 预热失败不应该阻止服务启动（RAG 挂了其他功能还能用）。

## 25.8 面试问答

### Q1：为什么需要专门的向量数据库？普通数据库不行吗？

**答**：能存，但检索不行。

存是可以的（存成数组字段），问题在检索。暴力检索要算 N 次相似度，10 万条 512 维就是 5000 万次乘法，Python 里要 1 秒；百万级就是十几秒，完全不可用。

向量数据库用 ANN 索引把 O(N) 降到 O(log N)。代价是**近似**——不保证找到最近的，但保证又快又接近（召回率通常 95%+）。对 RAG 来说这个取舍完全值得，因为后面还有 rerank 兜底。

### Q2：HNSW 是什么原理？

**答**：分层可导航小世界图。建一张多层导航图：最上层最稀疏（节点少、边覆盖远，像"高速公路"），最下层最密集（全量数据）。

检索时从最高层的入口点开始，在当前层贪心地走向更接近 query 的邻居，走不动了就下降一层继续，最后在底层精细搜索。整体复杂度约 O(log N)。

优点是**无需训练**（可以增量插入）、召回率高、查询快。缺点是**内存占用大**（要存图结构）、构建慢、删除不友好。

我们 pgvector 用的就是 HNSW，配 `vector_cosine_ops` 算子（因为我们的向量做了归一化，余弦 == 点积）。

### Q3：为什么选 pgvector 而不是 Chroma 或 Milvus？

**答**：决定性理由是**和主库同源**。

一次查询可以同时做向量相似度排序 + 元数据过滤 + 返回任意字段，不需要"先查向量库拿 id、再查主库拿数据"两次往返。而且向量数据和业务数据在**同一个事务**里，不会出现"文档删了但向量还在"的不一致。

Chroma 是嵌入式的，零配置，适合开发。Milvus 是独立服务，适合千万级以上规模。我们选 pgvector 是因为数据量和主库一起管理最省事，运维负担最小。

**诚实说明**：Milvus 我们实现了接口但没有实机验证（Windows 不支持 Milvus Lite，要 Docker 部署），所以简历上写的是"了解"而不是"实跑"。

### Q4：三个后端怎么抽象？

**答**：抽象成统一接口，五个方法：`is_ready` / `count` / `add_chunks` / `delete_chunks` / `search`，外加 `list_chunks`（BM25 需要全量文本）。

上层检索代码完全不知道用的是哪个后端，切换只改一个环境变量 `VECTOR_BACKEND`。这是面向接口编程——接入新后端（Qdrant、Weaviate）只需实现这五个方法，不动上层。

工厂函数里有个细节：**pgvector 是硬失败（不 try）**，因为用户明确配置了就该大声报错；**Chroma/Milvus 会降级到 None**，因为 RAG 不是核心功能，向量库挂了系统还要能用。降级后 `_vector_search` 返回空列表，BM25 检索仍能工作。

### Q5：删除文档时为什么按 document_id 而不是按块 id？

**答**：因为一份文档会被切成几十个块，每个块有独立 id（`{document_id}#{index}`）。删除文档要删掉所有块。

按 `document_id` 删除的好处：一次操作删干净、不需要知道具体有多少块、而且幂等。

这体现了元数据设计的重要性——`document_id` 从切块时就带上，一路贯穿到检索过滤和删除。

### Q6：upsert 为什么重要？

**答**：因为重新上传同名文档时，块 id 会和已有的重复。如果是纯 INSERT 会主键冲突报错。

`ON CONFLICT (id) DO UPDATE` 让写入变成**幂等操作**——同一份操作执行多次结果一致。这让"重新索引"可以安全重试，不会出现"重试一次就报错"的情况。

### Q7：pgvector 检索 SQL 有什么要注意的？

**答**：三个点。

一是**查询也要 embedding**，而且必须用**和索引时同一个模型**（我们都是 `_embed_texts`）。

二是 `<=>` 是 pgvector 的余弦距离算子（`<->` 是欧氏、`<#>` 是内积负值），要和向量的归一化方式匹配。

三是**性能陷阱**：`ORDER BY` 里必须写原始的算子表达式（`ORDER BY embedding <=> :vec`），HNSW 索引才能生效。如果你包装成 `ORDER BY score DESC`（score 是 `1 - distance`），**索引用不上，会全表扫描**。

另外 SQL 注入方面：表名用 f-string（因为它是代码常量不能参数化），所有值用 `:param` 绑定，这是安全的。

## 25.9 速记卡

> **向量库 = 用 ANN 索引把 O(N) 检索降到 O(log N)，代价是"近似"。**

**为什么不能用普通 DB**：暴力检索 O(N)，百万级不可用

**三种 ANN 算法**：
- **IVFFlat**：聚类 + 只搜最近几簇（快、省内存、需训练）
- **HNSW** ⭐：多层导航图，O(log N)，**无需训练**、召回高、内存大
- **PQ**：乘积量化，压缩 32 倍，精度损失大

**pgvector 杀手锏**：**和主库同源** —— 向量 + SQL 条件 + 事务，一次查询搞定

**三后端对比**：Chroma（嵌入式/零配置）/ **pgvector（主库同源/推荐）** / Milvus（独立服务/大规模）

**统一接口**：`is_ready` / `count` / `add_chunks` / `delete_chunks` / `search` / `list_chunks`

**工厂降级策略**：
- pgvector → **硬失败**（用户明确配置，该大声报错）
- Chroma/Milvus → **降级 None**（RAG 非核心，BM25 仍可用）
- `_init_attempted` → **失败后不再重试**

**★ upsert**：`ON CONFLICT (id) DO UPDATE` → 幂等，可安全重试

**★ 删按 document_id**：一份文档几十个块，一次删干净

**★ ORDER BY 陷阱**：必须写 `embedding <=> :vec` 原表达式，包装后索引用不上

**诚实边界**：Milvus 未实机验证（Windows 不支持 Lite）

**代码位置**：`vector_store.py`（501 行）

## 25.10 延伸思考

1. **HNSW 索引删除不友好，我们的 `delete_chunks` 会有什么问题？**
   提示：pgvector 的 HNSW 删除是"标记删除"，图结构不会立即重建。大量删除后索引质量下降、查询变慢。解法：定期 `REINDEX`，或者对删除频繁的场景用 IVFFlat。思考：我们的场景（文档偶尔删一次）需要担心吗？

2. **如果要支持"同时搜多个 document_id"（比如用户勾选了 3 份文档），SQL 怎么改？**
   提示：`WHERE document_id = ANY(:docs)`（PostgreSQL 数组）。接口要从 `document_id: str | None` 改成 `document_ids: list[str] | None`。这会牵动哪些层？（`kb_service.retrieve` → `_vector_search` / `_bm25_search` → `search_lab_docs` 工具）

3. **向量库挂了，BM25 还在，用户体验会差多少？**
   提示：BM25 只能匹配字面相同的词，语义泛化能力为零。可以做一个"降级实验"：关掉向量检索，跑一遍评测集（第 38 章），看 Hit@K 掉多少。**这个数字就是"向量检索的价值"的量化证明**，写进简历会非常有说服力。
